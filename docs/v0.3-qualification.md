# v0.3 qualification record

This record lists the evidence for each implemented slice of the [v0.3 PHP sites](v0.3.md) specification. It says what was tested and on which revisions. Anything it does not list as tested is not qualified, and no slice qualifies another. v0.3 is not released.

Contributors: the tests named below are described in [acceptance against a real server](ssh-connections.md#acceptance-against-a-real-server).

### Results

- Ubuntu 24.04: 55 tests tagged `ssh` ran, OK, 3 skipped. Ubuntu 26.04: 55 ran, OK, 1 skipped. The skips are existing bootstrap tests for fixtures a release does not carry. Both results are recorded as the `native (Ubuntu 24.04)` and `native (Ubuntu 26.04)` commit statuses.
- `discovery/test_sites_remote.py`:
  - A site an administrator made by hand with `useradd`, `install`, a link, the convention's exact files, `nginx -t`, `php-fpm<version> -t` and a PHP-FPM reload is reconstructed through the dashboard request, the worker and SSH, with its names, root, socket, UID and home.
  - A broken site, an enabled file without account, directories, pool or socket, has those resources absent.
  - The account without sudo, with its own key and a fresh database, rebuilds the same site observations. Only its password lock is inaccessible, since it cannot read `/etc/shadow`.
  - External edits and removal show on the next discovery: a shared name, widened pool and socket modes, a removed link, and removed sites.
- `dashboard/test_browser.py` reviews reconstructed sites with the keyboard against the production build.
- Parser, refusal, collection, page and permission tests run in the repository suite without a server.

### Limits

- **Inaccessible evidence.** Ordinary discovery uses the SSH identity's own rights and never escalates. What that identity cannot read is inaccessible, and the site is not complete:
  - the password lock without read access to `/etc/shadow`
  - another enabled site file or pool it cannot read, such as the disposable image's root-only site file
  - paths it cannot see
  
  In the tests, the SSH user reads `/etc/shadow` as a member of the `shadow` group, and root's site file is moved aside for the complete case.
- **Not read.** Discovery does not read sudo rules or anything the [site observation table](ssh-connections.md#what-each-candidate-reads) does not name. A site that matches the convention says nothing about serving; no request is made.
- **Not qualified.**
  - amd64 servers: the `Native` workflow's disposable jobs did not run for this revision.
  - Real virtual machines or hosts other than the containers above. Hosts other than the containers were only checked by read-only discovery, without a site.

### Results

- Each environment: 61 tests tagged `ssh` ran, OK; 3 skipped on 24.04 and 1 on 26.04, the existing bootstrap tests for fixtures a release does not carry. The results are recorded as the `native (Ubuntu 24.04)` and `native (Ubuntu 26.04)` commit statuses.
- `sites/test_review_remote.py`, through the dashboard request, the worker and SSH:
  - Before and after every preparation, a root read through `docker exec` of every path's metadata under `/etc`, `/var/www`, `/run/php` and `/var/backups`, the passwd, group, shadow and gshadow digests, the Nginx and PHP-FPM main and worker process IDs, the log sizes, `barectl-apply-*` units and dotfiles in the configuration and web trees is unchanged: preparation wrote nothing, created no account, staged nothing and reloaded nothing.
  - The reviewed files equal the templates, the account policy matches `/etc/login.defs`, the site listens on IPv6 as Nginx does, and the recorded revalidation digest equals the one the server computes as root with the same command.
  - A site an administrator created by hand collides by name, and is a plan without changes for its own names; a lone site account is an incomplete site; sudo narrowed to `systemd-run` and the account without sudo are refused for privilege; the provisioned root-only site is an unsupported layout.
  - **Name bound**: with the release's own `nginx -t` on a scratch configuration in `/tmp`, a default server and the site template, a 46-octet name loads and a 47-octet name fails with `could not build server_names_hash, you should increase server_names_hash_bucket_size: 64`, on both releases and both architectures.
- `dashboard/test_browser_remote.py` prepares a site plan with the keyboard in Chromium against the production build and the same servers, refused input first, and finds the server unchanged; `dashboard/test_browser.py` covers the form, the review, expiry, permission separation and the absent apply action against a simulated server.
- Name, template, admission, payload and workflow tests run in the repository suite without a server, including the maximum admitted request's payload (about 10.5 KB of 16 KiB) and the unchanged refusal of both bootstrap profiles for a tree holding convention files.

### Limits

- **Not applied.** The draft payload is built and measured but never submitted; its steps, fault boundaries and verification are not qualified.
- **Grammar.** Any Nginx or PHP-FPM file other than distribution files and exact templates refuses, including inert files in `sites-available`.
- **Name hash.** Each name fits the default bucket; many sites' names together may still need a larger `server_names_hash_max_size`, which applying's `nginx -t` would report.
- **Not qualified.** Real virtual machines or hosts other than the containers above; no preparation ran against a live server.
