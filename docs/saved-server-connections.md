# v0.9: Saved server connections

Accepted specification for adding and changing server connection details through the custom dashboard. Implementation, qualification and release remain pending. Existing SSH alias registrations remain supported.

Tracked in [#293](https://github.com/rajandangi/barectl/issues/293).

## Problem Statement

An operator should be able to add a server by entering its address and username, choosing an existing way to sign in, and checking the connection. Today the operator must first create an SSH alias outside Barectl. Someone managing a business website may not know how to edit that configuration or understand why a saved server cannot be reached.

The operator also needs confidence that Barectl is contacting the right server. Saving an address must not silently trust an unknown server, upload a private key, grant new server permissions, or make a previous successful check look current after the connection changes. Another authorized computer must be able to connect with its own credentials without copying the first computer's database.

## Solution

Offer two ways to add a server: **Enter connection details** and **Use an existing SSH alias**. The first is the ordinary journey; the second preserves the existing advanced workflow.

For connection details, ask for a display name, server address, SSH username and authentication choice. Put the port under optional details, defaulting to 22. Offer **Use this computer's SSH agent** or **Use an existing key file** from an administrator-approved list. Explain that the computer means the controller host running Barectl, which can differ from the computer displaying the browser. Barectl stores the non-secret connection details in its local database. Keys, agent access and server trust remain on the controller host.

**Save and check connection** saves the registration and queues the existing read-only discovery journey. The result explains whether the server identity was accepted, signing in succeeded and supported observations were collected. Unknown, changed and revoked server identities are refused before credentials are offered. Explain how to have the server identity checked and trusted outside Barectl; do not add an accept-any-key button.

Opening pages and editing unsaved fields do not connect to a server. Later checks require an explicit action. Changed connection details require a new check, and old observations remain clearly labelled with the connection and time that produced them. Current server management still depends on fresh native evidence and the existing reviewed workflows.

## User Stories

1. As an operator, I want to add a server without editing an SSH configuration file, so that I can begin using the panel with details supplied by my server provider.
2. As an operator, I want to give the server a simple name, so that I can recognize it in my server list.
3. As an operator, I want to enter a server address, so that Barectl knows which server to check.
4. As an operator, I want to use an IP address or a supported host name, so that I can use the address my provider gives me.
5. As an operator, I want to enter the SSH username, so that Barectl signs in with my existing server account.
6. As an operator, I want port 22 to be the default, so that I need not fill in an extra field for an ordinary connection.
7. As an operator, I want to change the port when needed, so that I can reach a server using another SSH port.
8. As an operator, I want short explanations beside unfamiliar fields, so that I can fill in the form without understanding SSH settings.
9. As an operator, I want field errors to say what to fix, so that a typing mistake does not become a confusing connection failure.
10. As an operator, I want my valid entries kept after a form error, so that I do not have to enter everything again.
11. As an operator, I want to choose the SSH agent on the computer running Barectl, so that keys already loaded there can be used without uploading them.
12. As an operator, I want to choose an approved existing key file, so that I can use a key already available to that computer.
13. As an operator, I want the panel to explain an unavailable authentication choice, so that I know when an administrator needs to prepare the computer.
14. As an operator, I want a clear explanation when my key needs an SSH agent, so that I can use a protected key without entering its passphrase in the panel.
15. As an operator, I want the chosen authentication method to be respected, so that Barectl does not silently try unrelated keys.
16. As an operator, I want private keys and passwords to stay out of browser forms, so that connecting does not create another copy of my secrets.
17. As an operator using a private management host, I want to know that its keys are used, so that I do not expect the browser to provide my laptop's SSH agent.
18. As an operator, I want to save and check the connection in one action, so that I can see whether the supplied details work.
19. As an operator, I want to see a queued or checking message, so that I know a background check is still in progress.
20. As an operator, I want repeated clicks to share the same active check, so that I do not start several checks accidentally.
21. As an operator, I want an understandable message when another operation is active, so that I know why connection changes must wait.
22. As an operator, I want to know when the worker is unavailable, so that a saved request is not mistaken for a completed check.
23. As an operator, I want a successful check and its time shown clearly, so that I understand what Barectl has verified.
24. As an operator, I want supported server observations after a successful check, so that I can continue to the normal server dashboard.
25. As an operator, I want limited server permissions explained, so that an unreadable resource is not reported as missing.
26. As an operator, I want a helpful message when the server cannot be reached, so that I can check the address, port or network.
27. As an operator, I want a helpful message when signing in fails, so that I can check my username and existing key access.
28. As an operator, I want an unknown server identity refused, so that saving an address cannot silently authorize an impostor.
29. As an operator, I want a changed or revoked server identity refused, so that Barectl cannot continue using a connection that is no longer trusted.
30. As an operator, I want safe instructions for checking server identity with my provider or administrator, so that I can resolve trust problems without guessing.
31. As an operator, I want connection errors to hide keys, raw output and private file contents, so that troubleshooting does not expose secrets.
32. As an operator, I want to retry a failed check explicitly, so that changing a network or agent does not trigger unexpected remote work.
33. As an operator, I want my saved connection kept after a failed check, so that I can correct it and try again.
34. As an operator, I want to reopen a saved server without starting a connection, so that reading the panel has no unexpected remote effect.
35. As an operator, I want to change the display name without a new connection check, so that organizing my list does not contact the server.
36. As an operator, I want changed address, port, username or authentication details checked again, so that old success is not presented as verification of new details.
37. As an operator, I want old observations labelled with their original connection and time, so that I do not mistake another target's information for the current server.
38. As an operator, I want old plans to require fresh preparation after connection details change, so that an approved change cannot be redirected to another target.
39. As an operator, I want active and uncertain server operations to block connection changes, so that recovery still checks the target that accepted the work.
40. As an operator, I want interrupted checks to preserve honest status and earlier observations, so that a stopped worker cannot invent a result.
41. As an operator, I want conflicting edits to be explained instead of silently overwriting my changes, so that two people cannot accidentally redirect a registration.
42. As an operator, I want existing SSH alias registrations to keep working, so that an upgrade does not require me to re-enter every server.
43. As an operator, I want to choose an existing SSH alias for an advanced connection, so that my supported controller configuration remains useful.
44. As an operator, I want to change a registration's connection method through a clear edit, so that I can move between supported aliases and saved details without losing its local history.
45. As an operator, I want an unavailable key or alias described accurately, so that Barectl does not silently choose a replacement credential.
46. As an operator on a second authorized computer, I want to enter the same server details and use that computer's own credentials, so that I can reconstruct supported state without copying the first database.
47. As an operator, I want to understand that saved details do not share SSH access, so that I do not expect another computer to inherit my keys or trust.
48. As an operator, I want conflicting server changes from separate computers prevented by existing native coordination, so that new connection forms do not weaken safe management.
49. As an operator with viewing access, I want to see only the permitted connection summary, so that viewing a server does not give me editing or credential-selection authority.
50. As an administrator, I want only accounts allowed to add or change servers to select approved credentials, so that a form cannot become access to arbitrary files or agent controls.
51. As an administrator, I want current permissions checked before queued work runs and publishes results, so that removed access takes effect even after a request was saved.
52. As an operator, I want to remove a registration without deleting server data, keys or trust records, so that tidying my list does not damage the connection or server.
53. As an operator, I want the form and progress messages to work with a keyboard and small screen, so that I can complete the journey comfortably.
54. As an operator, I want ordinary reloads and direct links to work, so that the journey remains usable without relying on a particular fragment update.
55. As an administrator, I want documented setup and qualification limits, so that I know which credentials, platforms and connection methods have actually been tested.

## Implementation Decisions

- **D1. Scope and status.** Add one saved-details connection mode to existing managed-server registration and editing. Preserve SSH alias mode. This is planned design for a later release, not a change to the released alias-only v0.1 contract. It does not depend on backups or Jobs and must remain usable with the released discovery foundation.
- **D2. Ownership and reuse.** Registration owns the non-secret connection definition and its revision. Existing application services own save, queue, edit and remove. Discovery and the shared remote-operation lifecycle own checks, recovery and snapshot publication. The sole verified pyinfra SSH adapter owns connection execution. Extend these owners rather than adding a connection-testing service, competing queue, SSH transport or controller daemon.
- **D3. Stored settings.** Store a discriminated alias or saved-details definition in typed local database columns. Saved details include address, explicit SSH username, integer port, authentication mode and an optional approved key-reference identifier. A server has exactly one mode; contradictory combinations are rejected at the request, service and database boundaries. Keep the display name and local registration identity separate from the network address.
- **D4. Form and validation.** Use the custom USWDS/Django/HTMX dashboard. Preserve the 100-character display-name bound. Accept a plain ASCII DNS host name of at most 253 characters with valid labels, IPv4 address or IPv6 address, not a URL, command, user-at-host expression, scoped IPv6 address or port embedded in the address. Normalize supported DNS casing, an optional trailing DNS dot and IP representations without resolving DNS during form display or validation. Require a nonempty SSH username of at most 64 ASCII letters, digits, dots, underscores or hyphens, with no leading hyphen; reject whitespace, control characters and shell syntax. Key-reference identifiers are opaque and at most 128 characters. Port defaults to 22 and must be 1–65535. No arbitrary SSH options or browser-supplied transport keyword arguments are accepted.
- **D5. Credentials remain host-managed.** Store no private key bytes, SSH passwords, passphrases, agent sockets or credential contents in application rows, task payloads, browser storage or responses. Do not generate, upload, download or edit keys. The computer supplying credentials is the worker's controller host, not necessarily the browser user's device.
- **D6. Agent mode.** Use the worker's existing SSH agent with private-key file search disabled. Do not accept a browser-supplied socket, forward the agent to the server or silently fall back to files. An absent or unsuitable agent produces safe guidance. This uses pyinfra's existing agent controls rather than new agent integration.
- **D7. Existing-key mode.** Offer opaque references to existing, controller-administrator-approved identity files. Use that selected file with unrelated agent identities and default-file search disabled. Protected files requiring a passphrase direct the operator to agent mode; there is no passphrase prompt. Do not recursively scan the filesystem, accept arbitrary browser file paths, run local commands, or expose private file contents. Build the allowed catalogue from documented administrator configuration, reusing supported controller SSH identity references and standard key locations where admitted. A stale, removed, unreadable or replaced reference is revalidated at dispatch and cannot fall back to another key.
- **D8. Trust.** Reuse existing controller known_hosts parsing, plain/hashed host matching, port handling and revoked-key refusal. Saved details use the controller's documented default trust files; arbitrary trust-file paths are not a form field. Re-read trust on every connection. Unknown, changed or revoked host keys refuse before user authentication. No trust-on-first-use, accept-new policy, browser trust editor or bypass is introduced. Guidance requires comparison against an independent trusted source outside Barectl; a network scan alone does not establish trust.
- **D9. One execution path.** Both modes resolve to the existing typed connection target and the same verified pyinfra connector in the worker. Explicitly set supported connector authentication controls; pyinfra's default accept-new policy is insufficient for Barectl. Preserve current handshake, authentication, command, session and output bounds, resource cleanup, no automatic connection retries and safe failures. Keep existing alias authentication semantics intact; restrictions in the new saved mode do not silently change old registrations.
- **D10. Save and check.** A successful initial save or connection-definition change queues discovery atomically with the registration change, using the current active-operation slot. The action requires authentication, current server add/change and viewing authority, discovery-request authority and CSRF. An account without check authority cannot trigger SSH through registration as a substitute. Explain any resulting permission limitation. A display-name-only edit saves without a check. Repeated explicit checks reuse the current eligible discovery attempt.
- **D11. Stable request binding.** Capture the non-secret connection definition and revision needed by the queued operation. Validate current account authority, registration existence, definition revision, selected key reference and host trust before dispatch, and current publication authority before saving observations. Do not dispatch work against a different definition than the one requested. Controller key availability and trust are live inputs, never cached authorization. Existing alias resolution continues to revalidate current supported controller configuration.
- **D12. Editing and races.** Refuse changes to either connection mode while a remote operation is queued, running or reconciling. Preserve existing removal protection and abandoned-read recovery. Use transactional save/queue and conditional revision checks to reject conflicting submissions or edits after removal; an old worker cannot overwrite recovery, a newer revision or newer observations. Do not hold a database transaction open through network I/O.
- **D13. Previous evidence and plans.** Changing connection details invalidates current connection verification and requires new plan preparation. Never retarget an existing immutable plan or uncertain apply run. Retain private audit with its original connection provenance. Previous observations may remain accessible only as explicitly older evidence from their original target/revision, not as current inventory, current counts, feature authority or fallback approval for the edited target. This applies to saved details, alias changes and changes between modes.
- **D14. Whole workflow integration.** Discovery, plan preparation, reviewed apply, reconciliation, authorized transfer and any delivered feature that opens SSH must use the same connection-definition contract. Changing the registration form alone is insufficient. Maintain reviewed host-key, boot and native evidence admission; do not weaken cross-controller mutation exclusion or change supported feature conventions. Reconciliation preserves the original target and never replays uncertain work.
- **D15. Local uniqueness and identity.** Preserve existing display-name and alias uniqueness through migration. Detect exact duplicate normalized saved definitions locally and explain them; aliases, DNS names, IPs and different logins can still reach the same physical server. Do not claim endpoint uniqueness is physical identity or cross-device coordination. Existing host-key/boot admission and native locks continue to govern mutations.
- **D16. Presentation and permissions.** Present address, username and port only to permitted server viewers; restrict key-catalogue access and editable credential references to authorized registration editors. Key contents, arbitrary paths and agent identities are never inventory. Use existing feature-specific permissions for plans, results and links; registration editing grants no apply or root authority. Validate direct requests, fragments, queued dispatch and publication, including permission revocation. This feature does not claim tenant isolation or safe shared credential delegation for team hosting.
- **D17. Honest connection states.** Reuse not verified, queued, checking, failed, interrupted and verified-as-checked states with a visible timestamp. Distinguish identity refusal, unreachable server, failed authentication, unavailable credential reference and unavailable worker using sanitized business-owner wording. Partial discovery can succeed with explicit observation warnings. A saved form, historic successful check or worker queue is not proof of live health or server acceptance.
- **D18. Read-only boundary.** Opening saved pages, choosing form values, reloads and history navigation do not queue or run SSH. Saving and checking is explicit; retry and refresh remain explicit. The discovery check installs nothing, executes no application code, edits no native configuration and uses only the SSH account's existing authority. Do not write controller SSH configuration, trust or key files to make a connection work.
- **D19. Migration and removal.** Migrate every existing registration and retained operation as alias mode without changing its resolved settings or pretending it was checked again. Preserve existing history and audit. Upgrade tests cover nonempty databases and active/uncertain operations. Removal deletes only the established local registration records, is blocked by active work and never changes server data or controller credentials/trust. Document backup and supported rollback limits for schema changes; do not promise older binaries can read the new schema.
- **D20. Independent computers.** A second installation uses its own database, SSH agent/key references and known_hosts. It can enter the same public endpoint and reconstruct supported native state without the first installation. It cannot recover private controller records, copy another host's credential references automatically or inherit trust from a saved address. Optional remote databases and shared connection synchronization remain separate planned work.
- **D21. Prior art and the custom-code gap.** pyinfra already accepts explicit host, port, user, key, agent and known_hosts settings; Paramiko already handles authentication behind that connector. Native host-managed keys and existing trust records satisfy credential and trust requirements. The missing Barectl behavior is a validated non-secret saved definition, approved credential references, operation revision binding and operator presentation. Keep custom code limited to that gap. Record source/version compatibility and any additional upstream gap in the implementation issue before adding a new mechanism; no new SSH client or configuration generator is required.
- **D22. Delivery.** Deliver typed records/migrations, request services, all affected worker/adapter consumers, safe presentation, operator instructions and qualification together through complete vertical slices. Use the existing Django 6.1.1, Python 3.14, USWDS, HTMX 4 and Vite contracts. No version pin or frontend lifecycle change is implied by this specification.

## Testing Decisions

- **Primary boundary, confirmed with the operator.** Follow Add server → enter address and username → select existing key or agent → Save and check connection → existing discovery worker → verified SSH → typed snapshot → rendered server result. Include correction and retry, editing, switching supported modes and removal through this same public journey. Use the highest existing operator boundary; do not add a public connection-test API just for tests.
- **Behavior over structure.** Assert requests, remote effects, permitted stored evidence and visible states. A good test proves that the correct target and credential mode were used, trust was checked before authentication, no unexpected work happened and the result is honest. Do not mirror validators or assert internal helper calls as the feature's main proof.
- **Prior art.** Extend existing registration/worker/page tests, in-process SSH transport workflows, SSH trust/authentication tests, SQLite race tests and production/development browser journeys. The established remote-shell seam remains useful for fault cases; real SSH integration must also exercise the default connector without substitution. Registration, discovery, shared operations, owning plan/apply services, the SSH adapter and dashboard presentation are the affected owners.
- **Authentication and trust proof.** Use different agent/file identities and show that the unchosen mode is not tried. Cover missing files, removed catalogue entries, protected keys, absent agents, wrong usernames, nondefault ports, supported IPv4/IPv6/host names, unknown/changed/revoked host keys and hashed trust entries. Refusal must precede user authentication. Never use production secrets or trust-on-first-use in fixtures.
- **Safety and races.** Cover malformed input, injection strings, tampered key references, direct unauthorized endpoints, CSRF, access revocation before dispatch and publication, worker interruption, duplicate requests, removed registrations, simultaneous edits and active/uncertain operations. Verify that local key/config/trust files and remote configuration are unchanged and secrets/raw output never enter rows, logs, pages or fragments.
- **Provenance and compatibility.** Upgrade a populated alias-only database without losing history or active-operation binding. After a connection revision changes or fails, old snapshots remain distinctly older evidence and cannot populate the current target's inventory/actions; existing plans require fresh preparation. Exercise delivered preparation/apply/reconciliation consumers in saved mode, including loss after native acceptance and no replay. Keep alias behavior qualified independently.
- **Fresh computer proof.** Use two independent controller processes, accounts, databases, key sources and trust records against the disposable supported server. The second reconstructs native state with no import from the first. Demonstrate existing native exclusion where both submit a supported reviewed mutation; losing the first installation must not prevent independent access by the second.
- **Browser and release evidence.** Run the agreed journey with keyboard/focus, responsive layout, full-page and fragment requests, progress/stale/empty/refusal states, and both production and development assets. Run repository quality gates and affected native suites before pushing, required exact-head CI before delivery, and record exact revision, tool patches, tested controller/server environments, credential modes, migration evidence and remaining limits. Untested environments or authentication methods remain explicitly unqualified.

## Out of Scope

Browser private-key uploads or downloads, SSH passwords/passphrase prompts or storage, key generation or rotation, SSH-agent forwarding or browser-agent access, arbitrary file paths or local commands, editing SSH configuration or trust, automatic host-key acceptance, jump hosts/proxies, hardware-backed keys or SSH certificates without separate qualification, arbitrary SSH options, new sudo grants, new server mutation workflows, automatic retry/replay, scheduled discovery, fleet management, CLI parity, tenant isolation, team credential delegation, shared remote databases and synchronization, backup retention, application deployment and Barectl production packaging.

## Further Notes

- The existing alias-only connection and registration contracts remain the current implementation until this feature is delivered. Saved definitions are controller records, not native server inventory; native state remains authoritative.
- [pyinfra 3.x SSH connector guidance](https://docs.pyinfra.com/en/3.x/connectors/ssh.html) documents explicit targets and authentication controls. Check them against the pinned [pyinfra 3.10.0 connector implementation](https://github.com/pyinfra-dev/pyinfra/blob/v3.10.0/src/pyinfra/connectors/ssh.py). Barectl's strict pre-authentication host trust, safe credential catalogue and revision rules are product requirements, not pyinfra defaults.
- [Django 6.1 testing guidance](https://docs.djangoproject.com/en/6.1/topics/testing/overview/) supplies the existing test-runner foundation. The operator journey and independent-controller proof are Barectl-specific acceptance decisions.
- Existing remote-shell, shared lifecycle, native apply admission and controller-independent reconstruction decisions remain in force. This specification extends the input to those contracts; it does not reopen their execution boundary or create a second path.
- This work can be developed independently of the v0.7 Jobs milestone. All already delivered SSH consumers must be covered, and consumers added in parallel must adopt the shared definition contract before their release.
