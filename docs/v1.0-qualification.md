# v1.0 qualification record

This record names the evidence for the 1.0 compatibility and proof release, the single
source of truth in [#528](https://github.com/rajandangi/barectl/issues/528). It qualifies
the candidate revision, the only supported controller upgrade source (v0.4.x), the
versioned native contract, the v0.4.0-managed server proof, the recovery matrix and the
low-resource result. Anything this record does not list as passing is not qualified.

Contract version **1** is frozen by [ADR 0042](adr/0042-version-the-native-contract-without-a-server-marker.md)
and published in [native contract](contracts.md). Servers on the earlier Nginx, Certbot and
APT-PHP stack (v0.3.0 and earlier) are outside the supported upgrade path and are read as
**Not manageable**.

## Upgrade in place

The v0.4.0 fixture at `dashboard/upgrade_fixtures/v0.4.0.sqlite` is recorded from the tag by
`scripts/record-v040-database-fixture.py`. `dashboard.test_upgrade.FixtureMigrationTests`
copies it, applies every pending migration (including `jobs.0002`), and asserts that the
operator, saved connection revision, server, discovery snapshot and setting observation,
change preparation/review/run and the Viewer, Site operator and Administrator groups with
their permissions survive. The procedure and its limits are in
`dashboard/upgrade_fixtures/README.md`.

`dashboard.test_upgrade` also proves the command's success path, refusal while a remote
operation or queued task or worker is active, refusal of a pre-0.4.0 database with one
sentence, a failed migration restoring the original database and naming the backup, and the
truthful `--check` pending count. A v0.3.x database is refused by the same path; it is not
an upgrade source. The operator journey is [upgrading Barectl](upgrade.md).

## Native contract and mixed versions

`contract.test_contract` (13 tests) pins the manifest built from the owning modules against
`contract/manifest.json` and `contract/history.json`. A changed, removed or renamed promise
fails unless the contract version and a new history entry change together; the history
entry is the canonical SHA-256 of that version's sections. The sections are the site
convention, foundation, backups, results and application surface. The application surface
pins 12 permission names, every named route (103 at this revision), the documented
management commands and 10 documented environment variables.

Every change's `barectl-result` line carries `"contract": 1`. A pre-field line records `0`
and remains compatible with contract 1. `contract.test_recognition` and
`servers.test_preparation` prove a newer version and an older positive version are
unrecognized, while a matching or pre-field line is compatible. `operations.test_contract_refusal`
proves a direct prepare POST is refused; the same gate withholds every card and the server
status line reads **Outside supported settings**. Discovery stays read-only: the version is
read from the retained native result line, never from a server-side marker.

## Recovery

The [recovery guarantee matrix](recovery-guarantees.md) is the reader-facing index: one row
per covered failure, the test that proves it, the operator action and the explicit
non-promise. It links the Phase C, D and E records instead of re-qualifying them.

The abrupt-termination cases added by #538 cover a worker killed after review before
dispatch, a worker killed after dispatch, a server stopped during a body, and a reboot during
a paused full capture. They assert the evidence-warranted result class, exactly one
submission, the single recovery action and the absence of a success or "nothing changed"
claim. Local arm64 item times were 9.1 s, 11.5 s and 22.9 s for the three new merge-eligible
cases; the strengthened breadth reboot item was 56.0 s. On hosted amd64 the same cases
passed at 30.0 s, 32.7 s and 37.9 s. The existing controller-loss and fresh-controller
reconstruction cases passed in the same native suite.

## Low resources

[The 1.0 low-resource load result](v1.0-low-resource.md) records 1, 2 and 4 GiB memory-capped
containers from the existing breadth harness. All three classes passed in one local arm64 run
(3 of 3 in 25 s), with disk and memory readings in the same sample. Every class met the 4 GiB
free-disk target. The literal 900 MiB available-memory reading was met only because
`/proc/meminfo` is the shared Docker VM's. Read against the cgroup's own headroom, **1 GiB
left 534.2 MiB at peak and is a recorded miss** against the provisional 900 MiB threshold;
2 GiB and 4 GiB met it. The record names the next action and does not treat the 1 GiB size
as meeting the threshold. No real 1, 2 or 4 GiB host was measured.

## Not qualified

- **A real 1, 2 or 4 GiB host.** The low-resource result is three cgroups on one Docker VM,
  and the 1 GiB headroom miss is recorded above. A real small host is a follow-up, not a
  pass.
- **Journald log-retention settings.** Deferred from Phase E and 1.0 to 1.1 by
  [ADR 0043](adr/0043-defer-log-retention-settings-to-1-1.md). Not delivered, not qualified.
- **v0.3.0 and earlier.** Not an upgrade source; their database and Nginx/Certbot/APT-PHP
  stack were replaced. A fresh installation and discovery is the supported path.
- **A kernel reboot or power loss during an in-flight change.** The VM lane proves a real
  reboot and the restart body, not an interruption of another change. The container
  stop/start is a userspace restart; the matrix says so.
- **`RebootedFullBackup` on amd64.** It is breadth-only and was run on local arm64. The
  merge-eligible abrupt-termination cases did run on hosted amd64.
- **Power loss at every instruction boundary.** Four stages are sampled; the matrix makes no
  completeness claim.
- **A real 1/2/4 GiB host for the low-resource targets and a hosted amd64 low-resource
  dispatch.** The measurement is local arm64 only.
- **RPO/RTO beyond the measured restore scenarios**, automatic rollback, replay, and recovery
  of another controller's private database records. The matrix states each non-promise.
- **Ubuntu release upgrades, cloud/provider firewalls, fail2ban/CrowdSec, CIS/Lynis scores,
  Ubuntu Pro and fleet-wide patching.** Outside 1.0 and not qualified here.
- **A hosted amd64 VM lane dispatch.** The VM lane evidence is local arm64; hosted amd64
  native evidence is the `Native` run above.
