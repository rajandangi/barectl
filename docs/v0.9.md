# v0.9: Server security baseline and package maintenance

Accepted design for implementation, tracked in [#301](https://github.com/rajandangi/barectl/issues/301). Runtime behavior and qualification remain pending. This milestone is limited to a read-only security review, one UFW firewall convention, one OpenSSH sign-in policy, Ubuntu's automatic security updates, reviewed package updates and a reviewed reboot. The [native contract](security-native-design.md), [competitor research](security-competitor-analysis.md) and ADRs [0023](adr/0023-change-server-access-with-native-confirm-or-revert.md) and [0024](adr/0024-admit-exact-reviewed-upgrade-transactions.md) own the supporting decisions.

## Problem Statement

An operator who prepared hosting with Barectl has a server whose packages, sites and certificates are reviewed, but whose exposure is not. Barectl does not show whether a firewall is active, whether SSH accepts passwords or root password sign-in, whether Ubuntu installs security updates automatically, which updates are pending or whether the server needs a restart. Bootstrap refuses package upgrades by design, so the operator must leave Barectl and use the terminal for routine patching and reboots. A new authorized device must understand the same security state from the server alone.

## Solution

Each server gains a **Security** section. A security review lists plain-language findings with their collection time: firewall, SSH sign-in, automatic security updates, pending updates and restart required. Each finding names what was observed, why it matters, and the reviewed action that addresses it or the ordinary administration required.

The section offers reviewed actions, each prepared from fresh native evidence and applied through the existing native execution: Turn on the firewall and manage its allowed ports, Require key sign-in, Turn automatic security updates on or off, Install updates, and Restart server. Firewall and SSH changes stay in a short confirm-or-revert window: the server reverts them on its own unless a fresh connection from the controller proves that access still works. Barectl supports one standard per resource and warns about, and blocks changes to, a resource that does not follow it.

The review does not compute a security score or claim the server is secure. It reports the evidence Barectl can read and the limits of that evidence.

## User Stories

1. As an operator, I want a security review for each server, so that I can see its exposure without terminal commands.
2. As an operator, I want each finding in plain language with what to do next, so that I can act without Linux expertise.
3. As an operator, I want findings reconstructed from the server alone, so that another authorized device sees the same state without my database.
4. As an operator, I want unreadable evidence shown as unknown, so that missing access is not presented as a safe result.
5. As an operator, I want no security score, so that a number does not imply guarantees Barectl cannot prove.
6. As an operator, I want to see whether a firewall is active and which ports it allows, so that I know what the internet can reach.
7. As an operator, I want public listening services compared with firewall rules, so that an accidentally exposed database port is visible.
8. As an operator, I want to turn on a firewall that keeps SSH, HTTP and HTTPS open, so that other ports are closed by default.
9. As an operator, I want the SSH port taken from the server's effective configuration, so that enabling the firewall cannot close my current access.
10. As an operator, I want to allow an extra port from anywhere or from one address range, so that a monitoring or database client can connect.
11. As an operator, I want to remove a rule I added, so that I can close a port I no longer need.
12. As an operator, I want firewall and SSH changes reverted automatically if my access breaks, so that one mistake cannot lock me out.
13. As an operator, I want to know how long the revert window is and what happens if my connection drops, so that I can plan the change.
14. As an operator, I want existing firewall configuration I did not create through the standard preserved and explained, so that Barectl never silently replaces my rules.
15. As an operator, I want a firewall action refused on servers where another tool manages packet filtering, so that two managers do not fight.
16. As an operator, I want cloud provider firewalls described as outside Barectl's view, so that I do not mistake a server rule for complete network policy.
17. As an operator, I want to see whether SSH accepts passwords, keyboard-interactive or root password sign-in, so that I know the brute-force exposure.
18. As an operator, I want to require key sign-in through review, so that password guessing cannot sign in.
19. As an operator, I want the review to list accounts that would lose sign-in, so that I do not lock out a colleague who uses a password.
20. As an operator, I want root sign-in limited to keys or refused when my own connection does not use root, so that the policy matches how Barectl connects.
21. As an operator, I want the SSH change validated before reload, so that a syntax error cannot stop SSH.
22. As an operator, I want to see whether Ubuntu installs security updates automatically, so that I know the server is patched without me.
23. As an operator, I want to turn on Ubuntu's standard automatic security updates through review, so that I get the distribution's default behavior.
24. As an operator, I want automatic updates never to reboot the server on their own, so that restarts happen when I choose.
25. As an operator, I want custom automatic-update configuration shown as not following the standard, so that I can keep or correct it deliberately.
26. As an operator, I want to see pending updates with security updates separated, so that I can prioritise them.
27. As an operator, I want the age of the package information shown, so that an old list is not mistaken for current availability.
28. As an operator, I want to refresh package information through the existing reviewed action, so that the pending list is current.
29. As an operator, I want to install security updates only, or all available updates, so that I control the size of a maintenance window.
30. As an operator, I want the review to list exact packages, versions, new dependencies and services that restart, so that downtime is disclosed.
31. As an operator, I want installation refused when the transaction differs from the review, so that nothing unreviewed is installed.
32. As an operator, I want updates that would remove packages, replace my edited configuration files or need held packages refused with an explanation, so that maintenance never silently changes my setup.
33. As an operator, I want packages Ubuntu is still phasing in shown as waiting, so that I follow the distribution's rollout.
34. As an operator, I want site serving and service state verified after updates, so that installation success is not the only evidence.
35. As an operator, I want to see when a restart is required and which packages require it, so that I know a kernel or library update is not yet in use.
36. As an operator, I want to restart the server through review, so that I do not need the terminal or provider console.
37. As an operator, I want the restart refused while Barectl, backup, renewal or update work runs, so that a restart never interrupts managed work.
38. As an operator, I want Barectl to confirm the server came back with a new boot and its services and sites serving, so that I know the restart finished.
39. As an operator, I want a server that does not return within the expected time reported as outcome unknown with provider-console guidance, so that I am not told it failed or succeeded without evidence.
40. As an operator, I want all security mutations coordinated with every other Barectl change through the shared native lock, so that two devices cannot change the server at once.
41. As an operator, I want Barectl changes refused while Ubuntu's own automatic update run is active, so that they do not race package installation.
42. As a restricted Barectl account, I want separate permissions for viewing, preparing, access changes, updates and restarts, so that inventory access does not grant disruptive authority.
43. As an operator, I want each action's private plan and audit kept in my Barectl database, so that the server holds no Barectl records.
44. As an operator, I want exact tested releases, architectures and limits published, so that an accepted design is not confused with released capability.

## Implementation Decisions

- **D1. One deep module.** Add one `security` app. Its interface is the server's typed security observation and six named requests: firewall standard, firewall rule, SSH sign-in policy, automatic security updates, install updates and restart. Parsing of native evidence, rule rendering, the confirm-or-revert window and verification stay inside it. It reuses the action registry, immutable plans and audit, the remote-operation lifecycle, the native execution adapter and the verified pyinfra SSH connection. No generic hardening framework, rule language or plugin system.
- **D2. Package transactions stay in the package engine.** Install updates uses the existing profile-agnostic package engine, extended under [ADR 0024](adr/0024-admit-exact-reviewed-upgrade-transactions.md) to admit an exact reviewed upgrade transaction. Security supplies the reviewed selection; the engine owns digests, the guard and installation. There is one package admission path.
- **D3. Compatibility.** Ubuntu 24.04 and 26.04 on amd64 and arm64, with their release OpenSSH, UFW, unattended-upgrades and needrestart. Other distributions and unqualified architectures refuse every security action with an explanation. Docker or another packet-filter manager refuses firewall actions only; the rest of the section stays available.
- **D4. Security review.** Discovery gains passive unprivileged observations: listening sockets, UFW package and service state, unattended-upgrades package, timers and effective APT settings, package list age, pending upgrades and `/run/reboot-required`. Privileged facts (UFW rules, effective sshd settings, accounts without keys) come from a named authorized inspection, never implicit escalation. Each finding has a fixed category, observed facts, impact wording, collection time, and a linked action or ordinary-administration guidance. Unreadable evidence is unknown, never good.
- **D5. Firewall standard.** UFW is the only supported firewall. The standard is UFW active, IPv6 enabled, default deny incoming, allow outgoing, deny routed, logging low, and exactly these allow rules: each SSH port (D5a), 80/tcp and 443/tcp from anywhere, plus operator rules of the form port and protocol from anywhere or one IPv4 or IPv6 network. Barectl changes rules only through `ufw` commands and reads them through `ufw show added` and `ufw status verbose`. Any other rule, an active non-UFW nftables or iptables ruleset, firewalld, or Docker makes the firewall not follow the standard: Barectl reports it and blocks firewall actions without converting it.
- **D5a. SSH ports.** The firewall's SSH ports are those `sshd -T`, an enabled `ssh.socket` and sshd's actual listeners agree on, and must include the verified connection's port; any disagreement refuses firewall actions.
- **D6. SSH sign-in policy.** The standard is one fixed drop-in under `/etc/ssh/sshd_config.d/` that sorts before every other drop-in, setting `PasswordAuthentication no`, `KbdInteractiveAuthentication no` and `PermitRootLogin prohibit-password`, or `PermitRootLogin no` when the verified connection does not sign in as root. The effective `sshd -T` result is the authority; a later setting that wins over the drop-in is reported. Port, listen address, user, key and multi-factor management are outside this milestone. Barectl's own connection always uses keys; the review lists login-capable accounts without authorized keys that would lose access.
- **D7. Confirm-or-revert.** Firewall and SSH changes run under [ADR 0023](adr/0023-change-server-access-with-native-confirm-or-revert.md): the payload saves a root-only recovery preimage, arms a transient systemd timer that restores it, then applies and validates the change. The controller then opens a new verified SSH connection; only its success stops the timer. Loss of the controller, the new connection or the worker lets the server revert. The window is fixed at five minutes. The revert waits a bounded time for the lock, disables UFW when it was disabled before, and confirmation never removes a preimage a started revert is using. While a revert is armed, running or failed, every other Barectl mutation refuses.
- **D8. Automatic security updates.** The standard is Ubuntu's default: unattended-upgrades installed, `APT::Periodic::Update-Package-Lists "1"` and `APT::Periodic::Unattended-Upgrade "1"` as written by `dpkg-reconfigure` for the package, the distribution's allowed origins unchanged, `Unattended-Upgrade::Automatic-Reboot` false and the apt-daily timers enabled. Turning on and off use the package's own reconfiguration, installing the package first through the existing reviewed package profile when absent. Customised origins, blacklists or automatic reboot are reported as not following the standard and are left unchanged.
- **D9. Pending updates.** The review uses the server's current package lists without refreshing them and shows their age. It separates updates from the release's security pocket from other updates, marks phased updates Ubuntu has not yet offered to this server, held packages and packages whose upgrade would remove another package. A metadata refresh remains the existing separate reviewed action.
- **D10. Install updates.** The operator selects security updates or all available updates. The plan names each upgradable package at its reviewed candidate version and every new dependency, the services needrestart or maintainer scripts may restart, and the sites on affected PHP and web services. Candidates come only from the release's authenticated Ubuntu origins and the approved PHP source of [ADR 0016](adr/0016-limit-third-party-php-supply.md). It refuses removals, held packages, phased-out candidates, pending dpkg states, and packages whose installed configuration files differ from dpkg's or ucf's recorded version, since a configuration prompt cannot be answered safely. After installation it verifies versions, `dpkg --audit`, automatic marks, units and site serving readiness, then queues discovery.
- **D11. Restart server.** A reviewed restart lists the reasons from `/run/reboot-required.pkgs`, affected sites and services and the expected downtime. Under the mutation lock it refuses while any finite Barectl, revert, renewal, backup, retention, Laravel scheduler or apt-daily unit has processes, then runs `systemctl reboot`. Long-running queue workers are stopped by systemd within their stop budget and started after boot; the review says so. Verification needs a fresh connection reporting a new boot ID, profile services active, and site serving readiness. A server that does not return within ten minutes leaves the run as outcome unknown with provider-console guidance. The restart is never retried automatically.
- **D12. Native exclusion extension.** Every Barectl mutation payload, existing and new, refuses while `apt-daily-upgrade.service` or `apt-daily.service` has processes, in the same way as Certbot's renewal. Unattended upgrades do not take Barectl's lock; dpkg's own locks remain the final package exclusion. Because they can restart PHP-FPM or Nginx, v0.5 release activation and v0.6 full capture and restore must recheck idle apt-daily units and their drained services before reading data and before resuming, or disclose the limit; the [native contract](security-native-design.md#exclusion) records this.
- **D13. Permissions.** `security.view_securityplan` reviews plans and inspection results, `security.prepare_securityplan` prepares and runs the privileged inspection, `security.change_access` applies firewall and SSH plans, `security.apply_updates` applies automatic-update and package plans, and `security.restart_server` applies a restart. Inventory access shows passive findings only.
- **D14. Reconstruction.** Every observation comes from native configuration, package state, unit state and the kernel. Barectl adds no inventory, marker or status file. A fresh controller with independent SSH access and an empty database reconstructs the same findings and recognises the firewall and SSH standards Barectl applied.
- **D15. Native history.** unattended-upgrades logs and the journal remain the operating system's history. This milestone shows the last observed unattended-upgrades result in the review only; listing those runs belongs to the planned Jobs view.

## Testing Decisions

- Test observable behavior through the authorized operator workflow: preparation, review, apply, native evidence and rendered result. Reuse bootstrap package, coordination and reboot prior art, TLS and site native tests, and hosting browser support. Focused tests cover the parsers for `ufw`, `sshd -T`, `apt-config`, pending updates and reboot-required against real output from both releases.
- Prove reconstruction from an independent controller database after Barectl changes and after equivalent and conflicting external changes made with ordinary tools.
- Qualify confirm-or-revert on disposable servers: success, controller loss before confirmation, a rule that blocks the new connection, an SSH configuration that blocks key sign-in, worker stop, and two controllers. Each failure case must show the server reverted and reachable.
- Qualify Install updates with real upgrades from the release's own pockets, installing an older release-pocket version first: exact admission, drift refusal, removal refusal, held packages, modified configuration files, service restarts and site serving after upgrade.
- Qualify Restart server in the VM runner with a real kernel reboot: new boot ID, services and sites, refusal under active work, and outcome unknown when the server stays down.
- Test every existing mutation's refusal while `apt-daily-upgrade.service` runs.
- Run production and development browser journeys for the Security section with permissions, keyboard, focus, responsive layout, progress and recovery. Each slice runs the repository gates and affected native tests locally, independent Standards and Spec reviews, and exact-head CI before merge.

## Out of Scope

Cloud or provider firewalls, outbound filtering, rate limiting rules, port forwarding, Docker hosts, SSH port or listen-address changes, SSH key and user management, multi-factor sign-in, fail2ban, CrowdSec and intrusion detection, CIS or Lynis audits and scores, malware scanning, Ubuntu Pro, Livepatch and ESM enrolment, release upgrades, scheduled or automatic reboots, automatic retry, fleet-wide patching, notifications and compliance reports.

## Further Notes

The [native contract](security-native-design.md) records fixed grammar and version-matched upstream sources, and the [competitor analysis](security-competitor-analysis.md) separates documented capabilities from unproven ones. GitHub owns the parent/child and blocking relationships. This request delivers the design and implementation tickets; it does not implement or qualify the runtime.
