# v0.9: Server security baseline and package maintenance

Delivered in Phase E ([#301](https://github.com/rajandangi/barectl/issues/301)) for fresh
Ubuntu 26.04 servers on amd64 and arm64 ([ADR 0026](adr/0026-manage-fresh-hosts-on-one-target-stack.md)).
This document describes the behavior Barectl now provides; [security](security.md) owns the
detail, and the [Phase E qualification record](phase-e-qualification.md) names the tested
revision, environments and limits.

Each server has a **Security** section beside Sites, Activity, Settings and Advanced. It
shows plain-language checks for the firewall, public ports, SSH sign-in, automatic security
updates, waiting Ubuntu updates, whether a restart is needed and the web runtimes. Each
check says what Barectl read, why it matters, when it was read and at most one next action.
Unreadable evidence is **Could not check**, never a passing result. There is no score.

Opening the section reads the stored discovery snapshot. It makes no SSH connection and
queues no operation. The same connection check that refreshes the rest of the server
refreshes these checks, and a second controller reconstructs them from the server alone.

## What can be changed

Every action is a kind of the one change engine
([ADR 0035](adr/0035-one-change-engine-with-effect-derived-consent.md)). Preparation reads
fresh evidence, the confirm screen lists what the action reaches, and applying runs one
transient native unit under the shared mutation lock. A server-wide action declares a server
effect, so it needs Shared consent and its site list is rechecked under the lock.

| Action | Scope |
| --- | --- |
| Turn on firewall, Allow a port, Remove a port | UFW standard and operator rules |
| Require key sign-in | The fixed OpenSSH drop-in |
| Turn automatic security updates on or off | Ubuntu's own unattended-upgrades |
| Check for updates, Install security updates, Install all updates | The Ubuntu 26.04 archive |
| Restart server | The whole host, after the reviewed evidence |

Firewall and SSH sign-in changes run inside the five-minute confirm-or-revert window of
[ADR 0023](adr/0023-change-server-access-with-native-confirm-or-revert.md). The server saves
the previous settings, arms a transient timer, applies the change, and puts the previous
settings back unless a new verified connection from the controller confirms access. While
the window is open, or after a failed put-back, every other Barectl change refuses.

The restart body refuses while another Barectl change, a site backup, copy, integrity check
or cleanup, or Ubuntu's package maintenance still has processes. It writes its result and
asks systemd to restart the host. Success means a new boot identity on a fresh verified
connection, with the web server, each site's proxy and PHP, the database engine and every
enabled object cache running and each site answering its readiness path. No connection
within ten minutes leaves the outcome unknown with provider-console guidance; Barectl never
retries the restart.

## Ubuntu updates

Barectl reads waiting updates from the server's current package lists without refreshing
them, with their age. Security updates come first. Phased updates are shown as waiting for
Ubuntu's rollout; held packages and updates that would remove a package are shown as kept
back and are never installed. **Check for updates** refreshes the lists through Ubuntu's own
`apt-get update`. **Install updates** extends the exact reviewed package transaction of
[ADR 0024](adr/0024-admit-exact-reviewed-upgrade-transactions.md): every selected package and
version and every new dependency is named, and a removal, downgrade, hold, unfinished package
state or locally edited configuration file refuses before dpkg changes anything. The confirm
screen names the services Ubuntu may restart and the sites they serve.

## Limits

- Barectl reads and changes Ubuntu-archive state only. Caddy, PHP, HAProxy, Composer,
  WP-CLI, Node.js and restic come from the pinned Nix catalog; their fixes arrive through a
  reviewed catalog update shipped with a Barectl release.
- Cloud or provider firewalls are outside what Barectl can see.
- Docker hosts, firewalld and packet-filter rules outside UFW's supported shape block
  firewall actions only. A provider console is the fallback for a server that does not
  return from a restart.
- A real kernel reboot can only be proven on a real machine; the scheduled cloud-image lane
  owns that evidence, not the merge build.
- Barectl keeps its own change records in its application database. It leaves no Barectl
  inventory, journal or management database on the server.
