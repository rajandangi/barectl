# v0.2: Reviewed bootstrap

Status: accepted design for implementation, tracked in [the v0.2 specification](https://github.com/rajandangi/barectl/issues/106), not a released capability. Discovery already runs through the pyinfra connection this design builds on. The shared remote-operation lifecycle, read-only plan preparation and immutable plan review are implemented ([plan preparation](ssh-connections.md#plan-preparation)). Applying a reviewed metadata refresh through a detached transient systemd service, the native mutation lock, boot and deadline fencing, evidence revalidation, and reconciliation of lost acknowledgements and stopped workers from native evidence are implemented and qualified on the disposable Ubuntu server only ([applying a metadata refresh](ssh-connections.md#applying-a-metadata-refresh)); the control is not offered in production. Exclusion between independent controllers and aliases, outcome-unknown closure, terminal cleanup, and applying package profiles are not implemented, and production mutation depends on the qualification gates below. The existing discovery dashboard remains usable independently.

## Problem Statement

Operators can inspect servers but cannot yet prepare a standard web stack through Barectl. Bootstrap must provide a reviewable package and service change, keep working after the controller disconnects, and prevent independent controllers from applying conflicting plans. It must leave an ordinary Linux server that a fresh controller can reconstruct without private management records.

## Solution

Deliver Ubuntu 24.04 bootstrap in two independently selectable profiles: Nginx, and PHP 8.3 FPM plus CLI. Implement Nginx first to establish the shared package-admission engine; PHP reuses it without requiring Nginx to be installed. Each profile uses authenticated Ubuntu distribution packages and their defaults. The complete baseline contains `nginx`, `php8.3-fpm`, `php8.3-cli`, and required dependencies. Do not add recommended or optional packages implicitly.

The operator prepares a read-only configuration plan, reviews its package transitions and service effects, explicitly applies that revision, and checks the native outcome and refreshed observations. Package metadata refresh is a separate reviewed action; preview never runs an update. Finite native execution continues after SSH or controller loss. Conflicts, drift, and uncertain outcomes require reconciliation or a fresh review, never automatic replay.

## User Stories

1. As an operator, I want to see whether a server supports bootstrap, so that I know what prevents a safe change.
2. As an operator, I want to choose a standard Nginx or PHP profile, so that the resulting server follows distribution conventions.
3. As an operator, I want package versions and dependency changes in the review, so that I understand the complete installation.
4. As an operator, I want preview to remain read-only, so that inspecting a proposal cannot change the server.
5. As an operator, I want to refresh package metadata explicitly, so that network and package-list changes require my authorization.
6. As an operator, I want existing customization left untouched, so that bootstrap does not adopt or overwrite an application.
7. As an operator, I want default listeners and service-start effects disclosed, so that I can assess exposure and downtime.
8. As an operator, I want unavailable privileges explained before submission, so that application permissions are not mistaken for Linux authority.
9. As an operator, I want separate review and apply permissions, so that inventory access alone cannot change servers.
10. As an operator, I want an immutable reviewed revision, so that Apply cannot silently execute a regenerated proposal.
11. As an operator, I want drift rejected immediately before mutation, so that a stale review cannot authorize different work.
12. As an operator, I want duplicate submissions to refer to one run, so that double clicks cannot install twice.
13. As an operator, I want accepted work to survive controller disconnection, so that closing a laptop does not kill package installation.
14. As an operator, I want another device's conflicting work to block mine, so that independent databases cannot authorize concurrent mutations.
15. As an operator, I want the same protection across different SSH aliases, so that naming one server twice cannot bypass coordination.
16. As an operator, I want package-manager contention reported without waiting to apply an old plan, so that maintenance remains deliberate.
17. As an operator, I want failed steps and partial completion distinguished, so that a failure is not presented as automatic rollback.
18. As an operator, I want lost acknowledgements shown as uncertainty, so that a network error cannot cause blind replay.
19. As an operator, I want Check outcome to inspect native execution, so that recovery does not depend on the original worker remaining alive.
20. As an operator, I want an explicit outcome-unknown state when native history is missing, so that current configuration is not invented historical proof.
21. As an operator, I want reboot and timeout limitations disclosed, so that I know when ordinary Linux recovery is necessary.
22. As an operator, I want successful execution and post-change validation distinguished, so that an exit code alone cannot claim a usable web stack.
23. As an operator, I want fresh observations after bootstrap, so that the dashboard reflects native package and service state.
24. As an operator, I want a fresh installation to discover the baseline, so that losing Barectl's database does not lose server manageability.
25. As an operator, I want private review and apply history retained locally, so that native execution records are not confused with another device's account history.
26. As an operator, I want application audit records retained after removing a registration, so that removal cannot erase prior mutation decisions.
27. As an operator, I want completed native execution records cleared explicitly, so that ordinary runtime resources can be maintained without altering applications.
28. As a contributor, I want one operation lifecycle and one infrastructure boundary for apply, so that each profile does not invent its own queue or recovery rules.

## Implementation Decisions

### Supported baseline

Support Ubuntu 24.04 with systemd as the system manager, native APT/dpkg, and an architecture for which the qualified official packages are available. Release claims must name the architectures exercised in acceptance; package availability alone is not runtime qualification.

Use only authenticated Ubuntu Noble, updates, and security origins for the reviewed transaction. Do not modify repositories, signing policy, holds, firewall rules, SSH settings, or native automatic-update policy. Refuse unsupported sources or configuration affecting the transaction, broken/pending package states, held transitions, and any removal, downgrade, reinstall, or upgrade of an installed package, including dependencies. Ordinary Ubuntu maintenance can resolve such prerequisites outside this milestone.

Permit missing baseline components or an already conforming distribution baseline. Refuse leftover/custom web-stack configuration, additional sites or pools, unit overrides, conflicting listeners, or evidence that cannot establish the supported defaults. Repeating a healthy, already satisfied profile reports no changes before invoking installation, even when archives offer newer versions, and preserves auto/manual markings. Failed syntax, unhealthy services, masked units, or unverified defaults cause refusal rather than implicit repair. An otherwise conforming installed profile with merely stopped or disabled services can propose explicit enable/start effects for review without reinstalling packages. A partial installation is eligible only if native package health and standard configuration pass the same checks; no special trust is inferred from an earlier Barectl run.

Retain the distribution's default Nginx site and PHP pool. The review explains that package scripts can start services, expose the default HTTP listener, and trigger native restart policy before Barectl's final validation. PHP installation does not create an application route, per-site pool, database, certificate, or application user. No configuration editor or arbitrary command/package input is added.

### Review and package admission

A configuration plan is an immutable, typed local record for a profile or supported maintenance action. Its evidence and postconditions depend on the action; metadata refresh and terminal cleanup do not invent package transitions. Package-profile plans contain their profile revision, operator intent, verified host identity, target boot identity, evidence collection time, relevant configuration fingerprints, package sources/preferences/index identity, installed package and hold state, auto/manual markings, architecture, root package versions, complete dependency transitions, service effects, and postconditions. Store bounded normalized evidence, not raw configuration or credentials.

Bind each plan to a server-monotonic start deadline 15 minutes after preparation. Apply rechecks account authorization, SSH alias/host identity, current privilege, expiry, and evidence. It acquires native exclusion and revalidates again on the server before side effects. A changed package list, configuration, installed state, boot, or dependency result invalidates the revision. Do not refresh and apply a replacement without review. The deadline controls admission, not the lifetime of accepted work.

An explicitly reviewed metadata-refresh plan uses the same execution and audit contract but authorizes only updating authenticated package indexes. Its completion invalidates older package plans. Fingerprint effective APT configuration, including update and dpkg hooks; allow only a tested distribution hook baseline and disclose its native cache effects. Unknown hooks block admission before APT runs. Prove allowed pre-install guard predecessors cannot change packages; the guard cannot undo earlier hook effects. Require full update success, not a successful exit hiding partial repository errors; missing, unauthenticated, or expired release/index evidence blocks installation planning. Verify APT signature and validity checks rather than treating a local refresh record as authority.

APT simulation is preview evidence, not a lock or executable transaction. Use exact reviewed versions for root packages while preserving native automatic dependency markings. Compare the actual dependency transitions against the approved closure using a per-invocation native APT pre-install hook, protocol version 3, before dpkg changes packages. Supply the fixed guard inline; install no helper or plan file. Reject unknown action forms, malformed/truncated data, extra or missing transitions, architecture changes, partial install rounds, and unexpected hook behavior. Do not use missing-package fallback, removable-media sources, force options, unauthenticated packages, or automatic package repair.

The guard, frontend-lock ordering, complete transaction comparison, ordinary APT contention, existing hook behavior, and auto/manual preservation must be proven against the installed Noble APT release before enabling package installation. Root-version pins, `--no-upgrade`, or re-simulation alone are insufficient. Reject native package-lock contention without waiting to execute a stale plan. Arbitrary concurrent root edits cannot be made transactional by this protocol; refuse observed drift and document that maintenance must not bypass the coordination contract.

### Native execution and coordination

Use pyinfra's documented SSH/shell interface to submit a fixed, allowlisted native payload. Do not serialize pyinfra's internal operations or treat its prepare phase as a saved command program. Keep discovery's RemoteShell contract unchanged; put apply submission and inspection behind one small infrastructure adapter shared by the application services.

Submit a uniquely named transient systemd system service for each apply run. Use detached input, native journal output, `Type=exec`, `ExitType=cgroup`, disabled systemd variable expansion for the literal payload, `Restart=no`, a 30-minute runtime limit, a 60-second stop limit, and control-group termination. No SSH-owned scope, PTY, inherited pipe, uploaded script, resident helper, or automatic restart is allowed. Supported payload size is bounded and tested; reject an oversized plan rather than split it into independently accepted writes.

The finite payload acquires one root-controlled, exclusive, nonblocking native flock shared by all profiles, controllers, and aliases. The empty runtime lock and its private parent directory contain no inventory, lease, PID, history, or plan. Never unlink or replace the lock inode during its boot. Validate the boot identity and monotonic start deadline after acquiring the lock, then revalidate the reviewed evidence. Conflict exits before changes and requires fresh review; no wait queue or lock-stealing timeout is permitted. Native APT/dpkg locks remain separately required.

Keep required child commands in the foreground. Prove that exclusion covers all mutating descendants through success, failure, timeout, and termination. Under the lock, also reject another bootstrap unit with remaining execution processes: a child can close inherited descriptors after its wrapper dies. Require normal main-process exit with status zero and an empty execution cgroup for native success; Result=success alone is insufficient. An active/exited retained unit with no processes is terminal evidence, not an active mutation. Native service-start acknowledgement is not evidence that the mutation lock was acquired or that bootstrap succeeded. A remote timeout can leave package recovery work; it is not a rollback guarantee.

Persist the unique submission identity locally before sending anything, then inspect that same native unit, boot, and invocation identity after lost acknowledgement. Never submit a replacement because the response was lost. Retain successful terminal unit state with `RemainAfterExit=yes`, and failed state until explicitly cleared; do not use immediate collection. Expose a permission-protected clear-results action for individually verified terminal units with empty execution cgroups only. Model cleanup as a reviewed apply action through the same worker, local active slot, and native exclusion; it is never direct view-to-SSH work. Never stop active work or clear results as part of read-only discovery. Refuse new submissions at 100 retained bootstrap units until terminal cleanup; qualify simultaneous admission/cleanup so rejected or partially created units cannot accumulate without a bounded maintenance path. Native journal retention remains the operating system's policy and may be unavailable.

Bootstrap privileges are effective root or an existing, verified noninteractive sudo authorization for the actual commands. Never install a sudo policy, prompt for passwords, or assume `sudo -n true` proves permission for dispatch. Broad authorization for privileged shell/systemd execution is root-equivalent, not command-level sandboxing. Ordinary discovery remains unprivileged.

### Local lifecycle and uncertainty

Extend the shared remote-operation lifecycle when plan preparation introduces its second real workflow. Use kinds for discovery, plan preparation, and apply, with typed kind details and one local active-operation constraint. Preserve existing discovery identifiers/history and permissions during migration. Django transactions protect local state; never hold a database transaction open across SSH work or treat it as remote coordination.

Plan preparation is a distinct read-only workflow and may require explicitly authorized privileged inspection; it does not change ordinary discovery's no-escalation rule. Queue it outside HTTP requests. Keep plan revisions and audit events in the application database. Separate permissions for viewing plans/audit, preparing plans, applying reviewed actions, and clearing terminal native results. Check outcome requires inspection authorization; explicit outcome-unknown closure requires apply authorization. Recheck that the acting account is active and authorized at dispatch. Inventory access alone cannot expose privileged plans or audit details; filter preparation/apply entries in Activity accordingly. CSRF-protected confirmation names the server, revision, effects, and expiry.

Shared lifecycle states are queued, running, reconciling, succeeded, and failed. Queued, running, and reconciling occupy the active slot. Execution outcome and postcondition-verification outcome are separate typed fields. Discovery retains its current interruption behavior; an apply run that may have reached the server moves to reconciling when the worker disappears. Never apply discovery's ten-minute failure rule to accepted or uncertain remote mutations.

Check outcome inspects within the existing operation, so the active-operation constraint cannot block its own recovery. Conditional updates prevent competing reconcilers or stale workers from overwriting newer evidence. Confirmed native success plus verified postconditions yields success. Confirmed terminal execution with unavailable verification closes the local lifecycle as failed with reason verification unavailable, while preserving the known execution outcome and stale snapshot; later mutations still require complete fresh planning.

If native history is lost, display outcome unknown. Safe closure requires a changed boot or expiry of the old server-monotonic admission deadline, successful acquisition of the same native lock, no active native execution, fresh available state inspection, and explicit uncertainty acknowledgement. Close that reconciled request as failed with reason outcome unknown; retain its unknown execution outcome and present that wording prominently, never a claim that nothing changed. An old delayed payload then rejects its boot/deadline before changes. Keep the operation reconciling when these proofs are unavailable. Acknowledgement alone never releases it. The server can remain independently manageable through ordinary Linux tools; do not add a forget-and-retry bypass.

Transient execution survives controller/SSH loss, not server reboot. Do not resume automatically after reboot, infer that absent units never ran, or reconstruct private plans/accounts/history from native units. After terminal execution, validate Nginx/PHP syntax, expected package versions and native package health, service enablement/activity, and relevant listeners, then refresh supported discovery observations. Report partial completion, reboot requirements, and recovery steps without automatic rollback or blanket repair.

Registration removal is blocked by any active local operation. Terminal apply audit survives removal using copied non-secret server identity and plan details; it does not cascade with discovery history. Fresh controllers can inspect current native work and state but not recover another installation's private approval record.

## Testing Decisions

Use the authorized dashboard request, application services, database worker, actual native execution, typed persistence, and rendered server/Activity view as the main acceptance boundary. Retain RemoteShell/FakeServer for ordinary discovery. Add only the small submission/inspection adapter boundary needed to test local apply lifecycle faults; mocks do not establish APT or systemd correctness.

Mandatory qualification includes:

- Browser authorization, CSRF, review/expiry, duplicate submission, keyboard/focus behavior, partial results, Check outcome, and registration removal with retained audit.
- Existing discovery behavior across the shared-lifecycle migration, including queue races, stale-worker protection, snapshot retention, and local active-operation constraints.
- Disposable Ubuntu with actual supported package-manager and systemd revisions; read-only preview; metadata refresh; Nginx/PHP installation; default configuration/listeners; syntax and native postcondition validation; repeated no-op.
- Package-hook mismatch injection, dependency/candidate drift, extra/configure-only actions, malformed evidence, package holds, unknown hooks, changed auto/manual flags, native package-lock contention, partial download/install, and no execution of unreviewed dpkg transitions.
- Two independent controllers and databases, two aliases for one server, simultaneous submission, conflict refusal, lost acknowledgement, delayed delivery beyond admission expiry, controller destruction, child termination including killing only the wrapper while a child closes inherited descriptors and continues, reboot, missing journals, and terminal cleanup.
- Fresh-controller reconstruction without imported inventory or history, plus native external configuration changes and explicit unsupported/customized refusals.
- Same-boot unknown-outcome closure with actual lock acquisition and expired admission; old-boot delayed dispatch rejection; unavailable proof must remain blocked.
- All repository quality gates and real-browser/disposable-server acceptance before enabling each mutating action. An unavailable runtime, skipped suite, or unverified upstream assumption blocks that action's release.

## Out of Scope

General package upgrades/removals/repair, repository management, other distributions, unqualified architectures, custom stack adoption, application sites/users, optional PHP extensions, databases, TLS, firewall/SSH hardening, deployments, backup scheduling, arbitrary commands, general log viewing, persistent agents, custom remote tracking records, shared databases, and credential storage are outside v0.2. Future site provisioning follows the standard configuration and reconstruction requirements already recorded in the architecture.
