# v0.7: Server Jobs and native server history

Accepted operator journey and implementation specification for v0.7, the next planned work after v0.6, tracked in [#284](https://github.com/rajandangi/barectl/issues/284). Implementation, qualification and release remain pending. Jobs is a per-server view of supported native work and retained evidence, distinct from Activity's private Barectl records.

## Problem Statement

A business owner or developer needs to know what happened on a managed server while Barectl was closed. A backup may have run overnight, a certificate renewal may have failed, or a website update may have stopped halfway through. The operator needs a clear explanation and a safe next step without knowing Linux service names or reading raw logs.

Activity currently shows records kept by this Barectl installation. Another authorized computer does not have those private records. It still needs to inspect what the server can establish from its native configuration, execution state and retained history. Missing history, denied access and a failed inspection must not become a false claim that work succeeded, failed or never ran.

## Solution

Add Jobs inside each managed server's dashboard. It opens a saved view with Last checked at and four groups in this order: Needs attention, Running, Automatic work and Recent results. Refresh explicitly checks the server through the existing worker and verified SSH boundary. Opening the page, inspecting saved details and changing filters do not start remote work. While a check is queued or running, and after a failed check, show the previous results with their original time and a clear freshness notice.

Cover supported native backup-related runs, website deployments, server setup changes, certificate renewal, Laravel scheduler state and Laravel queue-worker state. Support each only against its delivered and qualified convention. Show the state as last checked, safe explanations, known website relationships and available times. A normally stopped worker or disabled schedule is not automatically a problem. Worker state does not establish whether every individual application task succeeded.

Opening a result explains what happened and links to the existing permitted feature or recovery screen. For example, when both findings are established: "The backup was saved on this server, but copying it offsite failed." Technical evidence is optional. Raw application output, private application logs and secrets stay outside the view. Jobs adds no independent change controls or automatic retry.

Recent results default to Past 7 days, with Today and Past 30 days choices and optional Website, Type of work and Result filters. Times use the viewer's local time with the time zone named, without changing native schedules. These ranges select available evidence; they do not promise that much retention. Another authorized controller can reconstruct supported server evidence without copying another Barectl database. Unknown action, website, time, outcome or history coverage stays explicit.

## Implementation Decisions

- **D1. One read-only composition.** Extend the existing server, discovery and presentation composition with a focused Jobs observation module. Discovery owns bounded native collection and typed snapshot publication; servers owns navigation and authorized rendering. Application services own request validation and queueing. Keep native interpretation inside this module and its owning feature readers. No generic event bus, job engine, plugin framework or speculative abstraction is required.
- **D2. Existing lifecycle and transport.** Refresh extends the existing read-only discovery request, worker, remote-operation slot and recovery behavior. Reuse the one verified pyinfra connection and existing native execution inspection. Never put SSH in a view, introduce another connector or schedule controller polling. Navigation and local progress polling read saved state only.
- **D3. Supported native sources.** Recognize the delivered conventions for retained finite apply runs, backup services and timers, certificate renewal, and Laravel scheduler and worker units. Reuse each owning feature's validated state/result interpretation. Native configuration, unit state, invocation identity, process evidence and permitted retained records are authority; neither a unit name nor a successful journal line is enough on its own.
- **D4. Fresh-controller classification.** Derive type and site relationship only from supported native evidence. Current transient names contain a random identity and do not establish action or site. Existing or older runs lacking adequate evidence remain unclassified. Do not parse arbitrary shell payloads, application text or private audit to invent their meaning. Expose only an authorized generic finding when classification is unavailable; otherwise withhold details and disclose a coverage limitation without leaking them. Classification uncertainty is an accepted result, not a reason to install tracking storage.
- **D5. Local schema.** Add migrations for typed Jobs observations attached to a successful discovery snapshot, including native identity, optional proved type/site/time fields, execution state/result, independent verification/result availability, timer/worker state and coverage warnings. Preserve the previous successful snapshot on failed collection. Record request authority needed for worker checks locally. The cache is a bounded observation, not an indefinite mirror or replacement server audit. Existing registrations and Activity keep their meaning.
- **D6. Read contract.** The public Jobs read returns permitted summary groups, filtered result rows, safe detail projections, collection time, freshness, inspection progress and coverage warnings. Templates lay out those projections without interpreting native evidence or accessing raw observation models. Native identities and timestamps remain distinct from local refresh-request times.
- **D7. Navigation and refresh contract.** Add a bookmarkable per-server Jobs section with ordinary navigation, reload and back/forward behavior. Its page, saved detail and filter reads queue nothing. Refresh is an authenticated, CSRF-protected request through the existing discovery service and worker. Require server viewing and the existing discovery-request authority; reuse active-attempt/busy behavior instead of creating duplicate inspection requests. Show the relevant queued, checking, interrupted, busy and failed states.
- **D8. Summary behavior.** Present Needs attention, Running, Automatic work and Recent results in order. Distinguish failed, skipped and could not confirm within attention. Running always means running when checked. Show normally disabled or stopped configuration as such, without inventing a failure. Unknown evidence never becomes a zero, a healthy state or an absence finding.
- **D9. Practical results.** Keep execution completion, feature verification, available safe messages, backup copy availability, artifact integrity and restored serving separate. Do not trigger new backup validation or serving execution merely to fill the view. Display existing verified findings only when the supported source and freshness establish them; otherwise show their unavailability. Worker state does not expose or prove individual queue-item outcomes.
- **D10. Detail and next steps.** Show the work's practical effect, available website/times, safe reason/messages and permitted known-route feature or recovery links. Technical evidence is optional and remains authorized. Feature workflows own all changes, preparation, review, native admission, reconciliation and recovery. Jobs never retries, stops, restarts, restores, acknowledges or clears work itself. A link cannot recreate a missing private plan or run record on another controller.
- **D11. Safe result sources.** Preserve each feature's disclosure contract. Use bounded validated non-secret result projections, scoped to the exact native identity and invocation where applicable. Do not export raw application stdout/stderr, private application logs, dump content, environment/configuration secrets or arbitrary journal messages. Missing safe output can coexist with proven execution completion. Native access refusal never triggers automatic sudo or access reconfiguration.
- **D12. History coverage.** Distinguish no available evidence, denied access, unsupported or malformed evidence, query failure, explicit truncation and established expiry. Journal and unit retention remain native policy. Repeated scheduled service state may establish the latest invocation without every historical tick. Show incomplete coverage honestly, including after reboot or native cleanup; never claim a full audit or infer that no work ran.
- **D13. Date selections.** Default to Past 7 days; offer Today and Past 30 days. Evaluate boundaries in the named viewer time zone. Today starts at local midnight; the multi-day ranges include today and the preceding six or twenty-nine local calendar days through the displayed current time. Filter execution evidence by its established native time, not the local inspection time. Unknown or inconsistent times remain unavailable and are accounted for in coverage, not assigned a guessed date.
- **D14. Optional filters.** Website and Type of work match only proved associations. Server-wide work need not belong to a website. Result choices are finished, failed, skipped and could not confirm; terminal completion and independent result/verification findings stay visible even when a row matches a filter. Define the filter mapping centrally from the validated outcome projection. Keep notices for unclassified, untimed and truncated evidence, and never infer completeness from filtered counts.
- **D15. Time presentation.** Display aware times in the viewer's supported local time zone with its name. Use the existing frontend lifecycle for a bounded browser time-zone preference when needed; validate any supplied zone and provide an explicitly labelled UTC fallback if it cannot be resolved. Preserve native schedule configuration and show its authoritative zone in optional details. Use native next-run evidence, not a custom scheduler or an assumed recurrence. Daylight-saving or viewer-zone changes alter display and filter boundaries only.
- **D16. Authorization.** Require authentication and server viewing, then the existing owning feature's view authority for classified rows, safe messages, details and action links. Apply disclosure rules to grouped counts and filter choices as well as direct endpoints and fragments. Recheck active account and refresh authority at queue/dispatch/publication boundaries; reapply current viewing authority on every read. A shared worker's SSH credentials never expand a Barectl account's viewing rights.
- **D17. Unclassified access.** Inventory viewing does not grant access to arbitrary retained unit or journal contents. Without a proved owning permission rule, keep action/site/messages and sensitive identifiers hidden. A permitted generic coverage or busy finding may explain that further details cannot be identified or shown; it does not name restricted work. Do not create a blanket read-all-log permission or a browser privilege prompt.
- **D18. Resource limits.** Preserve the existing remote time and output ceilings. Use finite native candidate queries and bounded item/message storage, with literal limits established and tested within those budgets before delivery. Limit exhaustion is explicit incomplete evidence, never silent dropping or a reason to raise global SSH caps. Do not add background retention, journal collectors or a server-side index to make longer history appear complete.
- **D19. Race and lifecycle safety.** Publish a complete typed observation only for the still-authorized current inspection; an interrupted or superseded worker cannot overwrite newer results. Preserve the active operation's server-removal protection. Saved rows remain registration-scoped and never join another server or a reused site identifier through text. Native changes between reads produce conservative transitional/partial observations, not a transaction guarantee.
- **D20. Interface and language.** Use the existing custom dashboard, USWDS theme, Django templates, HTMX lifecycle, Inter and Vite integration. Keep business-owner wording ahead of technical evidence. Use labelled filters, keyboard/focus handling, responsive layouts and accessible queued/checking/completion announcements. Do not reintroduce Django admin, raw command controls or an implementation-led operator flow.
- **D21. Upstream reuse and bounded custom work.** Native systemd introspection and retained journal facilities own execution evidence and timer state. Check supported pyinfra facts and existing feature readers before adding fixed native queries; service-mutating operations are not a read-only refresh. Custom work is limited to convention recognition, safe projections, typed caching, permission filtering and this operator journey. Record any additional gap and checked upstream alternatives in the owning issue before implementing a new mechanism. No new infrastructure dependency is selected by this specification.
- **D22. Delivery sequencing.** This is v0.7, planned after v0.6, and depends on the backup milestone's delivery and qualification. Generic hosting/native inspection work can be built from delivered foundations; application-specific integrations remain gated by their actually delivered conventions. Every implementation slice includes its necessary records, inspection, permissions, dashboard states, tests and operator guidance rather than leaving interface work until the end.

## Testing Decisions

- The primary test boundary is the approved operator journey: authorized server Jobs request, Refresh, existing worker and discovery service, native collection, typed publication, rendered summary/detail, filters and feature links. Prefer this one existing boundary over new public test interfaces. A good test proves an observable outcome, refusal, retained information, access boundary or absence of remote mutation; it does not mirror helper structure or count private calls.
- Extend prior art from server-section navigation and permission tests, discovery refresh/lifecycle and transport workflows, typed snapshot/presentation tests, site Activity outcome separation, existing browser hosting journeys and fresh-controller native reconstruction. Use reusable existing fake/real adapters as internal support, not a second production execution path. Keep shared test support out of test-module imports.
- Exercise initial emptiness, stale observations, queued/checking progress, occupied operation slot, absent worker, interrupted collection, failed refresh and complete/partial publication. Prove page/detail/filter reads start no SSH work and repeated Refresh requests do not create duplicate active inspections.
- Use native fixtures for each delivered included feature and a fresh second controller with its own account, database, alias, key and host trust. Establish native ground truth independently. Disconnect or remove the initiating controller and prove supported results remain inspectable only to the extent native evidence permits. Include external changes, native cleanup, ordinary log rotation and real server reboot; a container restart is separate evidence.
- Cover safely classified and unclassified transient work, changed/spoofed names or invocation identity, missing site relationships, unsupported unit states, unreadable process evidence, absent timestamps and inconsistent observations. Prove no arbitrary command or log text becomes an action, site or permission assignment.
- Cover running, normally stopped/disabled, failed, refused/skipped, timed out, partial, completed-with-unavailable-result and unknown outcomes. Keep backup execution, onsite/offsite availability, integrity and restore-serving findings separate. Prove no individual application-job success is inferred from worker state and no refresh performs application execution, artifact validation or replay.
- Exercise malformed, oversized, secret-bearing and inaccessible sources, query timeouts, truncated coverage and all configured resource limits. Seed recognizable secret fixtures and prove they do not reach observation rows, worker messages, optional technical details, browser HTML or progress responses. Preserve per-feature safe-result contracts.
- Test authenticated and unauthenticated direct requests, each relevant feature-view permission, inventory-only access, rejected refresh authority, revocation before dispatch/publication and after collection, safe generic unclassified presentation and forbidden row/count/filter disclosure. Verify normal SSH host-trust refusal and limited-server-access partial results without privilege escalation.
- Test Website, Type of work and Result filters, untimed/unclassified rows, explicit partial coverage, newest-first ordering and no filter defaults beyond the seven-day range. Verify local-midnight Today boundaries, seven/thirty calendar-day ranges, zone travel, daylight-saving transitions and labelled fallback behavior. Native schedules must remain byte-for-byte unchanged by display/filter requests.
- Run production and development browser journeys for ordinary links, direct loads, back/forward, keyboard use, focus, responsive presentation and assistive-technology announcements. Assert plain-language state and next-step wording, with technical evidence optional and permission-appropriate links enforced at their destination.
- Before pushing runtime changes, run the repository quality gates and the affected native suites on supported Ubuntu releases. Record exact-head native CI as required. Before claiming delivery, publish a qualification record naming source revision, tool patches, architectures, native evidence fields, limits, safe-result support, reboot coverage and unresolved combinations. An accepted spec or local unit-test pass is not runtime qualification.

## Out of Scope

A combined all-server Jobs page or fleet monitoring; automatic page-open/periodic SSH checks; email, phone, push or external alerts; independent Jobs mutation buttons; arbitrary unit control, shell commands or cron editors; individual Laravel application queue items and WordPress cron-event histories; raw application/system log browsing or export; recovery of another controller's private audit and approvals; guaranteed history retention or changes to native log policy; new server journals, indexes, markers, agents or management databases; replay/resume of uncertain work; general security auditing; new SSH credential storage, shared Barectl database support or team-hosting design; automatic backup validation or restore rehearsal; support for undelivered or unqualified feature conventions; automatic health, rollback or exactly-once guarantees.

## Further Notes

The managed server remains authoritative. Local accounts, refresh requests, cache and private operation records stay in the application database. Jobs supports another authorized controller without database transfer and cannot reconstruct evidence that the server did not retain. It does not change native execution, cooperative exclusion, scheduled backup policy or an owning feature's destructive review.

The primary test boundary and second-controller verification were confirmed. Publication makes this design ready for implementation planning, not released functionality. The post-v0.6 sequence is gated by [backup milestone #271](https://github.com/rajandangi/barectl/issues/271); application and database compatibility claims still require their delivered qualification records.

Existing design owners are the [architecture and state boundary](https://github.com/rajandangi/barectl/blob/main/docs/architecture.md#state-and-discovery), [native execution decision](https://github.com/rajandangi/barectl/blob/main/docs/adr/0006-use-native-bootstrap-execution.md), [Laravel native contract](https://github.com/rajandangi/barectl/blob/main/docs/laravel-native-design.md) and [backup native contract](https://github.com/rajandangi/barectl/blob/main/docs/backups-native-design.md). Their restrictions take precedence over a convenient but unsafe source of display data.

Official guidance checked for the selected reuse:

- systemd's machine-readable property inspection is documented in the versioned [255 systemctl manual](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemctl.xml) and [259 systemctl manual](https://raw.githubusercontent.com/systemd/systemd/v259/man/systemctl.xml). Use installed-version supported properties and qualify them; human-readable status output is not the parser contract.
- Timer configuration and activation semantics belong to systemd, as documented in the [255 timer manual](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.timer.xml) and [259 timer manual](https://github.com/systemd/systemd/blob/v259/man/systemd.timer.xml). This view reads schedules and does not alter catch-up or recurrence policy.
- Journal selection and access rules are documented in the [255 journalctl manual](https://github.com/systemd/systemd/blob/v255/man/journalctl.xml) and [259 journalctl manual](https://raw.githubusercontent.com/systemd/systemd/v259/man/journalctl.xml). Native matching capabilities do not authorize export of arbitrary message bodies or establish complete retention. Preserve each feature's bounded safe-result contract.
- [pyinfra 3.x systemd facts](https://docs.pyinfra.com/en/3.x/facts/systemd.html) provide native status/enablement prior art; [systemd operations](https://docs.pyinfra.com/en/3.x/operations/systemd.html) manage service state. Check the installed pyinfra 3.10.0 implementation for compatibility. The additional Barectl requirement is safe convention-specific identity, outcomes, coverage and permission presentation through the existing verified connection, not replacement of upstream process management.
- [Django 6.1 testing guidance](https://docs.djangoproject.com/en/6.1/topics/testing/overview/) provides the version-matched database/test-runner foundation. The operator journey as primary boundary and second-controller native proof are Barectl-specific decisions.
