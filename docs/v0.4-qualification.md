# v0.4 qualification record

This record lists the evidence for the [v0.4 WordPress](v0.4.md) specification as implemented by its sub-issues ([#244](https://github.com/rajandangi/barectl/issues/244), [#245](https://github.com/rajandangi/barectl/issues/245), [#246](https://github.com/rajandangi/barectl/issues/246), [#247](https://github.com/rajandangi/barectl/issues/247), [#248](https://github.com/rajandangi/barectl/issues/248), [#249](https://github.com/rajandangi/barectl/issues/249), [#250](https://github.com/rajandangi/barectl/issues/250), [#253](https://github.com/rajandangi/barectl/issues/253)) and the final qualification slice [#251](https://github.com/rajandangi/barectl/issues/251). It says what was tested, on which revision and where. Anything it does not list as tested is not qualified, and no slice qualifies another. Issue state, test results, published commit statuses, merges and release availability are separate facts. This record identifies each result by revision and environment. **v0.4 is not released**.

Contributors: the operator guide is [WordPress](wordpress.md), the contract is the [native design](wordpress-native-design.md), and the native suites are described in [native suites](quality.md#native-suites).

## Container restart and real reboot

A Docker restart keeps the host kernel's boot ID and monotonic clock, so the container tests prove the boot fence with the old payload but not a real reboot. They cover the installation, Finish, inspection and maintenance suites; the real kernel reboot is separate:

- `bootstrap/test_reboot_vm.py` (existing): a reboot while dpkg installs PHP; and the renewal timer, lock and sentinel data across a second reboot.
- `bootstrap/test_reboot_vm.py::test_a_reboot_ends_the_wordpress_tool_setup_which_is_reconciled_never_resumed` (new): the server reboots as the WP-CLI setup starts downloading the PHAR. The new boot has a new boot ID and a restarted clock, no unit or private directory remains, and the PHAR is not installed; Check outcome keeps the run reconciling and explains the restart; an acknowledgement closes it as outcome unknown; the leftover staged download makes a fresh review refuse, and after the administrator removes it a new review installs and verifies the tool in the new boot.

At `5898d81`, all three tests passed on the 24.04 virtual machine (1,247 seconds) and on the 26.04 virtual machine (2,010 seconds), both aarch64 under software emulation. These VM tests were not rerun at the continuation revision.

The tool setup is the lightest WordPress run on the shared admission, boot fence and reconciliation, and it is the only WordPress run exercised across a real reboot. The installation, Finish, inspection and maintenance bodies use the same admission, fence and acknowledgement code, but no virtual machine ran a WordPress application, so a reboot during those is covered by the container evidence and the shared code, not by a real-kernel test.

## Failures and skips

- **Live PHP source (not WordPress).** At `5898d81`, eight items failed on both releases in `bootstrap.test_php_source_remote.PhpSourcePublicationTests`, `dashboard.test_php_versions_remote.SelectedPhpHostingJourneyTests` and `dashboard.test_php_versions_browser_remote` (production and development). The refusal was the designed behaviour; those tests then depended on live source freshness. Current gating tests use the frozen fixture and do not depend on live metadata freshness. Nothing was weakened, and the WordPress workflows, which use Ubuntu's own packages, are unaffected. The later frozen-fixture gating tests supersede this live-source dependency for native status recording; a fixture pass makes no claim about current live metadata.
- **Transient at `5898d81`.** In that earlier local full run, `wordpress.test_finish_remote.FinishControllerLossTests` failed once on 24.04 with WP-CLI's core checksum verification of the extracted tree refused, a request to wordpress.org's checksum service; the same two tests passed on an immediate rerun on both releases, and on 26.04 in the full run. - **Skips.** The three `vm` tests skip in the container runs and ran on the earlier virtual-machine revision above. The continuation counts use the explicit skips in retained Django item logs. Ubuntu 24.04 also skips tests for an absent third-party repository and absent provider customizations.
- **Gate and journeys.** The WordPress reviews refuse any combination outside `wordpress/qualification.py`, and the site page shows the supported combinations. ## Limits

- **Not qualified for production.** amd64 admission on both releases remains disabled pending review of its candidate evidence; PHP branches and sources other than the release's own Ubuntu packages; MariaDB series other than the release's own; PostgreSQL; core releases other than 7.1.3; WP-CLI other than 2.12.0; multisite, subdirectory installs and every item in the [specification's out-of-scope list](v0.4.md#out-of-scope). Real hosts other than the containers and virtual machines above were not tested.
- **Architecture and reboot evidence.** The earlier local and virtual-machine results are aarch64; the hosted continuation adds x86_64 container candidate evidence. The virtual machines ran under QEMU's software emulation without KVM, so their timing says nothing about production hardware. No real-kernel amd64 reboot run is recorded.
- **Installed-application TLS.** Renewal and activation now have both-release local aarch64 proof and hosted x86_64 candidate proof through `wordpress/test_tls_remote.py` at `b894dc7eb525fa03e3b4b8e57049f320e0202296`. Those hosted TLS items passed within the initially failed aggregate run; their result does not qualify the failing PHP items. The authority is the private Pebble fixture, not a public CA or a production server.
- **Serving verification does not validate the certificate chain.** The installation's HTTPS checks go to the loopback with `--resolve` and `--insecure`, so they prove routing, the front controller and denials for the canonical name, not the certificate; the certificate is the TLS workflow's evidence.
- **Private evidence.** Passive discovery reads only what the SSH identity can read; a lesser identity sees the private configuration and database catalogs as unavailable. The result of an inspection or maintenance run is retrieved from the native journal and is unavailable once it rotates; the outcome stays what systemd recorded.
- **Network services.** The tool setup and installation depend on GitHub and wordpress.org being reachable from the server and on the pinned artifacts still being served; a change to either refuses a run rather than weakening a pin.
- **No broad isolation.** The lock coordinates cooperating Barectl controllers and guarded renewal. It does not stop web requests, application cron, WordPress's updater or an administrator, and Barectl promises no containment of hostile application code ([after installation](wordpress.md#after-installation)). Barectl keeps no backup of the application; ordinary patching and backups remain the operator's.
- **Durations.** The committed WordPress duration estimates come from the earlier passing aarch64 items and are scheduling data, not qualification evidence. New architecture measurements affect committed estimates when those measurements are incorporated.

## Remaining qualification and release decisions

1. amd64 production admission remains disabled. Its hosted candidate evidence must be reviewed with the disclosed limits before a separate change enables it.
2. Real-kernel WordPress application reboot evidence is still limited as [recorded above](#container-restart-and-real-reboot). Container evidence does not become real-reboot proof.
3. Publication of v0.4 is a release decision outside this record.
