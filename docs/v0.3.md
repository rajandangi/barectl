# v0.3 PHP sites

Status: implemented, with per-action qualification recorded in [v0.3 qualification](v0.3-qualification.md). v0.3 is not released. The public Let's Encrypt staging challenge and local functional verification passed; the dependency audit remains a release gate. Tracking issue: [#144](https://github.com/rajandangi/barectl/issues/144). See the [implementation tickets](v0.3-delivery.md). Delivery order was HTTP sites, database profiles and site databases, then TLS. Each action must pass its own acceptance gates before it is offered. The [configuration convention](site-conventions.md) supplies the concrete native layout; [design decisions](v0.3-decisions.md) record the resolved trade-offs and sources.

## Problem Statement

An operator can discover a server and bootstrap Nginx and PHP, but cannot create a PHP site, give it a private database, or enable renewable HTTPS. Hand-written configuration can drift between review and apply, and a dashboard inventory can hide that the files or permissions no longer describe a working site. A new controller must reconstruct the site from the server without importing the previous controller's database.

## Solution

Create a site through separate reviewed actions. First establish a Linux site user, document root, PHP-FPM pool and HTTP Nginx configuration. Offer MariaDB and PostgreSQL bootstrap profiles independently; after the selected engine is ready, provision a site's database and database principal. Finally, prepare TLS prerequisites and issue a certificate with native automatic renewal.

Each action shows its exact intended changes, checks current native evidence again immediately before mutation, runs through the existing detached execution boundary, and verifies real behavior. Unknown layouts and conflicts produce refusals. Interrupted changes remain visible as partial or unknown outcomes and require fresh inspection; no action silently replays or adopts an unrelated resource.

## User Stories

1. As an operator, I want to see sites reconstructed from the server, so that changing computers does not lose my inventory.
2. As an operator, I want the dashboard to distinguish a site from an isolated Nginx file or FPM pool, so that incomplete configurations are visible.
3. As an operator, I want to create an HTTP PHP site before adding a database or TLS, so that I can verify one working change at a time.
4. As an operator, I want to choose a site identifier and explicit domain names, so that I can predict the resulting resources.
5. As an operator, I want collisions in names, accounts, paths, sockets and domains refused, so that an existing application is not overwritten.
6. As an operator, I want each site's PHP processes to use its own Linux identity, so that one site's private files and database are not available to another site's runtime user.
7. As an operator, I want configuration ownership separated from application ownership, so that an application cannot rewrite its service configuration.
8. As an operator, I want to review complete generated configuration and permission changes, so that approval describes what will actually be installed.
9. As an operator, I want drift and unavailable evidence to invalidate a plan, so that an old review cannot overwrite a newer administrative change.
10. As an operator, I want a conflicting controller or scheduled renewal to block apply, so that shared files and services are not changed concurrently.
11. As an operator, I want Nginx and PHP syntax checked before reload, so that a bad candidate is not knowingly activated.
12. As an operator, I want a real HTTP and PHP check after apply, so that a successful command is not mistaken for a working site.
13. As an operator, I want partial changes and recovery instructions to survive controller loss, so that I can inspect and repair the native server safely.
14. As an operator, I want Check outcome to inspect the original run, so that lost acknowledgements do not create duplicate resources.
15. As an operator, I want a fully satisfied request to become a no-op, so that repeating a request does not reset files or application data.
16. As an operator, I want external edits and removals to change the next discovered view, so that cached intent never replaces native evidence.
17. As an operator, I want inaccessible and unsupported relationships named explicitly, so that missing permission is not presented as absence.
18. As an operator, I want MariaDB and PostgreSQL installed through the existing package review engine, so that database setup has the same exact-transaction protection as Nginx and PHP.
19. As an operator, I want each database engine's initialized service and native cluster verified, so that an installed package alone does not mean the engine is ready.
20. As an operator, I want one optional database per site on my selected engine, so that I can prepare the site's storage without granting global administration rights.
21. As an operator, I want database authentication tied to the site's Linux identity, so that no password must be stored in a plan or transported through command arguments.
22. As an operator, I want a site's runtime to access its own database and be refused access to another site's data, so that the access boundary is demonstrable.
23. As an operator, I want native database ownership, authentication and grants inspected by an authorized connection, so that a second controller can reconstruct the relationship.
24. As an operator, I want database data preserved after partial failure, so that recovery cannot delete an application that started using a newly created database.
25. As an operator, I want TLS readiness to check every requested name and IP family, so that stale DNS and broken IPv6 are discovered before a production request.
26. As an operator, I want to create and install a certificate for my site with one action, so that readiness, issuance, activation and renewal do not require separate approvals.
27. As an operator, I want staging certificates kept out of public HTTPS, so that a rehearsal cannot replace a trusted certificate.
28. As an operator, I want failed validation and rate limits reported without automatic issuance loops, so that repeated clicks do not exhaust CA limits.
29. As an operator, I want HTTPS activated only after certificate and service verification, so that a failed request leaves working HTTP available.
30. As an operator, I want certificate renewal to run without any controller, so that closing Barectl does not break HTTPS later.
31. As an operator, I want to distinguish a renewed certificate on disk from the certificate currently served, so that reload failures are visible.
32. As an operator, I want renewal failure, expiry and unsupported renewal configuration displayed from native evidence, so that another controller can diagnose the site.
33. As an operator, I want private keys and certificate account secrets kept on the server, so that discovery never copies them into the dashboard database.
34. As an operator, I want preparation, application and privileged inspection separately authorized, so that inventory access does not grant server mutation or sensitive catalog access.
35. As an operator, I want server removal to keep completed apply audit and leave native resources running, so that removing a registration is never site deletion.
36. As an operator, I want documented manual management and recovery commands, so that the server remains usable without Barectl.

## Implementation Decisions

### Scope and domain

- Target the existing supported Ubuntu 24.04 and 26.04 policies on amd64 and arm64, using each release's distribution packages and default PHP version. Qualification is per action, release and architecture; v0.2 evidence does not qualify new actions.
- A Site consists of native evidence linking explicit Nginx server names and document root to one Unix FastCGI socket, one PHP-FPM pool and one site user. Database bindings and TLS are optional capabilities, not prerequisites for HTTP site existence.
- Create one site at a time. Accept a lowercase ASCII identifier starting with a letter followed by letters or digits, 3 to 24 characters, and 1 to 10 distinct explicit ASCII DNS names. No wildcards, IP literals, regex names, automatic www alias, arbitrary root paths or shell fragments. Reject reserved or existing resource names. Canonicalize case and a terminal DNS dot before collision checks; require punycode input for international names.
- One default-version pool per site, one document root and one optional database binding to either MariaDB or PostgreSQL. No database switching or second database in this milestone. The server may run both engines for different sites.
- The initial site serves an identifiable static placeholder and supports ordinary PHP execution, with no framework installer, front-controller rewrite, uploaded application or deployment workflow. Preserve the distribution default site and pool. HTTP remains available without public DNS and is verifiable through explicit Host routing.
- Treat the filesystem convention as a bounded supported grammar. Native names locate candidates; only resolved directives, account identity, ownership and service evidence prove relationships. A matching name or comment never establishes ownership. A manually created site that meets the complete convention is observable; this is not blanket permission to modify custom configurations.

### Existing boundaries and local records

- Reuse the remote-operation lifecycle, worker queue, immutable configuration-plan review, native submission and inspection adapter, shared native lock, boot/deadline fencing, bounded payloads, duplicate suppression, reconciliation and separate execution/verification outcomes. Keep SSH behind the current pyinfra connection adapter. Do not introduce another runner, agent or job system.
- Keep site-domain planning separate from stock bootstrap-profile admission. Nginx and PHP bootstrap retain their refusal for customized trees. Site readiness accepts only the qualified site convention and an otherwise supported effective configuration. The dashboard explains which action is available; adding a site does not silently broaden a bootstrap repair action.
- Extend typed discovery snapshots and typed action-specific plan/run details. Cache observations, not desired-state authority. Preserve old discovery identifiers, history, permissions and audits. Retain reviewed non-secret file/account/database/certificate effects with completed apply audit after registration removal.
- Add separate view, prepare and apply permissions for site/database/TLS workflows, with dispatch-time checks of the active requesting account. Privileged catalog and renewal inspections belong to explicitly authorized read-only plan preparation and its protected result, never automatic sudo in ordinary discovery. Inventory-only users cannot see privileged plans or audit. All confirmations are CSRF-protected and name server, action, revision, effects and expiry.
- Keep the existing 16 KiB submission bound. A generated payload exceeding it is refused before submission; do not split it into separately dispatched mutations or silently increase the limit. Reduce supported input bounds if necessary and prove the maximum admitted case during implementation.

### Exact configuration review and admission

- A file-change review specifies every Barectl-authored configuration or content file's complete proposed non-secret bytes, prior bytes or explicit absence, path, type, ownership, mode, link target and native service effects. Review account/group creation, root and directory permissions, endpoints and listener exposure. Existing certificate keys, database contents, credentials and unrelated configuration dumps never enter plans. Native-generated account records, database catalogs, certificates and Certbot state cannot have predetermined bytes; review their fixed native action, bounded names/paths, ownership, policy and postconditions instead. This exception never permits unreviewed Nginx, FPM, timer or hook configuration.
- Admission evidence covers the complete relevant Nginx and FPM include closure, package/service identity, enabled entries, supported symlink chains, account and group name/ID availability, target ancestors and metadata, relevant listeners, and all domain/socket/root collisions. Bound reads; an unreadable, truncated, dynamic or unsupported include closure refuses apply rather than assuming it is empty.
- Preparation is read-only. Stage nothing and perform no ACME challenge during preparation. Immediately before the first requested mutation, acquire the same nonblocking native lock and re-read all admission evidence on the server. A changed boot, expired admission deadline, conflict, changed preimage or missing evidence refuses without requested changes. Recheck each destination and its safe ancestors immediately before publication. Native account tools' own locks and database uniqueness constraints supplement this exclusion.
- Restrict config writes to root-controlled directories. Refuse unexpected symlinks, hardlinks, devices, permissive ancestors, ownership changes and existing files that are not the reviewed preimage. Use same-filesystem staging, exact metadata, atomic publication per file and directory durability checks. Atomic file publication is not an atomic transaction across files, accounts or services.
- Validate candidate syntax with native binaries and the complete effective configuration; validate again after publication and before each service reload. Publish and validate the pool before loading it, verify its socket and user, then publish and load the site's Nginx entry. Never reload a configuration known to be invalid. Verify a real request and the executing PHP identity through a temporary, non-secret acceptance probe removed before success; verify no probe remains. Normal operation must not depend on a permanent diagnostic endpoint.
- When replacing a supported file, retain its reviewed preimage as a root-readable ordinary configuration backup outside active include directories. It is recovery material, not a remote plan, inventory or journal. Local audit records its location and digest; reconstruction never consults backups for current state.
- After the first write, failure is partial completion, never refusal without changes. Conservative compensation may restore only exact preimages or remove newly published configuration links whose after-state still matches this run, under exclusion, followed by native validation. Never remove users, application directories, operator data, databases or production certificates automatically. Exact reviewed temporary probes and staged candidates may be cleaned up only while their identity and bytes still match; external replacements are preserved. If any current bytes differ, retain the evidence and give manual recovery instructions. Reboot or power loss may leave a partial layout; there is no automatic resume, replay or multi-file rollback guarantee.
- Independent root administrators can bypass cooperative locks. State this limit; native preimage checks do not claim to serialize arbitrary uncooperative root writes between checks and publication.

### Discovery and reconstruction

- Ordinary discovery remains read-only and uses the SSH identity's existing rights. Trace enabled Nginx entry, effective root and FastCGI socket, pool socket/user/group and native account/home identity. Confirm package includes and service configuration rather than assuming all files are active. Preserve standalone Nginx site-file and FPM-pool observations alongside the higher-level Site observation.
- Show resource-level observed, absent, inaccessible or unsupported evidence, including incomplete or ambiguous relationships. A broken socket link, missing account, multiple matching pools, shared root, conflicting domains or unknown includes cannot become a healthy Site. Syntax/configuration evidence and live serving verification are distinct; a discovered layout alone is not a health claim.
- Database bindings are proven by socket authentication's OS identity mapping, database ownership or exact grants, and the observed site user. A shared spelling alone proves nothing. Certificate bindings follow effective Nginx certificate references and parsed public certificate names, issuer, validity and fingerprint; inspect renewal configuration only where authorized. Never read private-key bytes or private ACME account keys for inventory.
- Use authorized privileged read-only preparation to complete observations that ordinary discovery cannot read, such as database catalogs. It remains an inspection with explicit permission and provenance. A fresh controller with the same authorized access can rebuild supported relationships; it cannot reconstruct the first controller's approval history or missing evidence. Refuse mutations when required fresh evidence is inaccessible.
- Reconstruction means rebuilding the server view, not restoring application files or database data after disk loss. Restoring a server from backups remains v0.6. Native database catalogs and ordinary Certbot state are part of server evidence; no custom Barectl manifests are introduced.

### Database bootstrap and site access

- Add independent MariaDB and PostgreSQL bootstrap profiles to the existing exact-package-transaction engine. Admit only the server release's authenticated archive candidates and fully reviewed dependency closure. Verify every required archive component, including universe where used; do not weaken origin, hook, package-health, hold, mark or transition checks. General upgrades, distribution changes and third-party repositories supplying any transaction package remain refused.
- Generalize profile service/postcondition handling only where these profiles need it. MariaDB readiness requires the initialized distribution service, local administrative socket access and expected listener exposure. PostgreSQL readiness requires the release-default major, one supported default cluster, its real cluster service and SQL readiness, not merely the umbrella service's active/exited status. Qualify actual package versions and initialization behavior on both releases before enabling the corresponding profile.
- Existing MySQL conflicts, unowned data directories, extra clusters, custom authentication/listeners, remnants and ambiguous installations refuse; do not erase, adopt or migrate them. A fully established supported engine is a no-op. Installing an engine is separate from creating a site's database; no site action hides a package installation.
- Add explicitly reviewed PHP database-driver package actions for the site's default PHP release when required, through the same package guard. These show FPM restart/reload effects on all hosted sites. A database binding cannot be reported ready until a PHP process under the site user connects with its actual driver. Driver readiness accepts only the qualified site convention and fingerprints the effective site/pool closure; it does not reuse or loosen the stock PHP profile's default-only configuration rule. These fixed driver actions are not general optional-extension management.
- Use local Unix sockets and same-name Linux/database principals. MariaDB uses unix_socket authentication only, without password fallback, with explicitly listed application DDL/DML privileges limited to the new database and no global, grant, file or administrative privileges. PostgreSQL uses peer authentication, a LOGIN role without password, superuser, createdb, createrole, replication or bypassrls powers, and an owned database. Revoke PUBLIC access to each new site database and its public schema as needed before publishing readiness. Do not alter unrelated databases or global authentication policy.
- Freeze database collation/encoding in the review: MariaDB utf8mb4 with a distribution-supported explicitly shown collation; PostgreSQL UTF8 with the cluster's observed supported locale. Reject unsupported values rather than inheriting opaque defaults. No migrations or user data are written by provisioning.
- Review expected absence or the fully satisfied supported state of the principal/database, authentication rules, grants, relevant defaults and service identity. Revalidate under the shared lock before DDL. Native uniqueness conflicts fail safely; never use conditional creation to silently accept a resource another administrator created. DDL is not generally transactional across the whole operation, including PostgreSQL database creation. Preserve partial principals/databases and report exact missing steps; incomplete resources require ordinary-administration repair, after which a fresh review can recognize a fully satisfied supported state. v0.3 offers no automated resume/repair action and never drops/recreates them. The same rule applies to partial site identities and directories; explain the missing native steps without reusing them silently.
- Demonstrate own-site access and denial of other-site data and administrative operations. Database connection instructions include native socket, database and principal, with no secret. Existing native authentication prevents TCP password login; do not expose new public database listeners or require changing administrator authentication.

### TLS preparation, issuance and renewal

- Use distribution-packaged Certbot with the webroot authenticator and certonly issuance. Package installation is a separate exact reviewed action. This is a Barectl choice to reuse qualified APT admission; it is not a claim that Certbot recommends distribution packages over its published snap instructions. Qualify the packaged versions and options, not just the current upstream manual. TLS setup accepts a pristine installation with no lineages/accounts or a fully satisfied supported setup, and refuses unrelated existing automation. Review temporary native service inhibition during package installation and establish the guarded override before enabling the timer or creating any lineage; test interruption at that boundary so a package-created timer cannot renew unguarded.
- Use one certificate lineage per site containing exactly its explicit names. No wildcard, DNS API integration, imported keys, custom CA or arbitrary Certbot plugins/hooks. Keep Certbot's ordinary account, renewal and certificate files on the server. Never persist ACME account credentials or certificate private keys in Barectl.
- The operator chooses a discovered site with its displayed domain names, provides an ACME contact email and clicks Create and Install. This action authorizes the fixed installation goal and noninteractive CA subscriber-agreement handling, without a separate terms checkbox or approvals between steps. Record exact plans and audit for the challenge route, renewal setup, production issuance and activation. Staging remains diagnostic qualification. Freeze the names, connection, identity and authority; stop on drift, refusal, failure or unverified outcomes. Never silently reuse a different account/lineage or automatically retry an order. [ADR 0014](adr/0014-install-site-certificates-with-one-operator-action.md) supersedes the original separate TLS approvals.
- Preparation checks fresh public A/AAAA resolution for all names, intended destination addresses, supported CNAME resolution, CAA where available, server HTTP routing, current listeners, outbound ACME connectivity and clock. An AAAA record must work over IPv6; IPv4 success cannot override it. Unsupported proxy/CDN, multiple-server routing, unreachable evidence or uncertain destination refuses production readiness. No DNS, firewall or provider API changes are included.
- Listening on port 80 and a controller-side HTTP request cannot prove public CA reachability. A separately reviewed staging challenge demonstrates the public path and returns time-stamped evidence, without installing the untrusted staging certificate in Nginx. Preparation itself never writes a challenge file. Recheck DNS/routing before production apply; staging success is diagnostic evidence, not a guarantee that a later production request succeeds.
- Production issuance and activation reuse detached execution and reconciliation. Keep working HTTP and existing certificates on issuance failure. After obtaining a valid certificate with exact names and matching private-key identity, admit two exact reviewed Nginx candidate states through the file contract: first enable HTTPS while retaining unchanged HTTP, validate syntax, reload and verify hostname/SNI, chain, expiry and actual served fingerprint; only then publish the separately reviewed HTTP redirect state. Failure of the second publication is partial completion with working HTTPS/HTTP where verified. Keep the HTTP challenge route available; redirect other HTTP traffic after HTTPS succeeds. Create or verify a shared default TLS rejection server and enforce declared Host names so unknown/no SNI and mismatched Host cannot route to the first site. Refuse a competing custom default. Do not enable HSTS in v0.3.
- A lost response after a CA request never triggers another order automatically. Inspect the same unit, native lineage and actual served certificate. Native evidence can establish current state without proving private issuance history; preserve outcome unknown when historical proof is gone. A newly issued certificate remains on the server if activation fails and a fresh activation-only plan may reference it without reissuing.
- Respect CA error details and Retry-After. No automatic production retry loops, forced renewals or certificate replacement to work around limits. The UI distinguishes DNS/routing, challenge, authority/rate-limit, issuance, activation and renewal failures. Limits are live upstream policy, not hard-coded release constants.
- Configure renewal before production TLS is considered complete. Use the distribution's Certbot systemd timer and a reviewed ordinary service override/deploy hook for serialized renewal and validated Nginx reload. Retain Certbot's native locks. Every scheduled renewal and interactive mutation uses the same safe native lock inode, acquired before Certbot's own locks and held across renewal plus deploy hook. Do not reacquire it from a child hook. Lock contention skips this attempt and leaves the native timer to try later; it does not wait while holding another lock.
- After acquiring the shared lock, renewal checks apply control groups and applies check the renewal service's control group, including children that close inherited lock descriptors. Qualify wrapper death and timeout; no other mutation may enter while a renewal child survives. An existing uncoordinated timer, cron entry, alternative installer or hook refuses TLS setup until ordinary administration resolves it. Do not disable or rewrite unrelated certificate automation. The coordination guarantee requires controllers implementing this v0.3 contract; v0.2 clients do not recognize renewal control groups. Upgrade or stop older mutation clients before TLS setup, document mixed-version mutation as unsupported, and test v0.3 controller interoperability without inventing a remote version registry. Arbitrary administrative invocations that bypass this contract remain outside exclusion guarantees.
- Renewal configuration is a finite native service integration, not a persistent agent or custom remote history store. The deploy hook validates effective configuration and reloads only after successful renewal. Report deployment failure even if Certbot exits zero; distinguish certificate on disk, timer/service outcome and served certificate. Discovery can show expiry/renewal warnings when a controller returns; no remote notification service is promised.

## Testing Decisions

The primary acceptance seam is the authorized dashboard request through the real worker, existing SSH adapter and native server, ending with real serving/access behavior and reconstruction by an independent controller. Reuse the existing operator-journey, two-controller coordination, recorded-shell, browser and reboot fixtures. Small parser/review tests cover malformed inputs and refusal decisions, but mocks, source scans, hashes or rendered snippets alone do not qualify mutation safety.

- HTTP sites: create two sites on each supported release; serve static and PHP requests with correct Host routing and runtime identity; prove denied cross-site private-file access, safe document-root permissions and absence of diagnostic probes. Destroy the first controller database, reconstruct through another account/key, and observe external addition, edits, removal and inaccessible configuration accurately.
- Admission: name/domain/root/socket/UID collisions; unsupported include and symlink layouts; truncated reads; changed bytes/modes/owners/ancestors/accounts between review, lock and publication; invalid candidates; native syntax/reload failures. Confirm no unreviewed write and no unrelated-site outage for every refusal that claims no changes.
- Recovery: inject failure after each native account/file/link/reload boundary; full disk, permissions failure, worker loss, lost acknowledgement, timeout, wrapper/child death, reboot and unavailable history. Verify partial outcomes, no automatic deletion of app data, safe preimage restoration only when still applicable, and new-review recovery. Prove true reboot behavior separately from container restart for every release on which that guarantee is claimed.
- Databases: actual distro package transactions/initialization, archive-component admission, conflicting MySQL/data/clusters, service readiness, review drift, partial DDL, driver availability, own-site access and cross-site/admin denial using real SQL and PHP. Preserve sentinel data on every fault/retry/no-op case. Verify native grants/authentication and inaccessible catalogs from a fresh controller; never print credentials.
- TLS: deterministic local ACME/DNS fixtures for faults and limits, then opt-in Let's Encrypt staging on an operator-controlled disposable public domain for actual external validation. Cover unknown/no SNI and unmatched Host, wrong A/AAAA, CAA denial, port 80 blocking, redirect-stage failure, IPv6 failure, rate limiting, account/lineage collision, issuance success with failed activation, and certificate-on-disk versus certificate-served mismatch. Never use production issuance in routine CI.
- Renewal: remove/stop every controller, force an isolated test certificate into renewal eligibility, exercise the real timer/service and a real renewed certificate, and observe new HTTPS fingerprint. Dry-run alone does not prove deployment. Cover lock conflict with a site apply and bootstrap, simultaneous controllers, wrapper death with live child, reboot, timer-disabled state, failed validation/reload, and protected key/account storage. Reconstruct certificate and renewal relationships from a fresh controller.
- Authorization/browser: keyboard review and confirmation, separate view/prepare/apply access, privileged inspection, worker reauthorization, CSRF, duplicate submissions, expiry, refusals, partial/unknown results, Check outcome and completed audit after registration removal.
- Run all repository checks and both native suites on the implementing revision. Record exact commits, OS/architecture/package revisions, skipped suites and remaining limits per slice. A missing external staging test, real renewal proof or native fault gate blocks release of the corresponding action; it is never counted as passed.

## Out of Scope

Application deployment, Git/Composer/WP-CLI workflows, framework rewrite templates, arbitrary configuration editing, site deletion/rename/move, adopting custom layouts for mutation, user-data migration, password/remote database users, multiple databases per site, switching database engines, general package upgrades or repair, DNS/firewall management, wildcard or imported TLS, custom CA/plugin support, HSTS, backups/restore, container isolation, hostile multi-tenant security guarantees, persistent agents, custom remote tracking files, shared controller databases and notification services.

## Further Notes

Implementation is a later session. Work in the requested phase order, but record only real blocking dependencies: a database bootstrap profile does not require a site, and TLS does not require a database. Read-only reconstruction and exact review are independently demoable slices; mutation is enabled only when its complete journey is qualified. No broad prefactoring ticket is needed. Small profile generalization belongs with the first database profile, and its peer profile follows it if they touch the same extension.

The test boundary and scope decisions were resolved through repository inspection and documented trade-offs. No new general-purpose test seam, runtime dependency or remote control plane is authorized by this specification. The [source and decision record](v0.3-decisions.md) distinguishes upstream behavior from Barectl policy and names remaining version checks that implementation must prove.
