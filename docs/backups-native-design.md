# Backup native contract

Accepted design supporting [v0.6](v0.6.md). Implementation and qualification remain pending. This document owns the fixed native grammar, upstream reuse decisions and recovery limits. Examples use fictional identifiers. Template values and limits are Barectl policy, not claims that upstream mandates them.

## One storage convention

| Resource | Fixed grammar |
| --- | --- |
| Onsite ciphertext | `/var/backups/barectl/v1`, root:root, directories 0700 and regular files 0600; no links or other users' writes. Outside every document root. |
| rclone config | `/etc/rclone/barectl.conf`, root:root 0600, encrypted through rclone's native config encryption. No application/controller account receives its content. |
| Config unlocking | One root-controlled systemd credential supplies the config password at execution. A fixed native password command reads only that runtime credential; no custom executable or secret command argument. Use noninteractive failure when unavailable. |
| Local crypt remote | `barectl-onsite`, type `crypt`, wrapping the fixed onsite path, standard filename encryption and directory-name encryption enabled. |
| AWS backend | `barectl-s3`, type `s3`, `provider=AWS`, one bucket/region and narrowly scoped credentials. No custom endpoint or TLS bypass. |
| Offsite crypt remote | `barectl-offsite`, type `crypt`, wrapping `barectl-s3:<bucket>/barectl/v1/<storage-namespace>`. Same content/password/salt/name-encryption settings as onsite. |
| Logical object path | `<site-identifier>/<database-or-full>/<UTC-basic-timestamp>-<UUID>.tar.gz`. Read through crypt; physical onsite/offsite names are rclone encrypted names. No latest alias or marker. |
| Schedule units | `/etc/systemd/system/s<identifier>-backup.service` and `.timer`, root:root 0644, exact template with validated scope/destination/calendar values and credential references. No secret values. |
| Retention deletion remotes | Optional `barectl-s3-retention` (`s3`, `provider=AWS`, same bucket and region, a principal limited to list, read and delete under the backup prefix) and `barectl-offsite-retention` (`crypt` over the same namespace path with the offsite crypt settings). Used only by the retention cleanup unit. |
| Working data | Private operation-owned stages outside web roots, confined and cleaned by qualified native systemd runtime/temporary-directory facilities only after no processes use them. Finalized objects are deleted only by a reviewed [retention policy](backup-retention.md). |

The storage namespace is an operator-provisioned UUID encoded in the operative offsite remote path, not an inventory file or controller database key. A new server setup requires an unused prefix; disaster-recovery access deliberately reuses the old namespace and key material. Native reads establish the current bucket/path relationship. Independent controllers share the server's existing configuration rather than inventing namespaces from their local registration IDs.

Secret configuration is established through the terminal following one documented template. The dashboard verifies named non-secret projections, resource metadata and protected digests through authorized inspection without rendering passwords, credential values or raw config diffs. Ordinary non-root discovery reports inaccessible resources; it never escalates implicitly. Recognition depends on exact operative grammar and relationships, not filenames alone. Allow only declared template fields; reject additional remotes other than the optional retention deletion pair `barectl-s3-retention` and `barectl-offsite-retention` defined by [retention](backup-retention.md), flags, config overrides, environment backend injection or executable hooks in the selected configuration. Other unrelated rclone configs remain untouched.

AWS's fixed account/bucket setup requires Block Public Access, bucket-owner-enforced ownership with ACLs disabled, TLS-only policy and an IAM principal confined to this bucket/prefix. Permit list scoped to the prefix, read/write objects and necessary multipart operations; omit object deletion and bucket/account administration. Server-side S3 encryption remains enabled as another layer. Client-side crypt protects application secrets before upload. No Object Lock, version retention or ransomware-proof claim is implied. Sources: [AWS security practices](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html), [least privilege](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-iam.html), [Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html), [rclone AWS backend](https://rclone.org/s3/#amazon-s3).

Rclone config obscuring alone is insufficient. Native config encryption and [systemd credentials](https://systemd.io/CREDENTIALS/) supply unattended protected access. Back up crypt password, salt and portable config recovery material separately on an operator-controlled device; do not include them in their own encrypted artifact. Host-bound credentials cannot unlock a backup after server loss. Changing keys is outside this milestone; lost keys make copies inaccessible. Sources: [crypt configuration](https://rclone.org/crypt/), [config encryption](https://rclone.org/docs/#configuration-encryption), [password command](https://rclone.org/docs/#password-command).

## Artifact format and scope

One decrypted `tar.gz` recovery artifact has exactly these top-level members:

- `recovery.json`, a bounded versioned descriptor of source site identifier, application kind, convention revision, PHP branch, engine/major/client version, scope, capture time/generation, admitted file roots and recovery limitations. No credential values or private controller audit.
- `checksums.sha256`, checksums of the payload's regular files, excluding itself. This is integrity data, not proof of origin or successful restore. The crypt key and protected source selection establish the admitted trust relationship.
- `database/`, containing exactly the engine's one scoped logical dump.
- `application/`, present only for full scope, containing exactly the admitted runtime file set.

Keep the descriptor at most 16 KiB and return at most 128 catalog candidates/16 KiB of summary per inspection, with explicit truncation. Native files/dump bytes are not command output. The initial fixed ceiling is an 8 GiB decrypted archive, a 4 GiB dump, a 16 GiB admitted uncompressed tree, 100,000 entries and a 2 GiB individual application file. Runtime is 30 minutes and controller-submitted payload is at most 16 KiB. Enforce per-file limits with native facilities, aggregate admitted lengths before extraction, known finite staging objects and conservative free-space reservations before writes. Qualify the actual peak disk use and fail if the native limits cannot enforce the declared bounds. Do not install a helper, invent a quota engine or split a capture into replayable units to bypass limits. These are initial support ceilings, not promises every artifact at the ceiling finishes within the runtime.

Generic PHP includes its public application and private application files. WordPress includes core/plugins/themes/uploads, installed runtime files, the operative public config wrapper and private application configuration. Laravel includes exactly the selected protected release, installed production dependencies/committed assets, shared private configuration and persistent storage. For Laravel, retain the selected commit's credential-free protected Git object/tree/HEAD evidence required by the v0.5 convention. Exclude Git hooks, credential helpers, secrets and arbitrary executable/transport configuration; regenerate only the exact non-secret operative Git configuration and verify the restored tree against that commit without network access. Generic PHP/WordPress Git working directories are not part of their supported runtime scope. Exclude source credentials, retired releases, operational logs and disposable cache/runtime state only where the application's qualified profile establishes they are regenerable without package acquisition. If a required runtime file falls in a proposed exclusion, retain it or refuse. No operator exclusion editor exists.

Native system files are not restored from archive contents. Existing target Nginx/FPM, site identity, database binding and certificate resources must match their supported convention; reconstruct required application links from the admitted application's grammar. Recorded source identity informs compatibility but never authorizes archived numeric ownership on the target. Neither rclone config/keys nor SSH/TLS secrets enter application scope. Application `.env`, `wp-config.php` and similar private data are intentionally included and remain encrypted.

Native GNU tar owns archive creation/listing/extraction. Before extraction into an absent root-protected private tree, admit bounded relative member names and lengths, reject duplicate paths, traversal, absolute names, hardlinks, devices/FIFOs/sockets, setuid/setgid and link escapes. Generic PHP permits no links; WordPress/Laravel permit only their exact operative links, which are re-rendered rather than trusted from arbitrary archive input. Do not run archive PHP to inspect versions or execute hooks. Native archive guidance: [GNU tar security](https://www.gnu.org/software/tar/manual/html_section/Security.html), [rclone local links](https://rclone.org/local/#symlinks--junction-points). Narrow metadata/member validation is Barectl's admission work, not a replacement archive engine.

## Database mechanics

Database only still means a recoverable dump of the whole bound application database, not selected tables. Require the satisfied local socket/peer binding from [ADR 0010](adr/0010-use-local-site-identities-for-database-access.md). The engine's ordinary database catalog and actual object privileges govern admission.

MariaDB uses its distribution-matched `mariadb-dump`, `--single-transaction --quick`, one explicitly selected database, no global accounts/grants and no database creation/drop statements that can target another database. Require InnoDB for every data table and refuse unsupported concurrent DDL. Admit routine/trigger/event definitions only if their identity, privilege and restore behavior qualify under the site principal; do not silently omit application objects. Native dump/import run as the site identity over its socket, not root SQL. Suppress dump/error content from journald and controller messages. Pin client behavior, including sandbox headers; same engine/major is necessary but exact client compatibility still needs tests. Source: [MariaDB dump guidance](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump).

PostgreSQL uses matching-major `pg_dump` custom format, one bound database, no owner/ACL replay and no globals. Restore uses the bound site's principal with fixed `pg_restore` no-owner/no-ACL behavior. Before destructive import, positively inspect and qualify the exact bound object's replacement/reset semantics and prove unrelated roles/databases unchanged. PostgreSQL restore executes source SQL; a compatible authenticated artifact is trusted application recovery data, never an instruction to use a database superuser. Sources: [pg_dump 16](https://www.postgresql.org/docs/16/app-pgdump.html), [pg_dump 18](https://www.postgresql.org/docs/18/app-pgdump.html), [pg_restore 16](https://www.postgresql.org/docs/16/app-pgrestore.html), [pg_restore 18](https://www.postgresql.org/docs/18/app-pgrestore.html).

Live database-only dumps claim their engine's supported transactional consistency, with no concurrent unsupported DDL, but make no coordinated file/database claim. Full capture and every destructive restore additionally require writer quiescence.

## Capture, scheduling and cooperation

Manual work reuses the existing worker, action registry, lifecycle, pyinfra connection and finite transient submission. The existing root-owned empty native mutation lock remains the only coordination inode. Staging/resource properties are explicit extensions of the existing adapter; the SSH/backend and original-run reconciliation remain the same.

The scheduled service contains the exact fixed native composition for admitted dump, archive and rclone operations, rendered by the same module as manual capture. It has no persistent script/runner binary. It executes in the foreground with native cgroup lifetime, `TimeoutStartSec=30min` for the oneshot execution ceiling, `TimeoutStopSec=60s`, `KillMode=control-group`, no automatic restart and controlled environment/output. Review and qualification must establish correct installed-systemd shell/specifier/credential semantics on Ubuntu 26.04. A payload that cannot fit the established submission ceiling is a refusal, not a reason to create a helper. Install/enable/change/disable remains a reviewed transient operation.

One timer per site supports daily `HH:MM UTC` or weekly weekday plus `HH:MM UTC`, rendered to literal `OnCalendar`; defaults are disabled. Review suggests daily 03:00 UTC when available, otherwise the next free time. Reserve a 32-minute execution/stop window per scheduled tick and warn/refuse overlapping windows among admitted backup schedules, accounting for daily/weekly and midnight wrap. This finite calendar check prevents the same sites losing every tick to the shared nonblocking lock; it is not a custom scheduling engine. Set `AccuracySec=1s`, no randomized delay, and review the chosen UTC time. `Persistent=false` disables catch-up. Native active-service semantics prevent starting a second invocation of that service; the global lock/cgroup checks exclude manual capture, restore, other sites' backup, deployments, Certbot and cooperating mutations. A conflict exits with a classified refusal/skip and no waiting. Native service state/journal can describe retained evidence, but a fresh controller cannot promise every historical tick after log/unit evidence expires. Sources: systemd [v255 timer](https://github.com/systemd/systemd/blob/v255/man/systemd.timer.xml), [v259 timer](https://github.com/systemd/systemd/blob/v259/man/systemd.timer.xml), [v255 service](https://github.com/systemd/systemd/blob/v255/man/systemd.service.xml), [v259 service](https://github.com/systemd/systemd/blob/v259/man/systemd.service.xml).

Every existing apply payload and outcome-unknown acknowledgement must also check backup cgroups, including descendants that close their inherited lock descriptor. New scheduled invocations validate current evidence under the lock rather than reuse an expiring controller plan. Enabling the timer reviews that recurring policy and its downtime. Older controllers must upgrade or stop before scheduling starts; a local database or server version marker cannot fence them.

Full capture gates new application requests, inhibits boot activation of admitted background work and drains in-flight writers before reading files/database. Existing FPM runs one service per PHP branch; stopping/draining it affects all pools on that branch. Review and native results identify that shared effect, including recovery of its prior enabled/start state. Disable/drain actual convention scheduler/queue units and inspect relevant database sessions. Known unmanaged writers or inaccessible evidence refuse. Document that scheduled full capture repeats this reviewed downtime.

The gate does not itself stop in-flight requests, external database clients, administrator cron or commands. The standard's exclusive-maintenance requirement excludes conflicting ordinary administration while capture/restore runs. It is an operator trust requirement, not a claim that process scans can prove absence of all future writes. Root and arbitrary external writers cannot be fenced by Barectl. Where this contract cannot be established, the panel warns and refuses full capture/restore instead of producing a supposedly consistent recovery point.

On normal capture completion, verify onsite data and return only the exact prior admitted routing/FPM/background state after fresh checks. Offsite transfer occurs after application resumption so network latency does not unnecessarily extend capture downtime. The finite native job still holds exclusion during replication. If interruption prevents safe resumption, retain the persistent gate and native boot inhibition; provide reviewed recovery to re-open the unchanged application after fresh binding/serving evidence. Reboot does not automatically repair an interrupted capture. Do not reconstruct previous desired process state from absent private audit.

## Publication, integrity and catalog

Produce the dump/archive privately. Validate the decrypted artifact before rclone encrypts it into the fixed local crypt remote. A unique generation avoids overwrite; incomplete encryption stays in operation-owned staging and cannot be mistaken for a final candidate. Publish only the complete onsite ciphertext, using safe native no-replacement publication. Metadata is inside the encrypted artifact, not a server status file.

Copy the finalized raw ciphertext object with `rclone copy --immutable`, preserving its entire validated relative encrypted path below the onsite root in the AWS namespace. The destination parent includes the encrypted site/scope directory segments; copying one file directly to the namespace root would lose the catalog grammar and is forbidden. Matching crypt settings allow raw replication without custom encryption or re-encryption. Verify source/destination through rclone checks; retain hash and HEAD behavior, and use bounded `check --download` comparison when a common trustworthy checksum is unavailable. Source: [copy](https://rclone.org/commands/rclone_copy/), [immutable flag](https://rclone.org/docs/#immutable), [encrypted remote replication](https://rclone.org/crypt/#backing-up-an-encrypted-remote), [S3 hashes](https://rclone.org/s3/#hashes), [download checking](https://rclone.org/commands/rclone_check/). Replication retries select exact existing bytes and do not regenerate a backup. Never delete onsite after upload.

A catalog candidate is only observed available/incomplete/inaccessible until authorized inspection authenticates/decrypts bounded descriptor data. Transfer integrity is distinct from archive-content validation and demonstrated restore. Offsite object listings alone do not prove a valid backup. No custom remote success markers or index are permitted. Integrity verification timestamps are cached local findings with explicit freshness; after external changes their authority ends.

## Restore and download

Restore preparation validates source identity/digest, decryption, complete archive admission and target compatibility without application execution. Materialize verified offsite data privately if onsite is absent; capacity failure refuses before touching the target. For an existing nonempty target, take and verify a same-scope current safety backup before destructive writes. A failure to capture refuses. An already prepared positively empty target may skip that safety copy after review. The safety copy is recovery data, not a promise of automated compensation or space-efficient snapshots.

Gate/drain the target using the full coordination contract even for database-only restore. Review code/schema compatibility and data loss; full restore replaces current application state rather than overlaying it and leaving later files behind. Use confined protected staging and preserve displaced application trees as ordinary recovery preimages. Keep target UID/GID, native database principal/grants, PHP selection, TLS and SSH/rclone setup. No root extraction into arbitrary target paths, database superuser restore, migrations, install scripts or dependency downloads.

After native import/publication, verify binding, file digests/ownership, supported configuration and application readiness over the exact qualified route. Generic PHP uses its qualified serving probe; WordPress uses its supported canonical HTTPS route; Laravel uses its qualified readiness request. Admit only the supported fixed route per application profile, not a custom verification-script editor. This proves that request, not universal business correctness. Resume only reviewed desired background state after verification. Partial or unknown restore leaves the gate and boot inhibition; report the reached boundary and terminal recovery instructions. No automatic rollback or blind replay.

Download supplies the selected verified ciphertext object with its original encrypted filename. The operator places it in a private local directory and configures rclone crypt over that directory using separately escrowed recovery material; native rclone decrypts it to the original recovery archive. Rclone name encryption works per path segment, so the original encrypted basename can be placed at a fresh local crypt root; authenticated recovery metadata retains site/scope identity. A runbook must prove this round trip for nested onsite and offsite source objects on a fresh machine without the original server. No decryption secrets accompany a browser download.

Current SSH command reads are capped at 64 KiB and the metered connection cannot carry an archive. Extend the existing connection explicitly for a bounded disk-backed pyinfra connector transfer, preserving host trust and normal read limits. Review the artifact, byte/disk/time budget and authenticated SSH identity first. For non-root SSH, a reviewed native export grants only that identity a private, temporary copy of ciphertext; use native expiry after no transfer/cgroup uses it. A controller worker stages privately and the Django response streams an authenticated attachment, never a DB blob or public URL. Check authority again at download access; no-store, token expiry, cancellation/error cleanup and finite server/controller lifetime are acceptance requirements.

[Pyinfra file transfer](https://docs.pyinfra.com/en/3.x/operations/files.html#files-get) warns about large-file staging. The [locked 3.10.0 connector](https://github.com/pyinfra-dev/pyinfra/blob/v3.10.0/pyinfra/connectors/ssh.py) supports SFTP, but its sudo get path uses a readable temporary copy. Do not blindly use that path or expose plaintext. Qualify ordinary connector transfer of the exact authorized ciphertext export through Barectl's sole connection. Missing a safe supported transfer primitive remains a download qualification gate, not permission to add a second Paramiko/scp/HTTP integration.

## Reuse assessment

| Existing option | Reuse | Remaining Barectl requirement |
| --- | --- | --- |
| Existing registry/lifecycle/native adapter | Immutable review, typed audit, permissions, SSH, exclusion, bounded execution and reconciliation | Backup scope/admission, schedule cgroups, destructive restore postconditions and explicit transfer budget. Extend the existing module. |
| [pyinfra files](https://docs.pyinfra.com/en/3.x/operations/files.html), [systemd](https://docs.pyinfra.com/en/3.x/operations/systemd.html) and [SSH connector](https://docs.pyinfra.com/en/3.x/connectors/ssh.html) | Native file/unit setup and connector transfers | Controller-owned deploy composition alone does not provide durable finite execution, approved recurring policy, scoped restore or private large-file authorization. Check supported operations within the accepted native contract. |
| Native database clients and GNU tar | Transactional dump, import, archive mechanics | Full-application quiescence, exact recovery scope, confined member admission and target identity/grant preservation. Do not replace these engines. |
| rclone local/crypt/S3 | Native encryption, copy, retrieval and integrity checks | It does not create a DB dump, freeze an application or define Barectl restore scope. Narrow orchestration connects those mechanics. |
| [restic rclone backend](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html#other-services-via-rclone) | Established encrypted snapshot repository with rclone transport | Its snapshot repository/catalog and retention model would become another required recovery tool. Full independent native archives and rclone-only crypto/transfer are the selected scope. Reconsider only if incremental/deduplicated chains become an accepted requirement. |
| [systemd timers](https://github.com/systemd/systemd/blob/v255/man/systemd.timer.xml) | Native schedules, units, credentials and process containment | Recurring policy admission and cooperative exclusion with existing actions. Do not create a scheduler or installed helper. |

This records a scoped architecture comparison, not proof that upstream tools cannot be customized. Each implementation ticket must record checked version-matched operations and its exact remaining gap before adding custom mechanics. Missing qualified systemd/transfer/app compatibility blocks that path; independent work continues. The final qualification record includes exact versions, architectures, source revisions, real AWS and real-kernel evidence, plus literal unavailable combinations. No v0.6 runtime is qualified by this document.
