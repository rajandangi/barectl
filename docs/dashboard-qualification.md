# Dashboard qualification record

This record lists the evidence for the integrated server and site workflows of the [dashboard specification](https://github.com/rajandangi/barectl/issues/179), qualified in [#188](https://github.com/rajandangi/barectl/issues/188). [Dashboard workflows](dashboard-workflows.md) describes the behavior. Anything this record does not list as tested is not qualified. Qualification is not clean: the npm dependency audit fails, as recorded under [limits](#limits).

The qualified result is native PHP hosting: a site with its own Linux user, PHP-FPM pool and Nginx configuration serving a placeholder page, an optional single database and HTTPS. It is not application deployment, monitoring, automatic rollback, DNS management or a change of design system.

### Integrated journeys

`dashboard/test_hosting_journey_remote.py`, tagged `ssh` and `native-browser`, drives Chromium with the keyboard against the production build, the real worker and the disposable server, with the Pebble authority and challtestsrv DNS answers ([ACME and DNS fixtures](ssh-connections.md#acme-and-dns-fixtures)). Ground truth is read through `docker exec`. Each class brings the server to its starting state when it starts and restores it when it ends.

- **New server, full journey** (`FirstSiteJourneyTests`). The class starts without Nginx, MariaDB, the PHP MariaDB driver or Certbot. The test signs in to an empty inventory, adds the server by its SSH alias and follows the connection check to **Verified**. Overview links **Prepare web hosting**; Setup shows Nginx observed absent; the Nginx profile is prepared, reviewed and applied. Overview then links **Open Sites**. A site with two domains is prepared, reviewed and applied from Sites; the run hands off to the site's Overview and the site serves its placeholder. Its **Database** section refuses a MariaDB plan, naming the missing MariaDB profile and PHP MariaDB driver, and links to Setup with `?from=shop&origin=database`. The MariaDB profile and the driver are applied there; **Return to site shop** opens the site's Database section again, and the database plan is prepared, reviewed and applied, creating `sshop`. **Enable HTTPS** with a contact email shows every stage completed and **Installation recorded as verified**. For each domain the served certificate equals the issued one on disk, `openssl s_client -verify_return_error -verify_hostname` accepts it and returns the placeholder, and HTTP answers 301. After the discovery that follows activation, the site's Advanced section shows **Names, root and socket not shared** as observed as the convention requires, with the server's `tls-default-reject.conf` in place, and **Locked password** as inaccessible, because the SSH identity cannot read `/etc/shadow`; Overview therefore reports exactly one resource not confirmed. Site **Activity** lists the creation, database and installation records with links to the original runs, and none of the Nginx, MariaDB or driver Setup work. The server Overview, the new site's Overview, its HTTPS section, its Activity and the server's Sites section have no horizontal overflow at 320 pixels.
- **Prepared server, HTTPS without a database, wrong DNS** (`PreparedServerJourneyTests`). The class starts with Nginx and PHP-FPM, without Certbot, the default-reject file or the provisioned root-only site. Overview links directly to **Open Sites**, and a site is created. A readiness review before any installation refuses with "Apply the site's challenge route plan first". With A and AAAA answers pointing elsewhere, **Enable HTTPS** applies the route and renewal setup and stops at the certificate order's preparation: the installation names `blog.test`, its observed IPv4 address and that the addresses are not the server's own; no order run exists and no lineage is created. The readiness review then lists the observed A and AAAA answers beside the server's recorded addresses. After DNS is corrected, an explicit recheck is ready for review and a new request installs HTTPS with one order run and no database run. The activated site is observed as for the first journey: names, root and socket conform and only the locked password is inaccessible. A direct link to the site's Activity, a reload, back and forward keep the site's context.
- **Another controller** (same test). A separate process with its own database, SSH alias and key creates a server record (`Server.objects.create`, not the registration form), runs discovery and requests the site's Overview, Database, HTTPS and Activity pages through Django's test client, not a browser. The first fact list of each of Overview, Database and HTTPS, the observed evidence with times removed, equals the first controller's. Its HTTPS section has no installation, its site Activity lists no runs or installations, and it holds 0 runs, 0 preparations and 0 installations.

The reconstructed site has no database. Reconstruction of a site with a database binding and an activated certificate on another controller is covered by `tls/test_issuance_remote.py` `SecondDeviceTests` ([v0.3 qualification](v0.3-qualification.md#v03-journeys-reconstruction-and-native-recovery)). A database added to a site Barectl did not create is covered by `databases/test_bindings_remote.py`, where the administrator creates the convention sites by hand.

## Limits

- **Dependency audit.** `npm run audit:dependencies` fails on GHSA-vfj7-8cjw-p6xm through Stylelint, with no patched version. It is disclosed, not suppressed; qualification is not clean while it fails.
- **No measured usability.** The walkthrough above is the implementer's heuristic inspection. No usability sessions with operators were run.
- **Architecture.** The native suites ran locally on arm64 only. amd64 was not run for this record.
- **Hosts.** Only disposable containers were changed. Real virtual machines and live servers were not mutated; no real certificate authority or public DNS was used.
- **Fresh controller.** The second controller is driven through Django's test client, creates its server record directly rather than through the registration form, and reconstructs a site without a database.
- **Readiness before the first installation.** A readiness review on a site without its challenge route refuses on that prerequisite and shows no DNS answers until the route exists.
- **Not provided.** Application deployment, continuous monitoring, automatic rollback, DNS integration and a change of design system are outside this workflow.
