# v0.6: Onsite and offsite backup and restore

Accepted design for implementation, tracked in [#271](https://github.com/rajandangi/barectl/issues/271). Backup runtime behavior and qualification remain pending. This milestone is limited to database-only or full-application backup, on demand or on a native schedule, onsite storage, one optional rclone offsite template, restore and local download. [Native contract](backups-native-design.md), [competitor research](backups-competitor-analysis.md) and ADRs [0021](adr/0021-use-one-native-rclone-backup-convention.md) and [0022](adr/0022-review-destructive-restore-and-coordinated-capture.md) own the supporting decisions.

## Problem Statement

An operator needs recoverable copies of a site's database or its complete application and database, without keeping a Barectl controller connected. Copies must be available on the managed server, optionally offsite, and downloadable to the operator's computer. A new authorized device must understand the setup and available artifacts through the same standard convention. Existing bootstrap recovery preimages and retained Laravel releases do not provide this capability.

## Solution

A site's Backups section provides Backup now, one schedule, a catalog of observed copies, Restore and Download. Backup now and the schedule use the same capture policy. The operator chooses Database only or Full application with database, and Onsite or Onsite and offsite. Offsite means one exact AWS S3 template through rclone. No provider selector, arbitrary backend, archive-path editor or custom command configuration exists.

The dashboard warns when a required resource does not follow the standard and blocks the affected action until ordinary administration corrects it. It distinguishes local capture, offsite replication, artifact integrity, native execution and verified restore. The supported standard follows upstream tools and documented security practices; it is not claimed to be universally the most secure or most common configuration.

## User Stories

1. As an operator, I want backup setup reconstructed from native configuration, so that another authorized device can manage it without my old database.
2. As an operator, I want one documented storage template, so that setup has a predictable meaning across servers.
3. As an operator, I want a warning for conflicting configuration, so that I can correct it without silent conversion.
4. As an operator, I want unrelated resources to remain manageable, so that one backup conflict does not block the server.
5. As an operator, I want to back up only the site's bound database, so that database recovery does not require a full application archive.
6. As an operator, I want a full backup containing application code, installed runtime dependencies, private configuration, uploads, persistent storage and the same capture's database, so that restoration does not depend on a Git host or a dependency registry.
7. As an operator, I want the file scope and exclusions stated before capture, so that full application has a precise meaning.
8. As an operator, I want Backup now, so that I can capture before maintenance without waiting for a schedule.
9. As an operator, I want to keep an onsite copy, so that offsite outages do not erase a completed capture.
10. As an operator, I want an optional encrypted offsite copy, so that server loss does not necessarily lose every backup.
11. As an operator, I want offsite failure shown separately, so that an onsite success is not presented as complete offsite protection.
12. As an operator, I want to retry copying an exact existing artifact, so that an upload failure does not require a new capture or alter the original backup.
13. As an operator, I want daily or weekly schedules with an explicit UTC time, so that execution is predictable without an arbitrary cron editor.
14. As an operator, I want a schedule to run with Barectl closed, so that it does not require a hosted controller.
15. As an operator, I want to enable, change or disable the one site schedule through review, so that scheduling remains understandable.
16. As an operator, I want a skipped conflict or interrupted scheduled capture reported honestly, so that it does not count as a backup.
17. As an operator, I want no burst of missed runs after reboot, so that a returning server does not encounter unexpected repeated maintenance.
18. As an operator, I want capture to coordinate with deployment, database changes, TLS and other backups, so that different controllers cannot overlap conflicting work.
19. As an operator, I want full capture to gate traffic and drain managed writers, so that files and database form one supported application recovery point.
20. As an operator, I want branch-wide PHP downtime disclosed, so that shared FPM effects are reviewed before enabling full capture.
21. As an operator, I want unsupported writers or unreliable coordination to refuse full capture, so that a maintenance page is not mistaken for isolation.
22. As an operator, I want insufficient disk, size limits and timeouts reported without deleting old artifacts, so that capacity failures preserve recovery candidates.
23. As an operator, I want backups encrypted onsite and offsite, so that copying stored files alone does not expose application secrets.
24. As an operator, I want terminal-based secret setup and separate recovery instructions, so that keys never enter browser forms, unit arguments or the application database.
25. As an operator, I want to preserve decryption material separately, so that replacing the server can still recover offsite copies.
26. As an operator, I want an observed catalog with collection time and verification limits, so that a filename or stale view does not prove a successful backup.
27. As an operator, I want to select an exact onsite or offsite artifact for restore, so that a mutable latest pointer cannot change the reviewed source.
28. As an operator, I want a restore review naming the target, source, affected data and downtime, so that destructive effects are explicit.
29. As an operator, I want a database-only restore to leave application files alone, so that scope matches my request.
30. As an operator, I want a full restore to replace the current application data and database as a coordinated workflow, so that files and database are not from different recovery points.
31. As an operator, I want current target SSH/rclone credentials, database authentication, Linux identity and server configuration preserved, so that a backup cannot overwrite SSH access, database grants or TLS state.
32. As an operator, I want corrupt, incomplete or incompatible backups refused before destructive work, so that transfer success does not authorize unsafe restoration.
33. As an operator, I want application execution excluded from restore preparation, so that inspecting an archive cannot run its PHP or hooks.
34. As an operator, I want interrupted restoration to remain gated with precise recovery limits, so that partial data is not silently exposed.
35. As an operator, I want a lost response reconciled against its original native run, so that a restore is never blindly submitted twice.
36. As an operator, I want database and serving checks after restoration, so that successful extraction is not the only evidence of recovery.
37. As an operator, I want to download either copy through the authenticated dashboard, so that I can keep an independent local copy.
38. As an operator, I want the download to preserve encrypted rclone bytes and filename with local decryption instructions, so that storing a downloaded backup does not automatically disclose its secrets.
39. As an operator, I want bounded private transfer staging and clear download failure, so that large artifacts do not enter database blobs or command output.
40. As a restricted Barectl account, I want separate view, preparation, capture, schedule, restore and download authority, so that inventory access does not grant destructive recovery or access to secret-bearing backups.
41. As an operator, I want private audit retained in my Barectl database and native evidence kept distinct, so that another device is not promised my private history.
42. As an operator, I want exact tested versions and limits published, so that an accepted design is not confused with released capability.

## Implementation Decisions

- **D1. Narrow ownership.** Add one backups domain module. Its small interface exposes typed observations and named setup, capture, replicate-existing, schedule, restore and download requests. Callers know scope, destination, source identity, review and outcome invariants. Dump tooling, archive admission, native unit rendering, encryption and transfers stay inside the implementation. Do not add a generic provider framework, backup plugin system or alternate job engine.
- **D2. Existing seams.** Reuse the action registry, immutable plan/audit storage, remote-operation lifecycle, native execution adapter and verified pyinfra SSH connection. The primary test seam is the authorized operator workflow from request through review, dispatch, fresh evidence and rendered result. Existing real/fake adapters remain internal seams. No speculative prefactor or pass-through abstraction is required.
- **D3. Compatibility.** Start with qualified Ubuntu 24.04 and 26.04, their release-default MariaDB and PostgreSQL, and supported site/PHP conventions on amd64 and arm64 independently. Restore initially requires the same database engine and major, application kind, site identifier and compatible convention/runtime as the source. Cross-server restore uses a separately prepared target with that identity and standard recovery configuration; provisioning is outside restore. Unknown or unqualified combinations refuse, with an explanation.
- **D4. Standard storage.** Use fixed private onsite paths and exactly one root-only rclone configuration containing a local crypt remote, an AWS backend with `provider=AWS`, and an offsite crypt remote with the same crypt key material. Terminal setup supplies bucket, AWS region, unique storage namespace, least-privilege credentials and encryption material. No custom endpoint, provider, path, filter or flags. Local capture is required for every backup; offsite is an optional additional copy.
- **D5. Security policy.** Encrypt contents and names with native rclone crypt. Protect config through root-only modes and encrypted config with unattended systemd credential delivery. TLS verification, rclone checksum and post-upload checks stay enabled. The fixed AWS setup blocks public access, disables ACLs, enforces HTTPS and confines permissions to the unique backup prefix, without delete permission. Escrow crypt passwords/salt and config recovery material separately through the terminal. Never store them in Barectl rows or include them in the backup they unlock. Host-bound systemd credentials alone are insufficient for disaster recovery.
- **D6. Independent artifacts.** Produce one versioned, self-contained archive per capture with bounded recovery metadata, a scoped native database dump and, for full scope, exact admitted application contents. Artifact-contained metadata and checksums describe recovery data; they are not live-server inventory, a schedule journal or proof of execution. Names only locate candidates. Never add a custom server catalog, status marker, latest pointer or management database.
- **D7. Capture scope.** Database only requires one satisfied local database binding. Full scope requires that binding plus an admitted application layout. Generic PHP captures public/private application data; WordPress adds its private configuration; Laravel captures the selected release including installed production dependencies, committed assets and credential-free protected Git object/tree evidence plus shared private configuration/storage. Regenerate only its exact non-secret operative Git configuration; exclude hooks and credential/transport helpers. Include files necessary for runtime recovery without downloading dependencies. Exclude other sites, old Laravel releases, source credentials, SSH/rclone configuration, TLS keys, OS packages, database globals/roles/grants, service logs, sockets and temporary runtime state. No files-only mode or configurable exclusion list.
- **D8. Database mechanics.** Use native `mariadb-dump` with transactional InnoDB admission and native socket identity, or version-matched `pg_dump` in custom format without owner/ACL replay. Capture supported application routines/triggers/events only where scoped identity can safely restore them; otherwise refuse rather than omit them silently. Concurrent unsupported DDL and nontransactional MariaDB tables refuse. Do not copy live engine data directories or add physical/PITR tooling.
- **D9. Coordinated full capture.** Under native exclusion, revalidate, install the persistent maintenance gate, inhibit background boot activation and drain admitted writers before dump/archive. Positively inspect drained FPM cgroups and managed application worker/scheduler state. Existing FPM is shared per branch; review names all affected pools. Known unmanaged cron/jobs, active external writers or unreadable coordination evidence refuse. The standard requires exclusive maintenance by cooperating administration; it cannot fence root or external commands that bypass it. A live tar beside a live dump is not a full consistent capture.
- **D10. Publication and replication.** Build privately, validate archive scope/contents and native dump completion, then encrypt and publish the onsite object under a unique generation without replacement. Copy those exact ciphertext bytes to the offsite prefix with rclone `copy --immutable`, never `sync` or `move`. Verify exact object length and content through upstream checks, including download comparison where hashes are insufficient. Immutable here means Barectl will not overwrite; it is not provider WORM. Offsite errors retain the usable onsite artifact and a distinct incomplete outcome. Replicate-existing may copy only the reviewed finalized bytes, never repeat capture.
- **D11. Schedules.** One finite native oneshot service and one systemd timer per site use the exact template and same capture policy as Backup now. Support daily or weekly UTC calendar selections; no arbitrary cron or catch-up, and no retry backlog. Warn/refuse overlapping fixed execution windows among admitted site backup schedules and suggest the next available time for review. Native units/configuration, enablement and retained system state establish current configuration. Repeated invocations do not require a controller or custom remote records. Each invocation freshly checks convention, credentials, capacity and writer admission. A conflict skips/refuses without waiting, and a later normal tick tries anew. That is not replay of an uncertain previous run.
- **D12. Native exclusion extension.** Explicitly extend ADR 0006 for fixed scheduled native units and action-specific bounded staging. Manual work keeps transient submission, reviewed host/boot/deadline fencing, finite runtime, shared lock, cgroup checks and no replay. Every existing mutation and outcome-unknown closure must recognize backup cgroups, including children that close inherited lock descriptors. Upgrade or stop older controllers before schedule enablement. No stored script, daemon, alternate SSH path or custom scheduler is introduced.
- **D13. Honest recovery.** Backup completion, local availability, offsite integrity and restored serving are separate findings. Full capture returns routing/background state only after its supported postconditions hold; interruption may leave a persistent gate and disabled processes, requiring fresh reviewed recovery. Reboot never opens a partial operation's gate or restarts inhibited writers. Native logs have ordinary retention and are not another device's private audit.
- **D14. Restore authority.** A separately authorized destructive restore binds the exact authenticated artifact, content digest, current target and numeric identity, compatible engine/runtime, overwrite effects, capacity, downtime and desired post-verification process state. Fully validate/decrypt/stage before destructive work. Database-only restore accepts a database-only artifact; full restore accepts a full artifact. No arbitrary upload/import, cross-kind restore or selective extraction editor. Newly provisioned targets must already match the same site identifier, convention and binding.
- **D15. Restore mechanics.** Gate and drain the target. Restore only the existing bound database under the scoped site principal, without superuser SQL or global privilege replay. Confine archive extraction to an absent private stage; reject traversal, special files, hardlinks, duplicate members, unsafe modes and links outside the fixed application grammar. Preserve target Linux IDs; render operative native configuration from the supported convention instead of trusting archived root configuration. Restore archived application secrets as application data, never regenerate keys, run migrations, arbitrary hooks or dependency acquisition.
- **D16. Destructive failure semantics.** File publication and database replacement are not one atomic transaction. Show which boundary was reached. Keep ordinary preimages and the source artifact, leave routing gated and processes inhibited after partial/unknown restore, and require terminal repair plus fresh review. Do not claim automatic rollback, delete ambiguous data or resubmit an uncertain import. A same-site current safety capture is required before destructive restore; the new target case qualifies positively empty data and reviews skipping that capture. Database-only restoration still needs code/schema compatibility acknowledgement.
- **D17. Restore verification.** Verify confined contents/digests/ownership and native database object/data fixture expectations, binding and selected PHP driver. Verify Nginx/FPM configuration and the supported same-site readiness request using its admitted HTTP/HTTPS serving form without exposing its body. Standard application execution is only the separately disclosed serving check, never preparation. Serving success proves that request, not all business behavior. Keep execution, data verification and serving outcomes separate; release the gate and restore only explicitly reviewed background state after verification.
- **D18. Download.** Return encrypted rclone-format files with their original encrypted basename and documented local crypt recovery. Obtain either onsite bytes or verified offsite retrieval without modifying the source artifact. Extend only the existing verified pyinfra connection for bounded disk-backed file transfer in the worker. Grant the current authorized SSH identity an exact private temporary ciphertext export when non-root access requires it; never use pyinfra's broad readable sudo copy for plaintext. Preserve command-output caps and host trust. Private controller staging, authorized streamed attachments, no-store responses, expiry and cancellation cleanup are required. No HTTP rclone daemon, public URL, database blob or browser credential input.
- **D19. Warning behavior.** Observe absent, inaccessible, unsupported, incomplete and changed configuration distinctly. Name one mismatching resource and the expected standard, without converting it. Block only dependent actions; credential values never appear in warnings/diffs. Privileged verification is a named authorized inspection, not automatic escalation of passive discovery. A stale catalog cannot authorize capture, download or restore.
- **D20. Local persistence and permissions.** Add typed preserving observations, plan/audit and transfer rows in the local application database. Separate view, prepare/setup, capture/replicate, schedule management, destructive restore and download authority. Enforce active account/owning authority at direct endpoints, queue, dispatch, progress/audit, reconciliation and download access. Downloads grant access to secret-bearing recovery data even when encrypted. Server removal must respect active operations and transfer staging.
- **D21. Bounds and cleanup.** Keep the existing 16 KiB submission and 30-minute execution ceiling. Fixed artifact/member/count/staging limits in the native contract must be enforced and qualified. Capacity failure warns/refuses rather than pruning backups or releasing the gate unsafely. Only operation-owned temporary stages may expire after no processes use them. Finalized artifacts have no automated retention/deletion in v0.6; show storage use and document ordinary maintenance.
- **D22. Vertical delivery.** Each ticket delivers its own records, module behavior, custom USWDS/HTMX dashboard, permissions, empty/stale/inaccessible/progress/refusal/failure/recovery states, focused tests and operator instructions. Generic PHP/database work starts independently of unfinished application milestones. WordPress and Laravel support are separate gated extensions using their actually delivered application/process conventions.
- **D23. Upstream reuse.** Native database clients own dump/import, GNU tar owns archive mechanics, rclone owns crypto/storage/transfer and systemd owns scheduling/execution/cleanup facilities. Check existing pyinfra operations and established backup tools before custom orchestration. Record the missing requirement, alternatives checked, official links and narrow gap in each owning issue before custom code. Adapter limits cannot justify a second execution path or a persistent helper.
- **D24. Qualification.** The final qualification record names exact source revisions, distribution/tool patches, app versions, DB majors, architectures, configured bounds, live-provider evidence and remaining gaps. Public design/source documentation does not establish runtime qualification. Real AWS checks use a disposable private bucket and separately provisioned secrets, never production inventories or data. Missing safe external credentials is a recorded qualification blocker; continue independent native tests.

## Testing Decisions

- Test observable behavior through the same backups interface callers use, primarily the authorized operator workflow. Reuse bootstrap/native coordination and reconciliation, site reconstruction, database binding, TLS and hosting/browser prior art. Focused adapter tests prove dangerous archive, transfer and secret mechanics without multiplying public seams.
- Prove exact template reconstruction from independent controller databases after externally adding/changing/removing native units, storage objects and configuration. No application code executes in passive reads; config secrets and another device's private audit never become observations.
- Qualify real native MariaDB and PostgreSQL dumps/imports with meaningful fixtures, nontransactional/DDL refusal, roles/grants unchanged, constrained SQL authority and same-major compatibility. Verify actual application contents, uploads, secrets and installed dependencies survive full restore without package/network acquisition.
- Exercise corruption, truncated object, missing members, wrong key, missing offsite config, credential revocation, archive traversal/links/hardlinks/devices/duplicates, owner remapping, wrong target, incompatible runtime, full disk and every fixed limit. Refuse before destructive work where possible.
- Use two controllers/aliases/keys and independent databases for manual/scheduled/restore conflicts, child descriptor closure, original-run reconciliation and no replay. Test every existing mutation/closure against backup cgroups. Test both controller disconnection and real server reboot; a container restart is separate evidence.
- Fault gate, writer drain, dump, archive, onsite publication, offsite upload, database import, file publication, verification and process resumption. Assert retained source/preimages, unavailable evidence and gated partial restoration, rather than claiming rollback.
- Verify timer daily/weekly UTC configuration, no catch-up, disabled state, active invocation contention, finite cgroup lifetime, template drift and execution with both controllers offline. Capture policy and secrets remain server-native.
- Exercise encrypted downloads from onsite and offsite through the real verified connector, authorized non-root ciphertext staging, byte/disk/time limits, SSH trust changes, transfer cancellation, account revocation, expired access and successful offline rclone decryption. Never relax normal discovery output limits to transport backup bytes.
- Run production and development browser journeys with permission, keyboard/focus/responsive, progress and recovery checks. Each slice runs repository gates and affected native tests locally, independent Standards/Spec review and exact-head CI before merge.
- Final qualification demonstrates DB-only and full capture, onsite loss with offsite retrieval, downloaded-copy recovery, scoped destructive restore and fresh-controller reconstruction. WordPress/Laravel have their own delivered-convention dependencies; unresolved gates stay visible and their workflows disabled.

## Out of Scope

Other providers or S3-compatible endpoints, arbitrary rclone flags/configuration, arbitrary schedules/hooks, files-only capture, whole-server images, SSH/TLS/OS recovery, external database services, database globals, physical backups, replication/PITR, incremental/deduplicated chains, compression/encryption frameworks, Object Lock governance, automated retention/pruning, email/DNS backup, fleet jobs, notifications, backup billing, arbitrary archive uploads, universal app discovery and guaranteed zero downtime. Routine capacity and failure warnings remain part of backup workflows.
