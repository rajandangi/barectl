# Laravel deployment competitor analysis

Official product documentation reviewed on 2026-10-08 for the [v0.5 design](v0.5.md). This compares documented behavior, not independently tested implementations, pricing or market share. A missing capability in these pages means evidence was not established, not that a product cannot provide it.

## Comparison

| Product | Deployment and recovery | Application state and background work | Management model and trade-off |
| --- | --- | --- | --- |
| Laravel Forge | [Deployment documentation](https://laravel.com/forge/docs/sites/deployments) describes branch/manual/push workflows and release/current zero-downtime mode for new sites. It retains releases and separates preparation from activation. The `forge_deploy_commit` webhook field changes the history label, not the commit selected for deployment. | [Environment configuration](https://laravel.com/forge/docs/sites/environment-variables) includes shared `.env` and encrypted environment support. Deployment scripts supply Composer/migrations. [Queues](https://forge.laravel.com/docs/sites/queues.html) use Supervisor; [scheduler](https://laravel.com/forge/docs/resources/scheduler) supplies native scheduled tasks. | Hosted dashboard/API. Its deployment page does not establish automatic database rollback or automatic health-failure rollback. The release mode has documented creation-time restrictions. |
| Ploi | [Zero-downtime workflow](https://ploi.io/documentation/deployment/how-does-zero-downtime-deployment-work) retains timestamped versions and changes a symlink. Downtime depends on the deployment script. [Deployment API](https://developers.ploi.io/deployments/deploy-site) offers dashboard/API invocation. | [Queue instructions](https://ploi.io/documentation/laravel/how-do-i-set-up-a-queue-worker) use Supervisor and deployment restart commands. [Native cron](https://ploi.io/documentation/server/how-do-i-create-a-cron-job) is distinct from [cloud-scheduled scripts](https://ploi.io/documentation/server/how-do-scripts-work), which connect at run time. | Hosted management. Reviewed pages do not establish immutable commit admission, schema reversal or health-gated recovery. Native cron continues independently; hosted script dispatch is a different dependency. |
| RunCloud | [Atomic deployment stages](https://runcloud.io/docs/deployment-scripts) fetch/build before switching current and permit before/after scripts. [Recovery documentation](https://runcloud.io/docs/how-to-revert-to-a-previous-version-with-atomic-deployment) distinguishes code redeployment from shared persistent backup contents. | Configured shared application paths preserve state. Scripts can run migrations; [Supervisor jobs](https://runcloud.io/docs/create-supervisor-job-on-runcloud) own workers. | A [RunCloud agent](https://runcloud.io/docs/runcloud-packages) connects servers to its hosted dashboard. [Atomic conversion](https://runcloud.io/docs/enabling-atomic-deployment) is documented as irreversible. Barectl must not copy Git-history rewriting as a recovery action. |
| CloudPanel / dploy | [dploy workflow](https://www.cloudpanel.io/docs/v2/dploy/installation/) clones a branch/tag, copies overlays, links shared paths, runs configured commands, switches current and cleans old releases. It recommends tags for returning to older code. | Server-side overlays keep environment configuration; native site-user deploy keys fetch private source. [Crontabs](https://www.cloudpanel.io/docs/v2/frontend-area/cron-jobs/) supply native schedules. | Self-hosted server panel with an installed deployment utility. The reviewed workflow does not establish health-gated activation or database rollback; it grants PHP-FPM reload access and permits arbitrary configured commands. |
| Coolify | [Rolling updates](https://coolify.io/docs/applications/deployments/rolling-updates) and readiness checks can keep old containers until replacements start, with stated availability limits. [Rollback](https://coolify.io/docs/applications/deployments/rollbacks) uses an older retained image with current runtime configuration and does not reverse database/storage changes. | The [Laravel example](https://coolify.io/docs/applications/framework-examples/php/laravel) uses Supervisor in the application container. [Scheduled tasks](https://coolify.io/docs/applications/operations/scheduled-tasks) use Coolify's scheduling path. | Its [architecture](https://coolify.io/docs/core/how-coolify-works) uses SSH deployment and Docker with a persistent Coolify management installation. Existing containers can continue without it. Its documented optional monitoring agent differs from RunCloud's required management agent. |

## Decisions for Barectl

These are Barectl judgments drawn from the comparison and existing ADRs, not vendor claims.

- Exact commit identity must come from the actual reviewed checkout, never a displayed deployment label. Resolve a moving reference once and refuse unavailable or changed intent.
- Preserve the useful release/current/private-state pattern, but publish only through the existing native reviewed operation and protect its links from site-code replacement. A symlink switch is one code-selection operation, not a transaction over the database and background work.
- Provide a bounded Laravel workflow instead of arbitrary deployment scripts. Explicit named staging, migration, activation, diagnostics and process actions make effects and permissions reviewable.
- Keep schema effects and code reactivation separate. Preserve uploads/environment and never promise database recovery from a retained code directory. Verified restore stays v0.6.
- Make scheduler and workers native and controller-independent. Native operative files, Git evidence and unit state must support a fresh controller; a vendor dashboard inventory or private local audit cannot supply that authority.
- Publish a maintenance-window contract with readiness/process evidence. Do not inherit marketing claims about zero downtime without qualifying actual failure and concurrency behavior.
- Keep repository authentication native through site-identity deploy keys and verified host trust. Do not copy browser secret editors before designing a secret lifecycle.
- Evaluate established deployment tools before adding custom mechanisms. The [reuse analysis](laravel-native-design.md#upstream-reuse-and-the-specific-gap) explains why documented defaults do not meet the complete accepted contract and confines custom work to the remaining review/admission gap.

## Evidence limits

No competitor was installed or benchmarked. This analysis makes no universal security, uptime, lock, portability or exact-once guarantees about competitors. Forge, Ploi and RunCloud are useful workflow references; CloudPanel/dploy is a native reuse candidate; Coolify offers useful health/recovery semantics with a container model outside Barectl's initial scope. Recheck vendor documentation when reopening these choices. Barectl's architecture requirements, rather than feature-count parity, determine v0.5 acceptance.
