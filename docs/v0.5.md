# v0.5 Laravel

Accepted design for the roadmap's Laravel milestone. Implementation, native qualification and release publication remain pending. [Specification issue #256](https://github.com/rajandangi/barectl/issues/256) and its native sub-issues own delivery state. The [native design](laravel-native-design.md), [competitor analysis](laravel-competitor-analysis.md) and ADRs [0019](adr/0019-deploy-laravel-through-reviewed-native-releases.md) and [0020](adr/0020-run-laravel-background-work-with-native-systemd.md) form part of this contract.

## Problem Statement

An operator can establish PHP sites, local databases and HTTPS, but cannot deploy a Laravel application or manage its scheduler and queue workers through Barectl. A manual Git pull and a successful shell exit do not establish which code is serving, whether migrations ran, or whether background processes use the new code. Losing a controller must not lose the ability to inspect or manage the application. Deployment must preserve private configuration and application data, and must explain partial failures without pretending that code replacement reverses database changes.

## Solution

Attach one Laravel application to a prepared convention site. Establish its tools and selected PHP runtime through review, stage an exact Git commit with locked Composer dependencies, separately review migrations, and activate a verified release through the dashboard. Add native minute scheduling and a bounded database queue worker workflow. Reconstruct applications and their native process configuration from another controller without transferring Barectl records.

Use release directories and a root-controlled current link for code publication. Keep private environment configuration and writable storage separate. Activation uses a public maintenance gate and process draining. It promises verified serving and process convergence, with an explicit interruption window. It does not promise zero downtime, database rollback or complete application transaction isolation.

## User Stories

1. As an operator, I want to see a site's Laravel prerequisites and observation time, so that I can prepare missing infrastructure deliberately.
2. As an operator, I want to review Git, Composer and selected-branch PHP capabilities, so that tool preparation cannot silently switch other sites' runtimes.
3. As an operator, I want to deploy on either supported Ubuntu release with its qualified PHP and database, so that the milestone fits the existing hosting foundation.
4. As an operator, I want to choose a public HTTPS or supported private SSH repository, so that I can host my application source without uploading credentials to Barectl.
5. As an operator, I want terminal instructions for native read-only deploy keys and verified repository host keys, so that private-source access stays on the managed server.
6. As an operator, I want to resolve a branch or tag to an exact commit for review, so that a later moving reference cannot change the authorized source.
7. As an operator, I want to see source access refusals without exposed tokens or keys, so that authentication failures remain actionable and private.
8. As an operator, I want source resolution and plan preparation to avoid executing application code, so that review remains read-only.
9. As an operator, I want to review downloads, dependencies, disk limits and execution effects before staging, so that fetching and building are explicit changes.
10. As an operator, I want a missing or inconsistent Composer lock to refuse staging, so that production does not resolve unreviewed dependency versions.
11. As an operator, I want Git, Composer and Artisan to run as the site's identity and selected PHP CLI, so that application code never gains root execution.
12. As an operator, I want unsupported plugins, hooks, submodules, LFS and repository layouts refused, so that a bounded workflow does not become a remote script editor.
13. As an operator, I want to retain my existing application while a candidate stages, so that a failed download does not replace serving code.
14. As an operator, I want a staged candidate to remain inspectable after controller loss, so that a new controller can review it without replaying the build.
15. As an operator, I want private environment configuration to stay on the server, so that plans, journals and browser responses do not become secret stores.
16. As an operator, I want an application key generated once and retained, so that redeployment cannot invalidate existing encrypted data.
17. As an operator, I want to configure application-specific secrets through the terminal, so that Barectl does not need a browser credential transport.
18. As an operator, I want MariaDB socket or PostgreSQL peer access under the site identity, so that local database credentials need not be distributed.
19. As an operator, I want frontend assets supplied by my reviewed repository, so that v0.5 does not silently add a server-side Node build system.
20. As an operator, I want exact Laravel public routing with private-file and uploaded-PHP denial, so that only intended public content is served.
21. As an operator, I want to review candidate migration names and irreversible effects separately, so that code activation does not imply consent to schema changes.
22. As an operator, I want to acknowledge my recovery provision and application compatibility before migrations, so that unverified backup or code rollback is never represented as database protection.
23. As an operator, I want a migration action to gate new traffic and drain managed scheduler/workers, so that known background work cannot race the schema action.
24. As an operator, I want partial migration or uncertain outcomes to preserve data and refuse automatic replay, so that a retry cannot repeat unknown business effects.
25. As an operator, I want migration-table evidence and verification shown separately from command exit, so that skipped or incomplete work cannot be called migrated.
26. As an operator, I want to review activation against fresh candidate, current, environment and database evidence, so that stale approval cannot publish different code.
27. As an operator, I want activation to verify the selected PHP pool, HTTPS and an application readiness route, so that a switched link is not mistaken for a working deployment.
28. As an operator, I want ACME routes and certificate renewal preserved through maintenance and activation, so that deployment does not break HTTPS upkeep.
29. As an operator, I want an explicit failure stage and exposure state, so that I know whether old code, a maintenance gate or new code is serving.
30. As an operator, I want accepted work to continue when the controller closes, so that native execution owns its lifetime.
31. As an operator, I want Check outcome to inspect the original run, so that a lost response cannot cause a duplicate deployment or migration.
32. As an operator, I want a fresh reviewed code reactivation of a retained release, so that recovery does not rewrite Git history or claim to undo schema and uploads.
33. As an operator, I want changed or ambiguous partial resources refused with terminal recovery guidance, so that Barectl does not adopt foreign content.
34. As an operator, I want to reconstruct source commit, release layout, routing and process state on a new controller, so that my server remains portable.
35. As an operator, I want passive discovery to avoid Artisan and PHP inclusion, so that inspection of metadata does not execute application code.
36. As an operator, I want inaccessible, unsupported, candidate and current evidence distinguished, so that a directory name or old snapshot is not proof of successful deployment.
37. As an operator, I want separately authorized executable inspection with bounded results, so that runtime diagnostics have clear permissions and effects.
38. As an operator, I want minute scheduling to continue while Barectl is closed, so that application schedules do not require a hosted control plane.
39. As an operator, I want scheduler contention and skipped ticks recorded in native service evidence, so that conflict exclusion does not masquerade as successful execution.
40. As an operator, I want named scheduler enable, disable and run-once actions, so that I can manage a supported schedule without an arbitrary cron editor.
41. As an operator, I want a database queue worker that starts after reboot and restarts after a clean queue exit, so that jobs continue without a controller.
42. As an operator, I want bounded queue timeout, retry and stop policies, so that deployment can drain accepted work or refuse safely.
43. As an operator, I want explicit worker start, stop and graceful restart actions, so that process management is an independently usable workflow.
44. As an operator, I want workers to converge on the activated release, so that web and background code do not silently differ.
45. As a restricted Barectl account, I want separate view, preparation, staging, migration, activation, diagnostic and process permissions, so that infrastructure access does not grant application execution.
46. As an operator on another device, I want native conflict refusal and fresh review, so that local database locks cannot authorize competing changes.
47. As an operator, I want retained releases and disk exhaustion reported without automatic deletion, so that cleanup cannot erase recovery candidates or shared data.
48. As an operator, I want generic PHP and WordPress conventions to retain their own behavior, so that Laravel does not broaden or replace unrelated workflows.
49. As an operator, I want tested versions and architecture limits published separately from the specification, so that planned capability is not confused with available support.

## Implementation Decisions

- **D1. Application ownership.** Add a Laravel domain module attached to a convention site. Reuse the action registry, remote-operation lifecycle, typed plan/audit storage, passive discovery and existing native execution adapter. WordPress installation is not a prerequisite. No generic application framework or speculative prefactor is required.
- **D2. Deep interface.** The Laravel module exposes typed observations and named workflow requests for preparation, staging, migrations, activation, inspection and process changes. The interface includes admission invariants, permissions, refusal reasons and outcome distinctions. Git transport, dependency acquisition, filesystem admission and unit rendering stay inside its implementation. Existing adapters and their real/fake implementations supply the seams; avoid pass-through modules and test-only interfaces.
- **D3. Initial compatibility.** Qualify Laravel 13 with Ubuntu 26.04/PHP 8.5, with release-default MariaDB and PostgreSQL, on amd64 and arm64. Exact Laravel patch, tool package versions, dependency lock and fixtures must be pinned in qualification before enabling delivery. Extra branches and Laravel majors require separate evidence; no unsupported version is silently upgraded or downgraded.
- **D4. Tool workflow.** Prefer Git and Composer from each supported Ubuntu archive, using the existing exact package transaction. Invoke Composer through the site's explicit PHP binary. Refuse package choices that change PHP supply or other site selections. Check the locked project's Composer requirements and actual CLI/FPM extensions rather than treating an installed executable as compatibility proof.
- **D5. Source contract.** Support credential-free HTTPS URLs and fixed SSH repository locators with native read-only deploy keys and trusted host keys provisioned through the terminal. Resolve a validated branch/tag or full commit without executing a checkout. Review and fetch that exact full commit, never a mutable ref alone. No controller-agent forwarding, automatic host-key acceptance, URL credentials, browser key/token input, arbitrary transport helpers or untrusted Git configuration.
- **D6. Two reviewed stages.** Source review authorizes a finite stage operation, including network and site-identity execution effects. The stage fetches/builds and safely publishes an inactive root-protected candidate without changing current selection or routing. Site-identity tooling is not a sandbox and may affect application-accessible private state; disclose that trust. Later Artisan/migration actions execute only the protected candidate. Use the fixed bounded native ephemeral stage in the native design, and report unpublished artifacts unavailable after unit loss. A separate activation review binds the actual candidate, lock, private-configuration digest, database evidence, current target and native routing. Downloaded bytes and Composer diagnostics never retroactively become preparation-only work.
- **D7. Composer policy.** Require a consistent committed lock, locked production install, actual platform checks and no dependency update. Disable Composer plugins and lifecycle scripts initially; refuse projects that require them. Fixed, separately disclosed Artisan preparation supplies supported Laravel discovery/cache steps later. Composer remains trusted dependency tooling, not a sandbox or a guarantee of reproducible dependency archive bytes. No custom dependency resolver or blanket audit bypass.
- **D8. Native convention.** Adopt the explicit operative release/current/private-storage grammar in the native design. Root controls publication links and protected code; site-identity writes are confined to staging, private configuration and required writable application paths. Admit an explicit symlink allowlist rather than relaxing generic PHP path checks. Reject unsafe ancestry, hardlinks, special files, escapes and concurrent modifications before root publication. Never recursively take ownership of an arbitrary tree.
- **D9. Routing and prerequisites.** Initial activation requires a complete selected-branch convention site, local satisfied database binding and verified HTTPS. Adopt only empty or exact placeholder content on the first transition, never an existing application. Serve the release's public directory with one front controller, preserved query strings, canonical names and ACME; deny private files and other executable PHP. TLS workflows preserve the observed Laravel form and selected socket.
- **D10. Private state.** Keep environment configuration and storage native and private. Generate a missing application key once on the server through authorized site-identity execution; preserve an existing key. Run fixed package discovery against the protected candidate after environment setup and before migration. Never shell-source or execute environment files during discovery. Terminal setup supplies application-specific values. Native database socket/peer access remains the qualified default. Cached configuration can contain secrets and receives private permissions.
- **D11. Migrations.** Migrations are separately authorized against one candidate and exact native database binding, with recovery/compatibility acknowledgement. List only supported conventional migration identifiers during read-only review; do not invoke Artisan there. Gate new web traffic, stop/drain managed scheduler and workers, execute the fixed production migration command as the site identity, then verify native migration-table evidence. Success does not prove all arbitrary business effects. No implicit seeding, destructive reset, rollback, automatic retry or inference from exit zero alone.
- **D12. Partial schema.** A failed, timed-out or unknown migration requires ordinary application/database recovery and a fresh review. Existing schema and data remain. Completed migration rows are evidence of recorded completion, not proof that a failed migration made no changes. Code reactivation is separately authorized and requires operator compatibility judgement; it never supplies database restore.
- **D13. Activation.** Activation and redeployment use the maintenance gate and bounded native process draining. Every activation requires all candidate conventional migration identifiers recorded complete or positively no candidate migrations; extra historical rows remain. Verify candidate/platform/configuration, publish the exact current target, account for selected FPM/OPcache realpath behavior, verify private FastCGI and HTTPS readiness, and enable/start only the exact process state explicitly chosen in the activation review. Default unavailable process intent to disabled; a fresh controller must not infer previous enablement from a lost audit. Keep the gate on failed or uncertain verification; record any gate failure honestly. Do not automatically activate old code after schema work.
- **D14. Readiness.** Use a fixed same-site HTTPS readiness path, default `/up`, with bounded status handling and no response-body disclosure or arbitrary outbound health URL. Laravel's default route proves boot, not database/queue/business health. Applications can supply their own checks at that path. Record execution, migration evidence, serving verification and process convergence separately.
- **D15. Native execution.** Every executable workflow reuses the existing worker, pyinfra SSH connection, finite transient systemd submission, shared nonblocking mutation lock, evidence/boot/deadline fencing, cgroup checks, native limits and original-run reconciliation. Application code always runs as the dedicated identity with controlled inputs; root executes only trusted native mechanics. No second SSH path, persistent helper or release journal is introduced.
- **D16. Reconstruction.** Read bounded native routing, filesystem metadata, protected Git metadata, lock data, explicit operative links, database binding and systemd configuration/state. Report qualification separately. Never execute PHP, Composer or Artisan for passive discovery, and never treat a release directory name, cached view, native log absence or old private audit as authoritative completion evidence.
- **D17. Inspection and recovery.** Authorized finite inspection returns typed bounded non-secret results through the existing native outcome mechanism. Published protected candidates and shared state remain after interruption; unpublished ephemeral staging may be unavailable. Fresh review may activate an exact eligible candidate or retained release, but cannot replay an uncertain migration/build, repair ambiguous content or delete data. Retained releases require no custom status markers and are not called backups.
- **D18. Scheduler.** Use a native minute systemd timer and finite oneshot service for the supported `schedule:run` profile. It continues without Barectl, uses native nonblocking exclusion and site-identity application execution, and exposes skip/conflict/timeout evidence. Disable catch-up. Subminute schedules, unmanaged duplicate scheduling, detached/background tasks and fleet-wide scheduling are unqualified and block enabling this profile. Unit/cgroup containment and timeout failure are explicit.
- **D18a. Cooperative compatibility.** Extend every apply and unknown-outcome closure's scheduler cgroup checks, including children that close inherited lock descriptors. Upgrade or stop older mutation controllers before scheduler enablement; a private database cannot fence them. Disable native background boot activation while the site is persistently gated and restore it only after verified activation, so reboot cannot bypass deployment draining.
- **D18b. Process admission.** Scheduler enable/run-once and worker start/restart require fresh verified ungated activation with the selected current release's migrations recorded complete. A separate inactive candidate does not block the unchanged active application. Gated, partial or unknown application state refuses these actions; stop/disable remain available for recovery.
- **D19. Workers.** Use native systemd for one database queue worker profile with validated queue names and bounded timeout/retry/stop behavior. Explicitly select the PHP branch and current release; restart on successful queue exits as well as failures, with rate limits. Do not hold the global mutation lock for a worker lifetime. Deployment stops/drains exact managed units and refuses failure to quiesce them. External workers remain outside this guarantee.
- **D20. Cooperation limits.** The mutation lock covers cooperating controllers and guarded native scheduled work, not ordinary administrator commands, in-flight web requests, malicious application code or external services. A maintenance gate rejects new traffic but is not application-wide isolation. Migration review discloses these limits; reliable managed-process coordination is required, and unmanaged conflicting work refuses dependent actions.
- **D21. Permissions and persistence.** Separate Laravel observation/plan view, preparation, stage, migrate, activate/reactivate, executable inspection and process-management authority. Enforce account activity and owning permissions at endpoints, queue/dispatch, audit/poll views, reconciliation and acknowledgement. Preserve typed records through migrations, server-removal exclusion and retained audit without transferring secrets.
- **D22. Complete slices.** Each ticket includes its required database records, module behavior, custom dashboard, permission/refusal/progress/recovery states, tests and operator instructions. Use USWDS, the established HTMX/Vite lifecycle and current palette. Do not defer all interface work or safety verification to final integration.
- **D23. Reuse requirement.** Native Git, Composer, database clients, Nginx/FPM and systemd own their established mechanics. The reuse analysis compares pyinfra, Deployer and dploy before choosing narrow admission/publication glue. Record the specific unsupported requirement, alternatives and source links in the owning ticket before adding custom mechanisms. An adapter limitation must be reviewed explicitly rather than bypassed.
- **D24. Delivery evidence.** Each slice passes repository gates and affected native tests locally before push, independent Standards and Spec reviews, and required exact-head CI before merge. The final record owns pinned revisions, architecture/runtime/database combinations, real-kernel evidence and limits. No ticket closes because this specification is published.

## Testing Decisions

- Prefer one primary seam at the authorized operator workflow: request, immutable review, worker/native outcome, fresh evidence and rendered result. Exercise the same Laravel interface callers use. Existing native execution and filesystem/credential adapters still need focused adversarial checks; a single seam is a design preference, not permission to hide unsafe mechanics.
- Reuse site/reconstruction, bootstrap coordination/reconciliation, database binding, TLS and native hosting/browser prior art. A meaningful test proves external effects, denied effects, retained resources or honest outcomes. Do not mirror private helper structure or substitute fake SSH for native qualification.
- Prove moving refs cannot change reviewed commits, commit labels reflect actual protected Git evidence, locks/platform checks refuse inconsistent input, package installation preserves selected branches, and contaminated Git/Composer environment/configuration cannot invoke unauthorized helpers or root application code.
- Prove public/private repository paths with strict host trust, absent credentials, credential errors, bounded download/time/disk limits and no secret-bearing output. Check command text, process metadata, journal, records, errors and rendered pages. Suppression covers Barectl's output path; it is not containment of intentionally hostile application disclosure.
- Prove no-follow admission after untrusted staging, concurrent tree edits, hardlinks, symlink escapes, special files and private cache modes. Verify forbidden public files/PHP/uploads, canonical/query routing, IPv4/IPv6 where supported, ACME/renewal and existing generic PHP/WordPress conventions.
- Fault stage, environment setup, process drain, migration, publication, FPM convergence and serving checks. Check migration-table postconditions including lock-skipped commands, partial schema without a completed row, timeouts and lost responses. Never replay or delete data to make an assertion pass.
- Use independent controller databases, aliases and keys for conflict refusal, fresh evidence review, original-run reconciliation, wrapper/child failure and outcome unknown. Reconstruct staged/current/partial layouts and scheduler/worker state without controller audit, including after ordinary native changes and with limited SSH access.
- Prove timer contention/skip, no catch-up, finite cgroup lifetime, worker successful exits/restart-rate limiting, graceful stop budget, deployment convergence, reboot persistence and operation while both controllers are off. Container restart and real kernel reboot are separate evidence.
- Run production and Vite-development browser journeys for prerequisite review, stage, migrations, first activation, redeploy/reactivation, diagnostics, scheduler/worker actions and permission/stale/error states. Include keyboard/focus/responsive behavior and console-error checks.
- Qualify the complete matrix in D3 with pinned representative Laravel 13 applications, committed assets, real migration failure fixtures and database jobs. Missing required platform or reboot evidence remains a recorded gate. Keep unsupported combinations disabled.

## Out of Scope

Laravel major upgrades, arbitrary deploy scripts or Artisan consoles, implicit seeding, automatic migration rollback, verified backup/restore, automatic release deletion/retention, browser environment/credential editors, controller-agent forwarding, private Composer registries, Composer plugins/lifecycle scripts, Git LFS/submodules, monorepos, server-side Node builds, Redis/Horizon, Octane, Reverb, containers, remote databases, subminute/background schedules, fleet queue coordination and zero-downtime guarantees. Operators can use ordinary native tools with their own recovery process. Verified restore remains v0.6.

## Further Notes

The [native design](laravel-native-design.md) owns operative paths, workflow order, recovery limits and the upstream reuse record. The [competitor analysis](laravel-competitor-analysis.md) distinguishes vendor documentation from Barectl's choices. GitHub native sub-issue and blocking relationships own sequencing. There is no whole-WordPress-milestone dependency; existing PHP/database/TLS behavior supplies the foundation. Exact artifact/package pins and runtime compatibility are implementation acceptance gates, not claims established by this design.
