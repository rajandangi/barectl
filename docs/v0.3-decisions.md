# v0.3 design decisions and source record

Resolved on 2026-09-29 for the [PHP sites specification](v0.3.md). These are accepted design decisions, not implementation or qualification claims. [The native convention](site-conventions.md) records the concrete layout.

## Resolved design tree

| Decision | Choice and reason | Consequence |
| --- | --- | --- |
| Milestone boundary | HTTP PHP sites, then database profiles/bindings, then TLS. | No WordPress, Laravel or deployment implementation enters v0.3. |
| Meaning of reconstruction | Rebuild observed relationships from current native files, accounts, catalogs, services and certificate state. | It does not recover lost application data or private controller history. |
| Source of site identity | Nginx root/socket, FPM identity and account evidence must agree. | A filename, comment or cached record never proves a site relationship. |
| Configuration changes | Exact reviewed file/account effects, safe publication and preimage checks under existing exclusion. | Multi-resource failure remains partial; no automatic deletion of data to simulate rollback. |
| Custom installations | Observe what can be proved; mutate only the documented supported grammar. | Existing custom layouts are not silently adopted. |
| Bootstrap interaction | Keep stock package-profile restrictions; use separate site readiness. | An established site's extra files do not authorize a broad bootstrap repair. |
| First site profile | One default PHP pool, fixed native layout, existing-file routing. | Framework front controllers and arbitrary tuning wait for their own specs. |
| Database engines | Separate release-specific MariaDB and PostgreSQL package profiles in the existing engine. | Initialization and PostgreSQL cluster verification are explicit work, not a second package runner. |
| Site database credentials | Same Linux identity through local socket authentication. | No application password enters commands, plans, audit, controller storage or native service metadata. Remote clients are deferred. |
| Database scope | One optional engine/database binding per site, exact scoped privileges. | No role adoption, data migration, global grant changes or automatic drop on failure. |
| Privileged observations | Ordinary discovery stays unprivileged; protected read-only preparation can inspect catalogs and renewal config. | A lesser SSH identity may see inaccessible relationships. Fresh-controller proof states its actual privileges. |
| TLS authority interaction | One Create and Install action authorizes the displayed site names, account and fixed TLS installation; staging stays diagnostic. See ADR 0014. | Public reachability and CA state cannot be inferred from a listening socket. No retry loops. |
| Configuration ownership during TLS | Certbot certonly/webroot obtains certificates; the reviewed file action activates Nginx. | No unreviewed Nginx-installer rewrite. |
| Renewal owner | Native Certbot timer/service, shared exclusion and validated deploy hook. | Renewal survives all controllers; conflicts and certificate-versus-serving failures stay visible. |
| Primary test seam | Dashboard through real worker/native server, then independent reconstruction. | Parser and fault fixtures supplement this seam; hashes and mocks alone cannot qualify behavior. |
| Delivery graph | Read-only site reconstruction, review, apply; engine profiles; bindings; TLS setup/staging; production TLS/renewal; final qualification. | Execution follows phase order without pretending TLS depends on a database. |

## Official sources checked

These links explain upstream behavior. The chosen supported grammar, directory naming, privileges, scope and fault policy are Barectl decisions, not upstream endorsements.

- [Django 6.1 tasks](https://docs.djangoproject.com/en/6.1/topics/tasks/) and [authentication/permissions](https://docs.djangoproject.com/en/6.1/topics/auth/default/) support the existing queued workflow and permission boundary. No framework or task-backend change is proposed.
- [Ubuntu Nginx installation](https://ubuntu.com/server/docs/how-to/web-services/install-nginx/) , [request routing](https://nginx.org/en/docs/http/request_processing.html), [TLS handshake rejection](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_reject_handshake) and the [Nginx guide](https://nginx.org/en/docs/beginners_guide.html) describe the packaged web server and reload behavior. Nginx preserving old workers on a failed reload does not provide a filesystem transaction or protect PHP/account changes.
- [PHP-FPM configuration](https://www.php.net/manual/en/install.fpm.configuration.php) documents pool identities, Unix sockets, socket permissions and process limits. The fixed limits in the convention are a Barectl starting profile, not a universal workload recommendation.
- [MariaDB unix_socket authentication](https://mariadb.com/docs/server/reference/plugins/authentication-plugins/authentication-plugin-unix-socket) documents OS-identity authentication, default availability in Debian/Ubuntu packages and the pre-11.6 mapping difference. Same-name identities avoid depending on the newer alternate mapping. [MariaDB GRANT](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant) defines scoped privileges and wildcard behavior; alphanumeric names avoid grant-pattern ambiguity.
- [PostgreSQL 16 peer authentication](https://www.postgresql.org/docs/16/auth-peer.html) and [PostgreSQL 18 peer authentication](https://www.postgresql.org/docs/18/auth-peer.html) document local OS-identity checks. [CREATE DATABASE](https://www.postgresql.org/docs/18/sql-createdatabase.html) explains database creation and its non-transactional restriction; [REVOKE](https://www.postgresql.org/docs/16/sql-revoke.html) explains removing PUBLIC access. The implemented profile must use documentation matched to the installed major.
- Ubuntu's [MariaDB package for 26.04](https://packages.ubuntu.com/resolute/mariadb-server) lists the 11.8 series; [Certbot for 26.04](https://packages.ubuntu.com/resolute/certbot) lists 4.0.0 in universe. These listings are discovery evidence, not pins or native qualification. Other package listings were unavailable during this review; implementation must record the actual authenticated candidates, archive components and installed revisions for both releases.
- [Certbot 2.9 guide](https://raw.githubusercontent.com/certbot/certbot/v2.9.0/certbot/docs/using.rst) and [Certbot 4.0 guide](https://raw.githubusercontent.com/certbot/certbot/v4.0.0/certbot/docs/using.rst) describe certonly, webroot, separate working/configuration directories and renewal hooks. [Current Certbot guidance](https://eff-certbot.readthedocs.io/en/stable/using.html) warns that renewal's zero exit does not prove a certificate was renewed and deploy-hook failure needs separate interpretation. Versioned behavior still requires tests against Ubuntu's packages.
- [Certbot installation instructions](https://certbot.eff.org/instructions?ws=nginx&os=snap) describe the upstream snap approach. Distribution APT packages are selected here to reuse exact native transaction review, a deliberate Barectl constraint rather than an upstream recommendation to prefer APT.
- Let's Encrypt documents [HTTP-01 challenges](https://letsencrypt.org/docs/challenge-types/), [IPv6 validation behavior](https://letsencrypt.org/docs/ipv6-support/) and [rate limits](https://letsencrypt.org/docs/rate-limits/). DNS and public reachability remain external prerequisites. Record current CA errors and retry timing rather than copying numeric limits into code.
- [ADR 0006](adr/0006-use-native-bootstrap-execution.md), [ADR 0007](adr/0007-admit-exact-package-transactions-with-an-inline-apt-guard.md) and [ADR 0008](adr/0008-review-each-ubuntu-release-by-its-own-policy.md) retain the upstream native execution, APT and per-release sources already used by the existing engine.

## Concrete failure decisions

- Another administrator adds a domain after review. Re-read the whole supported Nginx closure under exclusion, refuse, and request a new plan. Do not compare only the target file.
- A new pool file lands, then the process dies before Nginx enablement. Record partial completion when native evidence survives, or outcome unknown when it does not. Discover the incomplete resources and require inspection; never delete the account or document root to make the next create succeed.
- The database exists after an interrupted DDL sequence. Preserve it and its data. A new review may report a fully satisfied supported binding, or refuse incomplete/custom grants with exact manual recovery guidance. Do not use IF NOT EXISTS as adoption.
- A new controller cannot read a database catalog. Show inaccessible, then allow an explicitly authorized privileged read-only preparation. Never fill the gap from the first controller's cache.
- IPv4 points to the server but IPv6 points elsewhere. Refuse TLS readiness for that name. A successful IPv4 probe is insufficient.
- The CA issues a certificate, but Nginx activation fails. Keep HTTP and the native certificate. Prepare an activation-only review; never request another order automatically.
- A matching production lineage already exists. The order is a plan without changes naming its validity dates and pointing at activation; never replace a certificate to work around limits, and never adopt a lineage for other names or another account contact.
- Another effective 443 default server exists or the shared rejection file has other bytes. Refuse activation; the shared file cannot own the default. Remove or restore it through ordinary administration, never by rewriting unrelated configuration.
- The second activation candidate is refused after HTTPS was verified. Keep the verified HTTPS state on disk; that is partial completion, and a fresh activation plan proposes the redirect again.
- Certbot renews a certificate but its deploy hook fails. Report the on-disk and served fingerprints separately; the timer's last exit alone does not prove HTTPS was updated.
- A renewal wrapper dies while a child keeps running. The control-group conflict check must continue to block site and bootstrap mutation, even if the child closed its lock descriptor.

## Qualification boundaries for implementation

Package candidates, native initialization effects, FPM syntax, service units, Certbot timer behavior and options must be verified on the installed release. A source-fetch failure is recorded above rather than filled in from memory. No real managed server was mutated for this design. External staging qualification uses an explicitly configured disposable domain/server; any existing production server's earlier port status is not a reusable readiness assertion.

Before release, each mutating ticket records exact commit, release, architecture, native revisions, behavior/fault tests and remaining limits. New real-reboot claims need new real-reboot evidence. Qualification of v0.2's package engine does not qualify site-file publication, database DDL or certificate renewal.
