# v0.4 WordPress

Accepted specification for the roadmap's WordPress installation and named WP-CLI operations. The workflows are implemented ([WordPress](wordpress.md)); the [qualification record](v0.4-qualification.md) names the tested revision, environments, enabled combinations and limits, and release publication remains pending. [Specification issue #243](https://github.com/rajandangi/barectl/issues/243) owns the published design; its sub-issues own implementation state. The [native design](wordpress-native-design.md) retains the previously accepted operative contract and artifact pins. ADRs [0017](adr/0017-manage-wordpress-as-a-site-application.md) and [0018](adr/0018-generate-wordpress-secrets-on-the-server.md) remain in force.

## Problem Statement

An operator can prepare a PHP site, its local database and HTTPS, but cannot install or inspect WordPress through the Barectl dashboard. Ordinary manual installation leaves the controller unable to distinguish verified application state, an incomplete install and inaccessible evidence. A new controller must recover supported server views without the previous controller's records, and installation must preserve native administration, existing applications and private credentials.

## Solution

Extend one prepared convention site with a single root-path WordPress application using its selected PHP branch, site identity, satisfied MariaDB binding and verified HTTPS. Provide reviewed tool and runtime preparation, an immutable installation review, guarded installation, explicit application inspection and named maintenance. Integrate each delivered behavior with the custom dashboard, permissions, native outcomes and operator guidance.

Passive discovery reconstructs application evidence without running WordPress. Accepted execution uses the existing detached native boundary and remains inspectable after controller loss. First-login password setup is an authorized terminal step. Ambiguous partial installation is refused without erasing files or tables.

## User Stories

1. As an operator, I want to install WordPress on a prepared convention site, so that I can publish a single WordPress application through the Barectl dashboard.
2. As an operator, I want to see the PHP, MariaDB, HTTPS and tool prerequisites with their observation time, so that I know what must be prepared before installation.
3. As an operator, I want to establish authenticated WP-CLI through a reviewed setup workflow, so that I can supply the required tool without an arbitrary installer.
4. As an operator, I want to prepare the selected PHP branch's WordPress extensions through a reviewed workflow, so that the CLI and application pool have the required capabilities.
5. As an operator, I want to retain every existing site's PHP selection while preparing WordPress, so that one application does not change another application's runtime.
6. As an operator, I want to choose an explicit canonical HTTPS name from the site's covered names, so that WordPress uses the intended secure address.
7. As an operator, I want to provide a site title and WordPress administrator login and email, so that the new application starts with the intended identity.
8. As an operator, I want to receive clear refusals for PostgreSQL, unsupported PHP or incomplete HTTPS, so that I can resolve the actual prerequisite without implicit conversion.
9. As an operator, I want to review exact tool/core releases, file effects, schema effects and network effects, so that I understand what installation authorizes.
10. As an operator, I want to prepare an installation review without changing the server, so that I can inspect the proposal before authorizing it.
11. As an operator, I want to receive a refusal for existing application content or tables, so that installation cannot overwrite my data.
12. As an operator, I want to receive a refusal when reviewed native evidence changes, so that an old review cannot silently authorize different work.
13. As an operator, I want to acquire only the reviewed authenticated WP-CLI and pinned WordPress archive, so that unapproved artifacts cannot run during installation.
14. As an operator, I want to have corrupt or unsafe downloads refused before application code runs, so that artifact failures do not become an installation.
15. As an operator, I want to keep public application routes gated during installation, so that visitors cannot claim an incomplete web installer.
16. As an operator, I want to have WordPress use the site identity and its local MariaDB binding, so that the application has no database password to distribute.
17. As an operator, I want to keep WordPress salts and initial password generation on the managed server, so that controller records and command metadata do not retain credentials.
18. As a WordPress administrator, I want to set my first-login password through an authorized terminal prompt, so that I can sign in without relying on email or a browser secret store.
19. As an operator, I want to see a clear password-setup requirement after installation, so that installation completion does not imply a usable password was delivered.
20. As an operator, I want to open the verified HTTPS home page and WordPress dashboard, so that I can use the installed application.
21. As an operator, I want to have accepted installation continue after the controller disconnects, so that connection loss does not own the server process.
22. As an operator, I want to check the outcome of the original native run after an uncertain response, so that I do not install the application a second time.
23. As an operator, I want to see execution and verification outcomes separately, so that a successful command does not hide failed serving checks.
24. As an operator, I want to preserve application files and tables after a partial failure, so that recovery cannot erase work that may have completed.
25. As an operator, I want to restore a verified provisioning gate after failed serving checks when safe, so that the actual exposure state remains visible.
26. As an operator, I want to review an eligible Finish from native evidence, so that I can complete missing resources without replaying database installation.
27. As an operator, I want to receive an ordinary-administration refusal for ambiguous partial tables, so that recovery does not guess which schema changes ran.
28. As an operator on another controller, I want to reconstruct WordPress without the first controller's database, so that I can manage a server independently.
29. As an operator, I want to see application evidence separately from site infrastructure, so that content changes do not make unrelated native resources disappear.
30. As an operator, I want to see candidate, partial, installed, blocked and unreadable evidence honestly, so that file presence and old snapshots do not become installation proof.
31. As an operator with limited SSH access, I want to see the private evidence I cannot read identified as unavailable, so that discovery never silently escalates my access.
32. As an operator, I want to have passive discovery avoid executing application PHP, so that refreshing the server view does not bootstrap WordPress or plugins.
33. As an operator, I want to explicitly authorize WordPress inspection, so that application code execution is a visible operation.
34. As an operator, I want to see bounded core, plugin and theme inventory with its inspection time, so that I can understand observed application state.
35. As an operator, I want to verify core and repository-plugin checksums with match, mismatch and unavailable outcomes, so that missing public checksums do not become a false trust claim.
36. As an operator, I want to see externally updated core versions and their qualification status, so that Barectl reports native state without downgrading it.
37. As an operator, I want to review soft rewrite-rule maintenance with its application-hook effects, so that I can refresh application routes without editing Nginx.
38. As an operator, I want to understand the limited effect of a default object-cache flush, so that I do not mistake a separate CLI request for live-site cache repair.
39. As an operator, I want to have shared or unverified cache targets refused, so that maintenance cannot clear another application's cache.
40. As a restricted Barectl account, I want to receive only the application views and actions my permissions allow, so that site or bootstrap access does not silently grant WordPress execution.
41. As an operator, I want to retain WordPress routing through certificate and native site workflows, so that HTTPS, challenge routes and the selected PHP socket stay consistent.
42. As an operator using an independent controller, I want to receive immediate native conflict refusal for competing changes, so that I can rediscover and review rather than rely on another device's local lock.
43. As an operator, I want to see that web requests, native updates and cron remain outside controller exclusion, so that I do not mistake a mutation lock for application-wide transaction isolation.
44. As an operator, I want to have malformed or secret-bearing application output withheld, so that operation results cannot disclose raw configuration or plugin debugging.
45. As an operator, I want to see implementation and qualification limits separate from release availability, so that I can choose only combinations with actual evidence.
46. As an operator, I want to have the existing generic PHP, PostgreSQL and TLS workflows continue working, so that adding WordPress does not remove previously supported operations.

## Implementation Decisions

- **D1.** Reuse the existing bootstrap, site, database, TLS, discovery, operation-lifecycle and dashboard boundaries. Add a WordPress application service with typed observations, immutable requests/plans and retained apply audit through preserving migrations. The existing adapters already supply the required seams; no speculative prefactor or second execution integration is needed.
- **D2.** The initial candidate pair remains WordPress 7.1.3 and WP-CLI 2.12.0. Qualify Ubuntu 24.04 with PHP 8.3/MariaDB 10.11 and Ubuntu 26.04 with PHP 8.5/MariaDB 11.8 on amd64 and arm64 separately. Additional PHP supply/branch combinations require their existing PHP gates and WordPress qualification; third-party PHP enablement is not a prerequisite.
- **D3.** WP-CLI preparation is a complete operator workflow using a separate immutable bootstrap review and native apply. Authenticate the versioned official PHAR against the approved primary signing identity or its valid bound signing subkey, then verify its pinned digest and protected installation. Refuse changed/invalid artifacts and unapproved key rotation. Native GPG owns authentication; no downloaded PHAR executes first.
- **D4.** WordPress runtime preparation is a separate complete workflow for the selected site branch, using the existing exact Ubuntu package transaction and pool verification. The fixed extension baseline includes MySQL, cURL, XML, mbstring, ZIP, GD and intl capabilities in both CLI and FPM. Preserve other sites and installed dependencies; no upgrade, repair, removal or third-party allowlist expansion is authorized.
- **D5.** WordPress is an application attached to one convention site, not a new server profile. Preserve site identity, native ownership, PHP branch/socket, MariaDB socket binding and certificate relationship. Introduce exact operative WordPress, canonical-name and provisioning-gate forms alongside historical generic PHP forms. Existing TLS and site workflows preserve the observed application form and branch.
- **D6.** Passive reconstruction uses bounded native metadata and server-side parsing of the supported configuration grammar, never application execution. Private configuration stays on the server; only non-secret projections and digests reach the controller. Fixed authorized catalog reads establish core schema and canonical options. Ordinary discovery never escalates or uses a cached fallback when evidence is unavailable.
- **D7.** Application evidence is independent of infrastructure evidence and distinguishes absent, candidate/unverified, partial, installed, blocked and unreadable states. Installed evidence requires matching operative configuration, a native binding, required core tables/columns and canonical options. Extra plugin tables in the same database may coexist without being read; first installation still requires a wholly empty database.
- **D8.** Report newer externally updated core versions with their qualification status. Installation, Finish and maintenance mutations require the exact qualified pair. Diagnostic execution against newer observed core is allowed only when the qualified tool supports its bootstrap/schema; otherwise retain passive evidence and refuse executable inspection. No automatic downgrade or runtime switch.
- **D9.** Installation targets one exact certificate-covered canonical HTTPS name at the root, with bounded title, administrator login and email. Reject credentials, nonstandard ports, query/fragment components, subdirectory installs, unsupported names and unsafe input. Alias redirects preserve the ACME route. Site/database/TLS prerequisites remain separately authorized workflows.
- **D10.** Installation preparation is read-only and yields an immutable refusal or review through the existing operation lifecycle. The review records exact tool/core/artifact intent, site identity/branch, URL, account metadata, file/schema/network effects, exposure changes, admission limits, verification and recovery responsibilities. No password or salt plaintext is recorded.
- **D11.** Admit only empty or exact known-placeholder application content, a wholly empty application database, inspectable safe ancestry/ownership, a complete site/binding, supported CLI/pool capabilities and verified HTTPS. Bind the review to native evidence, boot and monotonic deadline. Missing, changed, foreign or ambiguous evidence refuses dependent work rather than converting it.
- **D12.** Accepted application execution remains one finite transient systemd unit behind the established worker and pyinfra SSH connection. Revalidate under the shared nonblocking native mutation lock, preserving boot/deadline fencing, cgroup/renewal checks, native limits and no-replay reconciliation. No separate WP-CLI remote transport or persistent helper is introduced.
- **D13.** Root performs only trusted native configuration/publication. WP-CLI, WordPress, themes and plugins execute as the dedicated site identity with its explicit selected PHP CLI, controlled environment, private temporary location and fixed targets. Reject conflicting YAML/config/packages and unsafe runtime inputs. WordPress code never runs as root, including verification and recovery paths.
- **D14.** Bind acquired WordPress bytes to the maintained official archive URL, measured size and SHA-256 before safe native extraction. The native design owns literal pins and pre-download file/memory/staging limits. WP-CLI owns acquisition and core diagnostics; native hashing and archive tools own their established mechanics. Diagnostic checksum catalogs are distinct from immutable whole-archive admission and are not publisher signatures or malware scans.
- **D15.** Keep database access passwordless through the site identity's local MariaDB binding. Generate salts locally and retain them only in private operative WordPress configuration. The fixed public configuration wrapper directly bootstraps WordPress after loading private definitions, preserving the pinned WP-CLI bootstrap requirement. No secret-bearing source is transferred to the controller.
- **D16.** Verify a native provisioning gate before publishing application code or tables. Gate all application/PHP/setup routes while preserving ACME. Publication admits only positively identified absent resources or the reviewed placeholder, retains native preimages and avoids recursive ownership changes or overwriting arbitrary application content.
- **D17.** Verify schema, canonical options, core integrity and CLI/private-FastCGI access while publicly gated; then publish ready routing and verify HTTPS home/login and denial routes. After a serving failure, restore the exact gate only if current native bytes still match this run's ready candidate. Report restoration failure or uncertain exposure without erasing application data.
- **D18.** Generate an unpredictable initial WordPress administrator password as the site identity, feed it directly to the upstream installation prompt and discard plaintext. Suppress email notification and raw command output; no secret enters argv, environment, systemd text, journal, local records or browser responses. Completion requires terminal first-login password setup and makes no email-delivery assumption.
- **D19.** Separate execution outcome, postcondition verification and result availability. Check outcome inspects the original unit/invocation and never dispatches it again. Missing execution evidence uses the existing outcome-unknown acknowledgement fence. Active application operations protect server removal and finished audit survives removal like existing kinds.
- **D20.** A separate reviewed Finish workflow reconstructs eligibility from current native evidence without prior request records. Create only missing verified exact resources and the reviewed gate-to-ready transition. Compare first-install release files against a fresh copy of the same pinned archive, with private grammar/digest checks separately. Never replay core installation into partial tables, rotate salts, reset an administrator or delete content/database data.
- **D21.** Explicit WordPress inspection and integrity checks are complete dashboard operations. Fixed inventory covers installed/core state and bounded plugin/theme fields. Checksums distinguish match, mismatch and unavailable; private/custom packages and missing catalogs cannot become false trust or corruption claims. Diagnostic skip flags do not eliminate must-use plugin/drop-in execution, which the review discloses.
- **D22.** Validate and cap all application results before their journal/controller exposure, with at most 128 inventory items and one 16 KiB sanitized record. Retrieve only the exact unit/invocation's bounded typed native journal result. Missing/rotated output means result unavailable; systemd/cgroup evidence alone owns execution outcome. Suppression covers Barectl's command/result path, not intentional data disclosure by hostile application code.
- **D23.** Named maintenance supplies soft rewrite-rule flush with normal application route-registering hooks and bounded object-cache flush. It never edits Nginx or accepts arbitrary commands/flags. Default WordPress object cache is per request, so clearing a CLI request is not live-site/page-cache repair. No persistent cache provider is initially qualified; unknown/shared scope refuses. Review effects and revalidate relevant application inventory before mutation.
- **D24.** Separate application view, plan view/preparation, installation, executable inspection and maintenance permissions. Recheck active account and owning permission at endpoints, queue/dispatch, audit view, polling, reconciliation and acknowledgement. Existing site/database/TLS permissions grant no WordPress execution; prerequisite bootstrap plans retain their own permission contract.
- **D25.** Every implementation slice includes its necessary persisted records, service/endpoint behavior, custom dashboard flow, authorization, tests and operator guidance. Use the existing Django templates, USWDS palette, Vite assets and HTMX lifecycle. Avoid a final UI-only dependency, Django admin, frontend secrets, hidden prerequisite mutations and unqualified live-health claims.
- **D26.** Each slice demonstrates its own external behavior and passes required local repository checks plus affected native modules before push. The final qualification slice proves the complete published matrix, recovery/reconstruction, browser journey and exact-revision native statuses, documents omissions and keeps unqualified combinations disabled. Specification publication does not implement WordPress or release v0.4.
- **D27.** Reuse existing application services/native adapters, upstream WP-CLI commands, native GPG/hash/archive tools and established pyinfra composition. Custom work is limited to immutable admission, exact operative grammar, safe publication, permissions and bounded results. The native design and each slice record the specific upstream reuse gap before custom code is added.
- **D28.** The native lock coordinates cooperating controllers and guarded renewal. It does not stop web requests, ordinary administration, application cron or WordPress's native updater. Preserve native update/cron policy and explain ordinary patching/backup responsibility; no application-wide atomicity or hostile multi-tenant containment is promised.

## Testing Decisions

- Prefer the existing operator-workflow boundary as the primary seam: authorized dashboard request, application-service queue, worker/native execution, recorded outcome, refreshed server evidence and rendered operator result. Native coordination and credential safety require their existing lower boundary checks; no new parallel SSH or test-only execution seam is needed.
- A good test exercises a user-visible outcome, refusal, retained data or external execution boundary. Assert no unauthorized mutation, correct observed state and honest outcome/result distinctions. Do not test private helper structure, reproduce implementation logic or mock away the native boundary under qualification.
- Test bootstrap tool/runtime preparation, passive discovery, WordPress review/apply/Finish/inspection/maintenance services and their dashboard endpoints. Use focused validator/parser tests only where boundary rejection or bounded/secret-free output needs isolated adversarial coverage. Preserve migrations and enforce permission denials through direct and polled endpoints.
- Reuse the existing site journey tests for independent-controller reconstruction and missing-resource Finish, the hosting journey for dashboard-to-worker-to-HTTPS behavior, bootstrap coordination tests for alias/controller races and lost native outcomes, and TLS/browser fixtures for challenge/renewal and production/development browser behavior. Existing fake-server support serves local workflow tests; disposable-server tests prove native effects.
- Each slice has a complete demoable workflow and its own authorization, refusal, native effect, result and browser evidence where relevant. Add the operator guide as each workflow lands. Final qualification integrates these paths rather than postponing each slice's UI or verification until the last ticket.
- On both Ubuntu releases and both architectures, prove the pinned tool/core/runtime pair, authenticated PHAR, pinned archive, private temporary downloads, pre-download resource limits, safe extraction, selected CLI/FPM capability agreement and site-identity socket access. Refuse invalid signatures/checksums, wrong keys, contaminated caches, malformed archives and unsafe ancestry before downloaded code executes.
- Prove public provisioning gates throughout publication, private-FastCGI checks before ready routing, terminal password setup and HTTPS login/home/permalinks/query strings, canonical aliases, ACME/renewal preservation and config/private/uploaded-executable denial. Include post-ready failure and safe gate-restoration refusal; do not infer unobserved safe exposure.
- Fault each admission, gate, acquisition, configuration, publication, schema and serving boundary. Preserve existing files/tables/secrets and prove eligible Finish from an independent controller without the first controller's audit. Partial schema must refuse replay; no cleanup or compensation deletes user data.
- Use two independent controller databases, aliases and keys for conflict refusal, controller loss, original-run reconciliation, child/wrapper death, timeout and unknown outcome. Distinguish container restart from real kernel reboot evidence using the existing reboot harness; document unsupported/skipped environments explicitly.
- Passive discovery tests use malicious configuration that would signal if executed and verify no signal, escalation or raw-secret transfer. Executable inspection tests cover must-use plugins/drop-ins, hostile YAML/environment/output, exact site identity/CLI, malformed JSON and limit overflow. Check systemd metadata, process arguments/environment, native journal, local records, rendered HTML and error paths for Barectl-path credential disclosure.
- Integrity tests distinguish match, mismatch and unavailable, including newer unsupported core and custom packages. Maintenance tests prove soft rewrite uses normal registered routes, does not edit Nginx, refuses unverified cache scope and never claims a default CLI cache flush clears live-site caches.
- Run production-build and Vite-development Chromium journeys with the existing console-error checks, covering prerequisites, immutable review, installation/password guidance, inspection, maintenance, refusals, permissions, recovery and fresh-controller evidence. Keep existing generic PHP, PostgreSQL and TLS journeys green.
- Run all required repository gates and affected native modules locally before pushing implementation, then obtain full native statuses for the exact published revision. Record tested combinations, command/module evidence, failures and limits separately from issue labels or release publication.

## Out of Scope

Multisite, PostgreSQL adapters, subdirectory installations, imports, Git/Composer deployments, core/plugin/theme upgrades or replacement, activation/deactivation, deletion, URL migration, backups/restore, arbitrary commands/SQL/configuration edits, credential uploads or browser password transport, mail delivery, persistent/shared cache providers, containers, agents and a general configuration editor remain outside this milestone. Ordinary native administration and application security patching remain available with the operator's own backup/recovery process. Verified restore remains the roadmap's later milestone.

## Further Notes

- The operator requirements, native design and accepted ADRs form one contract. Changes to the native safety or application boundary require design review; runtime qualification and delivery checks remain separate evidence.
- The [native design](wordpress-native-design.md) owns literal resources, artifact pins, command/grammar constraints and publication/recovery details. It distinguishes upstream capability statements, observed artifact facts, Barectl policy and unproven runtime qualification. Consult its official source links rather than treating availability as compatibility evidence.
- GitHub Issues own implementation state and native blocking edges. Each ticket references this specification, its decision identifiers and the applicable native contract. Initial independent work is authenticated tool setup, selected-site runtime preparation and passive application discovery; installation review depends on those demonstrated prerequisites.
- Operator documentation develops with each workflow; the final qualification record owns tested revisions/environments/limits. Wiki navigation links to published owning documents. No issue closes because its specification exists, and this documentation task performs no production installation, application-data migration or release.
