# Native Node runtimes

This slice installs an exact supported Node LTS runtime on demand, selects a server default for future sites, and pins an existing site's runtime without changing other sites. It does not create applications, fetch source repositories, build applications, install application dependencies, or supply a deployment supervisor.

## Upstream reuse and authentication gap

[mise system installs](https://mise.jdx.dev/dev-tools/system-installs.html) support root-owned shared installations and `/etc/mise/config.toml`. [Its HTTP backend](https://mise.jdx.dev/dev-tools/backends/http.html) owns downloading, checksum checking and extracting an exact official archive. Absolute runtime paths avoid project configuration, shell activation and implicit installation when a service starts. The installer runs with a clean environment and root-controlled configuration outside application directories.

The [core Node backend](https://mise.jdx.dev/lang/node.html) verifies checksums and ordinarily GPG signatures, but explicitly accepts a missing signature. This does not meet Barectl's mandatory signature requirement. Its checksum lock can also bypass a fresh signature fetch. The HTTP backend supplies exact checksums but no mandatory GPG authentication. [node-build](https://github.com/nodenv/node-build#readme) verifies definition checksums and may compile source; [nvm](https://github.com/nvm-sh/nvm#readme) is a per-user shell tool. Neither removes this authentication and system-service gap.

The bounded bridge is the [Node project's verification procedure](https://github.com/nodejs/node#verifying-binaries): authenticate the release's signed `SHASUMS256.txt.asc` with native GPG and an explicitly reviewed upstream keyring, extract exactly one checksum for the official Linux architecture archive, and pass that checksum and fixed HTTPS URL to mise's HTTP backend. Missing signatures, unknown signing identities, revoked/expired signatures, duplicate or malformed checksum entries and changed artifact bytes refuse before runtime installation. The bridge does not extract or install a runtime itself. Node releases come only from `https://nodejs.org/dist/`; no source builds, alternate mirrors or user plugins are admitted.

The selected mise supply method is its [official verified-release download procedure](https://mise.jdx.dev/installing-mise.html#manual-download). Barectl pins mise 2026.10.6, the published signing fingerprint `24853EC9F655CE80B48E6C3A8B81C9D17413A06D`, signing-key SHA-256, and the exact Linux binary digest for each architecture. Native GPG authenticates the signed checksum document before the standard `install` operation publishes the binary. No downloaded installer script executes. The package alternative, extrepo plus APT, would require a separate approved source and exact package transaction; it is unnecessary for this documented upstream release method.

Node authentication uses the official active-key keyring at reviewed revision `481637f813e912c4aa3622d7964ab426c97b8e8d`, with SHA-256 `140f2ad5260fd62773b6243ce8e1d3009645d558f121b8262c55e383dc285932`. A fixed keyring and native signature-status checks reject new signing identities, revoked/expired signatures and missing signatures. The admitted exact LTS releases are 24.21.0 and 22.23.3. Both archives and the Node executable have fixed reviewed architecture-specific checksums; discovery does not execute an unknown Node or mise binary.

The HTTP backend's upstream namespace is `http-node`, distinct from core Node's `node`: installations live below `/usr/local/share/mise/installs/http-node/<version>`. The root installer uses a clean environment and `--no-config --no-env --no-hooks`; the explicit HTTP request carries the fixed official URL, checksum, archive layout and exact version. It cannot run application hooks, source builds or application-requested global npm packages. Mise owns downloading, checksum verification and extraction.

The common native-tool prerequisite is supplied through the existing reviewed bootstrap package operation. A single authorized runtime intent prepares and applies metadata refresh, native tools, then Node selection, checking the same SSH identity and permission at each stage. Existing discovery between operations is allowed to finish before continuation. A refusal stops the intent; there is no blind retry.

The signed archive supplies npm 11.19.0 with Node 24.21.0 and npm 10.9.9 with Node 22.23.3. Passive file-tree fingerprints were independently derived from the approved archives and matched between amd64 and arm64; this is supply-byte evidence, not amd64 execution qualification. The fixed verifier checks root ownership, file modes, file contents and symlink targets, and never invokes npm to inspect unknown bytes. Mise continues to own extraction and installation.

## Native authority and changes

The source of truth is root-owned native mise configuration, installed runtime directories and per-site `.node-version` files. Controller request/plan/run records are private audit records only. A fresh controller reads native configuration; cached observations are never fallback authority. Server defaults resolve to an exact patch release before review. Changing a default does not rewrite any site's pin or restart another service. The server command uses [dpkg update-alternatives](https://manpages.ubuntu.com/manpages/noble/man1/update-alternatives.1.html), with the standard `node` group and `/usr/local/bin/node` master link. Registration uses `--install` and explicit `--set` to select the exact reviewed executable. Discovery requires the root-owned alternatives state, both native links and mise configuration to agree. Foreign groups, real files or an existing distribution `/usr/bin/node` refuse; Barectl never overwrites them. Matching `npm` and `npx` links are native slaves of the same group, so all three ordinary commands select one exact authenticated archive. Foreign distribution commands, independent npm/npx groups and orphan links refuse. The bundled npm file tree and executable links must match the authenticated archive before their commands run or an existing installation is reused. Site changes preserve all application files, database state, routing and other units.

Each mutation uses the existing pyinfra SSH connector, db worker, transient systemd execution and shared mutation lock. Review captures the relevant native configuration and tool evidence; apply rechecks it under that lock. Root-owned paths and non-writable ancestry are prerequisites. Foreign configuration, symlinks, unsupported service layouts and concurrent changes refuse. There is no automatic rollback, runtime removal, pruning or self-update.

The fixed passive Python readers use isolated mode ([Python 3.12](https://docs.python.org/3.12/using/cmdline.html#cmdoption-I), [Python 3.14](https://docs.python.org/3.14/using/cmdline.html#cmdoption-I)), excluding the SSH user's working directory, user packages and `PYTHON*` environment from module lookup before inspecting privileged native state.

Server-default requests require the existing bootstrap preparation and application permissions. A site pin also requires the corresponding site preparation and application permissions. Requests and coordinator continuations check that scope; worker preparation, payload generation and admission refresh the requesting account's permissions before remote reads or submission. A prepared site pin cannot bypass revoked site authority through the generic plan application service.

## Qualification

The implementation must prove reconstruction without controller records, exact binaries on both supported Ubuntu releases, default changes preserving existing pins, scoped pin switching, signature/download failures before publication, lock conflict and drift refusal, and persistence after reboot. Supply, key rotation and architecture admission require recorded native evidence.

The final ten-method disposable-server module passed on each Ubuntu 24.04 and 26.04 aarch64 release, with no skips, in a 93-second run. It proves authenticated installation, ordinary unactivated `node`, `npm` and `npx` commands, matching defaults and per-site pins, preserved application files, fresh-controller reconstruction, one operator intent, missing-signature refusal, native drift refusal, unrecognized site-pin refusal, foreign npm-link preservation, modified bundled npm refusal, prepared-site permission revocation and a second controller's native lock conflict. Each passive Python helper also demonstrated the hostile working-directory/environment import without isolation and rejected it with its actual isolated command. Site-directory commands retained the global default while the displayed exact executable used the site's pin.

Seventeen local request/reconstruction/template/view tests and strict typing passed, including site authority denial, revocation and generic plan/run viewing scope. A separate real-kernel VM test reuses the existing reboot harness. It passed on Ubuntu 24.04 and 26.04 aarch64, one test per release with no skips in 387.001 and 439.504 seconds respectively, proving defaults, site pins, ordinary commands and fresh native reconstruction after a changed kernel boot ID. The runtime and harness source digests stayed unchanged throughout both runs. These are local candidate results; hosted CI, amd64 execution and release or delivery qualification remain unproved.

## Site pins and scope

An existing recognized native site root `/var/www/<identifier>` and its ordinary Linux site account are required. The selected exact patch version is published as root-owned mode 0644 `/var/www/<identifier>/.node-version`. Existing nonstandard files, writable ancestry or symlinks refuse. The pin records the runtime choice; the interface names its exact executable. This operation does not change any application service, process supervisor, build command or routing. A future Node application/service convention needs its own accepted design and qualification.

Ordinary `node`, `npm` and `npx` commands continue to use the server default, including from a pinned site's directory. Using a site's override requires its displayed exact executable. The pin does not activate a shell or rewrite commands automatically.
