# v0.1: Server connection and discovery

The original milestone remains below. Current discovery scope follows [ADR 0015](adr/0015-recognize-only-the-convention.md): exact convention recognition, individually blocked foreign resources and default-profile components. See [convention qualification](convention-qualification.md).

On 2026-10-10, [#345](https://github.com/rajandangi/barectl/issues/345) removed Ubuntu 24.04 support; Barectl supports Ubuntu 26.04 only. The Ubuntu 24.04 statements below record this milestone's original scope, not current support.

## User journey

1. Sign in and register a server by choosing an SSH alias configured on the controller host. See `docs/ssh-aliases.md`.
2. Establish host trust on the controller host before connecting. Unknown or changed keys block connection; the dashboard offers no trust bypass.
3. Test authentication and show a sanitized result.
4. Start a read-only discovery job and view progress without keeping the request open.
5. Review the timestamped inventory and warnings. Repeat from a new controller with its own database and authorized SSH access to rediscover the same supported configuration.

## Discovery contract

Record OS/release, architecture, CPU count, memory, filesystem capacity, relevant package versions, Nginx site files, PHP-FPM pools, and systemd service states. Each observation needs collection time and provenance. Missing permission, unsupported format, absent software, and connection failure are distinct outcomes. Do not read database passwords or application secrets into logs or snapshots.

Database and application-specific discovery should be added only where read permissions and parsers are established. Unsupported installations must appear as unsupported, not absent.

Barectl accounts, discovery requests, and attempt history are local application records. Discovery does not copy those records to the server or reconstruct them on another device. Only native server evidence determines observed state; saved observations remain explicitly stale when verification fails. The current controller worker owns discovery execution. See [the architecture](architecture.md#state-and-discovery) for planned native history inspection and management across devices.

## Acceptance criteria

- Anonymous users and users without inventory permissions cannot read server details.
- Unknown or changed host keys are rejected without a bypass checkbox.
- Failed authentication and timeouts produce actionable errors without credential exposure.
- Discovery runs through a durable job with queued, running, succeeded, and failed states.
- Restarting the worker gives interrupted jobs a defined recoverable outcome.
- Read-only operations install no packages and write no configuration on the target.
- Repeated successful discovery replaces the current snapshot without duplicate site records.
- Failed discovery preserves the last successful snapshot and labels it stale.
- Automated tests cover output parsing and failure cases; a disposable Ubuntu 24.04 VM proves the complete connection/discovery path.
- Reconnecting from a fresh application database reconstructs supported observed state without importing another installation's records or adding Barectl tracking records to the server.
- Removing a server requires a confirmed, CSRF-protected request, is refused during discovery, and deletes only Barectl's local records (`docs/ssh-connections.md#server-removal`).
- The dashboard is the only operator interface; Django admin is not installed. Operator accounts are created and passwords reset with terminal commands on the controller host, without public registration or email recovery.

Bootstrap, service restarts, site creation, remote secrets, saved SSH connection details beyond aliases, shared remote database support, native server history and job inspection, coordinated mutations across devices, and team credential sharing are outside this release.
