# SSH connections and discovery

> Phase A now supports [saved-address registration](saved-server-connections.md), immutable connection revisions and readiness checks through the existing worker and connector. Saved addresses use this computer's SSH agent with key search and forwarding disabled. Alias targets retain their supported configuration and also consult the controller-owned trust file, so revocation cannot be bypassed by selecting an alias. [ADR 0034](adr/0034-trust-a-fresh-host-by-confirming-its-fingerprint.md) records fingerprint confirmation for unknown saved-address hosts. The worker captures the presented public key before authentication; an editor confirms it against an independent provider fingerprint.

In the current release, Barectl connects to a managed server only from its worker, for discovery, for [plan preparation](#plan-preparation) and for [applying reviewed plans](#applying-reviewed-plans), using the SSH alias the server was registered with (`docs/ssh-aliases.md`). Credentials, connection settings and host trust stay on the controller host. Barectl never writes SSH configuration or credential key files. Saved-address fingerprint confirmation writes only the configured Barectl-owned trust file. Alias registration never writes trust.

Discovery attempts and their history belong to this Barectl application database. They are not native server history and are not written to the server. Another device can establish authorized SSH access and rediscover supported configuration with its own database; it cannot recover this installation's private attempt records. Future native history inspection, background server operations, and coordination across devices follow the [architecture requirements](architecture.md#state-and-discovery).

## Workflow

1. Registering a server, choosing a new alias for it, or pressing **Verify connection**, **Refresh observations** or **Retry connection check** queues a discovery attempt. The request returns immediately; it does not connect.
2. The worker claims the attempt and marks it running. It reads the SSH configuration again and resolves the alias.
3. It connects, verifies the server's host key against the controller's known_hosts files, then authenticates.
4. It reads the operating system release, architecture, CPU count, memory, root filesystem capacity, the component observations and the [sites](#site-observations) it recognizes, and publishes a snapshot and the attempt's outcome in one transaction. A successful refresh replaces the current snapshot; earlier attempts remain as history.

The server page polls while an attempt is queued or running and announces changes in a live region. **Verify connection** appears before the first check, **Refresh observations** after a success, and **Retry connection check** after a failure or interruption.

Attempts are stored separately from registrations and snapshots, with the states queued, running, succeeded and failed. Each attempt is a remote operation of the discovery kind: within one Barectl database, a server has at most one queued, running or reconciling remote operation of any kind, so repeated or concurrent requests share the active attempt, and a check cannot start while a plan preparation runs (the page says another remote operation is running and offers the check when it finishes). This constraint does not coordinate independent devices with separate databases. A failed or interrupted attempt does not remove earlier snapshots; the page shows the latest attempt and the latest snapshot separately, each with its alias and time, and notes that the snapshot may be out of date. Every registration edit and removal is refused while any remote operation is active. A connection correction creates an immutable revision and invalidates current verification and plans immediately; older observations remain labelled history of their original target and revision, excluded from current inventory and actions. A failed correction check retains that correction. Name-only saves queue no SSH work. Edit revisions prevent conflicting forms from overwriting each other. Forcing the worker to stop mid-task marks its attempt as interrupted. An attempt abandoned any other way, such as by killing the worker, is recovered as interrupted once it has been active for ten minutes; every read of attempts performs this recovery first (the server list and page, polling, the Activity page and the removal page), as do requesting a check and the worker's next task. Recovery keeps any previous snapshot, and the operator retries manually. Finishing filters on still-running attempts, so a stale worker cannot overwrite the recovery or a newer result. There is no automatic retry, scheduled discovery or live monitoring.

## Server removal

An operator with the `servers.view_server` and `servers.delete_server` permissions removes a server from its page. **Remove** opens a confirmation page, and only its CSRF-protected **Remove server** button deletes anything.

- Removal deletes the server's registration, its discovery attempts and snapshots, its plan preparations and their plans, and the worker's task records for those operations, all from the Barectl database. Finished apply runs are kept as audit with the server detached; they keep their own copies of the server name, alias, reviewed host key and boot, requester and plan details, and stay listed in Activity. The removal page counts plan preparations only for accounts that may review plans. A task record that a running worker claimed within the last ten minutes is kept, since that worker saves it when it finishes.
- It never connects to the server and never touches the controller's SSH configuration, keys, agent or known_hosts. The alias can be registered again.
- It is refused while a remote operation of any kind is queued, running or reconciling. Operations protect their server in the database, so a request that queues discovery while removal is in progress makes the removal fail and roll back, and a request that queues discovery after removal finds the server gone. Abandoned attempts are recovered first, so they do not block removal.
- An edit submitted after removal is refused rather than registering the server again.

## Running the worker

The worker is a separate process from the same application, using the Django tasks framework with the database backend from `django-tasks-db`. Queued work is stored in the application database and survives the request that created it. Discovery requires this controller worker and does not continue as a background server job if the controller stops.

```bash
uv run --env-file .env python manage.py db_worker
```

Run it as the controller account whose SSH configuration, keys and agent Barectl should use. If authentication relies on an agent, start the worker with that agent's `SSH_AUTH_SOCK`. Without a running worker, attempts stay queued and the server page says so.

## Host trust

Barectl reads the files named by the alias's `UserKnownHostsFile`, or `~/.ssh/known_hosts` and `~/.ssh/known_hosts2`. Missing files are ignored. The host name looked up is the resolved `HostName`, written as `[host]:port` when the port is not 22, as OpenSSH records it.

- Supported: plain and hashed host names, several key types per host, and `@revoked` lines. A revoked key is refused for every host, even when another line lists it.
- A key that is not listed is **unknown**: the connection is refused before authentication and the key is not recorded.
- A listed host that presents a different key is **changed**: the connection is refused before authentication.
- Not supported, so such servers are treated as unknown: `@cert-authority` host certificates, host patterns with wildcards or negation, `GlobalKnownHostsFile` and `/etc/ssh/ssh_known_hosts`, and `CheckHostIP`.
- `StrictHostKeyChecking` is ignored. Barectl always refuses unknown and changed keys and offers no bypass.

For an SSH alias, establish trust outside Barectl by comparing the key fingerprint with the server's console or provider before adding it to a configured trust file.

### Confirming a fresh saved-address host

An unknown host stops the worker check before authentication. Overview shows the captured key type and SHA256 fingerprint. Read the fingerprint independently from the provider console, serial console output, or provider web shell. For example, `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` prints the ED25519 host key fingerprint. Select the host key file for the displayed key type. Copy only its `SHA256:...` fingerprint into **Provider host key fingerprint**, then choose **Confirm fingerprint and check**.

The input must match exactly. A malformed value, another key's fingerprint or surrounding whitespace records nothing. The confirmation requires `servers.view_server`, `servers.change_server` and `discovery.add_discoveryattempt`, a CSRF-protected POST and the current saved connection revision. Browser input cannot supply the endpoint, public key or trust-file path. The failed attempt stores those public key facts and its immutable connection definition.

Confirmation serializes updates with an adjacent controller file lock, rereads trust under that lock and atomically replaces only the Barectl-owned file while preserving unrelated entries. A changed or revoked key refuses confirmation. A matching existing entry needs no write. Registration changes and active operations refuse confirmation. The queued follow-up captures the confirmed public key. At dispatch it rereads current trust and revocations, requires that exact key to remain trusted, and gives the strict connector a private trust copy containing only the confirmed identity for the endpoint. Replacing both the server key and trust-file entry still refuses authentication. Each controller confirms independently. Removing a registration leaves trust untouched.

The fast layer proves this path through real in-process SSH negotiation and Django requests. Native S1 and second-controller S5 qualification belong to the later Phase A scenario tickets.

## Authentication

Barectl uses only public-key authentication, with no password or keyboard-interactive prompts. Saved connections select the controller agent or an [approved key-file reference](saved-server-connections.md#approved-key-files). File mode binds its selected public and file identity and disables agent and default-key search. The following credential rules apply to advanced aliases.

- Keys in the SSH agent named by the worker's `SSH_AUTH_SOCK`.
- The alias's `IdentityFile` keys, or when it names none, the default `~/.ssh/id_rsa`, `~/.ssh/id_ecdsa` and `~/.ssh/id_ed25519`.
- A key file with a passphrase works only when the key is loaded in the agent. Barectl never asks for or stores a passphrase.
- The user is the alias's `User`, or the worker account's name.

An alias that uses any of these settings is not offered for registration, and a registered alias that gains one is refused when connecting, because Barectl's connection does not implement them: `ProxyJump`, `ProxyCommand`, `HostKeyAlias`, `IdentityAgent`, `IdentitiesOnly yes`, `CertificateFile`, `PKCS11Provider` and `SecurityKeyProvider`. Values that select OpenSSH's default behavior, such as `ProxyJump none`, are accepted. `UserKnownHostsFile` paths must not contain `%` tokens. Hardware-backed keys have not been verified.

## Bounds and read-only commands

Connecting, the SSH handshake and authentication each time out after 10 seconds, and each command must finish within 15 seconds, however steadily it writes output. All commands on one connection must finish within 5 minutes, so an attempt ends well before recovery would treat it as abandoned; a longer one fails, keeping any previous snapshot. Command output is read up to 64 KiB. Commands run without a terminal, environment variables or `sudo`, with the SSH user's own permissions. Discovery installs nothing and writes nothing on the server.

A target-stack site observation reads each site's live PHP protection evidence in its own bounded command, because one verification is far below the 15-second limit while several bundled into one command are not. The target-stack site read therefore runs one inventory command for the whole convention and one command per site that has a serving master, and reports a site whose per-site read fails as outside supported settings rather than as healthy.

The operating system observation runs `cat /etc/os-release`, falling back to `/usr/lib/os-release` as the [os-release specification](https://www.freedesktop.org/software/systemd/man/latest/os-release.html) describes. When `cat` fails, `test -e` and `test -r` distinguish a missing file from an unreadable one, whatever the server's language. Only `PRETTY_NAME`, `NAME`, `ID` and `VERSION_ID` are kept, unquoted with Python's `shlex` and length-limited. The snapshot records the file read and the collection time.

Capacity observations use the same bounds and permissions:

- `uname -m` reports the machine hardware name, such as `x86_64` ([uname invocation](https://www.gnu.org/software/coreutils/manual/html_node/uname-invocation.html)).
- `nproc` reports the processing units available to the SSH session, which can be fewer than the server has; the page labels them as available ([nproc invocation](https://www.gnu.org/software/coreutils/manual/html_node/nproc-invocation.html)).
- `cat /proc/meminfo` reports memory; only `MemTotal` in `kB` is kept and stored in bytes ([proc filesystem](https://docs.kernel.org/filesystems/proc.html)). When `cat` fails, `test -e` and `test -r` distinguish a missing file from an unreadable one.
- `df -B1 --output=size,avail,target /` reports the root filesystem in bytes; only its size and available space are kept ([df invocation](https://www.gnu.org/software/coreutils/manual/html_node/df-invocation.html)).

Observation outcomes are defined in the [glossary](../GLOSSARY.md). The snapshot records each observation's source and the collection time. A source is the commands or files whose results decided the observation's outcome, in the order they were read; the page shows each one. Memory and filesystem sizes are stored in bytes and shown with human-readable units plus byte counts. A command the shell cannot find (exit status 127) is unsupported and one it cannot run (126) is inaccessible, as the [POSIX shell](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html#tag_19_08_02) defines; any other failure is unsupported. A missing inspection command or file is never a finding that something does not exist.

Every server has an operating system, an architecture, CPUs, memory and a root filesystem, so these observations are never absent; the database refuses a snapshot that records one as absent.

| Outcome | Meaning |
| --- | --- |
| Observed | The file or command reported the observation in a supported format. |
| Inaccessible | The file exists but the SSH user cannot read it, or the command exists but the SSH user cannot run it. |
| Unsupported | The file or command does not exist on the server, could not be read, or did not report a supported format. |

A completed attempt with an inaccessible or unsupported observation still succeeds; the snapshot shows the warning. Missing observations never appear as zero values.

## Component observations

For each supported web-stack component — Nginx, PHP-FPM, MariaDB, PostgreSQL and Certbot — the snapshot records a component observation: the installed package versions from the server's dpkg database and the state of its systemd service units. Each installed package is judged against the exact package names of the server release's [bootstrap profile](bootstrap.md#what-the-profiles-install): a package set that follows a profile is observed as managed however it was installed, and a versioned or variant package, PostgreSQL major or cluster outside the profile is named as not following it, with what to remove or change. Both observations use fixed read-only commands with the SSH user's own permissions: no sudo, no package installation, no service restarts, no configuration writes, and no database credentials or application secrets. The observation commands are bounded by the same timeouts and output limits as every other discovery command.

Versions come from one dpkg database query of the release bootstrap profiles' exact package names. On Ubuntu 26.04 it is:

```text
dpkg-query -W -f='${Package} ${Version} ${db:Status-Abbrev}\n' 'certbot' 'mariadb-server' 'mariadb-server-core' 'nginx' 'php8.5-fpm' 'postgresql' 'postgresql-18'
```

A second bounded dpkg inventory query reads only installed names and states to name conflicting variants. It never obtains their versions, queries their units, or reads their configuration. Service states come from one `systemctl show` query per component, reading `Id`, `LoadState`, `ActiveState`, `SubState` and `UnitFileState` for its units. A missing systemd unit is reported as `not found`; a loaded unit is shown as `active (running)`, `inactive (dead)` and so on, with the unit file state such as `enabled` when systemd reports one.

These installation formats and service names are supported, based on the parsers and the transport results recorded from Ubuntu 26.04:

| Component | Installed packages match | Service units queried |
| --- | --- | --- |
| Nginx | `nginx` | `nginx.service` |
| PHP-FPM | The release default profile, `php8.5-fpm` | Only the release default unit, `php8.5-fpm.service` |
| MariaDB | `mariadb-server` and `mariadb-server-core` | `mariadb.service` |
| PostgreSQL | the release default major's packages, `postgresql` and `postgresql-18` | `postgresql.service`, then the release default major's `main` cluster: `postgresql@18-main.service` |
| Certbot | `certbot` | `certbot.timer` |

Behavior on other servers:

- Only dpkg installations are supported. When `dpkg-query` is missing or its output cannot be parsed, every component's package observation is **unsupported**, never absent: Barectl cannot know whether the software is installed. When the SSH user cannot run `dpkg-query` (exit status 126), the observations are **inaccessible**.
- A package counts as installed when its dpkg state is installed: status `ii`, `hi` for a package held with `apt-mark hold`, or either with the `R` reinstall-required flag. Packages that apt merely knows about, such as the `php-fpm` metapackage on a server that installed `php8.5-fpm`, and packages removed with only configuration files left (`rc`) are never reported as installed.
- A matching package in an unfinished dpkg state, such as unpacked (`iU`) or half-configured (`iF`), makes the component's package and service observations **unsupported**: the software may be partly present, so it is neither reported as installed nor as absent.
- Installed packages are compared with the exact names of the server release's bootstrap profile. A set that follows the profile is managed, whoever installed it; a versioned or variant package outside the profile, such as `php8.1-fpm`, is named as a deviation with what to remove or change. Its version, unit and configuration are not read. An unsupported release queries the supported release's finite names; that inventory does not qualify the server release.
- When `systemctl` is missing, fails (for example `System has not been booted with systemd`), or reports unknown state tokens, the service observation is **unsupported**, never absent. Querying it requires systemd's D-Bus interface, which stock servers provide and unprivileged accounts may read.
- Units are queried only for components with an installed package. Otherwise the service observation takes the package observation's outcome, with the dpkg query as its source and the same warning: **absent** when no package is installed, and unsupported or inaccessible when the dpkg database cannot be read.
- A missing unit appears as `not found`. A unit whose reported states do not match the supported tokens, or that systemd reports under a name other than the one queried (an alias resolving to another unit), makes the service observation **unsupported** rather than showing invented states.
- PHP-FPM discovery queries only the release-default unit. Other PHP package names are conflict evidence only; their units and pool trees are not inspected.
- PostgreSQL's units are found as the next section describes.

Package and service observations are stored per component with their own outcome, source commands and warnings, and the collection time of the snapshot. A component can report versions while its service state is unsupported, and the other way around. A service observation stores each service unit's name, load state, active state, sub-state and unit-file state as systemd reports them; the page shows them as one line per unit, such as `nginx.service active (running), enabled`.

## PostgreSQL clusters

On Debian and Ubuntu, `postgresql.service` is an umbrella unit. It stays `active (exited)` while the clusters it started run or stop. Each cluster runs as an instance of the `postgresql@.service` template named after its version and cluster name, such as `postgresql@18-main.service`. Barectl supports only the server release's default major and its `main` cluster. When the dpkg database shows PostgreSQL installed, it lists the configuration layout, reports any other major or cluster as not following the profile, and queries the umbrella unit and the release default major's `main` cluster's unit after it, in the same `systemctl show` query, so a stopped cluster appears as `postgresql@18-main.service inactive (dead), enabled-runtime` under an `active (exited)` umbrella. No other major's or cluster's directory is read and no other cluster's unit is queried.

What upstream defines:

- postgresql-common keeps each cluster's configuration in `/etc/postgresql/<version>/<cluster>/`. A cluster is such a directory holding `postgresql.conf`, as an existing file or a dead symlink. Version directories are named like `16` or `9.6`; other entries of `/etc/postgresql` are not versions. The `postgresql-common` package installs `/etc/postgresql` itself ([`PgCommon.pm`](https://salsa.debian.org/postgresql/postgresql-common/-/blob/master/PgCommon.pm), [`postgresql-common.dirs`](https://salsa.debian.org/postgresql/postgresql-common/-/blob/master/debian/postgresql-common.dirs)).
- `pg_createcluster` accepts cluster names made of word characters, `.` and `-`, and advises against `-` because it breaks the template's `%I` path in systemd ([pg_createcluster](https://manpages.debian.org/stable/postgresql-common/pg_createcluster.1.en.html)).
- Its systemd generator adds each cluster whose `start.conf` says `auto` to the umbrella unit's wants, so systemd loads those clusters' units. `manual` and `disabled` clusters are not wanted and stay unloaded until something names them ([`README.systemd`](https://salsa.debian.org/postgresql/postgresql-common/-/blob/master/systemd/README.systemd), [`postgresql-generator`](https://salsa.debian.org/postgresql/postgresql-common/-/blob/master/systemd/system-generators/postgresql-generator)).
- A literal unit name refers to exactly one unit, while a glob such as `postgresql@*` matches only units currently in memory ([systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)). On Ubuntu 26.04, `systemctl show` with the name of an unloaded cluster's unit reports it, such as `inactive (dead), disabled` for a `manual` cluster.
- `pg_lsclusters` lists clusters from the same directories, but it skips a directory it cannot open without reporting an error, and its status column reads the cluster's socket and data directory ([pg_lsclusters](https://manpages.debian.org/stable/postgresql-common/pg_lsclusters.1.en.html)).

What Barectl does, with the SSH user's own permissions and no database connection, credentials or data directory access:

```text
ls -1b /etc/postgresql
ls -1bA /etc/postgresql/<release major>
test -e /etc/postgresql/<release major>/main/postgresql.conf
```

Barectl lists the configuration directories itself and does not run `pg_lsclusters`; a directory it cannot read is reported, never treated as empty. It lists `/etc/postgresql` to name other majors and the release default major's directory to name other clusters, but it never lists another major's directory below that. The release default major's directory is listed with `-A`, as postgresql-common reads names starting with `.` too. The `main` cluster's unit is named in the query, loaded or not, as the generator names it: `postgresql@<release major>-main.service`. When `postgresql.conf` is not found, `test -L` accepts a dead symlink. Entries of `/etc/postgresql` not named like a version are ignored, as postgresql-common ignores them. The service observation's source records the listing commands, then the unit query.

Supported cluster names are 1 to 64 ASCII letters, digits, `_`, `.` and `-`. Version directories follow postgresql-common's pattern, at least two digits with an optional dot between them, such as `16` or `9.6`, bounded to four digits on each side of the dot. Other names are never used in a command, a unit name or a warning; unknown cluster names are skipped and counted, and a supported name other than `main`, and every version other than the release default major, is reported as not following the profile.

| Outcome | Meaning |
| --- | --- |
| Observed | `/etc/postgresql` and the release default major's directory were listed and the `main` cluster checked. The umbrella unit and, when `main` exists, its unit are shown. Another major or cluster is reported as a deviation, not scanned. |
| Inaccessible | The SSH user cannot list `/etc/postgresql` or the release default major's directory. The umbrella unit is still shown. |
| Unsupported | `/etc/postgresql` does not exist or a listing could not be read. The umbrella unit is still shown. |

A listing Barectl could not complete is never absent: Barectl cannot tell whether other clusters exist. A cluster whose unit systemd reports as `not found` is shown as `not found`. The cluster unit is checked like every other unit: a record under another name, or in an unsupported format, makes the observation unsupported. When systemd cannot be queried, the observation is unsupported or inaccessible as for other components, and its warning also names the listing problem.

The [convention qualification record](convention-qualification.md) describes fresh-process reconstruction of all states with independent controller databases and keys.

## Site observations

A site observation recognizes one PHP site that follows the [native site convention](site-conventions.md) from native evidence alone ([ADR 0015](adr/0015-recognize-only-the-convention.md)). Discovery renders the convention's expected files and account attributes for a candidate identifier and compares them byte for byte with native evidence; it does not interpret a foreign layout. Only accounts with the `discovery.view_siteobservation` permission see the **Sites** section of a server page, in the page and in its polled fragment; Activity and discovery history never list site warnings. Other accounts still see the rest of the snapshot.

Site observations follow the Nginx package observation ([ADR 0001](adr/0001-configuration-observations-depend-on-package-observation.md)): when Nginx is absent, unsupported or inaccessible in the dpkg database, the site collection takes that outcome and reads nothing. The convention depends on the release's default PHP version, so on a server that is not a supported release the collection is unsupported. When `sites-enabled` could not be listed, the collection takes that failure's outcome and warning.

### Candidates

Names only locate candidates. A candidate is every identifier `<id>` (3 to 24 lowercase ASCII letters and digits, starting with a letter) that names an entry `<id>.conf` in `/etc/nginx/sites-available` or `/etc/nginx/sites-enabled`, except the reserved `www` and `html`. An enabled Nginx site file that is neither the distribution's `default` nor a candidate is reported once as **not following the convention**, by file and with the server names it declares, and nothing else is read from it. A pool file without a corresponding Nginx candidate is reported once by file, without reading its contents. At most 50 candidates, in name order, are inspected; a warning names the cap.

### What recognition reads

Every command is a fixed, read-only command run with the SSH user's own permissions, bounded like every other discovery command; only validated identifiers and the convention's paths appear in them, shell-quoted. Recognition lists the three Debian directories and, for each candidate, reads the site's paths, link, files and account:

```text
ls -1b /etc/nginx/sites-enabled
ls -1b /etc/nginx/sites-available
ls -1b /etc/php/<default-version>/fpm/pool.d
stat -c '%n %f %u %U %g %G %h' -- <the candidate's convention paths>
readlink /etc/nginx/sites-enabled/<id>.conf
cat /etc/nginx/sites-available/<id>.conf
cat /etc/php/<default-version>/fpm/pool.d/<id>.conf
getent passwd s<id>
getent group s<id>
id -G s<id>
getent shadow s<id> | cut -d: -f2 | cut -c1
```

The paths are the enabling link, the source file, `/var/www/<id>` with its `public`, `private` and `.ssh`, the pool file and the socket. A site file that declares the convention's HTTP-01 challenge location costs one more `stat` of `/var/lib/letsencrypt/<id>`, its webroot. The shadow read runs only when `test -r /etc/shadow` succeeds, and keeps one character of the password field, never the hash. Once per discovery, when there is a candidate, discovery also reads `/etc/login.defs` for the normal accounts' UID range and `test -r /etc/shadow`.

No main configuration is read beyond the packaged include: `nginx.conf`, `php-fpm.conf`, `/etc/nginx/conf.d` and `/etc/nginx/fastcgi.conf` are not read, and no include inside a site or pool file is followed. A foreign enabled file is read only for its declared `server_name` values. `stat` describes a path without following a symbolic link, and its raw mode (`%f`) gives the file type and permission bits whatever the server's language. A path `stat` does not describe is checked with `test -e` and `test -L`: it is absent when neither sees it and its nearest existing ancestor can be searched, and inaccessible otherwise. `getent` exits with status 2 when the account database has no entry, which is an absent user.

### One state per site

Recognition derives the values the convention fixes for the identifier: the Linux user, paths, document root, FastCGI socket, pool name, and certificate paths. Each site observation carries exactly one state:

| State | Meaning |
| --- | --- |
| Managed | Every convention resource exists and matches. A hand-made site that follows the convention is managed. |
| Partly applied | Every existing resource matches and some are absent. The observation lists the missing paths; a reviewed plan can finish the site ([creating a PHP site](sites.md)). |
| Changed outside Barectl | A convention candidate exists and at least one existing resource differs. The observation names the first differing file and offers the content Barectl expects there, with no per-difference list. The site is locked until it matches again. |
| Not following the convention | An enabled Nginx site file that is neither the distribution's `default` nor a candidate, or a pool file that is not a candidate. The file is named, with a site file's declared server names only. |

A resource the SSH user cannot read or see, or one Barectl cannot interpret, keeps its own outcome (inaccessible or unsupported) and is not reported as drift or changed. Barectl does not use sudo.

### Stored and shown

Site observations are stored one row per site, with the state, the named file, the expected content and the missing paths ([ADR 0003](adr/0003-store-discovery-snapshots-in-typed-columns.md)); a refresh replaces them like every other observation. Sites added, edited or removed by the server's administrator show on the next discovery, and a foreign file fixed by hand into the convention is recognized on the next discovery. The server page shows one state per site, the named file or resource for blocked and changed sites, and the expected content for a changed file. Barectl never adopts, changes or removes a foreign site or pool.


## Site database observations

Each site observation records the site's optional database binding: what MariaDB's and PostgreSQL's catalogs hold under the site's principal name `s<id>` ([database convention](site-conventions.md#database-convention)). It is shown as the **Database** entry of the site in the **Sites** section, to the same accounts, and is not counted in whether the site matches the convention. A snapshot collected before Barectl observed bindings shows that it was not collected by that version.

Catalogs are readable only by the database administrators, and ordinary discovery never escalates. Discovery reads them only when `id -u` reports that the SSH identity is root; any other identity, including one with sudo, sees each binding as inaccessible, with a warning that an account allowed to prepare database plans can run a [privileged database inspection](databases.md#privileged-inspection). Root reads, without a password and without writing anything:

```text
id -u
mariadb --no-defaults --protocol=socket --socket=/run/mysqld/mysqld.sock --user=root -N -B -e '<catalog reads>'
runuser -u postgres -- psql -X -A -t -q -v ON_ERROR_STOP=1 -h /var/run/postgresql -p 5432 -d postgres -c '<catalog reads>'
runuser -u postgres -- psql -X -A -t -q -v ON_ERROR_STOP=1 -h /var/run/postgresql -p 5432 -d s<id> -c '<public schema read>'
```

One MariaDB and one PostgreSQL read cover every candidate site; the names in them are the validated principal names, and every query is ordered. MariaDB's read lists the unix_socket plugin's status; each `mysql.global_priv` account named `s<id>`, with its plugin, whether its authentication string is empty, its global privileges, its resource limits and its setting names; the site database's character set and collation from `information_schema.SCHEMATA`; every `mysql.db` row of the account, and of any other account whose database pattern matches the name; the account's database privileges from `information_schema.SCHEMA_PRIVILEGES`; how many `tables_priv`, `columns_priv`, `procs_priv`, `roles_mapping` and `proxies_priv` rows the account holds; and how many rows of other accounts in those tables name its database, its role or it as a proxied user. PostgreSQL's read lists the server's version, data directory and `hba_file`, and whether it loaded its configuration after `pg_hba.conf` last changed; the role's attributes from `pg_authid`, with whether it has a password or expiry; how many `pg_auth_members` rows name it; the database's owner, encoding, locale provider, locale, ACL and connection settings; how many `pg_db_role_setting` rows belong to the role, and how many to the database; its `pg_shdepend` dependencies by database, catalog and kind; and each rule `pg_hba_file_rules` reports, by rule number, with its file, line, type, databases, users and method, and whether it has options or an error. The public schema of a site database is read only when the database otherwise matches the convention, accepting connections. No password hash, authentication string, alternative authentication method's value, `pg_hba.conf` option or error text is selected, since options may hold an LDAP bind password or a RADIUS secret; `mariadb` reads no option file.

An engine whose packages the component observation does not list holds nothing. A catalog is inaccessible when its engine's service (`mariadb.service`, or the release default's `postgresql@<major>-main.service`) is not running, and unsupported when the read fails, answers in another format, or port 5432 is served by another cluster than the release default's `main`.

The recognition of each engine's rows is the one database plans use:

| Engine | A satisfied binding |
| --- | --- |
| MariaDB | One account `s<id>@localhost` authenticating by unix_socket alone, with an empty authentication string, no global privileges, no resource limits and no settings beyond MariaDB's own; no other host for the name. A database `s<id>` using `utf8mb4` with `utf8mb4_unicode_ci`. One `mysql.db` row of the account, on its own database, holding exactly `SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP, REFERENCES, CREATE TEMPORARY TABLES, LOCK TABLES` without grant option, and no other grant of the account. The unix_socket plugin is active. |
| PostgreSQL | A role `s<id>` with `LOGIN` and `INHERIT` and none of `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION` or `BYPASSRLS`, no connection limit, password or expiry, and no role memberships or stored settings. A database `s<id>` owned by it, `UTF8` with the libc locale provider and a collation and character type equal to each other and among the convention's locales, not a template, accepting connections without a limit, whose ACL grants only the owner's own `CTc` and whose public schema, owned by `pg_database_owner`, grants PUBLIC nothing. The role owns nothing outside its database. The server loaded `pg_hba.conf` after it last changed, and the loaded rules are exactly the supported release's distribution `pg_hba.conf`: no error and no options, peer for local connections, and no rule Barectl did not expect. |

A name is absent in an engine that holds no account, role or database under it and no grant of it. Another account's grant that reaches the name, such as a MariaDB database pattern like `s%`, is no binding of the site; a binding it reaches is reported as not following the convention, without naming the foreign account or listing differences. The convention's statements that took effect in their order, and nothing else, make a **partial** binding, whose warning names the missing statements: the principal; then the database; then the privileges, or for PostgreSQL PUBLIC's database rights; then, for PostgreSQL, PUBLIC's rights on the public schema. Any other state of a principal or database named like the site, such as a password fallback, another collation, a data directory entry MariaDB lists as a database, an owner other than the role, a site database without a usable public schema, or a `pg_hba.conf` that is not the distribution's, is shown as **not following the convention**, with no list of differences.

A site's binding is:

| Outcome | When |
| --- | --- |
| Absent | Neither installed engine holds anything under the name. |
| Observed | One engine holds it. It **matches the convention** only when it is satisfied, the site user was observed as the convention requires, the other engine was read or is not installed, and no other account's grant reaches the name. |
| Inaccessible | No engine holds it, and an installed engine's catalog could not be read for lack of privilege or because its service is not running. |
| Unsupported | Both engines hold it, since a site has at most one binding, or no engine holds it and a catalog read failed. |

From the catalogs, discovery keeps the engine, principal, database, owner, authentication method, privileges, character set or encoding, and collation or locale. Database observations are stored in their own table, one row per site observation.

## Site application observations

Each site observation also records the site's WordPress application evidence, shown as the **WordPress** section of the site page to accounts with `discovery.view_siteapplicationobservation` (and the site permission). It is independent of the site's state: a missing or edited application never changes whether the site is managed. The site file's recognized application form and canonical name are part of the site observation, since they are Nginx configuration.

Every read is bounded and read-only, uses only the SSH user's permissions and runs only for a candidate with an identifier:

```text
id -u
ls -1bA /var/www/<id>/public
ls -1bA /var/www/<id>/private
stat -c '%n %f %u %U %g %G %h' -- /var/www/<id>/public/wp-config.php /var/www/<id>/private/wp-config.php
python3 -I -c '<fixed script>' <id>
mariadb --no-defaults --protocol=socket --socket=/run/mysqld/mysqld.sock --user=root -N -B --init-command='SET SESSION TRANSACTION READ ONLY' -e '<schema read>'
mariadb ... -e 'SELECT option_name,LEFT(option_value,201) FROM `s<id>`.`wp_options` WHERE option_name IN (...) ORDER BY 1'
```

The `stat` runs only for a file that the listing names; the script runs only when the user is root and the site holds WordPress files, private configuration or WordPress routing; one schema read covers every MariaDB site database, and the options read runs only for a database whose core tables and columns are complete. A user other than root reads nothing beyond the listings and the file metadata its permissions allow, and the application is unreadable with the reason. [Passive application discovery](wordpress.md#passive-application-discovery) describes the states and the script. Application observations are stored in their own table, one row per site observation, holding states, the version literal, the configuration digest, the canonical options and the blocked and unread findings, never a secret.

## Database plan preparation

A PHP driver plan ([site databases](databases.md#php-database-drivers)) runs every read a package profile's preparation runs below, for the driver's packages, the release's `php<version>-fpm.service` and the PHP trees, and adds:

- `/usr/sbin/php-fpm<version> -m`, when the driver is installed, which lists the modules PHP-FPM loads and writes nothing;
- `apt-cache madison php<version>-mysql` or `-pgsql`, when the driver is missing, to find whether a source offers it at the installed `php<version>-common` version, which the simulation then requests;
- as root or through noninteractive sudo, the site preparation's reads of the configuration trees ([site preparation](#site-preparation)): the listing with owners, modes, links and devices, the MD5 digests, and the candidate site and pool files' bytes, besides the packages' configuration files and ucf's registry.

A database plan ([database bindings](databases.md#database-bindings)) runs a site plan's reads for the site, the engine's profile's preparation reads, including its readiness check, a driver plan's reads for the engine's PHP driver, and the dpkg state of the other engine's server package. Then, as root or through noninteractive sudo of each fixed script under `/usr/bin/sh -c`:

```text
c(){ echo '== mariadb'; mariadb --no-defaults --protocol=socket --socket=/run/mysqld/mysqld.sock --user=root -N -B -e '<catalog reads for s<id>>'; [echo '== postgresql'; runuser -u postgres -- psql ... -d postgres -c '<role and database named s<id>>']; } 2>/dev/null; c
c(){ echo '== postgresql'; runuser -u postgres -- psql ... -d postgres -c '<catalog reads for s<id>>'; runuser -u postgres -- psql ... -d postgres -c '<template1's encoding and locale>'; runuser -u postgres -- psql ... -d s<id> -c '<public schema read>'; [echo '== mariadb'; mariadb ... -e '<account, database and grants named s<id>>']; } 2>/dev/null; c
if [ -e /var/www/<id>/dbprobe-<token>.php ] || [ -L /var/www/<id>/dbprobe-<token>.php ]; then echo present; else echo absent; fi
```

The first form is a MariaDB plan's, the second a PostgreSQL plan's. The catalog reads are discovery's ([site database observations](#site-database-observations)), each ordered so an unchanged catalog reads as the same bytes; the public schema read prints nothing while no database `s<id>` exists, and the other engine's part runs only when its server package is installed. The plan records the SHA-256 of the read's output and of its predicted output once the binding exists, never the output itself.

A privileged database inspection ([privileged inspection](databases.md#privileged-inspection)) runs discovery's own reads, each as `sudo -n /usr/bin/sh -c '<read>'` when the SSH user is not root, after `sudo -n -l` lists the first one as authorized.

## Plan preparation

The Bootstrap plans section below is the legacy workflow for the profiles and metadata refresh. Cleanup of finished runs is now prepared and applied from the server's **Changes** page through the `operations` engine. The remaining bootstrap cleanup details in this document describe the legacy API exercised by native regression coverage; the operator-facing action is the engine's first change kind.

An operator with `servers.view_server`, `bootstrap.view_configurationplan` and `bootstrap.prepare_configurationplan` chooses the Nginx profile, the PHP profile (FPM and CLI), the MariaDB profile, the PostgreSQL profile or a package metadata refresh in the server page's **Bootstrap plans** section and presses **Prepare plan**. The CSRF-protected request accepts only those choices and queues a remote operation of the plan preparation kind; it never connects. The worker checks that the requesting account is still active and holds those permissions, connects through the same pyinfra connection and bounds as discovery, reads the evidence below, and records one immutable configuration plan with the operation's success in one transaction. The section polls while the preparation is queued or running, moves focus to its heading after the operator's request, and announces progress in a live region. Applying a reviewed plan is described [below](#applying-reviewed-plans).

A plan records its action and profile revision, the supported Ubuntu release it was reviewed against, the operator intent, the SSH alias and verified host key, the collection time, the boot ID from `/proc/sys/kernel/random/boot_id`, and an admission deadline 15 minutes after collection on the server's monotonic clock, as hundredths of a second of `/proc/uptime`; the page shows the controller's estimate of that time and marks an older plan expired. It records the platform (operating system, dpkg architecture, and the apt, dpkg and systemd package versions), the privilege available for applying, the requested packages at exact versions, APT's complete simulated transitions with the archives offering each version, the effects and postconditions, the refusal reasons, and a SHA-256 fingerprint with a short summary of each kind of evidence. It never stores configuration, command output or credentials. Preparation that cannot connect fails like discovery and records no plan; an interrupted or abandoned preparation is recovered as interrupted after ten minutes, since it only reads.

Preparation runs only these reads, each bounded like discovery's commands:

- Platform: `cat` of `/proc/uptime`, the boot ID and `/etc/os-release`; `test -d /run/systemd/system` ([sd_booted](https://www.freedesktop.org/software/systemd/man/latest/sd_booted.html)); `dpkg --print-architecture`; the apt, dpkg and systemd versions from `dpkg-query`. `/etc/os-release` selects the release policy of [ADR 0008](adr/0008-review-each-ubuntu-release-by-its-own-policy.md): on a system that is not Ubuntu 26.04 nothing but these platform reads runs, and the plan is refused for an unsupported release.
- Privilege: `id -u`, and when the user is not root, `sudo -n -l /usr/bin/systemd-run` and, for a profile with a port, `sudo -n -l /usr/bin/ss -Hltnp sport = :<port>` (80 for Nginx, 3306 for MariaDB, 5432 for PostgreSQL), which list whether sudo authorizes those exact commands without a password and run nothing ([sudo](https://manpages.ubuntu.com/manpages/resolute/man8/sudo.ws.8.html); on Ubuntu 26.04 `sudo` is [sudo-rs](https://manpages.ubuntu.com/manpages/resolute/man8/sudo-rs.8.html) by default, which lists and exits the same way). The privilege evidence names the port whose query is authorized. A root user, or a verified authorization for the profile's listener query, allows the privileged read `ss -Hltnp sport = :<port>` with process names. For MariaDB, a root user, or a sudo user for whom `sudo -n -l` lists the exact command as authorized, also runs the fixed read-only readiness check of [MariaDB](bootstrap.md#readiness) or [PostgreSQL](bootstrap.md#readiness-1) while the engine is installed and running. Nothing else runs with privilege; without privilege, the plan is refused and explains that Barectl permissions do not grant Linux privileges.
- APT: `apt-config dump` ([apt-config](https://manpages.ubuntu.com/manpages/resolute/man8/apt-config.8.html)); SHA-256 digests of the files under `/etc/apt`, except `auth.conf` files; the source files that set `trusted`, `allow-insecure`, `allow-weak`, `allow-downgrade-to-insecure` or `check-valid-until`; `apt-get indextargets` with and without Release information, for the configured sources and the downloaded indexes with their origin, suite, codename, configured suite and authentication, where a field the downloaded Release file does not have, which APT prints as the field's placeholder such as `$(ORIGIN)`, is read as empty and any other form is refused; digests of the downloaded InRelease files; the server's clock (`date -u +%s`) and each InRelease file's `Origin`, `Suite` and `Valid-Until` fields; and, before and after those reads, the APT digest an apply payload recomputes on the server (`bootstrap.native.APT_DIGEST`: the effective configuration, the digests of the files under `/etc/apt` except `auth.conf` files, and the configured sources, sorted and hashed together). The plan keeps that digest as read; if the two reads differ, the plan is refused because the configuration changed while it was read.
- Packages, for a profile: `dpkg --audit`, `apt-mark showhold`, the dpkg states of the profile's packages, and `apt-mark showauto` for the installed ones. For PHP, also the dpkg states of every package matching `php[0-9]*`, to find other PHP versions' packages that are installed or left configuration files. For MariaDB, `apt-cache madison` of an installed `mariadb-server`, whose version the release's own archive must offer from the profile's components, and the dpkg states of every package matching `mysql-server*`, `mysql-client*`, `mysql-community-*`, `percona-*`, `mariadb-server-[0-9]*`, `mariadb-server-core-[0-9]*`, `mariadb-client-[0-9]*` and `mariadb-client-core-[0-9]*`, to find other database servers' packages that are installed or left configuration files. When a requested package is missing, `apt-get -s -o APT::Install-Recommends=0 -o APT::Install-Suggests=0 install` simulates installing only the missing ones, without recommended packages; simulation needs no privilege and takes no lock ([apt-get](https://manpages.ubuntu.com/manpages/resolute/man8/apt-get.8.html)). Every `Inst`, `Conf`, `Remv` and `Purg` line must be in APT's exact form and agree with its summary line. For the packages the simulation would change, `apt-cache madison` then lists every version each downloaded index offers, named by repository, configured suite, component and architecture as `apt-get indextargets` names the index ([apt-cache](https://manpages.ubuntu.com/manpages/resolute/man8/apt-cache.8.html)); source package lines are skipped and any other form is refused.
- Services and configuration, for a profile: `systemctl show` of the profile's unit, including `FragmentPath` and `DropInPaths`; for each configuration directory whose package is installed, a `find` listing and the MD5 digests of its files, compared with the package's conffiles from `dpkg-query` and, for PHP, with ucf's registry in `/var/lib/ucf/hashfile`; for Nginx, the listening sockets on port 80; and for PHP, the names directly under `/etc/php` and the release's version directory, `/etc/php/8.5`, and `ss -Hlx src` of the default pool's socket, `/run/php/php8.5-fpm.sock`, the Unix socket listening at that path, which needs no privilege. The PHP version is the release's default, 8.5. For MariaDB, `/etc/mysql`, compared with the conffiles of `mysql-common`, `mariadb-common`, `mariadb-client` and `mariadb-server`, where `/etc/mysql/debian.cnf`, which the server package's maintainer script writes for root alone, is compared with the digest recorded for the release only when the SSH user can read it; the listening sockets on port 3306; `ss -Hlx src /run/mysqld/mysqld.sock`; and `test -e` and `stat -c '%F %U'` of the release's data directory, `/var/lib/mariadb`, and its `mysql` directory, of `/var/log/mysql`, and of the paths the profile never adopts: `/var/lib/mysql`, `/var/lib/mysql-files` and `/etc/my.cnf`, where existence is `test -e` or `test -L`, so a dangling link counts; `update-alternatives --query my.cnf`, which exits 2 when the alternative does not exist; `readlink -f -- /etc/mysql/my.cnf`; and `/usr/sbin/mariadbd --print-defaults`, compared with the release's qualified options once MariaDB is installed.
- For PostgreSQL, the dpkg states of every package matching `postgresql-[0-9]*`, to find other majors' server packages; `systemctl show` of `postgresql.service` and of the cluster's unit, `postgresql@<major>-main.service`, whose unit file is the `postgresql@.service` template and whose enablement is `enabled-runtime`, from the package's generator; the trees `/etc/postgresql/<major>/main` and `/etc/postgresql-common`, the latter compared with the conffiles of `postgresql-common` and `postgresql-client-common` and ucf's registry; the names under `/etc/postgresql`, `/etc/postgresql/<major>`, `/var/lib/postgresql` and `/var/lib/postgresql/<major>`, where names starting with `.` under the data root, such as `postgres`'s shell history, are ignored; `test -e` or `test -L` and `stat -c '%F %U'` of the data directory, `/var/lib/postgresql` and `/var/log/postgresql`; the listening sockets on port 5432; `ss -Hlx src /var/run/postgresql/.s.PGSQL.5432`; `/usr/bin/pg_conftool <major> main show all`; and `apt-cache madison` of an installed `postgresql-<major>`, whose version the release's archive must offer from `main`. The PostgreSQL major is the release's default, 18.
- Package digest, for a profile: before and after the package and service reads, the digest an apply payload recomputes on the server (`Profile.revalidation`, built by `bootstrap.native.package_digest`): SHA-256 of `/var/lib/dpkg/status` and `/var/lib/apt/extended_states`, of the downloaded InRelease files, the name, size and modification time of every downloaded index, `systemctl show` of the profile's unit, a listing and SHA-256 digests of its configuration directories, and for Nginx the addresses listening on port 80; for PHP, also ucf's registry, the entries directly under `/etc/php` and the version's directory, and the path of any socket listening at the default pool's socket; for MariaDB, the addresses listening on port 3306, the path of any socket listening at `/run/mysqld/mysqld.sock`, `stat` of the data directories and forbidden paths, the SHA-256 of `/var/lib/dpkg/alternatives/my.cnf`, the path `/etc/mysql/my.cnf` resolves to, and the size and modification time of `/etc/mysql/debian.cnf` in place of its digest, since only root can read it and the digest must be the same for the preparing user and the root payload. A difference between the two reads refuses the plan.
- Retained runs, for clearing finished bootstrap runs: the list of `barectl-apply-*` units systemd keeps, and for each one `systemctl show` of its identity, states, result, exit status and invocation, and whether its control group has processes. No APT evidence is read for a cleanup.

A plan is refused, with every reason and what ordinary administration resolves it, when the server is not Ubuntu 26.04 with systemd, dpkg and APT on amd64 or arm64, or its apt or systemd is outside the series qualified on the release (apt 3.2 and systemd 259); no root or noninteractive sudo is available; dpkg reports unfinished packages or a profile package has configuration left from a removal; an effective APT hook is not one of the release's tested distribution hooks, or an option weakens authentication, overrides package selection or changes dpkg; a source disables authentication; an installation needs indexes and the authenticated Ubuntu `main` indexes of the release's three suites, `resolute`, `resolute-updates` and `resolute-security`, or, for a profile that installs from `universe`, such as PHP, also their `universe` indexes, are missing, or the Ubuntu Release file of one of those suites sets a `Valid-Until` that has passed on the server's clock (Ubuntu's archive sets none today); the simulation would upgrade, downgrade, reinstall or remove an installed package, change a held package, use another archive, including another release's or the release's backports, or architecture, configure without installing, or report an error or warning; any source other than the release's own Ubuntu archive, its three suites and its backports, offers any package the simulation would change, at any version, or has an unauthenticated index; the release's own archive does not list a reviewed version; a configuration directory holds a file, link or change that is not the distribution's default, or exists without its package; a package plan's source is not an `http` or `https` archive, such as removable media or a local file repository; the unit is masked, failed, overridden or changing state; another service listens on port 80; for PHP, another PHP version's packages are installed or left configuration, `/etc/php` holds anything besides the release's version, `8.5`, or that directory anything besides `cli`, `fpm` and `mods-available`, another process listens at `/run/php/php8.5-fpm.sock` while PHP-FPM is not running, or a running PHP-FPM does not listen there; for MariaDB, another database server's packages are installed or left configuration, a data directory exists that the installed packages do not account for, an installed engine's data directory is not a `mysql`-owned directory with its `mysql` system-table directory, another service listens on port 3306 or at `/run/mysqld/mysqld.sock` while MariaDB is not running, or a running MariaDB listens anywhere besides `127.0.0.1`; or any read failed, was truncated or was not in a known form. The tested hook baseline is the one Ubuntu 26.04's `debconf`, `needrestart`, `update-notifier-common`, `apt`, `command-not-found` and `ubuntu-pro-client` packages install, the `packagekit`, `appstream` and `snapd` packages that Ubuntu's official server cloud image adds, and `ubuntu-helper-virt-hwe`, which hosting providers' images install; none of these runs before dpkg except debconf's and `ubuntu-helper-virt-hwe`'s, which cannot change packages ([ADR 0007](adr/0007-admit-exact-package-transactions-with-an-inline-apt-guard.md#consequences)), and snapd's runs only for the `apt` command, which Barectl does not use.

A healthy, installed profile is a plan with no changes, even when the archive offers newer versions, and nothing simulates an installation. An otherwise conforming profile whose service is stopped or disabled proposes explicit enable and start effects. PHP never requires Nginx. An installation plan explains that maintainer scripts start and enable the service before validation, that the default Nginx site serves HTTP on port 80 on every address (or that the PHP pool listens only on a local socket, which the unit registers as the `/run/php/php-fpm.sock` alternative when it starts, and that no web server is installed, or that MariaDB's maintainer scripts initialize its data directory and root's socket-only administrative account and that it listens on its local socket and `127.0.0.1` only, creating no database, database user, password or PHP driver), that `needrestart` may restart services, that APT keeps existing installation marks, and that Barectl does not roll back. An installation plan also lists the sources other than the release's own archive whose indexes APT has, and states that none of them offers a package of the plan. A metadata refresh plan has its own evidence, lists the configured sources, separately the third-party sources among its downloaded indexes and the sources it has no indexes of yet, and the update hooks' cache effects, and proposes no package transitions; preparing it never runs `apt-get update`.

Accounts with `servers.view_server` alone see neither plans nor preparations: the server page omits the section, the plan pages and fragments refuse them, and Activity lists only discovery attempts. Accounts that may review plans see preparations in Activity beside discovery attempts, each linked to its plan.

## Site preparation

A site plan reviews creating one HTTP PHP site ([reviewing a PHP site](sites.md)). An account with `servers.view_server`, `sites.view_siteplan` and `sites.prepare_siteplan` enters a site identifier and DNS names in the server page's **Site plans** section. The CSRF-protected request validates them, stores them with the queued plan preparation in one transaction and never connects. The worker checks that the account is still active and allowed, validates the stored request again, and connects through the same pyinfra connection and bounds as any preparation. Bootstrap's plan views, fragments, Activity and removal counts show only the actions an account may view (`bootstrap.actions`), so a site plan never appears to a bootstrap-only account and a bootstrap plan never to a site-only account.

Every read that the revalidation digest covers, and every read of configuration an ordinary account may not see, runs as root: directly when the SSH user is root, or as `sudo -n` of the exact fixed argv after `sudo -n -l` of that argv authorizes it without a password. Most of those argv are `/usr/bin/sh -c <fixed script>`, so authorizing them is equivalent to granting a root shell. Without that, the plan is refused for privilege after the platform reads. No read changes what Barectl manages: there is no syntax check, which opens logs and temporary files, no HTTP request, which a site would log, and no staging. sshd and sudo still record the login and each command in the authentication log and journal. The reads, in order:

- Platform and apply privilege, as for [plan preparation](#plan-preparation).
- The [revalidation digest](#the-revalidation-digest), as root, before and after the others; a difference refuses as evidence that changed while it was read.
- `dpkg-query` of `nginx`, `nginx-common` and the default PHP release's `fpm`, `cli` and `common` packages, and of every `php[0-9]*` package; `systemctl show` of `nginx.service` and the PHP-FPM unit; the conffiles of the configuration packages and ucf's registry.
- As root: a `find` listing of `/etc/nginx`, `/etc/php/<version>/fpm` and `/etc/php/<version>/mods-available` with each entry's type, mode, owners, link count, size, filesystem and link target, at most 2,000 entries, and the MD5 digests of their files.
- As root: `head -c 8193` of each file in `sites-available` or the pool directory that is not a distribution file and whose name a site could have, at most 200 files; a file larger than 8,192 bytes refuses. No other file's bytes are read, except each enabled site file that is not the distribution's `default`, read only for the declared `server_name` values that refuse a domain another site already uses, at most 200 files.
- As root: for the site's parent directories and each path the site would use, including the probe and the TLS convention's certificate paths, `stat` of the path itself or that it is absent.
- As root: `ss -Hltnp sport = :80`. Unprivileged: `ss -Hlx src` of the site's socket.
- `getent passwd` and `getent group` of the site user and `www-data`, the numeric user and group IDs from `/etc/passwd` and `/etc/group`, `id -G` of an existing site user, and as root only the first character of its shadow password field; only `!` counts as the convention's locked password.
- `/etc/login.defs`, `/etc/default/useradd`, the `passwd` and `group` lines of `/etc/nsswitch.conf`, and whether `/etc/subuid` exists.

Preparation then builds the complete payload applying would submit and refuses when it is larger than 16 KiB. A plan keeps only fingerprints and summaries of this evidence, the generated files' own bytes, and the typed file, directory and account effects; never another file's bytes, the shadow database or command output.

### The revalidation digest

`sites.native.site_digest` is one fixed command, recorded as the plan's site revalidation evidence and repeated verbatim in the payload: SHA-256 of the sorted output of the configuration trees' listing and file digests, the type, mode and owners of `/var/www` and each entry directly in it, but nothing below, so application content is not drift, the enabled Nginx modules, `/etc/passwd`, `/etc/group`, `/etc/subuid`, `/etc/subgid`, `/etc/login.defs`, `/etc/default/useradd` and `/etc/nsswitch.conf`, the parent directories' metadata, the TLS certificate directories, the site user's and `www-data`'s accounts, both units, the packages, the port 80 listeners and the site's socket. It sets `LC_ALL` and `PATH` itself, so sudo and a systemd unit compute the same bytes. The shadow databases are not part of it, and modification times, queue lengths and process IDs are left out so that an unchanged server gives the same digest.

## Applying reviewed plans

Applying is implemented for every reviewed action: a package metadata refresh, clearing finished bootstrap runs, the Nginx, PHP, MariaDB and PostgreSQL profiles, and site plans ([applying sites](#applying-sites)). A run copies its plan's release and applies and verifies that release's profile and suites. The native mechanism is recorded in [ADR 0006](adr/0006-use-native-bootstrap-execution.md), and exact package admission in [ADR 0007](adr/0007-admit-exact-package-transactions-with-an-inline-apt-guard.md).

An eligible plan with changes whose admission deadline has not passed shows a CSRF-protected **Apply plan** button, with a confirmation naming the server, alias, plan revision, effects and deadline, to accounts that also hold `bootstrap.apply_configurationplan` for a refresh or a package profile or `bootstrap.clear_native_results` for a cleanup. The request queues an apply run of the apply kind with a new unit name, `barectl-apply-<32 hex digits>.service`, saved before the worker sends anything, and copies the audit details it needs from the plan and the server: the server's name and alias, the plan's number, intent, reviewed host key, boot, deadline and effects, and its exact changes, each package transition with its version, architecture and archives, or each unit a cleanup clears with its invocation. A revision has at most one run: repeated requests, including a double submission, show the same run, and a spent revision is never applied again.

The worker checks again that the account is active and allowed, connects with the plan's alias, and refuses without submitting when the host key differs from the reviewed one, when the SSH user is not root and `sudo -n -l` does not authorize the exact `systemd-run` command line, when 100 or more bootstrap units are retained (110 for a cleanup), or when the payload would exceed 16 KiB. It reads the digest of `/var/lib/dpkg/status`, records the dispatch, and submits the unit with `sudo -n`. The payload takes the mutation lock and checks the boot, deadline, other bootstrap units, the retained limit and its reviewed evidence before it changes anything. The worker then inspects the unit every two seconds for up to four minutes over the same connection. The run's page follows it by polling while the worker is on it or a check is pending, announces changes in a live region, and says that the run continues on the server if the page or the controller disconnects.

- **Execution** is what native evidence established: completed, one of the refusals before changes (lock held, unsafe lock directory, server restarted, deadline passed, another bootstrap run still has processes, scheduled certificate renewal still has processes, evidence changed, package manager busy, too many finished runs retained), failed, stopped at the 30-minute limit, terminated by a signal, or outcome unknown. Success needs a zero exit, `Result=success` and an empty control group.
- **Verification** runs only after a successful execution, with fresh reads: for a refresh, the authenticated `main` indexes of the release's three suites for the server's architecture and an unchanged dpkg status; for a cleanup, that no reviewed unit is still retained; for a package profile, the checks listed under [Applying package profiles](#applying-package-profiles). A run succeeds only when both hold; otherwise it fails with the reason, keeping the execution outcome. If the reads fail after a terminal execution, the run fails with verification unavailable, keeps its execution outcome, and leaves the discovery snapshot marked as older than the run; a controller-side error is never recorded as a remote failure.
- A lost answer to the submission, a connection lost while watching, unreadable evidence, a run still active after four minutes, or a stopped worker leaves the run **reconciling**. It keeps the server's active slot, blocks editing the registration's alias and removing it, and is never submitted again. **Check outcome**, for accounts that may review plans, runs within the same operation, so no discovery attempt is queued; it inspects the same unit with a new connection, requiring the recorded invocation once known, and closes the run from terminal evidence or explains why it stays reconciling. Each check starts a new revision of the run and records only while it is still the newest, so an older check or a stale worker never overwrites a newer result.
- When the unit is gone, the run shows **outcome unknown so far** and stays reconciling; Barectl never assumes it did not run. An account allowed to apply the run's action may tick an explicit acknowledgement and press **Close as outcome unknown**, which asks one check to close it. That check closes it only if a privileged probe takes the mutation lock and shows that the server restarted since the run's boot or its deadline passed on the server's clock, that no bootstrap run has processes, that no scheduled certificate renewal has processes, and that the unit is still absent, and if the acknowledging account is still active and allowed. Otherwise the page says which proof is missing and the run stays reconciling; the acknowledgement is used once. A closed run shows **Outcome unknown**, says that it may have changed the server, and names who acknowledged it.
- A successful refresh, or any dispatched refresh not shown to have stopped before changes, including one closed as outcome unknown, invalidates the server's earlier package plans; their pages say so.

The run's page shows the lifecycle outcome, execution, verification and the discovery snapshot's freshness separately, with the audit: requester, alias, reviewed host key and boot, unit and invocation, submission and acknowledgement, and the reviewed effects and changes, the same after the plan was deleted with the server's registration. It never shows or stores remote output. Activity lists apply runs for accounts that may review plans, including those of removed servers.

### Applying package profiles

A package plan is applied like any other run, with `bootstrap.apply_configurationplan`, or `databases.apply_databaseplan` for a PHP driver. It is refused at request time and again by the worker when a metadata refresh was dispatched after its review, and a healthy installed profile, a plan with no changes, is never applied. Before submitting, the worker also reads the digest of the sorted automatic marks (`apt-mark showauto`).

Under the mutation lock the payload recomputes the APT and package digests and refuses any difference before APT runs. For an installation it then runs `apt-get install` for the missing root packages at their exact reviewed versions, without recommended or suggested packages, removals or missing-package fallback, and without any `--allow` or `--force` option, adding Barectl's inline guard as the last `DPkg::Pre-Install-Pkgs` command in protocol version 3. debconf's own hook preconfigures the downloaded packages first; the guard then compares APT's actual actions, under APT's dpkg frontend lock, with the reviewed closure and stops APT before dpkg changes any package if they differ in any way. APT fails at once, without waiting, when another process holds the frontend lock: the invocation sets `DPkg::Lock::Timeout=0`, so a timeout the server configures, such as a provider's `99lock-timeout`, does not apply. Only the missing roots are named: when the CLI, `php8.5-cli`, is already installed, for example as another package's dependency, APT installs only FPM and the CLI keeps its automatic mark. For a stopped or disabled baseline, the payload runs only the reviewed `systemctl enable` and `systemctl start`. Every run ends with the profile's final check as root: `nginx -t -q` for Nginx, `php-fpm8.5 -t` for PHP, and for MariaDB and PostgreSQL their [readiness checks](bootstrap.md#readiness), whose output the payload prints and compares with the qualified output, exiting with the configuration check's status when it differs.

The run's execution distinguishes a transaction the guard refused, APT failing before dpkg changed anything, dpkg having changed packages without completing, the service not enabling or starting, and the syntax check failing after the changes, each with what to do through ordinary administration; nothing is rolled back or repaired. Verification then checks, with fresh reads, that every reviewed package is installed at its version with nothing for `dpkg --audit` to report, that the new roots are marked manual and their new dependencies automatic while every other package keeps its earlier mark, and that the profile's unit is the distribution's, enabled and running. For Nginx, port 80 must listen on every IPv4 and IPv6 address. For PHP, a Unix socket must listen at the default pool's socket, `/run/php/php8.5-fpm.sock`, and the first line of `php8.5 -v` must name the CLI package's upstream version, without epoch and Debian revision, for the `cli` server API. For MariaDB, port 3306 must listen at `127.0.0.1` and at no other address, a Unix socket must listen at `/run/mysqld/mysqld.sock`, `stat -c '%F %U'` must show the release's data directory and its `mysql` directory as directories owned by `mysql`, no forbidden path may exist, `/etc/mysql/my.cnf` must resolve to `/etc/mysql/mariadb.cnf`, `mariadbd --print-defaults` must report the release's options, and the first line of `/usr/sbin/mariadbd --version` must name the `mariadb-server` package's upstream version. After a run that may have changed the server, Barectl queues discovery, so the server page shows the native packages, service, default site and PHP-FPM pool; a fresh installation discovers the same state through its own alias. Selecting PHP never installs a web server: its closure is what APT resolves for the version's FPM and CLI packages without recommended packages, and it runs on a server with or without Nginx. A PHP driver's run reloads PHP-FPM after its check and waits for every reviewed pool's socket (exit 26 when either fails); its verification also resolves each module's `conf.d` link in both SAPIs, reads `php-fpm<version> -m` and checks every reviewed pool's socket ([applying a driver plan](databases.md#applying-a-driver-plan)).

### Applying sites

A site run is an apply run like any other, with `sites.apply_siteplan` at request, at dispatch and for acknowledging an unknown outcome ([creating a PHP site](sites.md#applying)). The request copies the plan's typed files, directories and account to the run's audit in the transaction that queues it. Before submitting, the worker also checks that the SSH user is root, or that `sudo -n -l` authorizes the fixed read-only command that verifies the site. The payload is `sites.native.site_steps`, and its exit statuses and compensation are recorded in [ADR 0012](adr/0012-publish-site-files-without-replacing-them.md). Exit 31 is a refusal before changes; exits 40 to 55 record the run as **partly applied** with the raw exit status, and the run's page names the boundary and its ordinary-administration recovery ([recovering a partial site](sites.md#recovering-a-partial-site)).

Verification reads, as root through that authorization, the site user's `getent passwd` and `getent group` entries, `id -G`, the first character of its shadow password field, `stat` of every reviewed path including the socket and the probe, the link's target, the SHA-256 of each reviewed file, both units' states, `ss -Hlx src` of the socket, `nginx -t` and `php-fpm<version> -t`; then, unprivileged, the PHP CLI's HTTP/1.0 requests for each name over each reviewed address family and for a name no site declares. It records the site user's IDs, whether the probe is gone and each difference from the review. Discovery is queued after every site run that was not refused before changes.

### Applying database bindings

A binding run is an apply run like any other, with `databases.apply_databaseplan` at request, at dispatch and for acknowledging an unknown outcome ([applying a binding plan](databases.md#applying-a-binding-plan)). The request copies the plan's statements and probe to the run's audit. Before submitting, the worker also checks that the SSH user is root, or that `sudo -n -l` authorizes the verification's fixed read. That read, as root, prints the catalog read, the engine's readiness check's output, whether the probe exists, the engine's serving unit's and PHP-FPM's states and whether the pool's socket listens; verification parses the catalog with discovery's recognition and requires exactly the convention's rows.
### Applying challenge routes

A challenge route run is an apply run like any other, with `tls.apply_tlsplan` at request, at dispatch and for acknowledging an unknown outcome ([TLS](tls.md#applying)). A challenge route plan is prepared from the same reads as a site plan, whose path states also include `/var/lib`, `/var/lib/letsencrypt`, `/var/backups` and `/var/backups/nginx`, and whose revalidation digest also covers their metadata, the webroot's and the listing of `/var/backups/nginx`. The request copies the plan's preimage, replacement and directories to the run's audit, with the backup's path named after the run's unit. Before submitting, the worker checks that `sudo -n -l` authorizes the fixed verification read. Verification reads, as root, `stat` of the site file, its link, `/var/lib/letsencrypt`, the webroot, its `.well-known`, the probe, `/var/backups/nginx` and the backup, the link's target, the SHA-256 of the site file and the backup, `nginx.service`'s state and `nginx -t`.

### Applying renewal setup

A renewal setup run is an apply run like any other, with `tls.apply_tlsplan` ([TLS](tls.md#applying-renewal-setup), [ADR 0013](adr/0013-inhibit-certbot-renewal-until-the-guard-is-verified.md)). Preparation is bootstrap's package preparation of the Certbot profile, plus the renewal digest and the renewal state, two fixed root reads (`tls.setup_native`) whose `sudo -n -l` authorization is checked first; without it the plan is refused for privilege. The request copies the plan's renewal files to the run's audit. Before submitting, the worker checks that `sudo -n -l` authorizes the renewal state read, which verification repeats as root, together with `dpkg-query` of each installed package and `dpkg --audit`.

### Clearing finished bootstrap runs

systemd keeps each bootstrap unit after its run, successful or failed, until it is cleared. Preparing **Clear finished bootstrap runs** reads every retained `barectl-apply-*` unit's state unprivileged and lists, with its invocation, state and exit status, each one that finished, has no processes and shows an invocation, up to 120; it leaves units with processes, units without an invocation, and units of this installation's unfinished runs in place and says so. With nothing to clear, the plan has no changes. The review explains that systemd then forgets the units, that journal entries stay as long as the server's retention keeps them, that another installation still establishing one of these runs can then only close it as outcome unknown, and that Barectl's own audit is kept. A fresh installation sees the units of other installations' runs this way, as native work, without their requesters, plans or approvals.

Applying the plan is an apply run like any other, through the worker, the local active slot and the native lock, never from a view. It stays available up to 110 retained units, so runs refused at the limit, partly created units and failed cleanups can always be cleared; above that, ordinary administration clears them. Under the lock the payload refuses the whole cleanup, before clearing anything, if any reviewed unit shows another invocation, has not finished or has processes, and it refuses while any bootstrap run has processes. Discovery never clears anything.

### Durability and its limits

Accepted work survives the controller: closing the browser, losing SSH, stopping the worker or destroying the controller and its database leaves the transient unit running under systemd, and Check outcome, from the same or a restarted controller, establishes its outcome later. A server reboot is different: transient units, their states and the lock directory are gone after it, nothing resumes, and a run caught by it can only be closed as outcome unknown. The journal is the operating system's and may be rotated or vacuumed; outcomes rest on unit state, not on the journal, but the journal is the only place a run's output remains. A run stopped by its 30-minute limit or by a reboot can leave package recovery work, which is ordinary administration; nothing is rolled back. While dpkg has records of an interrupted change that root has not completed, it refuses reads by other accounts, so a review through a sudo account is refused, naming `sudo dpkg --configure -a`.

## pyinfra connection

Discovery connects through pyinfra's SSH connector, the SSH integration future changes to servers will also use. Barectl uses pyinfra for SSH transport and command execution only, not its facts or operations.

- Each connection builds a new one-host pyinfra inventory and state from the resolved alias, so nothing carries over between attempts or servers. pyinfra never reads the controller's SSH configuration (`ssh_config_file` is the null device), so `Match` blocks and settings Barectl refuses have no effect.
- Host keys are checked with `ssh_strict_host_key_checking` set to `yes` against a private temporary copy of the alias's known_hosts entries, with revoked keys removed. pyinfra never adds a key, and the copy is deleted when the connection closes. The presented key decides which refusal is reported.
- Barectl opens the TCP connection and passes it, with the timeouts and credentials above, through `ssh_paramiko_connect_kwargs`, pyinfra's documented override for paramiko's `SSHClient.connect`. Its `transport_factory` argument keeps the SSH transport, which reports the verified host key and is closed at each deadline.
- pyinfra reports a command's success as a boolean and reads output as text lines without a limit, so each command runs in a POSIX `sh` wrapper. The wrapper runs the command in its own shell with its error output discarded, keeps at most 64 KiB and one byte of its output with `head -c`, encodes it with `base64`, and ends with a line holding the command's exit status and the encoder's. base64 contains no spaces, so remote output cannot imitate that line, and the wrapper always exits 0, so pyinfra never retries a command. The exact output bytes and exit status are recovered from that; anything else is refused as an unreadable result. On the controller, the connection stops receiving once more than 256 KiB arrive while connecting or during one command, so a server that ignores the wrapper cannot make the worker hold unbounded output. The wrapper uses only the shell and coreutils, and writes nothing on the server.
- A command may receive optional bytes on standard input. The connector passes them through pyinfra's `_stdin` channel, base64-encodes the bytes on the controller, and decodes them inside the remote wrapper before the fixed command reads them. The bytes are never part of argv, the pyinfra command log, or `RemoteShell`'s command transcript. This uses pyinfra 3.10.0's SSH connector standard-input implementation ([version-matched source](https://github.com/pyinfra-dev/pyinfra/blob/v3.10.0/src/pyinfra/connectors/ssh.py#L363-L430)); the in-process SSH test exercises the channel end to end.
- pyinfra waits for command output without a limit Barectl can rely on, so a timer closes the SSH transport at the command or connection deadline. A stalled or slowly writing command, a dropped connection and an unreadable result all fail the attempt with a fixed explanation; incomplete output is never returned as a result. The TCP connection, transport and trust copy are released on success, failure, truncation, timeout and when the worker is forced to stop, and nothing more is sent on a connection that was closed.
- The worker process is not changed by the integration: Barectl does not apply gevent's monkey-patching, so threads, sockets and the database driver behave as before. pyinfra reads command output in gevent greenlets on the worker's own thread. When connecting, pyinfra's connector replaces paramiko's key-type lookup for agent keys with the behavior of upstream paramiko's fix for security-key agent keys ([pyinfra connector source](https://github.com/pyinfra-dev/pyinfra/blob/v3.10.0/src/pyinfra/connectors/ssh_util.py)); this applies to every paramiko client in the process. pyinfra also keeps the host keys it loaded from each trust copy for the life of the worker process, a few kilobytes per attempt; the copy's file is deleted, and a restart of the worker releases them.

## Failures and logs

Failures are shown as fixed explanations that name the alias and the next step. They never include exception text, remote output, host names, user names or key paths. An unexpected error is recorded as such, and the worker log names only its type. pyinfra's and paramiko's own logging is discarded because it can quote host names, commands and server-supplied data.

## Target foundation reads and privilege

The target foundation on Ubuntu 26.04 accepts root or authorized passwordless sudo. Only its fixed foundation read, privilege check and privileged listener read use `discovery/root_read.py`. It reuses `operations/native.py` to check root, authorize the exact fixed argv without prompting, and run that argv on the existing `RemoteShell` from pyinfra. A denied or truncated authorization produces unavailable evidence, never guessed absence. The released Nginx collectors continue to read as the SSH user. This bounded reuse and the owning requirements are recorded on [#336](https://github.com/rajandangi/barectl/issues/336#issuecomment-6171527420).
