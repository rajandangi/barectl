# Per-site PHP competitor analysis

Research checked on 2026-10-07 for [#236](https://github.com/rajandangi/barectl/issues/236). This compares documented behavior against [Barectl's requirements](../README.md#core-philosophy), [ADR 0016](adr/0016-limit-third-party-php-supply.md) and the [qualification record](php-versions-qualification.md). It does not change the accepted specification or enable a runtime.

## Recommendation

Keep Ubuntu-default PHP as the available option today. Continue qualifying the explicit Surý source for multiple supported branches. It fits Barectl's ordinary APT, PHP-FPM, SSH and fresh-controller requirements without adding a panel agent or container runtime. This is a judgment about fit to those requirements, not a general claim that Barectl is the best hosting platform.

The comparison exposes useful product gaps beyond installation: reviewed patch updates, safe existing-site branch migration, a clear list of sites affected by a branch, support-expiry visibility and version-aware deployment or queue commands. Complete the current qualification before adding those operations. A broad PHP selector without an update and migration policy would overstate what operators can safely manage.

Use Forge and Ploi as the PHP lifecycle benchmarks, CloudPanel as the focused native site-settings benchmark and HestiaCP as an inspectable native packaging comparison. Coolify and Dokploy are useful alternatives when container deployment is the product goal. If paid PHP support and a longer vendor lifecycle matter more than a public repository, investigate Freexian as a separate supplier decision. None of these comparisons justifies changing Barectl's current supplier automatically.

Additional Surý branches remain disabled. Local arm64 native and browser proof does not replace amd64 qualification, the remaining fault coverage or checks on the published revision. [#221](https://github.com/rajandangi/barectl/issues/221) is closed as non-applicable; its [single-advisory ignore](braces-advisory-review.md#required-audit-policy) passes locally with the raw finding still visible. Existing Ubuntu-default workflows remain available. See the qualification record for tested revisions and limits.

## How to read the comparison

High confidence means a first-party document explicitly describes the behavior. It does not mean a deployment was tested here. Documentation can lag the product, particularly version matrices. No competitor received a destructive test, performance benchmark or security audit. An undocumented transaction guard, recovery method or update deadline is unknown, not absent.

Management independence, workload continuity and inventory recovery are separate questions. A website can keep serving after a dashboard disconnects while its management records or certificate renewal still depend on that dashboard. Importing a known panel's configuration once also differs from reconstructing supported native state repeatedly from an empty controller database.

Forge's security documentation distinguishes automatic Ubuntu security updates from PHP/MySQL updates, which it does not automatically apply. Its PHP patch workflow warns of possible downtime. Ploi also distinguishes unattended security updates from general package updates. Neither source establishes a guaranteed PHP security-patch deadline. [Forge policy](https://laravel.com/forge/docs/servers/security), [Ploi package updates](https://ploi.io/documentation/server/how-do-i-updateupgrade-packages-on-my-server).

Ploi describes two operational details worth retaining in future designs. Creating an isolated site's pool on another branch can restart that branch's FPM and interrupt other sites' requests. A Cancel button on a stuck installation resets panel status only; operators must still inspect server execution. Its deployment tokens and separately selected queue-worker PHP also show why a web-runtime change alone is incomplete. [Ploi PHP workflow](https://ploi.io/documentation/php/can-i-change-my-php-version).

RunCloud's August 2025 billing FAQ describes disabled web service and revoked certificates after payment failure, which conflicts with its newer March 2026 account-lock article. The table uses the newer account-specific explanation; confirm the applicable contract before relying on service continuity. Both documents show why workload continuity and certificate renewal need separate assessment. [Older billing FAQ](https://runcloud.io/docs/account-and-billing-faq), [newer account-lock explanation](https://runcloud.io/docs/locked-and-deactivated-accounts).

These products need not prevent ordinary Linux or Docker administration. The material difference is which configuration and records their documented management workflow needs. Barectl's requirement is narrower and stronger for its recognized native convention: authorized SSH and native evidence must be enough for a fresh controller to reconstruct supported sites. Its own audit history remains private controller data.

CloudPanel's official installer also demonstrates a different package trust boundary. The retrieved installer had SHA-256 `8146dbe0a488e7088b04071b0c34d59aa0ab1fe9dcec382d395fd155c9e6c476`, matching the published installation guide. It configures architecture-specific vendor repositories for PHP and other stack components, puts its key in global APT trust and sets a wildcard vendor-origin preference of 1000. This is an observation of that installer, not a security ranking. Barectl should retain its dedicated `Signed-By` and exact PHP-only admission instead of copying those broader supplier rules. [Installer source](https://installer.cloudpanel.io/ce/v2/install.sh), [installation guide](https://www.cloudpanel.io/docs/v2/getting-started/other/).

Ubuntu's guidance explains why an added repository is a trust decision: package scripts run with system privileges, and scoped keys or pinning do not sandbox an approved publisher. Restricting the source is valuable, but it cannot remove that trust. [Ubuntu third-party repositories](https://ubuntu.com/server/docs/explanation/software/third-party-repository-usage/).

Vendor backports can outlive the PHP project's upstream branch support. Ubuntu security coverage depends on package/component and the applicable support offering; a branch number alone does not establish it. A paid backport policy would also need an explicit change to Barectl's current support cutoff. [Ubuntu security updates](https://documentation.ubuntu.com/security/security-updates/).

## What to adopt, defer and reject

| Decision | Action and reason |
| --- | --- |
| Retain now | Explicit installed-branch selection, source/branch retained in the review and audit, site-specific native pools and sockets, other sites unchanged and reconstruction from native settings. Explain site selection separately from Ubuntu's default and the unversioned CLI alternative. These fit the accepted specification and the documented workflows above. |
| Add to a separately reviewed follow-up | Show affected sites and support deadlines for each installed branch, then design patching and existing-site migration with application compatibility checks, service effects, fresh review and recovery evidence. Ploi exposes end-of-life site and available-update insights; Forge supplies usage checks before branch removal. [Ploi insight types](https://developers.ploi.io/insights/insight-types), [Forge PHP](https://laravel.com/forge/docs/servers/php). |
| Defer until application lifecycle work | Version-aware deployment, Composer, queues, cron and daemons. These must agree with the chosen site branch; changing the server's plain `php` alternative cannot guarantee that agreement. Ploi explicitly documents those separate consumers. [PHP workflow](https://ploi.io/documentation/php/can-i-change-my-php-version). |
| Exclude from this milestone | Automatic supplier conversion, silent site switching, unreviewed extensions, unsupported PHP branches and global automatic PHP upgrades. They require additional migration and update policy under ADR 0016. A competitor's wider selector is not evidence that those actions satisfy Barectl's requirements. |

The PHP project's current policy gives two years of active support followed by two years of critical security fixes. PHP 8.3, 8.4 and 8.5 reach security end-of-life on 2027-12-31, 2028-12-31 and 2029-12-31. Use that owning source, rather than older panel articles describing a three-year cycle. Containers can isolate a workload but do not supply missing PHP security fixes. [PHP support policy](https://www.php.net/supported-versions.php).

## Choosing by the actual requirement

| Priority | Option to evaluate |
| --- | --- |
| Native Linux, local management and reconstruction without prior controller records | Barectl's current Ubuntu-default workflow; the Surý multi-branch workflow only after its remaining gates pass. This conclusion follows the accepted product constraints and current local evidence. |
| A hosted native PHP lifecycle dashboard available now | Forge or Ploi. Their documented patching and switching cover operations outside Barectl's present installation-only specification. Validate application, provider and renewal requirements before adopting either. |
| An installed native server panel | CloudPanel for a focused PHP site workflow; HestiaCP for its native MultiPHP and inspectable implementation. Accept the resident panel and its configuration/backup model. |
| Container application deployment | Coolify or Dokploy. Evaluate the current builder, image, restore process and architecture for the actual application. A native PHP branch matrix does not answer that container question. |
| Paid PHP support or vendor-backed extended lifecycle | Freexian, subject to contract, exact release/architecture availability, secure private-repository access and a separately reviewed Barectl integration. |

Application readiness is a separate selection criterion. Installing a PHP branch and database driver does not establish that Laravel or WordPress can run. Check the exact application version, Composer requirements, plugins, themes and needed extensions, then perform a real deployment smoke test. For example, Laravel 13 requires cURL, DOM, mbstring and XML in addition to its minimum PHP version; WordPress documents its own extension requirements. Barectl's additional extensions and application deployment remain separately scoped, so its runtime qualification does not establish application compatibility. [Laravel server requirements](https://laravel.com/framework/docs/13.x/deployment#server-requirements), [WordPress server environment](https://make.wordpress.org/hosting/handbook/server-environment/#php-extensions).

Native per-site FPM users and sockets do not provide container or VM isolation. PHP documents pool users, sockets and optional chroot settings; Docker uses namespaces and control groups and has its own daemon security considerations. Isolation requirements can therefore justify a container product, without implying that either runtime model is universally safer or faster. [PHP-FPM configuration](https://www.php.net/manual/en/install.fpm.configuration.php), [Docker security](https://docs.docker.com/engine/security/).

There is no demonstrated total-cost winner. Self-hosting still requires servers, backups, monitoring, maintenance and operator time; hosted management retains infrastructure and application responsibilities. Freexian's paid PHP support is a separate runtime-support cost, not a substitute for server management. The actual workload and required support determine the useful comparison.

## Evidence still needed

Before claiming a competitor's exact transaction safety or controller-loss recovery is equivalent, inspect its current implementation or obtain explicit documentation for package provenance, key rotation, duplicate-version repositories, executable-hook ordering, drift, concurrent controllers and partial failure. The reviewed public workflow pages do not settle those questions.

For Barectl, delivery remains tied to the exact published revision and the qualification record. This analysis supplies product comparisons and design judgments, not additional runtime qualification. It does not close the open implementation tickets or relax the audit gate.
