# 1.0 low-resource load result

This record is the measured low-resource result for the near-final 1.0 candidate
([#540](https://github.com/rajandangi/barectl/issues/540), part of
[#528](https://github.com/rajandangi/barectl/issues/528)). It runs the existing
memory-capped breadth harness on 1, 2 and 4 GiB containers and records the observed memory
and disk against the foundation's provisional thresholds. It is **not** a real 1, 2 or
4 GiB host measurement: the containers share the Docker VM's kernel, page cache and
`/proc/meminfo`, as the [Phase E record](phase-e-qualification.md#not-qualified) says.

The exact command:

```bash
docker/disposable-server/run-scenarios.sh --env-file .env -- --breadth \
  disposable.test_breadth.MemoryOneGiB \
  disposable.test_breadth.MemoryTwoGiB \
  disposable.test_breadth.MemoryFourGiB
```

Each class starts from L5, turns the site's 64 MiB object cache on, requests the page once
and waits two seconds. The container is booted with `--memory=N --memory-swap=N`, so the
whole cgroup is capped at the named size. The class reads `memory.max`,
`memory.current`/`memory.peak`, the cache instance's unit cgroup, both queue workers' unit
cgroups and the instance's `maxmemory`, and checks the site still serves. The 1.0 extension
reads the foundation's capacity evidence in the same sample: `df -B1` availability for `/`,
`/var`, `/var/www/<id>` and `/var/lib/barectl-backups/<id>`, `du -sb` for the site and its
backup root, and `MemAvailable` from `/proc/meminfo`. An absent root is read on its nearest
existing ancestor, so the figure is the filesystem that would receive the data. One
`BREADTH_MEMORY <json>` line per class carries every observation.

The thresholds are the provisional, unqualified values in
`bootstrap/standing.py`: **4 GiB free disk** and **900 MiB available memory**. A target is
met only when the observed value is readable and at least the threshold; an unreadable value
is not a pass.

The configured `maxmemory` was 67,108,864 B (64 MiB) in every class, far above the measured
instance footprint because the site's cache is nearly empty. Both workers were running and
the site answered `200` in every class. The whole-cgroup figure includes the prepared stack
and page cache, so it is not additive with the per-unit figures. `cgroup headroom` is
`memory.max - memory.peak`, the conservative unclaimed memory at the sample.

## Disk and foundation capacity

The run's `/` and `/var` are the same overlay filesystem; `/var/www/sqwalpha` is a real
directory on it. `/var/lib/barectl-backups/sqwalpha` does not exist because the breadth
fixture configures no backup, so it was measured on `/var/lib` and recorded as absent.

| Class | Available memory (`MemAvailable`) | 900 MiB target | Free disk (`/`, `/var`, site, backup filesystem) | 4 GiB target | Site `du` | Backup root `du` |
| --- | --- | --- | --- | --- | --- | --- |
| `MemoryOneGiB` | 14,648,152,064 B (13.64 GiB) | Met | 502,522,163,200 B (468.01 GiB) | Met | 28,628,062 B (27.3 MiB) | Absent (read on `/var/lib`) |
| `MemoryTwoGiB` | 15,119,687,680 B (14.08 GiB) | Met | 502,552,817,664 B (468.04 GiB) | Met | 28,628,062 B (27.3 MiB) | Absent (read on `/var/lib`) |
| `MemoryFourGiB` | 14,648,152,064 B (13.64 GiB) | Met | 502,522,163,200 B (468.01 GiB) | Met | 28,628,062 B (27.3 MiB) | Absent (read on `/var/lib`) |

Every disk target is met with wide margin: about 468 GiB free against the 4 GiB threshold on
every measured root. The literal available-memory target is also met in every class, but
only because `/proc/meminfo` inside a container reports the Docker VM's memory; the cgroup
cap does not change it. That reading cannot establish a 1, 2 or 4 GiB host's own available
memory.

Read as a host-shaped check, the same 900 MiB floor against the cgroup's own headroom
(`memory.max - memory.peak`) gives:

| Class | Cgroup headroom at peak | 900 MiB floor | Result |
| --- | --- | --- | --- |
| `MemoryOneGiB` | 560,115,712 B (534.2 MiB) | 900 MiB | **Miss** |
| `MemoryTwoGiB` | 1,734,144,000 B (1,653.8 MiB) | 900 MiB | Met |
| `MemoryFourGiB` | 3,612,921,856 B (3,445.6 MiB) | 900 MiB | Met |

**The 1 GiB miss.** The 1 GiB class leaves 534.2 MiB unclaimed at its peak, below the
foundation's provisional 900 MiB available-memory threshold. This does not fail the class's
own assertions (the capped stack served within its limit), but it is a real miss for a
1 GiB host claim: a real 1 GiB host must also carry its own kernel and base daemons, so its
`MemAvailable` would be lower still. **Next action:** measure a real 1 GiB host, where
`/proc/meminfo` is that host's, before the 1.0 record treats the 1 GiB size as meeting the
900 MiB foundation threshold. That measurement belongs to
[#541](https://github.com/rajandangi/barectl/issues/541) or a named follow-up. This record
neither raises the 900 MiB threshold nor reports the 1 GiB container as a pass against it.

## Run result

All three classes passed in one local arm64 run: **3 of 3 in 25 s**, against the 300 s lane
target and 900 s limit. The first pass prepared the missing L1 and L5 snapshots (20.0 s and
29.8 s); the recorded run reused those exact-key snapshots. Item times:

| Class | Measured | Result |
| --- | --- | --- |
| `MemoryOneGiB` | 8.2 s | Passed: cache and both workers measured, site served, disk and memory targets read |
| `MemoryTwoGiB` | 8.1 s | Passed: cache and both workers measured, site served, disk and memory targets read |
| `MemoryFourGiB` | 8.2 s | Passed: cache and both workers measured, site served, disk and memory targets read |

## Not measured

- **A real 1, 2 or 4 GiB host.** This run is three memory-capped containers on one Docker
  VM. It does not measure a cloud instance, a small VPS, a whole-host kernel, page cache or
  `MemAvailable`, and the 1 GiB headroom miss above says so.
- **Hosted amd64.** This is local arm64 only; no hosted `Native breadth` dispatch was made
  for #540.
- **A configured backup root.** The breadth fixture configures no backup, so
  `/var/lib/barectl-backups/<id>` was absent and its `du` is unknown. The filesystem
  headline is still measured on `/var/lib`, and the backup-cost figure is left to the
  backup scenarios.

The Phase E qualification record keeps its existing "A real 1, 2 or 4 GiB host" caveat and
links this page; the 1.0 qualification record
([#541](https://github.com/rajandangi/barectl/issues/541)) is the other page that names this
result. This record does not re-qualify the Phase E checks.
