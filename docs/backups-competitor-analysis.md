# Backup and restore competitor analysis

Official sources inspected on 2026-10-09. This review compares the workflows needed for [v0.6](v0.6.md), not product pricing or every available feature. A documented limitation is evidence of that restriction. "Not established" means the inspected sources do not prove the capability; it does not mean the product lacks it.

## Documented workflows

| Product | Documented behavior | Limits and unresolved evidence |
| --- | --- | --- |
| Laravel Forge | Scheduled database backups, retention counts and restoration to the originating database. Another server or database requires downloading from storage and using a database tool. The API supports manual runs. External storage supports named providers and custom S3-compatible endpoints. [Database backups](https://laravel.com/forge/docs/resources/database-backups), [manual-run API](https://forge.laravel.com/api-documentation), [storage providers](https://laravel.com/forge/docs/storage-providers). | Full application backup, onsite storage, rclone and direct panel download are not established by these sources. The separation between destination configuration and backup configuration is useful. |
| Ploi | Separate database and site-file workflows support schedules and manual runs. Destinations include local storage, external providers and rclone with configurable flags. MySQL/MariaDB dumps use `--single-transaction`; archives need server disk space. [Setup and behavior](https://ploi.io/documentation/database/how-do-i-set-up-database-and-file-backups). | The same guide explicitly excludes panel restoration of site-file backups and DB restoration from FTP/SFTP destinations. One consistent application-and-database capture is not established. DB restore guidance recommends application maintenance mode. [DB restore](https://ploi.io/documentation/database/how-do-i-restore-a-database-backup). |
| RunCloud | Backup modes include database only, application only and both. Scheduling supports local or external storage; manual runs and download are documented. Restore can target the current, another or a new application/database. [Modes](https://runcloud.io/docs/beginner-guide-to-runcloud), [creation](https://runcloud.io/docs/creating-backups), [manual-run API](https://runcloud.io/docs/api/v3/api-8900231), [download](https://runcloud.io/blog/website-backups), [restore](https://runcloud.io/docs/restoring-runcloud-backups). | Creation guidance says external storage does not support incremental backups. Automatic exclusions can omit dependencies and assume reinstall after restore. Atomic deployment archives contain persistent data rather than application code and cannot use standard restore. [Atomic deployment limitation](https://runcloud.io/docs/how-to-revert-to-a-previous-version-with-atomic-deployment). |
| CloudPanel | Local database dumps run nightly with seven-day retention; operators can change the native cron schedule. Remote backups use rclone with provider choices or custom configuration. Manual creation is documented. File scope includes the site home and vhost, excluding SSH files, logs and temporary files. [Database backups](https://www.cloudpanel.io/docs/v2/frontend-area/databases/), [remote backup](https://www.cloudpanel.io/docs/v2/admin-area/backups/). | Remote restore guidance instructs operators to download from the provider, upload to the server, extract and replace files manually. Database import uses its CLI. One coordinated DB/file capture, remote DB-only selection and integrated restore verification are not established. |
| HestiaCP | Manual creation, direct panel download and whole-backup or component restoration are documented. Remote downloads first stage the file on the server. The standard local directory is `/backup`; initial rclone configuration uses the CLI. Its CLI reference demonstrates scheduling user backups with cron. [Panel workflows](https://hestiacp.com/docs/user-guide/backups), [storage and formats](https://hestiacp.com/docs/server-administration/backup-restore), [CLI](https://hestiacp.com/docs/reference/cli). | Restore supports Hestia/Vesta backup formats. User backups cover more than applications and databases. Its broader mail, DNS, account and incremental-backup workflows exceed Barectl's requested scope. The storage guide checks disk capacity before backup creation. |

## Decisions for Barectl

These are design conclusions, not claims about competitors' implementations.

- Keep two scopes: database only, and full application with its database. Define the complete file set and consistency conditions explicitly. A transactional DB dump alone does not prove consistency with separately captured files.
- Support on-demand creation and native server scheduling through the same operation. Scheduled work must continue with the controller offline.
- Use one rclone configuration template: encrypted onsite storage through a local `crypt` remote and encrypted offsite storage through `crypt` over AWS S3. Do not copy competitors' provider menus, arbitrary flags or custom configuration editors. Encryption and key recovery belong in the owning backup specification and its upstream evidence.
- Present onsite and offsite availability separately. A failed upload must preserve a usable onsite backup and show incomplete offsite protection.
- Provide restore and local download for each supported backup. Offsite retrieval may require temporary server staging; capacity and integrity checks must precede use.
- Define a complete, independent artifact for each run. Exclude automatic retention, incremental chains, mail and DNS backup, provider snapshots, arbitrary archive import and unrelated recovery products.
- Warn when native configuration conflicts with the supported template. Preserve conflicting configuration and refuse unsafe operations until the operator corrects it.
- Keep transfer details within the rclone adapter, artifact validation within the backup-format module, and workflow coordination within application services. Destination, schedule and artifact are distinct concepts with small interfaces.
- Separate successful creation, verified integrity and demonstrated restoration. The inspected documentation does not establish automatic application/DB consistency or routine restore rehearsal across these products.

The evidence supports these operator workflows and the use of established tools. It does not justify describing a chosen Barectl template as objectively the most secure or most commonly used configuration. Barectl should document its supported standard and the evidence behind each security decision.
