# Share one PHP-FPM master per runtime, with protected OPcache

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323); not implemented. A runtime is a named PHP branch and extension set, such as `php84`; its exact build changes by profile generation when a catalog update is applied. It runs one FPM master as an instance of a native systemd template unit, with one pool per site under the site's user and a socket keyed by runtime. A master per site would multiply memory and OPcache on small servers; one master for every version is impossible.

Sharing a master shares its OPcache, whose protections are off by default. Every master therefore sets `opcache.validate_permission=1`, `opcache.validate_root=1` and a root-only `opcache.restrict_api`, with no file cache and no preload; without them one site could be served another site's cached scripts, reset every site's cache or list other sites' paths. Pools also share the master's private `/tmp`, so every pool gets its own session, upload and temporary directories, or one site could read another's sessions. A shared master is not qualified until native tests prove these settings block cross-pool reads.

A new build is applied with a restart, not `USR2`, until a native test proves re-execution safe. Adding or removing a pool reloads the whole master, so pool changes take Shared consent and list every site on that runtime, until a native test proves in-flight requests survive the reload. Master-level settings (extensions, OPcache) are always reviewed as affecting all of them. Per-site limits come from pool settings; systemd limits apply to the master. The trust model is one owner or a trusted team, not mutually hostile tenants. Details are in the [target architecture](../target-architecture.md#php-fpm).
