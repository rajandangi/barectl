# Review each Ubuntu release by its own policy

> Partly superseded for new servers: the target stack supports only Ubuntu 26.04 ([ADR 0026](0026-manage-fresh-hosts-on-one-target-stack.md)), and PHP supply and the single default version move to [ADR 0028](0028-supply-runtimes-and-tools-from-pinned-nix.md).

Bootstrap supports Ubuntu 26.04 LTS (resolute). Each supported release is one record in `bootstrap/releases.py`: its version and codename, from which its three suites and archive origins follow (`resolute`, `resolute-updates`, `resolute-security`, named by APT's simulation as `Ubuntu:26.04/resolute`, and so on); the APT and systemd series its package admission and native execution were qualified with (apt 3.2 and systemd 259); the PHP version its `php-defaults` package selects (8.5); the PHP packages besides FPM, CLI and their common files that the profile's closure contains (`php8.5-readline`, whose PHP builds OPcache in); its MariaDB series and data directory, shared with discovery in `discovery/releases.py`, and the archive components the MariaDB closure comes from, the `debian.cnf` its server package writes and the options `mariadbd --print-defaults` reports (11.8 from `main` in `/var/lib/mariadb`); its default PostgreSQL major, also shared with discovery, and the digests of the main cluster's `pg_hba.conf` and `pg_ident.conf` its `pg_createcluster` writes (18, from `main`); and the APT hooks its own packages install. There is one profile engine: `bootstrap/profiles.py` builds each release's Nginx, PHP, MariaDB and PostgreSQL profiles from the same definitions, and the review, payload, guard and verification are the same code for every release. A later LTS is added as another record by its own policy.

## The release decides every rule

Preparation reads `/etc/os-release` first. A system whose `ID` is not `ubuntu` or whose `VERSION_ID` is not a supported release is refused as an unsupported platform after only the platform reads, since no release policy exists to judge its APT, packages or units by. On a supported release, the plan records the release, and:

- an installed apt or systemd outside the release's qualified series refuses every plan as an unsupported platform, naming the version found and the series qualified;
- only the release's own tested hook baseline is admitted, so a hook another release installs is unknown here;
- an installation needs the authenticated indexes of the release's own three suites for every component its profile installs from (`main` for Nginx, MariaDB and PostgreSQL; `main` and `universe` for PHP), each installed version must be offered by the release's own archive from one of those components, as `apt-cache madison` names it, and a transition from any other archive, including another Ubuntu release's or the release's backports, is refused;
- the release's own archive is its three suites and its backports, identified by the downloaded Release files' `Origin: Ubuntu`, codename and suite; every other source is a third-party source, which may stay configured when authenticated, but refuses an installation while it offers any package of the transaction, at any version;
- the PHP profile installs the release's default PHP version and refuses every other PHP release's packages and directories, as the 26.04 profile refuses anything besides 8.5;
- the MariaDB profile installs the release's MariaDB and refuses another release's data directory;
- the PostgreSQL profile installs the release's default major and its `main` cluster and refuses every other major's packages and directories and every other cluster.

An apply run copies the plan's release and applies and verifies that release's profile and suites; it never re-derives the release from the server. A server upgraded to another release after review changes the evidence the payload rechecks and refuses as drift before APT runs, and needs a new review.

## Naming

The operator chooses the **PHP profile (FPM and CLI)**, action `php`. The plan's intent and effects name the version, such as "Install the distribution-default PHP 8.5 FPM and CLI from Ubuntu 26.04 packages", and the postconditions name its binaries (`php-fpm8.5 -t`, `php8.5 -v`) and socket (`/run/php/php8.5-fpm.sock`). The Nginx profile's definition is the same on every release; its intent names the release.

## Ubuntu 26.04 evidence

Recorded from Ubuntu 26.04.1 LTS, with apt 3.2.0, dpkg 1.23.7ubuntu1, systemd 259.5-0ubuntu3.4, sudo-rs 0.2.13-0ubuntu1.2, nginx 1.28.3-2ubuntu1.11 and php8.5 8.5.4-0ubuntu1.3, on the disposable server and on Ubuntu's official server cloud image, and qualified by the disposable-server suites run for both releases (`docker/disposable-server/run-tests.sh`):

- APT 3.2 prints `apt-config dump`, `apt-get indextargets` with and without Release information, and `apt-get -s` action and summary lines in the forms APT 2.8 prints, so the same strict parsers apply. `--error-on=any` still makes a failed index fail `apt-get update`, errors are still `E:` and `Err:` lines, and a held lists or frontend lock still fails at once with `Could not get lock`.
- APT 3.2 sends a `DPkg::Pre-Install-Pkgs` command protocol version 3 when `DPkg::Tools::Options::<first word>::Version` is 3, in the documented form, with `DPKG_FRONTEND_LOCKED=true` and `APT_HOOK_INFO_FD=0`; the inline guard of [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md) runs unchanged and refuses mismatched transactions before dpkg runs.
- systemd 259 accepts the submission of [ADR 0006](0006-use-native-bootstrap-execution.md) unchanged and reports the same properties; `ExecStartEx` shows `flags=no-env-expand`. A finished unit reports an empty `ControlGroup`, which inspection already reads as no processes.
- Ubuntu 26.04 makes sudo-rs the default provider of `/usr/bin/sudo`, beside the original sudo as `sudo.ws`. sudo-rs's `sudo -n -l <command>` prints the command and exits 0 only when the policy authorizes it without a password, and exits 1 without prompting otherwise, as sudo does, so the noninteractive authorization checks and dispatch through `sudo -n` are unchanged.
- The tested hook baseline of 26.04 includes PackageKit 1.3's hook, which also skips OSTree-booted systems, and `ubuntu-helper-virt-hwe`'s hook of hosting providers' images, below; Ubuntu's official 26.04 server cloud image has that baseline without the latter.

## Hosting providers' images

A hosting provider's Ubuntu 26.04.1 server (amd64, apt 3.2.0) was refused for every action before this policy admitted what its image adds. Barectl accepts these customizations, each reproduced in the disposable 26.04 image and qualified by all its suites:

- A signed third-party repository, the provider's security agent's, whose Release file names `Suite` and `Codename` but no `Origin`. `apt-get indextargets` prints a field the Release file lacks as its own placeholder, `$(ORIGIN)`; Barectl reads exactly that placeholder, in that field only, as empty, and refuses any other unknown form with the field and repository named. The source may stay configured: a metadata refresh updates it with every other source, lists it, and fails unless it authenticates and updates without errors; an installation lists it and is refused while it offers any package of the transaction. `apt-cache madison` names each offering index by repository, configured suite, component and architecture, which `apt-get indextargets` gives for every downloaded index, so each offer is attributed to an identified index; an offer from an index that cannot be identified refuses too. Offering at all refuses, not only being APT's candidate: pin priorities decide APT's choice, and a source that offers the same version as the archive with other contents would pass the guard, which compares names, versions and architectures.
- PackageKit, whose hooks are 26.04's baseline already, and `ubuntu-helper-virt-hwe` from `resolute-updates/main`, whose `99-ubuntu-virt.conf` adds a pre-install hook and its protocol option. Both are admitted only with their exact text; why the hook cannot change packages or stop the transaction is recorded in [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md#consequences).
- An unowned `99lock-timeout` setting `DPkg::Lock::Timeout "60"`. It stays, since Barectl never changes the server's configuration, and the installation passes `DPkg::Lock::Timeout=0` itself ([ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md#installation)).

The release's backports, configured by default, belong to its own archive: they may offer any package, since Launchpad publishes one pool per archive and a version of a package has one set of contents there, but never supply a reviewed transaction.

## Consequences

- Supporting another release adds one record, its profile data where the release's packages differ, its hook baseline and a disposable image, and needs the native suites run against it; nothing is qualified by package availability alone.
- The disposable-server suites run for each supported release; Ubuntu 26.04 is the only one.
- A server whose release is not supported is refused before anything but its platform is read.
