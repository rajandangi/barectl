# Give each site its own Valkey instance

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323); implemented for WordPress by [#392](https://github.com/rajandangi/barectl/issues/392) and extended to Laravel by [#393](https://github.com/rajandangi/barectl/issues/393). A site that enables an object cache gets its own Valkey server from Ubuntu's `valkey-server` package, running as the site user on a private Unix socket with its own `maxmemory` and eviction policy.

One shared instance with per-site ACL users and key prefixes was the first plan, for lower memory. It cannot contain flushes: Laravel's cache flush ignores the configured prefix, the WordPress Redis Object Cache plugin documents a database flush path, and per-database ACL rules exist only from Valkey 9.1, while Ubuntu 26.04 ships 9.0. Denying flush commands would break ordinary `cache:clear` and plugin flushes; allowing them would let one site wipe every site's cache. A small idle instance per site is the cheaper failure.

## The implemented convention

The packaged `valkey-server@<identifier>.service` template runs the instance. A root-owned drop-in (`/etc/systemd/system/valkey-server@<identifier>.service.d/barectl.conf`) sets the site account, the site's own `/etc/valkey/<identifier>.conf`, its `PIDFile`, a site-owned `RuntimeDirectory=valkey/<identifier>` at `0700`, and the writable runtime and data paths. The root-owned configuration is readable by the site account (`0640 root:s<identifier>`), the data directory is site-owned `0700`, and the socket is `/run/valkey/<identifier>/valkey.sock` at `0600`. The configuration is `port 0`, `protected-mode yes`, `save ""`, `appendonly no`, `maxmemory` from {32, 64, 128, 256} MiB, `maxmemory-policy allkeys-lru`, and one default-user ACL rule: `+@all -@admin -debug -module`. Ordinary flushes work; `CONFIG`, `MODULE`, `DEBUG`, `ACL` and `SHUTDOWN` are refused. There is no password because only the site account can open the socket. The instance stays outside the site's automation slice, and site removal stops, disables and removes it with the site's other resources.

The PHP client is phpredis, the catalog's packaged `redis` extension for each runtime ([#390](https://github.com/rajandangi/barectl/issues/390)); a site that does not load it cannot turn its cache on. WordPress gets the pinned Redis Object Cache plugin and its drop-in, with the three reserved `WP_REDIS_*` constants in the private configuration; turning off disables the drop-in and clears the constants before the instance stops. Details are in the [object cache](../object-cache.md#a-sites-own-cache-implemented-392) page.

**Qualification (Phase C, #398).** The one-instance-per-site decision stands. In containers capped at 1, 2 and 4 GiB, a site's idle 64 MiB-bound instance measured 4.2 to 8.8 MiB of resident memory and each of its two database queue workers about 33 to 34 MiB; the whole prepared stack peaked at 425 MiB of the 1 GiB cap. The figures are memory-cgroup limits, not whole hosts, and the [Phase C qualification record](../phase-c-qualification.md#memory) states that gap. The client supply is settled: phpredis loads from the locked store path through the site's own pool and command wrappers, and no `withExtensions` build is needed. A host that does not load it refuses the cache rather than falling back to Predis, because the review can prove phpredis and cannot prove a Laravel lock carries Predis.

Revisit when the supported release ships a Valkey with per-database ACLs and the applications flush only their own database. Details are in the [target architecture](../target-architecture.md#valkey).
