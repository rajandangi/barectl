# Limit third-party PHP supply to one reviewed source

Accepted on 2026-10-07 for [#203](https://github.com/rajandangi/barectl/issues/203). Per-site PHP versions need a source beyond the Ubuntu archive. Barectl permits an explicit PHP-only source choice using Ondřej Surý's `https://packages.sury.org/php/` repository, under the terms below. This changes the design's supply guarantee; it does not enable installation. The current archive-only implementation remains in force until the [per-site PHP specification](../php-versions.md)'s implementation and native qualification complete.

## Why the original PPA preference needs revision

The issue records a preference for `ppa:ondrej/php`. On 2026-10-07, the [live Launchpad archive API](https://api.launchpad.net/1.0/~ondrej/+archive/ubuntu/php) says the PPA is being merged into `packages.sury.org/php`, identifies that repository as the canonical source for Ubuntu Resolute, and says Jammy and Noble can still use the PPA while migration instructions are pending. The [PPA's Noble InRelease](https://ppa.launchpadcontent.net/ondrej/php/ubuntu/dists/noble/InRelease) was available; its [Resolute InRelease](https://ppa.launchpadcontent.net/ondrej/php/ubuntu/dists/resolute/InRelease) returned HTTP 404. The PPA's signing fingerprint is `B8DC7E53946656EFBCE4C1DD71DAEAAB4AD4CAB6`.

The unified repository published [Noble](https://packages.sury.org/php/dists/noble/InRelease) and [Resolute](https://packages.sury.org/php/dists/resolute/InRelease) metadata dated 2026-10-01, naming `Origin: deb.sury.org`, the matching suite and codename, `main`, and amd64 and arm64 among its architectures. These are read-only availability observations, not signature verification or native qualification. The older PPA page and the maintainer's general website still describe the former PPA/Debian split; the live archive description is the basis for revising the source choice. Barectl must not silently substitute the unified repository for an approved PPA.

## Upstream guidance and Barectl judgment

- [PHP's Debian-family installation guidance](https://www.php.net/manual/en/install.unix.debian.php) supports APT packaging but treats third-party builds as unofficial, with packaging bugs directed to their provider. It does not endorse this repository.
- [Ubuntu's third-party repository guidance](https://documentation.ubuntu.com/server/explanation/software/third-party-repository-usage/) describes publisher trust, conflicts, lack of Ubuntu support, scoped `Signed-By` keys and APT pinning. It warns that repository support can lag a new Ubuntu release. Its preference for sandboxed snaps does not establish a snap-based replacement for Barectl's native PHP-FPM layout.
- The [maintainer's repository instructions](https://packages.sury.org/php/README.txt) use a downloaded `debsuryorg-archive-keyring` package and `Signed-By`. They do not supply Barectl's PHP-only package admission, exact transaction review or release qualification. The [maintainer's support page](https://deb.sury.org/#support) points to commercial support; no fixed release-onboarding or security-update deadline was verified. The current Launchpad description promises neither a migration completion date nor a support lifetime for each unified Ubuntu suite. Package availability alone is insufficient evidence of either.
- The source restriction, explicit opt-in, version set and refusal rules below are Barectl judgments. Signing and pinning cannot sandbox package maintainer scripts or protect against a compromised approved publisher. Acceptance means trusting this publisher to run package code as root.

## Terms

### Source and signing key

Permit only `https://packages.sury.org/php/`, the server's own supported Ubuntu codename, component `main`, and its qualified architecture. Keep ordinary Ubuntu sources for all other packages. Do not enable the maintainer's Nginx or Apache repositories, the legacy PHP PPA, Debian suites, other mirrors or fallback sources.

Require a dedicated administrator-managed keyring under `/etc/apt/keyrings/`, referenced by that source's `Signed-By`, containing only the approved primary key and its verified signing subkeys. The approved primary fingerprint is `15058500A0235D97F5D10063B188E2B695BD4743`, read from the [published public key](https://packages.sury.org/php/apt.gpg) on 2026-10-07. The downloaded key's SHA-256 was `b486fd5488185c4c46467960fa69c53d5085fec492cf76b9eaf3db33561c9d7c`; this records the observation, not an immutable pin for future expiry extensions. Check the full fingerprint, key validity, revocation and authenticated index signatures before admission. A fingerprint read over HTTPS is not an independent proof of publisher identity; this decision approves that trust anchor.

Use the dedicated `Signed-By` key path together with the full approved fingerprint filter. Require source-specific `Check-Valid-Until: yes` and `Valid-Until-Max: 604800`; the publisher currently omits `Valid-Until`, so native APT must enforce a seven-day maximum from its signed metadata date. This is a Barectl freshness limit, not a publisher SLA. Do not apply this maximum globally to Ubuntu release metadata. The [metadata preflight](../php-source-preflight.md) verifies this behavior on both supported APT releases, without qualifying installation.

Never import it into global APT trust, disable authentication, accept a short key ID or automatically trust a rotated primary key. A new primary key requires another reviewed decision. A same-primary-key expiry extension needs fresh validity and signature checks and a new plan. The maintainer's keyring package can introduce keys and is outside the PHP package allowlist, so the decision does not authorize its installation or automatic keyring updates. Source setup belongs to the separately reviewed implementation workflow; this ADR is not an instruction to run the maintainer's installation script.

### PHP versions and package boundaries

The initial eligible branches are PHP 8.3, 8.4 and 8.5 on Ubuntu 24.04 and 26.04, separately qualified on amd64 and arm64. [PHP's support table](https://www.php.net/supported-versions.php), checked on 2026-10-07, gives security support through 2027-12-31, 2028-12-31 and 2029-12-31 respectively. Exclude 8.2 because its support ends on 2026-12-31, and exclude older branches, previews and unreviewed future branches. Native qualification can narrow this set; publishing packages does not enable a combination.

For each branch, permit only the exact reviewed binary names `php<version>-fpm`, `php<version>-cli`, `php<version>-common`, `php<version>-readline`, and `php<version>-opcache` where separately packaged. Permit `php<version>-mysql` and `php<version>-pgsql` only for their reviewed driver profiles. Permit the shared `php-common` dependency. Do not use `php*` or a source-package wildcard. Other extensions need a separate reviewed profile and qualification.

The [WordPress source extension profile](../wordpress-source-qualification.md), reviewed for #320 on 2026-10-10, adds only the exact versioned `curl`, `xml`, `mbstring`, `zip`, `gd` and `intl` binaries for the same eligible branches. It reuses the existing source trust and exact transaction checks. This package allowlist extension does not enable a WordPress combination; each branch, release and architecture still requires its separately recorded native qualification.

Use one PHP supply choice per server: the current Ubuntu-default profile or the unified-source profile. All managed PHP branches and the shared `php-common` must follow that choice. Preserve the release-specific FPM directories, units and versioned binaries, and record a site's explicit PHP branch in the native site convention so a fresh controller reconstructs it. Do not rely on the unversioned CLI alternative to select a site's PHP.

The first implementation covers fresh installation. Existing Ubuntu PHP, a legacy PPA installation or mixed-source PHP requires a separately specified migration; this decision authorizes no upgrades, package replacement, automatic conversion or downgrades. Installing another branch must not change existing sites' PHP selection.

### APT selection and transaction admission

Use a persistent native APT preference that assigns priority `-1` to all packages from the approved repository, then priority `700` to its exact allowed PHP binary names. Match its release origin and the server's codename, and separately verify the configured URL and signing key; an origin label alone is not identity. Validate effective priorities across all preference files and target-release settings, including each supported architecture, instead of assuming the intended file wins. [Noble apt_preferences(5)](https://manpages.ubuntu.com/manpages/noble/man5/apt_preferences.5.html) documents negative priorities and record precedence; qualify the same policy against Resolute's APT before enabling it there. Priority 700 expresses an intentional PHP-source preference without authorizing downgrades.

Pinning is an additional restriction for ordinary administration, not a replacement for package admission. Every non-PHP dependency must come from the server release's currently admitted Ubuntu suites and components. Keep the existing refusal whenever another source, including this repository, offers a non-PHP package in the transaction, at any version, even with a negative pin. If a PHP extension requires a third-party library, refuse that profile rather than widening the exception. Other third-party sources offering any transaction package still refuse it.

For allowed PHP packages, review every exact version and its authenticated source evidence. Preserve [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md)'s exact transaction, lock, drift checks, automatic dependency marks and prohibition on upgrades, removals, downgrades and repairs. Its guard compares package names, versions and architectures, not archive contents. Before relaxing source-overlap refusals for PHP, the implementation must prove the actual downloaded archives match the approved authenticated index and refuse ambiguous equal-version offers with different contents. Prefer native APT evidence; any additional mechanism requires the upstream-reuse assessment in the implementation issue. Pins alone do not settle that gap.

APT 2.8.3 and 3.2.0 accept an existing archive-cache file when its size matches the expected version's size, without hashing it in that path. See `pkgAcqArchive::pkgAcqArchive` in the upstream [2.8.3 acquisition source](https://salsa.debian.org/apt-team/apt/-/blob/2.8.3/apt-pkg/acquire-item.cc) and [3.2.0 acquisition source](https://salsa.debian.org/apt-team/apt/-/blob/3.2.0/apt-pkg/acquire-item.cc). Debconf's package configuration scripts run before the current appended guard, so adding hash checks only to that guard is too late to protect those scripts.

For unified-source transactions, use APT's documented `Dir::Cache::Archives` override with a fresh, root-controlled per-run native archive cache and require SHA-256 through native acquisition. Do not reuse or clear the shared cache and do not implement another downloader or cryptographic verifier. Refuse any exact package/version offered by more than one source instance, including equal-version Ubuntu offers, even if the contents appear identical. Keep the approved-source evidence unchanged through acquisition. Adapt the existing guard's archive-path admission to the isolated cache only after proving its ownership, emptiness, `_apt` access, locks, cleanup and hook ordering on both APT releases. The cache is temporary native package data, never a plan, inventory or management journal. The implementation issue must record this gap and upstream-reuse choice before code is added. This is a planned exception to ADR 0007's shared-cache path, not a qualification claim.

### Release lag and loss of support

If the source lacks a matching suite, architecture, required binary, valid key or authenticated usable indexes, refuse the affected PHP plan and explain the unavailable prerequisite. Never use a previous release's suite, another mirror or the Ubuntu archive as a transparent fallback for that plan. The existing Ubuntu-default workflow remains available where its own prerequisites hold.

Require a new reviewed release policy and native qualification before enabling a new Ubuntu release or PHP branch. Recheck the maintainer's published support policy and PHP's support dates at that point. When a branch reaches end of security support or the publisher withdraws support, refuse new installs and changes selecting it and tell the operator to migrate. Continue reporting existing native state; do not stop services, remove packages or switch sites automatically. No security-update SLA or automatic PHP patching is promised by this decision.

## Implementation boundary

This decision supersedes [ADR 0008](0008-review-each-ubuntu-release-by-its-own-policy.md)'s archive-only PHP supply and single-default-version rules only for the qualified unified-source profile. It changes the third-party-offer guarantee in [v0.2 package admission](../v0.2.md#review-and-package-admission) only for the exact PHP package set above, and ADR 0007's shared-cache-path requirement only for these transactions. The existing Ubuntu profiles retain their current rules. [ADR 0015](0015-recognize-only-the-convention.md)'s convention-only recognition and fresh-controller reconstruction remain required.

Check upstream reuse before adding provisioning code. Installed pyinfra 3.10.0 and its [APT operations documentation](https://docs.pyinfra.com/en/3.x/operations/apt.html) provide `apt.key` with a dedicated destination, `apt.sources_file` with `signed_by`, exact package versions in `apt.packages`, and a non-idempotent `apt.ppa` wrapping `apt-add-repository`. The PPA operation does not express this decision's source or pins. Key and source operations are useful upstream building blocks; they do not supply fingerprint acceptance, package admission or native detached execution. Compose supported operations where they fit, and review any gap against [ADR 0006](0006-use-native-bootstrap-execution.md) before selecting an implementation. Keep `discovery/ssh.py`, the worker and transient systemd execution under the shared native lock as the sole execution path. Add no installer, controller-dependent scheduler or server-side inventory.

The [per-site PHP specification](../php-versions.md) owns the implementation tickets for source/key/pin admission and reviewed setup; per-version package profiles; native site selection and discovery; selected-branch drivers and TLS; and cross-controller qualification. Specify any existing-PHP migration separately. Qualification must cover both releases and architectures, non-PHP and competing-source refusal, key and preference drift, equal-version source ambiguity, release lag, another branch without changes to existing sites, and reconstruction from a controller with no previous database. Only then may the operator docs claim per-site version support.

## Alternative

Keeping the Ubuntu archive as the sole package supplier preserves the qualified trust boundary and avoids new source admission, but leaves only PHP 8.3 on Ubuntu 24.04 and PHP 8.5 on Ubuntu 26.04. It was rejected as the sole future choice because it cannot provide per-site branches; it remains the current supported workflow and the default supply choice. A legacy-PPA-only exception cannot meet the currently supported Resolute scope. Automatic PPA-to-unified-source migration is outside this decision.

The [competitor and package-source analysis](../php-versions-competitor-analysis.md) also considers Freexian PHP LTS, container images and source builds. Paid support may justify a separately reviewed supplier and lifecycle policy. It does not authorize a supplier change, private repository credentials or extended-support exceptions under this decision.
