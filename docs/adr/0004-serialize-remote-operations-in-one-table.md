# Serialize remote operations in one table

One Barectl database permits at most one queued, running, or reconciling remote operation for a managed server. Discovery, plan preparation and apply runs are its kinds and share one lifecycle owner, rather than independent tables whose constraints cannot exclude one another. Native cross-device exclusion is separately defined in [ADR 0006](0006-use-native-bootstrap-execution.md).

The `operations` app's RemoteOperation table holds every kind's lifecycle columns, and `operations/lifecycle.py` owns queueing, claiming, conditional transitions, recovery and the one worker task. Each kind's details are a Django multi-table-inheritance model (`DiscoveryAttempt`, `PlanPreparation`, `ApplyRun`), whose implicit one-to-one parent link makes the detail share the operation's identifier and keeps discovery's permission codenames. Transitions update the shared table directly, so each remains one conditional UPDATE. One partial unique index enforces the active set. There is no busy flag on the registration, and no database transaction is held open across SSH work.

The shared states are queued, running, reconciling, succeeded, and failed; recovery is kind-specific. Each kind registers its step and a stale limit. Discovery and plan preparation only read, so an abandoned one is failed as interrupted after ten minutes. A kind that changes servers records `dispatched_at` through a conditional update before it sends anything: from then on an exception, a stopped worker, or abandonment past the stale limit moves the operation to reconciling, never to failed, and a reconciling operation is never touched by recovery. An apply run abandoned before dispatch is failed, since nothing was sent. The kind's `reconcile` step, asked for by Check outcome, runs within the existing operation without claiming it, so the active slot cannot block its own recovery; it closes the operation only through a conditional transition from reconciling. Execution outcome and postcondition verification are separate typed fields on the apply detail, not lifecycle states.

## Consequences

- Discovery, preparation, and apply cannot queue over one another for the same registration within one database. Different aliases and independent databases still require native mutation exclusion.
- Active operations block registration editing and removal. Removal deletes finished discovery attempts and plan preparations, and keeps finished apply runs with the server detached: `server` is nullable only for finished apply runs (a check constraint), and the run copies the server name, alias, requester, reviewed host key, boot, deadline, plan number, intent and effects it needs. Its link to the plan is cleared when the plan is deleted.
- The shared service owns queueing, claiming, conditional transitions, and persistence. Each kind owns its evidence, recovery policy, and work; a new kind does not get a competing lifecycle implementation.
- Local audit is not copied to the managed server and cannot be reconstructed by a fresh controller. Unknown remote outcomes remain explicit even if current configuration can be inspected. Closing a run whose native evidence is gone as outcome unknown is not implemented; such a run stays reconciling.
