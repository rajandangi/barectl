# Keep secrets in private native files, delivered over SSH standard input

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323); not implemented. Operators add, replace, rotate and remove application settings and secrets in the dashboard. The authoritative copy is on the server in private site-owned files: Laravel's `.env`, and for WordPress a private file outside the web root loaded by `wp-config.php`. The controller database and the Nix store never hold secret values.

A secret travels from an authenticated, CSRF-protected request over the SSH session's standard input into a root-only staging file, is validated and atomically placed, and the affected service is reloaded. It never appears in argv, systemd unit properties, the journal, operation records, events or responses. [ADR 0006](0006-use-native-bootstrap-execution.md) submits each fixed payload as a transient unit's properties, which are readable and journaled, so a secret cannot ride in the payload. This amends ADR 0006 with one narrow addition: the payload may read a secret from the same pyinfra SSH session's standard input before it detaches. The transient unit, shared lock, finite execution and no-replay rules stay as they are, and no second connection or execution service is added. The gap and the upstream options checked are recorded in the implementing issue before code is written.

systemd credentials were considered for everything, but FPM pools cannot read them: the credentials directory belongs to the unit's user, which is root for the master, and `env[]` exposes values the way `Environment=` does. Worker and timer units running as the site user may use `LoadCredential=`. Secrets are write-only in the interface; any future reveal is a separate audited permission. Details are in the [target architecture](../target-architecture.md#settings-and-secrets).
