# Classify Laravel release permissions in the deploy build

Accepted on 2026-10-18 for [#421](https://github.com/rajandangi/barectl/issues/421). Phase B requires that "only `current/public` is readable by `caddy`. The rest of a release, plus `.env`, storage and cache, are unreadable by `caddy`; `caddy` gets only directory traversal" ([#356](https://github.com/rajandangi/barectl/issues/356)), and [the site conventions](../site-conventions.md) already state that "deployment must keep PHP source at 0600 and give 0640 only to intended public assets". Phase A created `current/public` that way (site user:caddy 2750, PHP source 0600, static files 0640). Nothing classified a release, so a checkout's own modes stood, and a site whose release belongs to the site user read as outside supported settings while a permissive umask could leave a release any account can write.

The Deploy build classifies the release it just built, in place and under the site lock: every directory under the release is traversal-only for every other account (site user:site group 0711), every file belongs to the site user alone (0600), and `public` keeps Phase A's exception (site user:caddy 2750) with static files 0640, so Caddy serves assets while PHP source stays site-only. Symlinks are never followed, so the shared `.env`, `storage` and `bootstrap/cache` links into the site's private area are untouched. The stage runs after the build and the shared links and before the maintenance gate, and the review names it (`classify`); a failure is a release problem, so the previous release keeps serving.

Three alternatives were rejected. Leaving the checkout's own modes stands only while every process that writes into a release honours a restrictive umask; under the common permissive mask Caddy can read the application's source and configuration, and a permissive mask is exactly what makes the reader refuse a release as untrustworthy. Owning the release as root would satisfy a classifier but contradicts "releases are owned by the site user, not root" and the earlier decision to drop root-protected publication, which removed the copy-with-admission step. Recognizing a release by a Barectl-written marker is forbidden: "platform recognition is by shape, never by a marker."

The site shape verifies the result instead of trusting it. A release is recognized as Laravel by shape — `artisan` plus the shared `.env` and storage links in `current` — and then the site directory, `releases/`, the release itself (site user:site group 0711), `current/public` (site user:caddy 2750), the private directories, `logs/` and `bin/` are checked, together with `artisan` and `public/index.php` staying site-only at 0600. Anything else, including a release any account can write, reads as outside supported settings, and a Deploy refuses until the layout is repaired. Plain sites and `releases/initial` keep the root-owned check they had.
