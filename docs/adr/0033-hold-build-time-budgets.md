# Hold build-time budgets

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323) and [#322](https://github.com/rajandangi/barectl/issues/322); enforcement lands in Phase A. The whole build must stay fast enough to run before every change. A full local build, including the pre-push checks and the native suite, targets 10 minutes and never exceeds 15; the pre-push checks alone stay within 3 minutes; the full required CI targets 10 minutes of wall time and never exceeds 15. The reference host is a 14-CPU, 64 GiB workstation running Docker; CI may use more parallel runners.

The previous harness reached 60 to 80 minutes locally because every WordPress test reinstalled packages, MariaDB and WordPress, downloaded from live sites, and only per-CPU lane counts limited growth. Nothing failed when a test got slower, so the total drifted. A build that slow is not run before pushing, and then native changes reach CI untested.

The budgets are therefore enforced, not aspirational. The runner fails any test item over 3 minutes and any build over 15 minutes, and reports the total against the 10-minute target; CI does the same. Native tests start from snapshot images that already hold the state they need, reset by booting a fresh container rather than reinstalling, and read every download from a lane-local fixture. Fault permutations of a payload run against that payload in a lightweight container; full-stack native tests are kept for behavior that only the full stack can show, such as installation, switching, renewal, restore and reconstruction. A new full-stack test names why a cheaper level cannot prove it.

Snapshots alone are estimated to bring a full local build to about 14 minutes, within the hard limit but not the target. Reaching 10 minutes also needs roughly 40% less full-stack native work, by moving fault permutations to payload-only tests. A full build with the native suite cannot fit in 5 minutes on the reference host. Phase A must measure all of this with the first new-stack spike (Nix, Caddy, one WordPress site, snapshot-based tests) before the rest of the harness is built. If the hard limit cannot be met, the test design is revised first; the budget is not raised quietly.
