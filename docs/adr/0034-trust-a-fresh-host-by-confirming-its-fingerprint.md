# Trust a fresh host by confirming its fingerprint

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323) and [#293](https://github.com/rajandangi/barectl/issues/293); not implemented. Phase A adds a server through a saved connection: address, user (root by default), port and a key reference, either this computer's SSH agent or an approved key file. To trust the host, the operator pastes the host key fingerprint the provider shows for the new server. Barectl connects, accepts the presented key only when it matches exactly, and records it in a Barectl-owned known_hosts file on the controller. A changed or revoked key is refused, and nothing is trusted on first use. The check result shows the host's standing and, for a fresh host, the next action, Set up server.

This reverses the rule in [SSH connections](../ssh-connections.md) and the [saved connections specification](../saved-server-connections.md) that Barectl never writes SSH trust files and that trust is established outside Barectl. Under that rule an operator had to edit known_hosts by hand before Barectl could reach a server it was about to set up, and the target stack only manages fresh hosts, which always present new keys at first boot. Comparing against the provider's fingerprint keeps the same independent source of trust; only the copying moves into Barectl. Barectl writes only its own file, never the operator's `~/.ssh/known_hosts` or SSH configuration, and alias registration keeps reading the controller's files unchanged.

Trust-on-first-use and a network scan were rejected: neither proves the key belongs to the server. Each controller keeps its own trust file, so a second controller confirms the fingerprint again rather than inheriting trust.
