# Trust a fresh host by confirming its fingerprint

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323) and [#293](https://github.com/rajandangi/barectl/issues/293); implemented for saved-address checks by [#333](https://github.com/rajandangi/barectl/issues/333). Phase A adds a server through a saved connection: address, user (root by default), port and a key reference, either this computer's SSH agent or an approved key file. To trust the host, the operator pastes the host key fingerprint the provider shows for the new server. Barectl connects, accepts the presented key only when it matches exactly, and records it in a Barectl-owned known_hosts file on the controller. A changed or revoked key is refused, and nothing is trusted on first use. The check result shows the host's standing and, for a fresh host, the next action, Set up server.

This reverses the rule in [SSH connections](../ssh-connections.md) and the [saved connections specification](../saved-server-connections.md) that Barectl never writes SSH trust files and that trust is established outside Barectl. Under that rule an operator had to edit known_hosts by hand before Barectl could reach a server it was about to set up, and the target stack only manages fresh hosts, which always present new keys at first boot. Comparing against the provider's fingerprint keeps the same independent source of trust; only the copying moves into Barectl. Barectl writes only its own file, never the operator's `~/.ssh/known_hosts` or SSH configuration, and alias registration keeps reading the controller's files unchanged.

Trust-on-first-use and a network scan were rejected: neither proves the key belongs to the server. Each controller keeps its own trust file, so a second controller confirms the fingerprint again rather than inheriting trust.


The strict pyinfra handshake supplies the presented public key through Paramiko's `get_remote_server_key` after an unknown-key refusal. Host verification precedes authentication, so capture adds no alternate SSH execution path ([Paramiko 5 client](https://docs.paramiko.org/en/5.0/api/client.html), [transport](https://docs.paramiko.org/en/5.0/api/transport.html), [pyinfra SSH connector](https://docs.pyinfra.com/en/3.x/connectors/ssh.html)). Paramiko supplies public-key serialization and SHA256 fingerprints ([keys](https://docs.paramiko.org/en/5.0/api/keys.html)). Its host-key save method does not perform the required locked compare-and-write across controller processes. Barectl therefore adds an adjacent advisory file lock and atomic replacement, limited to its owned trust file. The [upstream reuse decision](https://github.com/rajandangi/barectl/issues/333#issuecomment-6169297710) records this gap.

Confirmation binds to the failed attempt's captured endpoint and immutable connection revision. It requires registration-editor and discovery authority, rereads current trust under the file lock, refuses changed or revoked keys, and preserves unrelated entries. The browser supplies only the fingerprint, attempt identity and revision. The following check remains strict and refuses any later key replacement before authentication.

Fast qualification covers dashboard confirmation, zero credential offers during capture, exact matching, stale revisions, permission and CSRF refusal, and changed or revoked current trust. Native S1 and S5 remain scoped to their later scenario tickets.
