# Use native bootstrap execution and exclusion

Apply runs submit one finite payload to a uniquely named transient systemd system service, which owns execution after the controller disconnects. Every payload acquires the same nonblocking native flock before validating its boot identity, admission deadline, the other bootstrap units, and its reviewed evidence. Pyinfra's shell interface, through the connection `discovery/ssh.py` opens, carries submission and inspection; neither a controller worker nor a local database lock owns remote execution or cross-device exclusion.

This is implemented in `bootstrap/native.py`, the one adapter apply services use, for three reviewed actions: a package metadata refresh, clearing finished bootstrap runs, and the Nginx profile, whose package transaction is admitted as [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md) records. All three are qualified against the disposable Ubuntu 24.04 server (`bootstrap/test_apply_remote.py`, `bootstrap/test_coordination_remote.py`, `bootstrap/test_package_remote.py`) and offered in every installation. The PHP 8.3 profile uses the same payload but is not offered yet.

## Submission

`systemd-run --unit=barectl-apply-<32 hex digits>.service --quiet --expand-environment=no --service-type=exec --remain-after-exit -p ExitType=cgroup -p Restart=no -p RuntimeMaxSec=30min -p TimeoutStopSec=60 -p KillMode=control-group -p StandardInput=null -p StandardOutput=journal -p StandardError=journal /usr/bin/sh -c <payload>`, run as root or through `sudo -n` after `sudo -n -l` authorized that exact command line. No `--scope`, `--pty`, `--pipe`, `--wait` or `--collect`; systemd-run returns once the main process was executed, and the SSH connection owns nothing of the unit. The unit name is saved locally when the run is queued. Payloads over 16 KiB are refused, never split. On systemd 255.4 `--expand-environment=no` appears as the `no-env-expand` flag of `ExecStartEx`, and `%` is not expanded in transient command lines.

## Payload

Fixed shell text with validated parameters (unit names, invocation IDs, boot ID, deadline in hundredths of a second, SHA-256 digests, package names, versions and architectures), each step in the foreground:

1. Create `/run/lock/barectl` with mode 0700 if missing, and refuse unless it is a root-owned directory with mode 0700 (`/run/lock` is world-writable, so another user could have created it). Refuse a symlinked lock file; open `/run/lock/barectl/mutation.lock` for appending, which never truncates or replaces it, and refuse unless it is an empty root-owned regular file with one link. It holds no data.
2. `flock -n` on descriptor 9, which children inherit; failure exits 10. There is no waiting or lock stealing.
3. Under the lock: the boot ID must equal the reviewed one (exit 12), `/proc/uptime` must be before the deadline (exit 13), no other `barectl-apply-*.service` control group may report `populated 1` (exit 14), since a child can close the lock descriptor and outlive its wrapper, and fewer than 100 other bootstrap units may be retained, or 110 for a cleanup (exit 18). Unsafe lock state exits 11.
4. A metadata refresh recomputes the APT digest that preparation recorded: `apt-config dump`, SHA-256 of every file under `/etc/apt` except `auth.conf*`, and `apt-get indextargets --no-release-info` sources, each sorted with `LC_ALL=C`. Any changed configuration, hook, source or preference exits 15. Then `apt-get -q --error-on=any update` runs, with its output captured and at most 16 KiB of it written to the journal. APT's lists-lock contention fails immediately without waiting (exit 16); a nonzero status or any `W:`, `E:` or `Err:` line exits 17; otherwise exit 0.
5. A package profile recomputes the APT digest and its package digest (exit 15 on any difference), then installs exactly the reviewed transaction through APT with the inline pre-install guard, or enables and starts the reviewed service, and finally runs the profile's syntax check. Its exits 20 to 24 are recorded in [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md); 21 is a refusal before dpkg changed anything.
6. A cleanup first checks every reviewed unit: one systemd no longer loads is skipped; one with another `InvocationID`, a state other than `active/exited`, `failed` or `inactive`, or a populated control group exits 15 before anything is cleared. Then it runs `systemctl stop` for each unit still `active` (a successful unit kept after exit) and `systemctl reset-failed` for the others; systemd then forgets them. A refused `systemctl` exits 19, which can leave some units cleared. Journal entries are not touched.

Simultaneous submissions from independent controllers can both refuse: each one's unit exists while the other checks for processes. Neither waits; each needs a new plan.

## Inspection and outcomes

Inspection reads the boot ID, `systemctl show` of `Id`, `LoadState`, `ActiveState`, `SubState`, `Result`, `ExecMainCode`, `ExecMainStatus` and `InvocationID`, and `populated` from the unit's `cgroup.events`, all unprivileged. A unit is terminal only when nothing remains in its control group and it is `active/exited`, `failed` or `inactive`; such a retained unit is evidence, never a conflict. Native success is `ExecMainCode=1` (exited), status 0, `Result=success` and an empty control group; `Result=success` alone is not enough. Exits 10 to 16, 18 and 21 are refusals before any requested change. `Result=timeout` is a timeout, and a killed main process is a termination. The journal is never read: outcomes rest on systemd's unit state, so journal rotation or vacuuming does not change them.

Verification is separate. For a refresh, the authenticated noble, noble-updates and noble-security main indexes for the server's architecture must be present, and `/var/lib/dpkg/status` must be unchanged since before submission. For a cleanup, none of the reviewed units may still be retained. For a package profile, every reviewed package must be installed and configured at its reviewed version with nothing for `dpkg --audit` to report, the new roots marked manual and the new dependencies automatic while every other package keeps the automatic mark it had before submission, the profile's units must be the distribution's, enabled and running, and Nginx must listen on every IPv4 and IPv6 address of port 80; discovery is then queued to refresh the server's observations. A terminal run whose verification cannot be read closes as failed with verification unavailable and keeps its execution outcome.

Acknowledgement is not evidence. The worker records the dispatch before sending; a lost answer, lost connection, unreadable evidence, a run still active after four minutes of watching, or a stopped worker leaves the run reconciling, and Check outcome inspects the same unit name with a new connection, requiring the recorded invocation once known. Nothing is ever submitted again, resumed or replayed.

## Unknown outcomes

A unit that systemd no longer knows, after a restart or a cleanup, leaves its run reconciling as outcome unknown; its absence is never taken as proof that it did not run. An operator with the permission to apply the run's action may acknowledge it, which asks one check to close it. That check runs a finite probe, `/usr/bin/sh -c <probe>` as root or through `sudo -n` after `sudo -n -l` authorized exactly it, directly over the connection rather than as a unit, so nothing is retained. The probe takes the mutation lock the same way every payload does, without waiting, and while holding it prints the boot ID, the monotonic uptime, the number of bootstrap units with processes and the run's `LoadState`. The run closes as failed with outcome unknown only when the lock was taken, the boot changed or the uptime reached the run's deadline, no bootstrap unit has processes, the unit is still absent, and the acknowledging account is still active and allowed. Otherwise it stays reconciling with the missing proof. A delayed delivery of the old payload then refuses its boot or deadline under the lock before any change.

## Consequences

- Native service state is the only execution evidence; private plans and audit records stay in the application database. Native journal retention is the operating system's, and outcomes do not depend on it.
- Exclusion is qualified between two controller processes with independent databases, different aliases and different keys, submitting together: at most one mutation runs. Lock ownership by descendants, wrapper death, finite stop-limit termination and the runtime limit are qualified with real processes.
- Transient units do not survive a reboot. The acceptance container shares the Docker host's kernel, so restarting it removes every transient unit and `/run/lock/barectl` but keeps the kernel's boot ID and monotonic clock; a new boot ID is bind-mounted over `/proc/sys/kernel/random/boot_id` to stand for a reboot. A real kernel reboot, where the monotonic clock also restarts, is not exercised.
- Clearing finished runs removes evidence another installation may still need; that installation can then only close its run as outcome unknown. The review says so.
- Upstream sources: systemd 255 [systemd-run](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd-run.xml), [systemd.service](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.service.xml), [systemd.kill](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.kill.xml) and [systemctl](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemctl.xml) (`stop`, `reset-failed`); util-linux 2.39.3 [flock](https://raw.githubusercontent.com/util-linux/util-linux/v2.39.3/sys-utils/flock.1.adoc); Noble [apt-get](https://manpages.ubuntu.com/manpages/noble/man8/apt-get.8.html) for `--error-on=any`; [sudo](https://manpages.ubuntu.com/manpages/noble/man8/sudo.8.html) for `-n -l`. That a stopped or reset transient unit is forgotten, that a descendant killed after a zero main exit leaves `Result=success`, and that APT fails at once on its lists lock are Barectl's observations of systemd 255.4 and apt 2.8.3, not upstream guarantees.
