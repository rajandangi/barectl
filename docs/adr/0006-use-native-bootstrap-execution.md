# Use native bootstrap execution and exclusion

> Amended by [ADR 0032](0032-keep-secrets-in-private-native-files.md): a fixed command on the same connection may stage a secret from standard input for the payload to consume.

Apply runs submit one finite payload to a uniquely named transient systemd system service, which owns execution after the controller disconnects. Every payload acquires the same nonblocking native flock before validating its boot identity, admission deadline, the other bootstrap units, and its reviewed evidence. Pyinfra's shell interface, through the connection `discovery/ssh.py` opens, carries submission and inspection; neither a controller worker nor a local database lock owns remote execution or cross-device exclusion.

This is implemented in `bootstrap/native.py`, the one adapter apply services use, for every reviewed action: a package metadata refresh, clearing finished bootstrap runs, and the Nginx and PHP profiles, whose package transactions are admitted as [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md) records. All are qualified against the disposable Ubuntu 24.04 and 26.04 servers (`bootstrap/test_apply_remote.py`, `bootstrap/test_coordination_remote.py`, `bootstrap/test_package_remote.py`, `bootstrap/test_php_remote.py`) and offered in every installation.

## Submission

`systemd-run --unit=barectl-apply-<32 hex digits>.service --quiet --expand-environment=no --service-type=exec --remain-after-exit -p ExitType=cgroup -p Restart=no -p RuntimeMaxSec=30min -p TimeoutStopSec=60 -p KillMode=control-group -p StandardInput=null -p StandardOutput=journal -p StandardError=journal /usr/bin/sh -c <payload>`, run as root or through `sudo -n` after `sudo -n -l` authorized that exact command line. No `--scope`, `--pty`, `--pipe`, `--wait` or `--collect`; systemd-run returns once the main process was executed, and the SSH connection owns nothing of the unit. The unit name is saved locally when the run is queued. Payloads over 16 KiB are refused, never split; an action may also set native limits on the unit (`LimitFSIZE`, `MemoryMax` and `MemorySwapMax=0`, which every process of the unit inherits or is bounded by), which are further `--property` arguments of the same reviewed command line. On systemd 255.4 and 259.5 `--expand-environment=no` appears as the `no-env-expand` flag of `ExecStartEx`, and `%` is not expanded in transient command lines. The same command line, through sudo or Ubuntu 26.04's default sudo-rs, is used on both releases.

## Staged bodies

An action whose reviewed text does not fit 16 KiB submits it compressed. The payload is the shared admission under the lock, a unit suffix assignment and three fixed steps: decode the body (`printf` of its base64 into `base64 -d | gzip -dc`, bounded to 192 KiB), refuse with exit 15 unless its SHA-256 is the digest the payload names, and `eval` it in the same shell, which holds the lock and its descriptor 9 for every child. The bound still applies to what is submitted, to `ps`, to sudo's authorization and to the unit's metadata; the compressed body is not a second submission, a file left on the server or a helper installed beforehand, and it is not split across runs. The body is a pure function of the reviewed plan rows, so preparation computes and records its SHA-256 and refuses a plan whose payload would still not fit; applying rebuilds it and refuses unless the digest equals the reviewed one. WordPress installation uses this ([WordPress](../wordpress.md#applying-an-installation)).

## Payload

Fixed shell text with validated parameters (unit names, invocation IDs, boot ID, deadline in hundredths of a second, SHA-256 digests, package names, versions and architectures), each step in the foreground:

1. Create `/run/lock/barectl` with mode 0700 if missing, and refuse unless it is a root-owned directory with mode 0700 (`/run/lock` is world-writable, so another user could have created it). Refuse a symlinked lock file; open `/run/lock/barectl/mutation.lock` for appending, which never truncates or replaces it, and refuse unless it is an empty root-owned regular file with one link. It holds no data.
2. `flock -n` on descriptor 9, which children inherit; failure exits 10. There is no waiting or lock stealing.
3. Under the lock: the boot ID must equal the reviewed one (exit 12), `/proc/uptime` must be before the deadline (exit 13), no other `barectl-apply-*.service` control group may report `populated 1` (exit 14), since a child can close the lock descriptor and outlive its wrapper, Certbot's `certbot.service` control group may not report `populated 1`, read at `/sys/fs/cgroup/system.slice/certbot.service` and wherever `systemctl show -p ControlGroup` places it (exit 25), since scheduled renewal takes the same lock but its children do not keep it, and fewer than 100 other bootstrap units may be retained, or 110 for a cleanup (exit 18). Unsafe lock state exits 11.
4. A metadata refresh recomputes the APT digest that preparation recorded: `apt-config dump`, SHA-256 of every file under `/etc/apt` except `auth.conf*`, and `apt-get indextargets --no-release-info` sources, each sorted with `LC_ALL=C`. Any changed configuration, hook, source or preference exits 15. Then `apt-get -q --error-on=any update` runs, with its output captured and at most 16 KiB of it written to the journal. APT's lists-lock contention fails immediately without waiting (exit 16); a nonzero status or any `W:`, `E:` or `Err:` line exits 17; otherwise exit 0.
5. A package profile recomputes the APT digest and its package digest (exit 15 on any difference), then installs exactly the reviewed transaction through APT with the inline pre-install guard, or enables and starts the reviewed service, and finally runs the profile's syntax check. Its exits 20 to 24 are recorded in [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md); 21 is a refusal before dpkg changed anything.
6. A cleanup first checks every reviewed unit: one systemd no longer loads is skipped; one with another `InvocationID`, a state other than `active/exited`, `failed` or `inactive`, or a populated control group exits 15 before anything is cleared. Then it runs `systemctl stop` for each unit still `active` (a successful unit kept after exit) and `systemctl reset-failed` for the others; systemd then forgets them. A refused `systemctl` exits 19, which can leave some units cleared. Journal entries are not touched.

Simultaneous submissions from independent controllers can both refuse: each one's unit exists while the other checks for processes. Neither waits; each needs a new plan.

## Inspection and outcomes

Inspection reads the boot ID, `systemctl show` of `Id`, `LoadState`, `ActiveState`, `SubState`, `Result`, `ExecMainCode`, `ExecMainStatus` and `InvocationID`, and `populated` from the unit's `cgroup.events`, all unprivileged. The kernel removes only an empty control group, so a `cgroup.events` that is absent, or that disappears while it is read as the unit exits, reports no processes; one present without a `populated` line leaves the evidence unreadable. The properties and the control group are read one after the other, so a unit that exits between them reads as still running until the next inspection. A unit is terminal only when nothing remains in its control group and it is `active/exited`, `failed` or `inactive`; such a retained unit is evidence, never a conflict. Native success is `ExecMainCode=1` (exited), status 0, `Result=success` and an empty control group; `Result=success` alone is not enough. Exits 10 to 16, 18, 21 and 25 are refusals before any requested change. `Result=timeout` is a timeout, and a killed main process is a termination. Outcomes never read the journal: they rest on systemd's unit state, so journal rotation or vacuuming does not change them. The one exception is an action's retained result: a WordPress inspection retrieves the one bounded record its own unit published, by exact unit name and recorded invocation, and a missing record makes that result unavailable without changing the outcome ([WordPress](../wordpress.md#the-result)).

Verification is separate. For a refresh, the authenticated main indexes of the release's three suites, such as noble, noble-updates and noble-security, for the server's architecture must be present, and `/var/lib/dpkg/status` must be unchanged since before submission. For a cleanup, none of the reviewed units may still be retained. For a package profile, every reviewed package must be installed and configured at its reviewed version with nothing for `dpkg --audit` to report, the new roots marked manual and the new dependencies automatic while every other package keeps the automatic mark it had before submission, the profile's units must be the distribution's, enabled and running, and Nginx must listen on every IPv4 and IPv6 address of port 80; discovery is then queued to refresh the server's observations. A terminal run whose verification cannot be read closes as failed with verification unavailable and keeps its execution outcome.

Acknowledgement is not evidence. The worker records the dispatch before sending; a lost answer, lost connection, unreadable evidence, a run still active after four minutes of watching, or a stopped worker leaves the run reconciling, and Check outcome inspects the same unit name with a new connection, requiring the recorded invocation once known. Nothing is ever submitted again, resumed or replayed.

## Unknown outcomes

A unit that systemd no longer knows, after a restart or a cleanup, leaves its run reconciling as outcome unknown; its absence is never taken as proof that it did not run. An operator with the permission to apply the run's action may acknowledge it, which asks one check to close it. That check runs a finite probe, `/usr/bin/sh -c <probe>` as root or through `sudo -n` after `sudo -n -l` authorized exactly it, directly over the connection rather than as a unit, so nothing is retained. The probe takes the mutation lock the same way every payload does, without waiting, and while holding it prints the boot ID, the monotonic uptime, the number of bootstrap units with processes, the run's `LoadState` and `renewal 0` or `renewal 1`, the payload's renewal check. The run closes as failed with outcome unknown only when the lock was taken, the boot changed or the uptime reached the run's deadline, no bootstrap unit and no renewal has processes, the unit is still absent, and the acknowledging account is still active and allowed. Otherwise it stays reconciling with the missing proof. A delayed delivery of the old payload then refuses its boot or deadline under the lock before any change.

## Consequences

- Native service state is the only execution evidence; private plans and audit records stay in the application database. Native journal retention is the operating system's, and outcomes do not depend on it.
- Exclusion is qualified between two controller processes with independent databases, different aliases and different keys, submitting together: at most one mutation runs. Lock ownership by descendants, wrapper death, finite stop-limit termination and the runtime limit are qualified with real processes.
- Transient units do not survive a reboot. The acceptance container shares the Docker host's kernel, so restarting it removes every transient unit and `/run/lock/barectl` but keeps the kernel's boot ID and monotonic clock; a new boot ID is bind-mounted over `/proc/sys/kernel/random/boot_id` to stand for a reboot. A real kernel reboot, where the monotonic clock also restarts, is qualified separately on Ubuntu's arm64 cloud image in a virtual machine (`bootstrap/test_reboot_vm.py`): a reboot during an installation leaves no unit or lock directory, nothing resumes, the run closes only as outcome unknown, and a payload delivered afterwards refuses its boot although its deadline is still ahead on the new clock.
- The renewal check holds only between controllers that perform it. A controller from before it, such as v0.2, does not check the renewal control group and must be upgraded or stopped before a server is managed with renewal; no remote version registry records which controllers exist. An administrator's own commands that do not take the lock remain outside the guarantee.
- Clearing finished runs removes evidence another installation may still need; that installation can then only close its run as outcome unknown. The review says so.
- Upstream sources: systemd 255 [systemd-run](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd-run.xml), [systemd.service](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.service.xml), [systemd.kill](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.kill.xml) and [systemctl](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemctl.xml) (`stop`, `reset-failed`); util-linux 2.39.3 [flock](https://raw.githubusercontent.com/util-linux/util-linux/v2.39.3/sys-utils/flock.1.adoc); Noble [apt-get](https://manpages.ubuntu.com/manpages/noble/man8/apt-get.8.html) for `--error-on=any`; [sudo](https://manpages.ubuntu.com/manpages/noble/man8/sudo.8.html) for `-n -l`. That a stopped or reset transient unit is forgotten, that a descendant killed after a zero main exit leaves `Result=success`, and that APT fails at once on its lists lock are Barectl's observations of systemd 255.4 and 259.5 and apt 2.8.3 and 3.2.0, not upstream guarantees. On systemd 259 a finished unit reports an empty `ControlGroup`, which inspection reads as no processes. The systemd 259 counterparts of those manual pages are [systemd-run](https://raw.githubusercontent.com/systemd/systemd/v259/man/systemd-run.xml), [systemd.service](https://raw.githubusercontent.com/systemd/systemd/v259/man/systemd.service.xml) and [systemd.kill](https://raw.githubusercontent.com/systemd/systemd/v259/man/systemd.kill.xml), and sudo-rs is documented in [sudo-rs(8)](https://manpages.ubuntu.com/manpages/resolute/man8/sudo-rs.8.html).
