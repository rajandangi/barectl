# Supply runtimes and tools from one pinned multi-user Nix

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323), subject to Phase A qualification. [#330](https://github.com/rajandangi/barectl/issues/330) implements the catalog lock, the CI job that generates and checks it, the freshness alarm against the pinned channel head and realisation evidence on both architectures; installing runtimes on servers is not implemented. Supersedes [ADR 0016](0016-limit-third-party-php-supply.md) and the PHP supply and single-default-version rules of [ADR 0008](0008-review-each-ubuntu-release-by-its-own-policy.md) for new servers.

Each server has one multi-user Nix installation from the official installer tarball for an exact release, whose hash is pinned in Barectl's source. Nix supplies PHP CLI and FPM with extensions, Composer, WP-CLI, Node.js, Python, uv, restic and Caddy. Servers never evaluate nixpkgs. Barectl's source holds a catalog lock, generated from one pinned nixpkgs commit, listing each entry's exact `out` output store path per architecture; a server realises exactly those paths from cache.nixos.org and refuses anything else, as [ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md) does for APT. A CI job with Nix regenerates the lock from the pinned commit and fails on any difference, so it is never edited by hand. Builds leave the lock only by retirement: still recognized by store path, never offered again. Each runtime is a Nix profile under `/nix/var/nix/profiles/barectl/`, so generations are the rollback candidates and garbage-collection roots, and discovery matches them to the lock with ordinary tools. Sites select a runtime; identical builds are shared, never copied per site.

Ubuntu's archive gives one PHP per release, and per-site versions needed a third-party APT source with its own trust, freshness and admission machinery (ADR 0016) that only covered PHP. Nix gives every supported version on both architectures from one reviewed supply, for every language. Ubuntu's `nix-bin` was rejected: it is in universe without updates. Evaluating a pinned nixpkgs tarball on each server was the first plan; it was dropped because evaluation costs memory on small hosts, needs a nixpkgs download, and makes the review unable to name the exact result. Flakes were rejected while they remain experimental.

Only root may use the daemon (`allowed-users = root`, `trusted-users = root`); there is no operator group, because discovery reads world-readable files. The only substituter is cache.nixos.org, `max-jobs = 0` and `fallback = false`, so a server never builds. The store is world-readable, so no configuration, credential or user data enters it. Security fixes ship as reviewed in-branch catalog updates with Barectl releases, so a fix reaches servers only when Barectl releases it; this latency is a stated limitation. The nixpkgs branch moves about every six months, when a stable branch ends, as a reviewed change. Phase A must qualify cold install cost, store size, AppArmor behavior, atomic profile switches and recovery from a failed switch. Details are in the [target architecture](../target-architecture.md#nix).
