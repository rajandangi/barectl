# Inhibit Certbot's renewal until the guard is verified, and guard it with the payloads' lock

Renewal setup installs the distribution's Certbot and makes its packaged `certbot.timer` run only Barectl's guarded wrapper ([ADR 0011](0011-use-native-certbot-renewal-under-shared-exclusion.md)). Installing the package would otherwise enable and start the timer from the maintainer scripts, before any guard exists. Implemented in `tls/setup_native.py` (the payload), `tls/renewal.py` (the files) and `tls/setup.py` (admission).

## Inhibition

The payload runs under the mutation lock of [ADR 0006](0006-use-native-bootstrap-execution.md), which refuses while Certbot's renewal service has processes (exit 25). It then masks `certbot.timer` and `certbot.service` with `systemctl mask --runtime`, rechecks the renewal control group, and only then installs the reviewed transaction ([ADR 0007](0007-admit-exact-package-transactions-with-an-inline-apt-guard.md)). With the runtime mask, the maintainer scripts' `deb-systemd-helper enable` fails to preset the timer and `deb-systemd-invoke` does not start a unit that is not enabled, on Certbot 2.9.0-1 with init-system-helpers 1.66ubuntu1 and Certbot 4.0.0-4 with 1.69: the timer is left disabled. A refusal that changed nothing (15, 16, 21, 23, 25) removes the masks it added; systemd refusing the mask exits 27. A reboot anywhere removes the runtime masks and leaves the timer disabled, and setup is admitted only while Certbot has no account, lineage or hook, so nothing can renew unguarded.

After the files are published, `systemctl daemon-reload` and unmasking the service, the payload requires `certbot.service` to load the packaged unit with exactly the reviewed drop-in: its one `ExecStart` the wrapper, `SuccessExitStatus=75 76`, a 30 minute start limit, a 60 second stop limit, `KillMode=control-group`, and both scripts valid shell (otherwise exit 29, timer still masked). Only then does it unmask the timer and run `systemctl enable --now certbot.timer` (exit 30 when refused). The packaged schedule, twice a day with up to 12 hours of random delay and catch-up after downtime, is kept unchanged.

A plan prepared after an interrupted setup recognizes the installed packages, pristine Certbot state and any renewal files that already have their reviewed bytes, and proposes only what remains. It is a new review, not a resume.

## Guarded renewal

The drop-in replaces Certbot's command with `/usr/bin/sh /usr/local/sbin/barectl-certbot-renew`. The wrapper takes the mutation lock with the payloads' own steps, generated from the same code (`bootstrap.native.lock_steps`), recreating the root-only lock directory and empty lock file after a reboot empties `/run`. It skips with exit 75 when another change holds the lock and with exit 76 when any `barectl-apply-*` control group has processes, since an apply run's child can close the lock descriptor. Holding the lock, it runs `certbot -q renew --no-random-sleep-on-renew --no-directory-hooks --deploy-hook /usr/local/sbin/barectl-certbot-deploy`, so a hook placed in `renewal-hooks` never runs and a manual `certbot renew` never reloads outside the lock. Certbot inherits the lock descriptor; its hook, started with Python's default `close_fds`, does not, which is why every apply run also refuses while the renewal control group has processes.

The deploy hook runs `nginx -t -q` before `systemctl reload nginx.service` and writes each failure to the journal. Certbot does not act on a deploy hook's exit status, so after `certbot renew` the wrapper compares, for each lineage whose `live` link changed, the certificate Nginx serves on 127.0.0.1:443 for each of its names with the one on disk, validated against the system trust store; a difference exits 80. The service's outcome, the certificate on disk and the certificate served stay separate facts, and none depends on the journal.

## Consequences

- Compatible controllers are required: a controller without the renewal check can apply while renewal runs. No remote registry records which controllers exist; administrative commands that ignore the lock remain outside the guarantee.
- Barectl never disables, stops or removes other automation. Other certificate units, snaps, scheduled tasks naming certificate tools, Certbot plugins or ACME clients, per-user Certbot configuration and unknown overrides refuse setup, naming the command an administrator would run.
- `systemctl enable` is not recorded by `deb-systemd-helper`, so purging Certbot may leave the `timers.target.wants` link. A later Certbot package from unattended upgrades may change the qualified version; the persistent drop-in keeps its renewal guarded.
- Qualified on both releases' disposable containers, where a container restart with a bind-mounted boot ID stands for a reboot; see the [qualification record](../v0.3-qualification.md). Upstream sources: Certbot's [using guide](https://raw.githubusercontent.com/certbot/certbot/v4.0.0/certbot/docs/using.rst) (`renew`, `--deploy-hook`, `--no-directory-hooks`), systemd's [systemctl](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemctl.xml) (`mask --runtime`) and [systemd.service](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.service.xml) (`SuccessExitStatus`, `TimeoutStartSec`), and init-system-helpers' `deb-systemd-helper` and `deb-systemd-invoke`. That a runtime mask leaves the timer disabled is Barectl's observation of those packages, not an upstream guarantee.
