# One change engine with effect-derived consent

Accepted on 2026-10-10 for [#323](https://github.com/rajandangi/barectl/issues/323). Implemented in `operations` as the one change boundary; every change kind registers with it. One engine in the `operations` app owns target-stack changes: prepare, review, apply natively, verify and reconcile. Each kind of change supplies four parts: an inspection, a pure review, a native body and a verification. A review is stored once, as a typed core plus a versioned document for its kind, and a run keeps a protected reference to the review it applies, instead of each feature keeping its own plan and run model pair.

The review declares the change's effects, and the engine derives its consent level from them: Read, Site, Shared or Destructive. A kind never chooses its own level. Server-wide changes require Shared consent; an effect that destroys data requires Destructive consent. A Shared change lists every affected site, read from current evidence, and that list is rechecked under the shared lock; if it changed, the run is refused and needs a new review.

Payloads report one journal line beginning `barectl-result ` followed by JSON with a `class` (`succeeded`, `refused`, `partial`, `failed`, `lock_busy` or `timed_out`) and, where useful, one fixed `reason`. The kind does not add result classes or exit-code catalogs. Bodies are checked-in scripts staged over the verified SSH connection's standard-input channel into `/run/lock/barectl`; the unit wrapper removes the staged copy on admission refusal, and the body removes itself on completion, failure or timeout. The staging area is volatile and is not an operation journal or inventory.

The released features each kept separate plan and run models and their own permission names, about twenty pairs of each. Three Phase A change kinds (host foundation, add runtime, create site) already share the same sequence, and consent follows the affected resources rather than the feature name. [ADR 0038](0038-drain-site-php-through-private-haproxy.md) later replaces shared serving masters; genuine shared effects still require Shared consent. Reopening the per-feature model is justified because the target stack replaces every feature that used it. The cost is that kind-specific details are no longer queryable columns; reviews are read whole by their own page, and [ADR 0003](0003-store-discovery-snapshots-in-typed-columns.md) still governs discovery snapshots, which are queried.

This reopens the per-feature immutable plan record of [ADR 0005](0005-review-exact-bootstrap-transitions.md): a review stays immutable and bound to fresh evidence, but it is stored once in the engine's record instead of in a model per feature, because twenty near-identical pairs made each new change kind costly and let permissions drift. [ADR 0004](0004-serialize-remote-operations-in-one-table.md)'s single operation table is kept.

After an authorized change finishes, its automatic observation uses Read authority: `operations.view_changes` and `servers.view_server`. It retains the original actor and captured connection revision. The worker rechecks that the actor still exists, is active and retains both permissions before SSH; a deleted actor never becomes anonymous authority. A changed connection revision refuses the refresh. A refused or busy refresh leaves the already completed native outcome intact and the cached view visibly awaiting observation. Manual registration, connection edits and connection checks retain their existing authority requirements. This allows a Site operator to complete the apply and observation workflow without a Server-management grant.
