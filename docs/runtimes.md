# Target runtime profiles and site PHP

This page describes the unreleased integration. [ADR 0038](adr/0038-drain-site-php-through-private-haproxy.md) separates per-runtime diagnostic masters from per-site serving masters. Caddy sends application requests through private per-site HAProxy admission. Each site has its own PHP-FPM master for its selected runtime, temporarily two during a switch. Full integrated qualification remains pending in [#339](https://github.com/rajandangi/barectl/issues/339). Earlier diagnostic protection evidence does not qualify the serving convention.

On a verified target-stack host, open **Stack → Runtime catalog** and choose **Add runtime** for `php84`, `php85`, `nodejs_22` or `nodejs_24`. Preparation is read-only. The review names the architecture, exact locked store path, shared effects, configuration and native postconditions. An Administrator applies its Shared review. A Site operator can prepare it but cannot apply a Shared change.

Preparation stores one immutable, versioned, non-secret catalog selection. The worker validates it before SSH. Native apply consumes the stored review, rechecks the touched native evidence under the shared mutation lock, and queries the signed cache before creating a profile or configuration. Nix has `max-jobs = 0` and `fallback = false`; a missing closure refuses rather than compiling. Node creates only `/nix/var/nix/profiles/barectl/<entry>` and starts no service.

A PHP profile selects one locked build. Its per-runtime master serves only the fixed diagnostic pool, never application pools. `/etc/php-fpm/<entry>/php.ini`, `php-fpm.conf` and `pools/diagnostic.conf` configure its `php-fpm@<entry>.service` master. The template follows the [pinned NixOS FPM module](https://github.com/NixOS/nixpkgs/blob/7c8764b7c7b09b34f632464276218ef9090eaa11/nixos/modules/services/web-servers/phpfpm/default.nix), using `Type=notify`, the profile executable, explicit ini/configuration, private temporary and device namespaces and `USR2` pool reload. It preserves the Nix wrapper's extension scan configuration by leaving `PHP_INI_SCAN_DIR` unset. A catalog build change requires a restart and is a later reviewed operation.

The master enables OPcache permission and root checks, restricts its API to `/etc/php-fpm/diagnostics/`, disables file cache and preload, and turns off `expose_php`. Passive discovery refuses unexpected diagnostic pool directives and files before executing its fixed probe. Each command has a time limit and its captured output is capped while it runs. A fixed diagnostic script returns only selected effective settings, OPcache directives, PHP version and loaded extensions. Barectl binds the active unit invocation and main executable to the catalog build's wrapped executable and binds the diagnostic worker's actual parent PID to that master. The native unit's MainPID and invocation must remain the same across the request. It executes through that running master's private pool, using the [official pinned fcgi 2.4.7 client](https://github.com/NixOS/nixpkgs/blob/7c8764b7c7b09b34f632464276218ef9090eaa11/pkgs/by-name/fc/fcgi/package.nix) with connect-only mode. Barectl does not implement FastCGI framing.

Before making a diagnostic request, discovery also requires native load evidence. The manager's initial `ExecMainStartTimestamp`, or the successful fixed `ExecReload` command's start timestamp, must follow every guarded configuration file's ctime and mtime. The manager's effective `ExecStart` arguments must select the exact profile executable and standard ini/master paths, with empty unit environment, environment-file, pass/unset-environment and drop-in sources; safe unit bytes on disk alone cannot attest cached manager settings. Current-master syslog datagrams must show the matching complete startup or reload sequence, with trusted PID, executable, boot and invocation fields. Discovery holds the native mutation lock and compares the load and file evidence before and after the request. A disk repair without reload, missing or bounded-out journal evidence, an unbound direct `USR2`, or an observed realtime/monotonic clock discrepancy makes the live evidence unavailable. Ordinary `systemctl reload php-fpm@<entry>.service` establishes a newer configuration-load boundary while the original executed-command binding remains available. A systemd manager reset such as `daemon-reload` clears that per-command PID/start tuple, even if the displayed arguments are unchanged; a service reload cannot restore it. Use ordinary `systemctl restart php-fpm@<entry>.service` to restore verified execution evidence after that reset. Adding another runtime avoids a manager reload when the shared template bytes are unchanged. Discovery never reloads or restarts a service itself.

This is a conservative inference from ordinary native configuration and trustworthy server clocks. It does not attest historical state against root changing clocks or filesystem metadata. PHP request overrides cannot prove the original loaded configuration: FPM can retain pool settings and cached ini `PATH` sections after safe disk bytes are restored. The [locked PHP8.4 FPM request handling](https://github.com/php/php-src/blob/php-8.4.26/sapi/fpm/fpm/fpm_main.c), [PHP8.5 ini activation](https://github.com/php/php-src/blob/php-8.5.11/main/php_ini.c), and [systemd259 execution properties](https://github.com/systemd/systemd/blob/v259/src/core/dbus-execute.c) and [service serialization](https://github.com/systemd/systemd/blob/v259/src/core/service.c) define this boundary. No diagnostic request overrides mandatory OPcache values.

The diagnostic worker runs as the unprivileged locked `php-probe` identity. Its root-owned socket is mode `0600`. The script and every ancestor are controlled by root; only the diagnostic group may read its directory. The pool sets `pm = ondemand`, `pm.max_children = 1` and `pm.process_idle_timeout = 10s`, with private session, upload and temporary directories. It does not override the master's OPcache protections. Per-site serving masters use their own private directories and independently bound diagnostic and status evidence. Because those on-demand workers start for any concurrent probe and exit when idle, a read of a master's process inventory judges only a listing that holds still across the read, waiting up to one second for one; a listing that keeps changing is unavailable evidence. See [PHP FPM configuration](https://www.php.net/manual/en/install.fpm.configuration.php) and [OPcache configuration](https://www.php.net/manual/en/opcache.configuration.php).

**Stack → PHP runtimes** reads the current discovery snapshot, including native profile generations, exact catalog identity, extensions, master state and live protections. An unknown profile path is reported without adoption. A protection fault makes that runtime's live protection evidence unavailable. It does not block adding an independent PHP master or a Node profile when the selected resource and shared identity/files remain safe; unchanged shared probe and unit files are not rewritten. Missing, inaccessible or malformed evidence is unavailable evidence, never a passing protection. A repeated Add runtime review proposes no changes only when the exact offered build and its live master convention match.

Site discovery reads the convention once and then each site's live PHP protection evidence in its own bounded command, because one site's verification is far below the [command bound](ssh-connections.md#bounds-and-read-only-commands) while several bundled into one command are not. A site whose own read fails is reported as outside supported settings, so one unreachable site cannot make the others unavailable.

This slice does not qualify cross-site isolation or minimum host capacity. Those require the Phase A native isolation and constrained-host measurements. The host foundation's 4 GiB disk and 900 MiB memory admission thresholds remain provisional.


The executable check follows the pinned [PHP extension wrapper](https://github.com/NixOS/nixpkgs/blob/7c8764b7c7b09b34f632464276218ef9090eaa11/pkgs/development/interpreters/php/generic.nix): the catalog output wraps FPM to preserve extension loading. Barectl compares the running executable with the resolved `.php-fpm-wrapped` inside that exact output, not the wrapper's configured `ExecStart` text alone. A restart during the diagnostic read makes that evidence unavailable.

## Server command defaults

Stack's Defaults section prepares separate Shared reviews for PHP and Node. The [server-default convention](runtime-defaults.md) owns command links, selected-interpreter wrappers, native refusal rules and reconstruction. Existing sites keep their own selections. New-site forms preselect only a fresh, verified observed PHP default.

## Site Node selection

A site's Runtime page offers its own installed Node selection through a Site review. This changes only the root-owned `bin/node`, `bin/npm` and `bin/npx` links under that site to the selected profile. It does not reload PHP or Caddy, change the site's PHP wrappers, change application files, or change server defaults. The native payload rechecks site evidence, profile identity and all link preimages under the existing native and site locks. Native discovery reconstructs the selected profile from all three links. Foreign commands refuse adoption. A mixed or incomplete known-link selection is reported as interrupted and can be repaired through another Node selection review.

## Site PHP selection

The site's Runtime page offers installed `php84` and `php85` builds from fresh discovery. Preparation reads native serving evidence and creates an immutable review through the change engine. The review identifies the exact build and any current optional modules missing from the target. Missing modules or unavailable serving evidence refuse the change. Consent follows the declared effects; a change confined to this site's serving and command wrappers takes Site consent.

Apply rechecks the review under the global native lock and the stable site deployment lock. It starts and verifies the target site's FPM master, enables its HAProxy backend and places the source backend in maintenance. It persists HAProxy's unedited native server state before draining the source. Both backend objects remain in the immutable proxy configuration. Neither Caddy nor HAProxy reloads during the switch.

Source cleanup requires HAProxy's exact native removable result and complete FPM status, application PID and cgroup evidence that source work has finished. This includes work after `fastcgi_finish_request()`. A bounded drain that cannot establish completion retains source PHP and reports an incomplete change. It never turns an expired wait into success or kills remaining work to complete the selection. Application request timeouts remain infinite at the private proxy; operation waits are bounded separately.

A fresh controller reconstructs selection and incomplete transitions from native configuration, HAProxy API and persisted state, service identity and command wrappers. The Runtime page distinguishes the current selection, unavailable evidence and a recognized incomplete transition. To finish or reverse an incomplete transition, choose the intended installed runtime and prepare a fresh review. Reversing after target admission drains that target through the same protocol. A successful selection updates the site's PHP, Composer and WP wrappers without editing application files, changing server defaults or changing another site's selection.

The fixed per-site FPM and HAProxy unit templates are installed with the host foundation. Site creation starts its private services before publishing the Caddy route through whole-tree validation and guarded reload. A separate proxy identity and private Unix socket permissions prevent the site identity and Caddy from bypassing admission. The HAProxy administrative API is root-only. These controls and the switch behavior still require the exact-source integrated evidence tracked in #339; this page makes no cross-site isolation, minimum-host or Phase A completion claim.
