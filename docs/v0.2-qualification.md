# v0.2 qualification record

This record lists the evidence for the [v0.2 bootstrap](v0.2.md) acceptance gates, as run on 2026-09-29 for [#112](https://github.com/rajandangi/barectl/issues/112) on Ubuntu 24.04 for [#128](https://github.com/rajandangi/barectl/issues/128) on Ubuntu 26.04, and for [#130](https://github.com/rajandangi/barectl/issues/130) on Ubuntu 26.04 with a hosting provider's customizations. It states what was tested and on which revisions. Anything not listed as tested is not qualified. It prepares v0.2 for release; it is not a release.

Operators: see [bootstrapping a server](bootstrap.md) for what to expect. Contributors: the tests named below are described in [acceptance against a real server](ssh-connections.md#acceptance-against-a-real-server).

## Acceptance criteria

### Operator journey through browsers and disposable servers

Qualified. `bootstrap/test_journey_remote.py` runs one server through a clean start without package indexes, the refusal for missing metadata, an explicit reviewed refresh, an Nginx installation left partly done by an external listener (packages installed exactly, verification failed, nothing repaired), recovery with `systemctl reset-failed` and a reviewed start, the independent PHP profile, satisfied profiles with no apply offered, a rejected customization, and a subsequent fresh review. `dashboard/test_browser_remote.py` drives Chromium through preparation, keyboard review and apply of the Nginx profile against the same server. Earlier suites cover each step in more depth: `bootstrap/test_package_remote.py`, `bootstrap/test_php_remote.py` and the fake-server browser tests in `dashboard/test_browser.py`.

### Destroyed controller and reconstruction by another installation

Qualified. At the end of the journey every record of the first installation is deleted, and a second installation, a separate process with its own database, account, SSH configuration and second key, reconstructs the packages, both services, the default site and pool, and reviews both profiles as satisfied. It holds none of the first installation's accounts, servers, plans, apply runs or Activity entries, and those runs' pages do not exist there; it sees their units only as finished native work in a cleanup review. A controller killed right after acknowledgement, whose run finishes and is reconciled from its database by a new process, is covered by `bootstrap/test_apply_remote.py`.

### External changes, denied evidence, drift and unsupported layouts

Qualified by the existing suites, with the journey adding an external listener during installation and an added `conf.d` file. `bootstrap/test_remote.py` covers customized and leftover configuration, missing indexes, unknown hooks and an account without sudo; `bootstrap/test_package_remote.py` and `bootstrap/test_php_remote.py` cover dependency, hold and mark drift between review and lock, guard refusals after revalidation, masked and stopped units, extra pools, other PHP releases and foreign socket listeners; `discovery/test_remote.py` covers external site changes and a refresh that cannot connect keeping the last snapshot marked possibly out of date. An expired Ubuntu Release file refuses an installation plan in `bootstrap/test_workflow.py`, against recorded evidence only. Plans are prepared only from fresh reads, and the payload recomputes its digests on the server; a cached snapshot never decides a plan or a run.

### Execution and uncertainty

Qualified, including a real reboot. Disconnection before and after acknowledgement, delayed submissions past the deadline and across a boot change, missing journals, wrapper and child faults, the runtime and stop limits, package-manager contention and a partial download that stops APT before dpkg are covered by `bootstrap/test_apply_remote.py`, `bootstrap/test_coordination_remote.py` and `bootstrap/test_package_remote.py`. The production submission's unit properties are asserted on real units, and only the timeout and stop-limit tests shorten a limit.

`bootstrap/test_reboot_vm.py` reboots a real kernel while dpkg installs PHP: the new boot has a new boot ID and a restarted monotonic clock, no transient unit, lock directory or package process remains, nothing resumes, Check outcome keeps the run reconciling until an acknowledgement closes it as outcome unknown with the lock taken, and a reviewed payload held in transit through a second alias, delivered while its deadline is still ahead on the new clock, refuses its boot before APT runs. The interrupted packages are refused until `dpkg --configure -a` and `apt-get install -f` complete them, after which a fresh review leaves PHP serving.

### Terminal-unit maintenance and registration removal

Qualified. `bootstrap/test_coordination_remote.py` keeps cleanup usable at 100 retained units, including failed and partly created ones, refuses a cleanup whose reviewed unit changed and never touches a unit with processes; journal entries and Barectl's audit stay. The journey refuses removal while a run is reconciling, removes the registration after Check outcome, and keeps all five runs as audit with every unit still on the server; the browser test removes a registration and finds the run's audit detached. `bootstrap/test_package_apply.py` and `bootstrap/test_cleanup.py` check that the audit keeps the exact reviewed package transitions, or the units a cleanup cleared, after the plan is deleted with the registration. Fake-server tests in `bootstrap/test_apply.py` and `bootstrap/test_cleanup.py` cover the local rules.

### Accounts, permissions and presentation

Qualified by existing tests, with one addition. Multiple accounts with separate permissions, inventory-only access, the worker's recheck of the requesting account before dispatch, CSRF on every mutating form, duplicate submissions converging on one run, Activity filtering, keyboard and focus behavior, and the wording of outcome unknown and verification unavailable are covered in `bootstrap/test_apply.py`, `bootstrap/test_cleanup.py`, `bootstrap/test_workflow.py` and `dashboard/test_browser.py`. In Chromium, a second tab that submits an already applied revision lands on the same run. The new browser test checks inventory-only access against a run that really changed the server.

### Repository gates and native revisions

Every command in the README's development checks, `docker/disposable-server/run-tests.sh --env-file .env` (49 tests, the `vm` test skipped) and `docker/vm-server/run-tests.sh --env-file .env` passed locally on arm64 on the branch that added this record, and every CI job of [its pull request](https://github.com/rajandangi/barectl/pull/124) passed, including the disposable-server tests on x86_64. The evidence added for [#106](https://github.com/rajandangi/barectl/issues/106), the partial download, the extra guard actions, the expired Release file, the repeated browser submission and the audit's reviewed changes, passed every development check and the disposable-server tests (50 tests, the `vm` test skipped) locally on arm64 with the same revisions; the virtual machine test was not rerun for it. The revisions are in the table above.

For [#128](https://github.com/rajandangi/barectl/issues/128), every development check and the disposable-server tests for both releases (51 tests each, the `vm` test skipped) passed locally on arm64, and the pull request's CI runs them for both releases on x86_64. `BARECTL_VM_RELEASE=26.04 docker/vm-server/run-tests.sh` booted Ubuntu's official 26.04 cloud image (`resolute/current`) on arm64 under QEMU emulation three times. Twice, a reviewed refresh and the Nginx profile were applied and verified on the image as shipped, but the server was not seen back within fifteen minutes of starting the PHP installation that should reboot it, and the test records no reason; once, emulation made the Nginx installation outlast the worker's four-minute watch. A plain `systemctl reboot` of that guest came back within a minute. The reboot test therefore established no result on 26.04; the script now prints the guest's console, and the test the run's journal, when it fails.

For [#130](https://github.com/rajandangi/barectl/issues/130), every development check and the disposable-server tests passed locally on arm64: 53 on each release, the `vm` test skipped, and on the unchanged 24.04 image also the two tests that need the provider customizations of the 26.04 image. The virtual machine test was not rerun.

### Manual browser acceptance

An operator session in Chromium, driven by an automation tool against a running Barectl with its worker, repeated the journey by hand against a fresh disposable Ubuntu 24.04.5 server on arm64 with the revisions above:
- a refusal for missing indexes;
- a reviewed refresh, submitted with a double click, which created one unit;
- Nginx, applied from the keyboard, then a satisfied profile with no Apply offered;
- PHP 8.3, with the worker killed while the unit ran; the run became reconciling after the stale limit, and Check outcome recorded success without a second submission;
- an external stop and disable fixed by a service-only plan;
- a refused customization, and a refused apply after the configuration changed under review;
- an immediate refusal while another process held the mutation lock;
- a privilege refusal through a second alias for an account without sudo;
- inventory-only access, which showed no plans and returned 403 for plan and run pages;
- cleanup of seven finished units, with journals kept;
- removal refused during a preparation, then removal with every run kept as audit;
- a fresh registration that reconstructed Nginx, PHP-FPM, the default site and the `www` pool from the server.

The manual browser acceptance was run on Ubuntu 24.04 only. On Ubuntu 26.04, the fake-server browser test of `dashboard/test_browser.py` reviews and applies the PHP 8.5 profile, and `dashboard/test_browser_remote.py` drives Chromium against the disposable 26.04 server.

### Ubuntu 26.04

Qualified on the revisions above by running every suite of this record against the disposable Ubuntu 26.04.1 server, unchanged except for the release's profile data ([ADR 0008](adr/0008-review-each-ubuntu-release-by-its-own-policy.md)): the operator journey and reconstruction, refusals and drift, the guard refusing every mismatched transaction before dpkg, contention, partial downloads, execution faults, coordination between two controllers, cleanup at capacity, and the PHP 8.5 profile with `php-common`'s epoch archive. APT 3.2.0's `apt-config dump`, index targets, simulation, update errors, lock messages and protocol-version-3 hook input are in APT 2.8.3's forms; systemd 259.5 runs the unchanged submission; sudo-rs, and `sudo.ws` when selected, lists exact commands and refuses a password-requiring rule without prompting (`bootstrap/test_remote.py`). The tested hook baseline was compared with `apt-config dump` of Ubuntu's official 26.04 server cloud image root filesystem, and matches it.

Since [#130](https://github.com/rajandangi/barectl/issues/130), the disposable 26.04 image also carries what a hosting provider's 26.04.1 amd64 server added ([ADR 0008](adr/0008-review-each-ubuntu-release-by-its-own-policy.md#hosting-providers-images)), and every 26.04 suite above runs with it: refresh, Nginx and PHP succeed with the third-party repository configured, whose index targets print `$(ORIGIN)`; the Nginx review lists it and admits PackageKit's and `ubuntu-helper-virt-hwe`'s hooks, and is refused once the repository also offers an `nginx-common` older than Ubuntu's (`bootstrap/test_remote.py`); a payload traced with `Debug::RunScripts` runs debconf's hook, then `ubuntu-helper-virt-hwe`'s, then the guard and its one admission before dpkg's first unpack, and succeeds; and with the `99lock-timeout` of 60 seconds, a held frontend lock refuses at once without APT's `Waiting for cache lock` (`bootstrap/test_package_remote.py`). The 24.04 image is unchanged.

## Changes made during qualification

- Ubuntu's official server cloud image installs APT hooks from `packagekit`, `appstream` and `snapd` that the disposable container did not have, so every plan on that image was refused for unknown hooks. They are now part of the tested baseline: none runs before dpkg, snapd's runs only for the `apt` command, the disposable image installs the three packages, and the virtual machine exercises them as shipped.
- The manual browser acceptance found three defects. The apply page now replaces its audit together with its polled status, so a finished run no longer shows "Not submitted". A reconciling run's execution now reads "Running when last inspected" instead of claiming it is still running. An unsupported platform's refusal now comes before the evidence gaps it causes.
- After an interrupted installation, dpkg refuses every read by an account other than root until its pending records are completed. The review still refuses, but it now names `sudo dpkg --configure -a` instead of only saying that dpkg's audit could not be read.

- Reproducing the provider's customizations showed that a repository address with a port, whose list files are named like `127.0.0.1:8750_dists_resolute_InRelease`, made its Release fields unreadable. They are read now.

## Not qualified

- amd64 in a virtual machine, and a real reboot on amd64. The reboot was exercised only on arm64 under emulation.
- A real reboot on Ubuntu 26.04, and the PHP profile on Ubuntu's official 26.04 cloud image booted as a server. The reboot test has not completed there; see above.
- A real Ubuntu 26.04 server. A read-only review of a hosting provider's 26.04.1 amd64 server was refused for its third-party repository, hooks and lock timeout, which [#130](https://github.com/rajandangi/barectl/issues/130) reproduces and admits; a new review there is pending; until then 26.04 is qualified on the disposable container and the cloud image's configuration only.
- Ubuntu interim releases, and Ubuntu 24.04 or 26.04 with APT or systemd of another series.
- Physical servers, and cloud providers' own images other than Ubuntu's official cloud image, beyond the customizations the disposable 26.04 image reproduces. Third-party repositories are qualified only as that local, signed, unpinned HTTP repository.
- needrestart restarting a service during an installation. In every run it reported nothing to restart.
- Arbitrary root processes that change packages without dpkg's locks between the guard and dpkg; the coordination contract excludes them rather than detecting them.
- Journal retention policies other than the defaults, beyond the rotation and vacuum test.
- Real network partitions; connection loss is injected by dropping a real connection's answers.
- Hardware-backed SSH keys.
- An expired Release file on a real server. Ubuntu's archive sets no `Valid-Until`, so the refusal is tested only against recorded evidence.
- Automated real-server browser tests for the PHP profile, metadata refresh and cleanup. They were exercised against a real server only in the manual browser acceptance above; the automated real-server browser journey covers Nginx.

## Blockers

None of the acceptance criteria failed.
