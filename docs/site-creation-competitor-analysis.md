# Site creation competitor analysis

Research checked on 2026-10-10 using first-party documentation. The question is how Barectl can make creating WordPress on a fresh supported server a roughly two-minute **operator task**, with a server PHP default and optional site overrides, and a similar model for Node.js. This is workflow research, not a deployment benchmark, accepted specification change or qualification evidence. Existing requirements remain in [WordPress](wordpress.md), [PHP versions](php-versions.md) and [the architecture](architecture.md).

## What the short setup claims include

| Product | Starting point and operator work | Timing boundary |
| --- | --- | --- |
| Coolify | An accessible dashboard and connected server precede service creation. Add-server setup collects connection details and an SSH key; validation checks SSH/OS/tools, installs or verifies Docker/Compose and starts the proxy. Advanced connection fields are collapsed. [Server onboarding](https://coolify.io/docs/core/infrastructure/servers/add-server). Self-hosting additionally requires installation, dashboard account creation and saving installation secrets. [Self-hosted setup](https://coolify.io/docs/start-with-self-hosted). | Validation can take several minutes on a new server. “One-click” describes a supplied service template and generated values, not zero setup or managed application maintenance. [Onboarding](https://coolify.io/docs/core/infrastructure/servers/add-server), [service meaning](https://coolify.io/docs/services/what-is-a-service). |
| Laravel Forge | Create a server by choosing its name/provider, type, region and size; custom VPS onboarding adds IP/SSH port. [Servers](https://laravel.com/forge/docs/servers/the-basics). On a provisioned server, choose WordPress and an existing or new database. Forge installs WordPress/WP-CLI; the operator completes WordPress setup in the browser. [Sites](https://laravel.com/forge/docs/sites/the-basics#wordpress). | Forge advertises provisioning in seconds, but limits instant Laravel VPS provisioning to specified sizes and the managed private network. This does not establish a general fresh-OS-to-configured-WordPress duration. [Servers](https://laravel.com/forge/docs/servers/the-basics). |
| CloudPanel | Its installer starts with an empty server and root access: update packages, select a database engine, run the verified installer and create a panel account. [Installation](https://www.cloudpanel.io/docs/v2/getting-started/other/). Then Add Site → WordPress asks for domain, title, admin username/password/email and Create. [WordPress](https://www.cloudpanel.io/docs/v2/php/applications/wordpress/). | The advertised under-one-minute WordPress installation starts **on CloudPanel**, after panel provisioning. Publicly trusted HTTPS is another step: sites initially receive a self-signed certificate; Let's Encrypt issuance requires domain selection and valid DNS. [WordPress](https://www.cloudpanel.io/docs/v2/php/applications/wordpress/), [TLS](https://www.cloudpanel.io/docs/v2/frontend-area/tls/). |

These sources describe forms and automation, not measured human completion times. Server acquisition, SSH access, DNS propagation, package downloads and certificate issuance must be distinguished from time spent entering choices.

## PHP defaults and overrides

Forge supplies the closest documented model: choose PHP during provisioning, install additional branches as needed, and use the server's new-site default unless Advanced settings overrides it. Changing that default preserves existing sites. CLI PHP is a separate default; branches have separate FPM processes. Removal is refused while a branch is a default or serves sites. [PHP management](https://laravel.com/forge/docs/servers/php), [site Advanced settings](https://laravel.com/forge/docs/sites/the-basics#advanced-settings).

CloudPanel exposes PHP version in generic PHP-site creation and later site settings, alongside common limits and an additional-directives escape hatch. Its WordPress instructions keep those choices out of the short form. The inspected pages do not establish a Forge-style server default for new sites. [Add Site](https://www.cloudpanel.io/docs/v2/frontend-area/add-site/), [settings](https://www.cloudpanel.io/docs/v2/frontend-area/settings/), [WordPress](https://www.cloudpanel.io/docs/v2/php/applications/wordpress/).

Forge warns that switching a site's branch requires matching extensions; it changes the Nginx FPM socket and reloads services. A short version selector therefore still needs application capability checks. [Site PHP versions](https://laravel.com/forge/docs/sites/the-basics#php-versions).

## Coolify templates and runtime detection

Coolify's WordPress catalog offers WordPress plus MariaDB or MySQL containers with automatic database configuration and health checks. Its general service flow selects project/environment, template, server/destination, reviews required variables/storage/domains, then deploys and verifies component health. Values can be generated and reused across components. [WordPress variants](https://coolify.io/docs/services/wordpress), [service workflow](https://coolify.io/docs/services/), [generated values](https://coolify.io/docs/services/configuration/docker-compose). The WordPress catalog page does not document every initial administrator field; its brevity is not proof of a completed, secured installation.

For source applications, Coolify builds an image using Nixpacks, Railpack, Static, Dockerfile or Compose. This is application-image configuration rather than a native server PHP default. [Build methods](https://coolify.io/docs/applications/builds/overview). Nixpacks remains supported but is in maintenance mode; Railpack is its successor and is labelled Beta in Coolify. [Nixpacks](https://coolify.io/docs/applications/builds/nixpacks/overview).

Railpack detects PHP from `index.php` or `composer.json`, chooses PHP from Composer requirements or its documented fallback, and derives extensions from Composer requirements plus explicit extension configuration. It uses FrankenPHP. [Railpack PHP](https://railpack.com/languages/php/). This demonstrates reducing prerequisite questions through an application profile; it does not justify replacing Barectl's native FPM convention.

## Node needs a complete application workflow

CloudPanel's Node site asks for domain, Node version and application port. Its per-site settings use NVM and Nginx reverse proxying. [Add Site](https://www.cloudpanel.io/docs/v2/frontend-area/add-site/), [settings](https://www.cloudpanel.io/docs/v2/frontend-area/settings/). Application files still need deployment. Its PM2 guide separately requires SSH, installation, starting the application, saving the process configuration and adding reboot startup through cron. [PM2 deployment](https://www.cloudpanel.io/docs/v2/nodejs/deployment/pm2/). A runtime selector alone is not a working Node deployment.

Railpack resolves Node from an explicit environment override, project declarations/version files, then its LTS fallback. It detects package managers and install/build/start behavior from project configuration. [Railpack Node](https://railpack.com/languages/node/). Coolify exposes detected commands for review and overrides only where needed, plus the internal port or static publish directory. [Railpack workflow](https://coolify.io/docs/applications/builds/railpack). These pages do not establish a native server-wide Node default.

## Proposed direction for Barectl

The following are design inferences from the comparisons, requiring specification review before implementation:

- **Start with the application.** Choose server, WordPress and domain; collect title/admin identity and the existing approved credential flow once. Present the required PHP capability baseline, database, WP-CLI and HTTPS as parts of that application's preparation. Avoid making operators discover those dependencies across separate setup pages. CloudPanel's compact application form and Coolify's bundled dependency template support this direction.
- **Default versions, expose overrides.** Show the resolved server PHP default beside a collapsed site override. Materialize each site's choice in native configuration; later default changes should affect new sites only. Distinguish web PHP from command-line consumers. Forge provides the benchmark. A proposed Node equivalent needs version-specific build and service execution, not merely a changed shell default.
- **Make authorization understandable.** Show what Create authorizes in one short summary. Keep exact source/provenance, versions, dependencies and service effects in the internal review records available under Advanced, without separate prerequisite approvals. Expose site overrides and actionable refusals where they matter. This changes the review journey, requiring the coordinator described in [site creation](site-creation.md), and must not bypass the qualified branch/source/architecture matrix. [Current PHP requirements](php-versions.md), [WordPress admission](wordpress.md#supported-combinations).
- **Compose existing native operations.** Retain worker-owned SSH, pyinfra, native locking, authenticated APT transactions, Certbot and WP-CLI. Simplification should coordinate their established operations and recovery, with fresh evidence at each required boundary. Coolify's container control plane and CloudPanel's resident panel are different architectures; their form design does not establish native reconstruction or controller-loss equivalence. [Barectl boundaries](architecture.md#standard-configuration-and-reconstruction), [native execution](adr/0006-use-native-bootstrap-execution.md).
- **Measure input and waiting separately.** Aim for roughly two minutes of operator input on the normal path; show provisioning progress and the next actionable failure. Record fresh-server and already-prepared-server elapsed times separately. Do not promise a two-minute live HTTPS site without measured evidence covering DNS, package supply and ACME.

No competitor was deployed here. Package trust, concurrent-controller safety, interrupted-operation recovery and reconstruction after losing dashboard records remain unverified for these products. This comparison supports a smaller operator workflow; it supplies no additional runtime qualification.

## Native runtime alternatives

**Candidate to qualify: mise's core Node backend.** Install a pinned mise package through reviewed APT supply; upstream documents an extrepo route on Ubuntu 22.04+, avoiding a downloaded installer. [Installation](https://mise.jdx.dev/installing-mise.html#apt). Declare the server default in root-owned `/etc/mise/config.toml`; install only requested exact releases with `mise install --system core:node@<version>` into `/usr/local/share/mise/installs`. Core system installs require a writable destination/root. [System installs](https://mise.jdx.dev/dev-tools/system-installs.html). User data normally lives under `~/.local/share/mise`, separately from cache/state. [Directories](https://mise.jdx.dev/directories.html).

At review, resolve defaults/aliases to exact patches: changing an alias changes every declaration using it. [Aliases](https://mise.jdx.dev/dev-tools/aliases.html). Pin each site's resolved executable in its systemd unit and matching build PATH, obtained through read-only `mise where`; no shell activation or installation on service startup. [Lookup](https://mise.jdx.dev/cli/where.html), [systemd execution](https://manpages.ubuntu.com/manpages/noble/man5/systemd.service.5.html). This proposed convention preserves existing sites when defaults change.

Core Node uses official nodejs.org binaries and SHA-256/OpenPGP checks. Explicitly disable source compilation. Missing signatures can skip verification; lockfile checksums can avoid fresh signature acquisition. [Node supply](https://mise.jdx.dev/lang/node.html). Qualification must establish package/signing-key provenance, rotation, missing-signature refusal, protected configuration without application hooks, concurrent installation, interruption/reboot and fresh-controller reconstruction. This is no admission decision. NVM's documented per-user/per-shell scope makes shared root-owned runtime supply less direct. [NVM](https://github.com/nvm-sh/nvm/blob/master/README.md).

**Password onboarding options require separate security review.** WP-CLI accepts `--prompt=admin_password` via stdin; `user reset-password --skip-email --porcelain` generates a password without email but prints plaintext. Neither protects dashboard queues/journals automatically. [Install](https://developer.wordpress.org/cli/commands/core/install/), [reset](https://developer.wordpress.org/cli/commands/user/reset-password/).

An alternative to investigate is a fixed WP-CLI invocation of WordPress's reset-key API, returning an authenticated password-setting link: WordPress stores a hash and checks expiry; the final password is entered directly into WordPress. [Key generation](https://developer.wordpress.org/reference/functions/get_password_reset_key/), [expiry](https://developer.wordpress.org/reference/functions/check_password_reset_key/), [reset URL](https://developer.wordpress.org/reference/functions/retrieve_password/). This needs an explicitly approved helper and secret transport, protecting tokens from queued results, logs, referrers and unauthorized reveal. No terminal/email-free channel is established here.
