# Laravel native design

Accepted v0.5 operative contract, pending implementation and qualification. [The specification](v0.5.md) owns operator behavior. These resources are native application configuration/content and systemd configuration, not a Barectl inventory or history format. A specification is not evidence that its candidate tool/runtime combinations work.

## Foundation and compatibility gates

Laravel 13 is the initial major. Its [release policy](https://laravel.com/framework/docs/releases) lists PHP 8.3 through 8.5. Start with Ubuntu 26.04/PHP 8.5/MariaDB 11.8 or PostgreSQL 18, on amd64 and arm64. Each combination needs its own pinned fixture/lock, Laravel patch and native evidence. Optional approved PHP supplies require their existing gates as well. The runtime ticket records literal package versions per architecture; activation stays disabled for unqualified combinations.

Prepare release-default Git and Composer through the existing exact APT review. Native APT authentication supplies tool authenticity. The selected branch's explicit `/usr/bin/php<version>` invokes Composer and Artisan. Verify required CLI and FPM extensions, actual Composer/platform compatibility, and PCNTL for workers. Do not change the machine's default PHP, weaken platform checks, or bypass failed dependency security policies. If a distribution's Composer cannot read the project's supported lock, refuse and record the gap rather than downloading another installer implicitly.

## Operative filesystem and routing

Preserve the site's Linux identity, root-controlled `/var/www/<identifier>` boundary, selected pool/socket, local database binding and Certbot lineage. The Laravel form explicitly adds:

| Native resource | Planned rule |
| --- | --- |
| Staging area | `/var/www/<identifier>/.laravel-stage-<32-hex-token>`, an ephemeral bounded filesystem in the transient unit's private mount namespace, with root-controlled ancestry and site-only build access. No current-link target may point here. |
| Protected releases | `/var/www/<identifier>/releases/<40-hex-commit>-<32-hex-token>`, under a root-controlled releases directory. Code and retained Git metadata become root-protected only after safe publication. Initial scope uses Git SHA-1 repositories; other object formats refuse. |
| Current link | `/var/www/<identifier>/current`, root-controlled relative link to one exact protected release. Nginx document root is `current/public`; no external, absolute or nested current-link target. |
| Private environment | `/var/www/<identifier>/private/laravel.env`, site-only readable/writable native configuration; each release's `.env` is an exact confined operative link. No secret export or shell sourcing. |
| Shared storage | `/var/www/<identifier>/private/laravel-storage`, site-only; release `storage` is the exact operative link. Initial scope excludes a public storage symlink and user uploads served directly by Nginx. Applications may serve authorized files through their front controller. |
| Per-release cache | `bootstrap/cache`, site-writable and site-only readable. Cached configuration is treated as secret-bearing. It is excluded from code immutability claims, not from path admission. |
| Native source evidence | Protected Git object/HEAD/origin metadata, committed Composer files and installed dependency metadata. No `REVISION`, status marker, deployment log or release manifest added by Barectl. |

Freeze/publish from untrusted staging after this run's site-identity build process tree stops. Establish a fresh bounded stable tree admission, descriptor/no-follow ancestry checks and a safe copy/publication into a new root-controlled destination. Refuse concurrent source changes; do not assume in-flight web or external processes are quiescent. Do not root-chown an arbitrary site-controlled tree. Refuse links/special files/hardlink aliases and source changes except the individually verified operative links. Existing releases are never overwritten. Compare protected tracked files with their native Git tree; Composer metadata establishes dependency observation rather than a malware or byte-reproducibility guarantee. Use private whole-tree digests for later review without returning secret content. An existing exact protected release created through ordinary administration is equally recognizable.

Initial transition accepts only an empty or exact known-placeholder generic PHP site. Never move or overwrite existing application content. Preserve the old public directory as ordinary native content; it is not a recovery authority. The root and every intermediate traversal directory expose only the read/traverse permissions required by Nginx and the site identity. Private configuration, Git metadata and cache remain inaccessible to Nginx even though code/public content is readable.

Treat the repository's `storage` and `bootstrap/cache` as reserved writable paths, separate from immutable source comparison. Admit only the qualified Laravel skeleton's empty directories and vetted `.gitignore` placeholders there; refuse other committed content or tracked generated configuration. Stage omits those descendants from protected code copying and explicitly creates the operative storage/environment links plus a private site-writable cache directory. A missing link target is candidate-not-ready evidence, never activation eligibility. Private preparation creates only missing shared storage directories from the vetted skeleton and keeps existing exact storage/data. Protected Git metadata retains the original tree, and source verification excludes only these declared reserved paths. Do not modify tracked application files or overwrite live storage to make Git comparison pass.

The exact new templates must use Laravel's public front controller with query preservation and `$realpath_root` for the resolved script path, one selected site socket, strict denial of other PHP execution and dotfiles, no directory listing and the existing default-host/TLS rejection behavior. Never serve a repository root, `.git`, Composer files, environment, private storage or cache. The maintenance form gates all application routes with 503 while preserving the exact ACME location. HTTP redirects and HTTPS activation must recognize and preserve these forms. Render/recognize complete exact bytes through the existing convention module; do not add a general Nginx editor.

## Source review and staging

Source resolution permits only bounded credential-free HTTPS URLs or validated SSH host/user/repository locators. Private keys and verified repository known_hosts are provisioned through terminal administration under a supported site-only native path. This does not give the Linux site user interactive login, sudo or inbound SSH access. Controller SSH credentials remain on the controller. Reject unsupported hosts/paths, URL tokens, control characters and flags, transport rewrites/helpers, credential helpers, untrusted Git hooks/configuration, forwarded agents and implicit submodule/LFS work. Public HTTPS is verified by native CA trust; SSH uses strict host trust without `ssh-keyscan` admission.

Preparation performs bounded remote resolution only, as the site identity with controlled native Git configuration. It may disclose the exact sanitized locator and full resolved commit. It makes no persistent checkout, Composer change or application-code call. A moved/unavailable ref during apply must either fetch the already reviewed commit or refuse, never substitute a different commit.

The reviewed Stage operation creates an isolated candidate, fetches and verifies the exact commit object, and uses a detached checkout. A full commit is identity evidence, not publisher-signature proof. Run [Composer locked installation](https://getcomposer.org/doc/01-basic-usage.md) with `--no-dev --no-interaction --prefer-dist --optimize-autoloader --no-plugins --no-scripts`, followed by actual `check-platform-reqs --no-dev`. Validate lock consistency without loading plugins. Do not call `update` or ignore platform requirements. Reject nonstandard dependency/vendor paths, private registries, arbitrary script requirements and unsafe repository layout. Committed frontend assets are required where the application uses them.

The standard Laravel skeleton declares Composer lifecycle scripts. Disabling them is intentional and does not imply equivalent installation behavior. Stage safely publishes an inactive root-protected candidate before any later Artisan step, verifies the copied source/tree/lock and ends its untrusted build processes. Separate executable preparation after private configuration is ready runs fixed package discovery before migration. It does not run the repository's lifecycle script list. Projects requiring other scripts/plugins refuse this profile. Composer's [safety guidance](https://getcomposer.org/doc/faqs/how-to-install-untrusted-packages-safely.md) means even disabled scripts are not a sandbox; trusted source consent and site-identity execution remain necessary.

Bound source resolution and all executable work by the existing 30-minute native run and 16 KiB payload limit. Initial profile caps a candidate at 100,000 entries and 1 GiB, requires 2 GiB free disk space and 2 GiB available memory before staging and protected copying, and refuses another stage when 20 protected release directories exist. These are initial Barectl policy limits to qualify, not workload capacity recommendations.

Use systemd's native `TemporaryFileSystem` for the exact root-ancestry staging path with tmpfs `size=1G,nr_inodes=100000,mode=0700,nodev,nosuid` and the verified site UID/GID, plus a 2 GiB unit memory ceiling. Direct Composer home/cache/temp and Git build writes there. Native aggregate byte/inode limits enforce exhaustion during writes; `LimitFSIZE` alone does not. Publish the validated persistent protected candidate before the unit ends. Unpublished ephemeral staging disappears on unit loss and cannot be reconstructed or resumed. Report that honestly and require original-run reconciliation plus fresh authorization for new work. This extends the existing transient adapter with fixed action-specific resource properties, preserving its SSH, lock and reconciliation contract; it is not another execution path. Refuse missing namespace/cgroup/mount support or insufficient resources instead of falling back to an unbounded disk stage. Verify installed-version semantics and cleanup on Ubuntu 26.04. Sources are [Ubuntu systemd execution configuration](https://manpages.ubuntu.com/manpages/resolute/man5/systemd.exec.5.html) and [Linux tmpfs limits](https://www.kernel.org/doc/html/latest/filesystems/tmpfs.html). No automatic cleanup of retained releases, retention or splitting into replayable units defeats these limits.

## Private configuration and executable work

Environment review returns a digest and fixed non-secret prerequisite projections only. Require production mode, `APP_DEBUG=false`, exact canonical HTTPS URL and supported native database socket/peer settings. Never evaluate PHP or dotenv through application code during read-only preparation. Conflicting repository `.env`/tracked cache, runtime injection and unsafe grammar refuse. Terminal setup owns application-specific secrets. Generate only a missing `APP_KEY` through separately authorized site-identity work, retain it privately, and never rotate an existing key during redeployment.

Application code can access its own private state, including through Composer/autoload and Artisan. Root controls publication mechanics, never application execution. Raw tool/application stdout/stderr are suppressed from managed command paths before journal/controller exposure. Typed results carry bounded enumerated fields and digests, capped at 16 KiB and 128 items per record; overflow is explicitly incomplete/unavailable. Native execution evidence establishes lifecycle outcome independently of result availability. Ordinary application-written logs stay on the server and are not exported by these workflows. This is not a sandbox or a promise that hostile code cannot disclose its own data.

Package discovery and configuration/cache preparation require explicit authority and revalidation against the reviewed inactive root-protected candidate. Named executable inspection separately targets the selected current release as defined below. Never run migration PHP from site-writable staging. After native environment setup and one-time key generation, run fixed `package:discover` before any migration and verify its private generated manifests. Review activation/cache preparation separately; require fresh private cache/configuration evidence before later execution. Avoid blanket `optimize:clear`, which can clear shared application cache. Treat generated cache as private, verify serving through the selected pool and account for OPcache/realpath behavior without granting the site user wildcard sudo. Where a selected-branch FPM reload affects other pools, show that effect in review and verify their retained behavior; do not label it a site-only action.

The named Inspect Laravel workflow targets only the exact selected current protected release and runs `about --only=environment --json --no-interaction` through selected PHP as the site identity under the finite native mutation contract. The [official environment overview](https://laravel.com/docs/13.x/configuration#displaying-your-environment) documents filtering, and the [Laravel 13 command implementation](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Foundation/Console/AboutCommand.php) supplies JSON output. It evaluates registered data callbacks before filtering output, so the filter does not prevent their execution. Qualify the exact framework version's command/output grammar before enabling it. Return only validated framework/PHP version fields and enumerated production/debug/maintenance indicators. Drop application names, URLs, arbitrary provider sections and all unexpected fields; malformed, oversized or unsupported output yields result-unavailable with a separate execution outcome. Do not expose a general configuration dump, cache flush or Artisan console. Application boot/provider effects are reviewed even though the command intends inspection; no result proves full business health. Current protected code and private configuration/cache evidence must remain exact. Gated/partial/unknown or unqualified runtime evidence refuses inspection, while passive observations stay available.

## Migrations, activation and recovery

Migration review binds candidate source/tree/lock, environment digest, database identity/catalog and the supported `database/migrations` identifiers. Unsupported migration paths or unreadable database evidence refuse. Execute `migrate --force --no-interaction` only after recovery provision and compatibility acknowledgement. Never run Artisan during migration preparation. Static identifiers and native table reads cannot predict arbitrary migration PHP effects; disclose application trust and operator schema compatibility responsibility.

Under the native lock, first disable and verify timer/worker boot activation, then verify/set the public gate, stop the timer before its service, and drain exact scheduler and worker control groups. Failed fencing or draining refuses the next schema/code transition. Fault interruption/reboot at each boundary. Revalidate the protected candidate and private/native database evidence, then invoke the selected PHP CLI as the site identity. Compare recorded migration identifiers after execution with the expected conventional set and report exit, table evidence and verification separately. An exit of zero alone is insufficient, particularly for upstream cache-isolated execution. Native migration rows do not prove that every unrecorded failed migration left no changes. Partial or unknown effects require terminal recovery and fresh review; there is no generic safe Finish or automatic retry.

After schema work the site stays gated until a separately reviewed activation. Every activation, including redeployment and code reactivation, requires fixed native table evidence that every candidate migration identifier is recorded, or a positively empty candidate migration set. Historical extra rows may remain; do not require table equality or delete them. This does not prove arbitrary schema compatibility. Activation rechecks the already protected candidate and all current evidence, performs fixed cache preparation as the site identity, revalidates its writable cache/link grammar, publishes the current link, validates Nginx/FPM, and verifies private FastCGI readiness before releasing the gate. Verify the same-site HTTPS readiness path, default `/up`, without returning its body. Require status 200 with redirects refused. It proves the configured application's check, not universal business health. The activation review explicitly selects desired enable/start state for each exact existing managed background unit, defaulting to disabled when intent is unavailable. Restore only that reviewed choice after serving verification, never an inferred prior state from a lost audit.

Failure before current publication leaves the old current target. After publication, retain the gate on failed verification; never automatically point old code at a changed schema. If gating/restoration itself fails or was changed externally, show unknown/unsafe exposure. Interrupted operations leave ordinary artifacts and native unit evidence; Check outcome never resubmits. Missing evidence uses the existing fenced unknown-outcome acknowledgement. Do not replay an uncertain stage or migration because the local controller has no result.

A fresh controller can inspect an exact retained release and prepare code reactivation with current environment/schema/process evidence and explicit compatibility acknowledgement. Reactivation does not reverse uploads, secrets, jobs or migrations. No automatic release deletion, migration rollback, data removal, key regeneration or Git-history rewrite is authorized. Recovery instructions use ordinary Linux, Git, Laravel and database tools; v0.6 owns tested restore.

## Scheduler and workers

The operative scheduler units are `/etc/systemd/system/s<identifier>-laravel-schedule.service` and matching `.timer`. Exact root-owned grammar uses a finite oneshot, native root launcher for the protected lock and a site-identity PHP child in `current`, with no installed helper script. Use `OnCalendar=*-*-* *:*:00`, `AccuracySec=1s`, `RandomizedDelaySec=0` and `Persistent=false`. Set a 55-second run bound and cgroup kill/stop limits. Refuse an enabled duplicate cron/scheduler. Applications must meet the supported minute/no-background profile; this is an operator-declared contract, not something static source scanning can prove for arbitrary code. Native containment terminates descendants on timeout and reports failure, without undoing effects.

The scheduler's lock may be skipped immediately during a mutation; expose that tick as conflict/skipped. No catch-up or exactly-once scheduling is promised. Every competing apply and unknown-outcome closure inspects recognized scheduler cgroups, including children that have closed the inherited lock descriptor. This extends the cooperative exclusion contract. Before enabling the scheduler, every mutation controller must support it or be stopped; old controllers cannot be automatically fenced by their private database. The timer is enabled only after a qualified release is active.

The worker is `/etc/systemd/system/s<identifier>-laravel-worker.service`, a root-owned `Type=exec` system service with `User=s<identifier>`, the private group, explicit selected PHP and working directory `current`. Initial command is fixed `queue:work database --queue=<validated-names> --sleep=3 --tries=3 --timeout=60`, with PCNTL verified, database `retry_after` at least 90 seconds, `Restart=always`, `RestartSec=5s`, `StartLimitIntervalSec=60s`, `StartLimitBurst=5`, `TimeoutStopSec=75s`, and `KillMode=control-group`. These literal initial bounds require native job fixtures. One process/profile is supported; database queue tables must already be established through reviewed migrations.

Workers do not hold the global lock. Exact native stop/drain prevents their restart during a live deployment; application job handlers remain responsible for idempotency on interruption/retry. A deployment must also disable enabled timer/worker boot activation before entering a persistent gate, restoring it only after verification. Otherwise a reboot could restart background work against a partly migrated application. Stopped unit state alone is not a reboot fence. Unit enablement is native operative state, never a custom deployment marker.

Expose separate authorized scheduler enable/disable/run-once and worker start/stop/graceful-restart workflows with review, progress, native outcome, refreshed state and terminal recovery. Enable, run-once, start and restart require fresh verified ungated activation and completed migration evidence for the selected current release; an inactive candidate does not block the unchanged active application. Refuse gated/partial/unknown application state. Stop/disable remain available for safe recovery. Never accept arbitrary unit names, command text or flags. Native state includes enabled/inactive/failed/rate-limited, observed time and result availability; retained logs do not reconstruct private Barectl audit. External commands and in-flight web requests remain outside cooperation. Unreliable known conflicting process evidence refuses dependent mutations.

## Upstream reuse and the specific gap

| Existing option | Reused capability | Requirement its documented defaults do not supply |
| --- | --- | --- |
| Existing action registry/lifecycle/native adapter | Immutable plan, permission contract, SSH submission, fencing, lock, cgroups and reconciliation | Laravel-specific operative grammar, trusted-root publication of site-built content and schema/process postconditions. Extend this implementation rather than adding another transport. |
| [pyinfra 3.x Git](https://docs.pyinfra.com/en/3.x/operations/git.html), [files](https://docs.pyinfra.com/en/3.x/operations/files.html), [systemd](https://docs.pyinfra.com/en/3.x/operations/systemd.html) | Native Git checkout, file and unit operations; detached worktrees and strict-host options | Controller-owned operation sequencing does not itself survive controller loss or supply the one reviewed transient-unit contract. Ownership parameters do not establish safe execution identity. Check composition under that contract before choosing fixed native glue. |
| [Deployer 8 release](https://deployer.org/docs/8.x/recipe/deploy/release) and [rollback](https://deployer.org/docs/8.x/recipe/deploy/rollback) | Established release/shared/current pattern and Laravel recipes | Defaults consult `.dep` history and revision/bad-release markers, and select rollback from those records. Barectl requires native operative evidence and its own audit only in the local database. Do not add a second execution integration or fork Deployer into a parallel engine. |
| [dploy](https://www.cloudpanel.io/docs/v2/dploy/installation/) | Server-native Git deployment and shared paths | Arbitrary before/after commands, mutable ref deployment, site-controlled current switching and automatic cleanup do not implement immutable review, protected publication and no-deletion recovery. Its documented broad PHP-FPM sudo permission is also outside the site identity contract. |
| Native [Git](https://git-scm.com/docs/git-fetch), [Composer](https://getcomposer.org/doc/03-cli.md), [Laravel](https://laravel.com/docs/13.x/deployment), [systemd](https://manpages.ubuntu.com/manpages/resolute/man5/systemd.service.5.html) | Source transport/object identity, locked dependency installation, named application commands and native process ownership | Barectl must connect these operations to reviewed evidence and narrowly validate their shared effects. Do not duplicate acquisition, dependency resolution, scheduling or process-supervision engines. |

This is an architecture assessment, not proof that no possible upstream customization exists. Each implementation issue records checked versioned operations, the specific remaining gap and source links before custom code. A new tool or execution-path proposal reopens the decision explicitly. The existing 16 KiB/30-minute adapter limits remain; an oversized proposal refuses rather than installing a helper or replaying split stages.

## Qualification and delivery

Each vertical slice delivers its own dashboard, permissions, refusals, recovery and focused native/browser evidence. Final qualification integrates the full matrix, private/public source, exact commits, no-follow publication, credentials, partial schema, independent controllers and real reboot. Test stopped/disabled process state across interruption and reboot, and all shared adapter actions against scheduler cgroup conflicts. Existing PHP/database/TLS and any delivered WordPress flows remain green. Run repository gates and affected native tests before pushing implementation, then record exact-head full statuses and independent reviews. Missing evidence is a gate, not a pass.
