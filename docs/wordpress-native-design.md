# WordPress native design

Accepted native contract for the [v0.4 specification](v0.4.md). The WP-CLI setup, PHP runtime preparation, passive discovery, installation review, installation apply, explicit inspection, Finish and maintenance implement it ([WordPress](wordpress.md)); the [qualification record](v0.4-qualification.md) lists what runtime qualification covers and what remains disabled. This document owns literal resources, artifact pins, command constraints, publication and recovery rules. The specification owns operator outcomes, user stories, implementation decisions and testing decisions; GitHub Issues own ticket state.

## Compatibility and supply

The initial candidate pair, checked on 2026-10-07, is WordPress **7.1.3** and WP-CLI **2.12.0**. The [official download page](https://wordpress.org/download/) and [WP-CLI release](https://github.com/wp-cli/wp-cli/releases/tag/v2.12.0) establish availability, not Barectl qualification. Pin these exact releases in implementation and evidence; never resolve `latest` during apply. If a security release supersedes either before qualification, refresh the explicit pin and repeat affected proof before enabling it.

Start with Ubuntu 24.04/PHP 8.3/MariaDB 10.11 and Ubuntu 26.04/PHP 8.5/MariaDB 11.8 from the qualified Ubuntu supply, on amd64 and arm64 independently; an architecture is enabled only after its native statuses are recorded ([supported combinations](v0.4-qualification.md#supported-combinations)). [WordPress requirements](https://wordpress.org/about/requirements/) recommend PHP 8.3+, MariaDB 10.6+ and HTTPS; the [compatibility table](https://make.wordpress.org/core/handbook/references/php-compatibility-and-wordpress-versions/) lists WordPress 7.1 with PHP 8.3, 8.4 and 8.5. These upstream statements do not qualify Barectl, third-party extensions or the pinned WP-CLI pair. Additional branch/supply combinations remain disabled until their existing PHP gates and separate WordPress qualification pass. v0.4 does not depend on enabling the unqualified supplier in #236.

Use the site's explicit `/usr/bin/php<branch>` for every WP-CLI invocation; never the unversioned PHP alternative. A reviewed WordPress extension profile on Ubuntu installs only the branch-specific `mysql`, `curl`, `xml`, `mbstring`, `zip`, `gd` and `intl` binary packages needed by the baseline, with their full exact Ubuntu dependency closure. Already satisfied packages require no change. Reuse the existing package review, authentication, drift, transaction guard and FPM reload; no upgrades, removals or general repair. Built-in modules are verified in both CLI and the site's own FPM pool. Check `mysqli`, JSON, hash, fileinfo, exif, mbstring, curl, DOM/XML, zip, GD and intl capabilities. Missing capabilities refuse installation. Imagick, Redis, external object caches, mail delivery and plugin-specific requirements are optional outside this baseline, and must not be shown as installed.

The original profile is qualified for Ubuntu packages. The [approved-source extension profile](wordpress-source-qualification.md), requested by #320, adds only the exact versioned curl, xml, mbstring, zip, gd and intl binary names to ADR 0016's existing source admission. Its reviewed native evidence admits PHP 8.3, 8.4 and 8.5 on Ubuntu 24.04 and 26.04 arm64; other combinations remain disabled. Follow the [hosting environment guidance](https://make.wordpress.org/hosting/handbook/server-environment/) and document the baseline's recommended-extension omissions.

WP-CLI setup is a separate reviewed native plan. Install the versioned official PHAR at `/usr/local/lib/wp-cli/wp-cli-2.12.0.phar`, root-owned 0644 under root-owned, non-writable ancestry. Never run the downloaded artifact before authentication. Require the release's detached signature and native GPG verification against primary fingerprint `63AF7AA15067C05616FDDD88A3A2E8F226F0BC06`, published in the [verification guide](https://make.wordpress.org/cli/handbook/guides/verifying-downloads/). Verify key validity, revocation and the full approved primary fingerprint; require the actual signing key to be that primary or a valid bound signing subkey, and record both identities. Use an isolated native keyring, not global trust. Review the authenticated artifact's SHA-256, also recorded by GitHub as `ce34ddd838f7351d6759068d09793f26755463b4a4610a5a5c0a97b68220d85c`; the signature is the authenticity check. Missing tools, invalid signatures, unavailable assets, changed pins and unapproved key rotation refuse. No self-update or arbitrary WP-CLI package installation.

Bind WordPress acquisition to the exact official `https://wordpress.org/wordpress-7.1.3.tar.gz` artifact. A read-only HTTPS download on 2026-10-07 measured 35,368,461 bytes and SHA-256 `d2a09acb6a15e3b9c471d72557753c266d6f41a79ed19bfe04cbfe49e283b2a5`; the archive's version literal is 7.1.3. These are observed artifact pins, not runtime qualification or an independent publisher signature. Review URL, byte count and digest. A different archive refuses until the maintained profile is explicitly reviewed again.

Use WP-CLI's native `core download` with that explicit URL and `--no-extract` in a fresh private download directory/cache. Set `TMPDIR` to the run's site-user-owned private staging directory and qualify the actual temporary location; `--path` alone does not control the first download. Before downloading, enforce native file/process limits: maximum archive 64 MiB, maximum extracted tree 256 MiB, 10,000 regular file/directory entries, per-file limit 64 MiB and native cgroup memory limit 512 MiB. Refuse a profile exceeding these reviewed bounds. Use systemd `LimitFSIZE`/`MemoryMax`, not a custom streaming downloader; do not combine URL mode with `--version`. Check the resulting single archive with native `sha256sum` before extraction. Native tar owns bounded safe extraction into an absent staging tree after admission of regular files/directories under the sole `wordpress/` prefix, with no links, devices, traversal or unsafe modes. The admission reads the member headers as the site user with Python's standard-library `tarfile`, since tar's listing cannot be parsed safely for arbitrary member names; it extracts nothing, and `tar` itself, as the site user without restoring owners or permissions, writes the tree. The archive pin, not a second download, binds actual acquired bytes to the review. Run native `core verify-checksums` with explicit 7.1.3/en_US before installation. No downloaded PHP may execute before archive and tree checks pass.

The [bundled core-command 2.1.20 source](https://raw.githubusercontent.com/wp-cli/core-command/v2.1.20/src/Core_Command.php) supports URL mode/no-extract and can continue with a warning if its MD5 response is unavailable; stock download success alone is insufficient. The [bundled checksum-command 2.3.1 source](https://raw.githubusercontent.com/wp-cli/checksum-command/v2.3.1/src/Checksum_Core_Command.php) fetches its own catalog and omits wp-content. Keep that diagnostic classification separate from whole-archive SHA-256 admission. Never claim a separate prefetched catalog binds the response WP-CLI consumes. Public checksums over HTTPS are integrity evidence, not signed release provenance or malware detection. Never use `--insecure`, `--force`, a prior user's cache or a custom downloader/cryptographic implementation.

## Native WordPress convention

[ADR 0017](adr/0017-manage-wordpress-as-a-site-application.md) defines the application boundary. Retain the site identifier, dedicated `s<identifier>` Linux identity, numeric ownership, selected pool/socket, public root, private directory and local MariaDB binding from the [site convention](site-conventions.md). WordPress uses database and principal `s<identifier>`, `DB_HOST` `localhost:/run/mysqld/mysqld.sock`, empty `DB_PASSWORD`, and table prefix `wp_`. Test actual WordPress mysqli access through both the selected CLI and pool. PostgreSQL sites refuse with the required MariaDB prerequisite; no adapter or engine conversion.

The public root contains ordinary WordPress release files and `wp-content`, owned by the site user/private group with directories 0755 and files 0644 beneath the retained site-user:www-data 0750 public root. The public root prevents other site users from traversing; world-readable leaf modes let Nginx read without giving the site user supplementary groups. Publish only validated new files, setting modes without following links or recursively changing existing content. Private configuration is `/var/www/<identifier>/private/wp-config.php`, owned by the site user/private group, mode 0600. The public `wp-config.php` is a fixed wrapper, site-user:www-data 0640, with these statements:

```php
<?php
require '/var/www/<identifier>/private/wp-config.php';
require_once ABSPATH . 'wp-settings.php';
```

Private configuration defines `ABSPATH` only if not already defined, binds it to the public root, and contains database literals and eight locally generated salt/key values. It never includes wp-settings itself. This preserves both the web bootstrap and WP-CLI 2.12.0's [direct wp-settings recognition](https://raw.githubusercontent.com/wp-cli/wp-cli/v2.12.0/php/WP_CLI/Runner.php); a wrapper containing only the private-file include is incompatible. Only the defined literal grammar is supported; arbitrary includes, environment indirection, remote credentials, relocated content and multisite constants block dependent actions. Runtime salts and passwords never become expected template bytes in a controller database.

The WordPress Nginx form has a fixed front-controller `try_files $uri $uri/ /index.php?$args`, an exact public config denial and case-insensitive upload-PHP denial before the generic PHP location. Deny PHP and alternate executable suffix/path-info forms beneath `wp-content/uploads`, private/dotfile paths and directory listings; keep the existing script-existence requirement, packaged FastCGI parameters, cleared HTTP_PROXY and selected socket. Canonical-name redirects preserve the explicit ACME route and never treat unknown Host names as trusted canonical input. WordPress writes no `.htaccess` authority for Nginx. Preserve the existing qualified TLS policy and default rejection server.

Support exact operative forms for provisioning-gated HTTPS, ready HTTPS and their HTTP challenge/redirect counterparts, on legacy default-branch sites and selected-branch sites. A provisioning gate serves 503 for application paths while retaining the ACME route and blocks `/wp-admin/install.php` and every direct PHP path. It is ordinary Nginx configuration, not an installation marker. Apply it and verify it before public release/configuration files or database tables are published. Restore the ready form only after installed-state verification. No publicly reachable WordPress setup wizard may exist during a partial install.

Every renderer, discovery recognizer, TLS plan and Finish path preserves application form, branch, canonical name, challenge route and certificate relationship. Do not silently upgrade a legacy site's branch/convention. Generic PHP files keep their exact historical bytes. Conversion replaces only a reviewed exact generic Nginx form and the exact known placeholder, preserving file preimages through the established mechanism. It never overwrites arbitrary application content. A site already having foreign files or application tables is refused, with no deletion, adoption or import.

## Passive discovery and explicit inspection

Passive discovery does not execute `wp-config.php`, include application PHP or run WP-CLI. Inspect bounded file metadata, the fixed loader, the supported private configuration grammar when readable, and core version literals. Validate private configuration grammar on the managed server and return only bounded non-secret projections and its digest. Never transfer the raw file into controller memory for later redaction. Parse configuration as data, never evaluate it. Report application evidence independently of infrastructure state: absent, candidate/unverified, partial, installed, blocked or unreadable. Ordinary unprivileged discovery does not escalate to read private configuration or catalogs. A root-authorized fresh controller can use fixed read-only catalog queries for the exact `wp_` tables, schema signature and bounded `siteurl`/`home` values. It must not read user password hashes, content, salts or arbitrary option values into the snapshot.

An installed observation requires matching configuration, native binding, required core tables/columns and canonical options. Additional plugin tables within the same site database are allowed and are never read or changed for core recognition; the first-install database must still be wholly empty. Custom user tables, missing/altered core columns and ambiguous table prefixes block dependent actions. File presence or `version.php` alone establishes only a candidate. Evidence caps, omitted access and parse failures remain explicit; never fall back to an old snapshot or infer another device's successful run. A newer observed core version is reported with its qualification status, not automatically downgraded or described as the originally installed release. Installation, Finish and cache/rewrite mutations require the exact qualified core pair. Diagnostic inventory/checksums may target an observed newer release only when the installed qualified WP-CLI can support its schema/bootstrap; otherwise refuse executable inspection and retain passive evidence. Diagnostic permission never grants mutation. Application content changes do not become generic-site configuration drift.

"Inspect WordPress" separately authorizes application execution. Run fixed `core is-installed`, core version, `plugin list` and `theme list` with explicit target, a controlled environment and bounded structured fields. Skip update-network checks for inventory where upstream supports it. Ordinary plugins/themes are skipped for diagnostic inspection, but must-use plugins and relevant drop-ins can still execute; disclose that fact. Results record their time and operation permissions, not a live-security assessment. Do not expose user lists, raw options/configuration, arbitrary package URLs or full debug output.

## Installation admission and execution

Read-only preparation checks the complete site's native form and ancestry, UID/GID, selected CLI/FPM and extensions, authenticated WP-CLI artifact, satisfied binding, empty application database and canonical HTTPS certificate. The public tree is empty or contains only the exact site placeholder; the private config, loader, core tree and `wp_` tables must be absent. Required native tooling, capacity and trusted HTTPS access must be available. No arbitrary existing content, symlinked ancestry, hard-linked configuration, unsafe permissions or writable root-level tool paths may be adopted.

The immutable review lists the exact tool/core release and acquisition evidence, site/branch/URL, account login/email, pinned archive URL/size/SHA-256, configuration paths, database/schema creation, provisioning gate, placeholder preimage, permissions, planned content publication, network effects, verification, password setup requirement and recovery limits. It includes boot, monotonic admission deadline and relevant evidence digests. The download and runtime limits fit the existing 30-minute finite native run; a review/payload exceeding native bounds refuses rather than splitting accepted work.

Apply uses `db_worker`, `discovery/ssh.py`, pyinfra's established connection and `bootstrap/native.py`. Acquire the shared nonblocking mutation lock, enforce boot/deadline fences, check conflicting cgroups/renewal, and revalidate the complete reviewed evidence before changing anything. Root performs only native configuration/publication steps. Download, WordPress config/install and application inspection run as the site user with the explicit selected PHP binary and a controlled umask. Do not use WP-CLI `--allow-root`, remote `--ssh`/`--http`, a controller-side WordPress process or a persistent helper.

The run is one script of more than 16 KiB, carried as a compressed body bound to its reviewed SHA-256 and run in the payload's own shell under the lock ([ADR 0006](adr/0006-use-native-bootstrap-execution.md#staged-bodies)), with `LimitFSIZE` and `MemoryMax` set on the unit. Prepare downloads in a fresh private native staging directory, `/var/www/<identifier>/.wp-<unit>`, owned by the site user on the site's filesystem. Before publication, verify the archive/tree and generated configuration; admit each destination only when absent or the positively identified placeholder. Never recursively chown an existing content tree. Retain partial operative files and tables after failure and keep the Nginx gate. Temporary downloads are application staging data, not inventory or execution journals; clean only the run's validated temporary resources. Native residue after termination is explained and never used as proof of authorization.

Generate salts and an unpredictable initial administrator password on the managed server. Feed the password directly from a site-user native process into the documented core-install prompt, with `--skip-email`, and discard plaintext. Suppress raw WP-CLI stdout/stderr before they can reach journald; emit only fixed success/failure codes and bounded validated non-secret fields. No shell tracing. Configuration generation also uses local randomness rather than fetching salts through a controller. [ADR 0018](adr/0018-generate-wordpress-secrets-on-the-server.md) owns the credential and terminal-login trade-off.

Before ready publication, verify schema/canonical options, core integrity and site-identity access through CLI and a private FastCGI probe while HTTPS remains gated. Then publish the ready Nginx form and verify HTTPS home/login and denial routes. If serving verification fails, restore the exact provisioning gate only while current Nginx bytes still equal this run's ready candidate, then validate/reload. Preserve application files/tables. If that safe restoration refuses or fails, report the actual potentially exposed state and urgent ordinary-administration recovery; never claim the gate remains active without proof. Preserve exact execution outcome even if verification fails. Missing native evidence leaves reconciliation pending; Check outcome inspects the same unit and never resubmits it. Lost/removed unit evidence follows the existing outcome-unknown acknowledgement fence.

Installation is not transactional. No automatic database drop, recursive content removal, salt rotation, administrator reset or rollback follows failure. A fresh reviewed Finish may create only independently verified missing exact resources and perform the explicitly reviewed gate-to-ready routing transition, keeping the native preimage. It never converts foreign content or replaces an existing application file. Existing release files must match a fresh safely staged copy of the same SHA-256-pinned archive, including its supplied wp-content files when finishing first installation. Compare native digests without replacing existing files. Private configuration uses its supported grammar and current digest separately; secrets never enter the comparison record. The review cannot read the archive within the time one remote read allows, so it judges only the top-level entries against the pinned release's list; the run compares every existing entry with its own staged copy by native `find` and `sha256sum` as the site user and refuses before changing anything on a difference. Stock upstream checksum diagnostics are not immutable Finish authority. Core installation into a database with any partial WordPress tables is refused rather than replayed. An already installed exact database may finish missing file publication or ready routing without running `core install` again. Ambiguous tables/content require ordinary administration; a retained run record does not authorize recovery.

## Named WP-CLI operations

Every action targets one reconstructed installed application and uses the same immutable review, native lock, site user, selected CLI, limits and reconciliation contract. No command textbox, free-form flags, `eval`, arbitrary SQL, config editing or additional WP-CLI packages.

| Dashboard action | Fixed upstream operation | Effects and result |
| --- | --- | --- |
| Inspect WordPress | `core is-installed`, core version, bounded `plugin list` and `theme list` | May execute application PHP; returns validated inventory and timestamp |
| Verify core | `core verify-checksums` with observed exact version/locale | HTTPS checksum request; reports match, mismatch or unavailable separately; never repairs |
| Verify repository plugins | `plugin verify-checksums` on explicit observed WordPress.org slugs | Private/custom packages or missing checksum catalogs are unavailable, not trusted or corrupt by inference |
| Flush object cache | `cache flush` | Refuse external/shared or unverified cache scope; without persistent cache, report that only this CLI process is cleared, with no public cache invalidation claim |
| Flush rewrite rules | `rewrite flush` without `--hard` | Updates application rewrite state; never edits Nginx or treats `.htaccess` as authoritative |

WordPress's [default object cache](https://developer.wordpress.org/reference/classes/wp_object_cache/) lives only for one request; flushing a separate CLI process cannot clear other web requests or page caches. Do not offer this as a live-site cache repair. No persistent cache provider is initially qualified, so an unknown drop-in refuses rather than expanding scope. Soft rewrite maintenance loads the application's normal plugins/themes for their registered routes; diagnostic skip flags must not silently remove plugin rewrite rules: WP-CLI's [`rewrite flush`](https://raw.githubusercontent.com/wp-cli/rewrite-command/v2.0.15/src/Rewrite_Command.php) warns that rules may be missing when plugins or themes are skipped, and its [`cache flush`](https://raw.githubusercontent.com/wp-cli/cache-command/v2.2.0/src/Cache_Command.php) reports only `wp_cache_flush()`. Any drop-in that can change where the cache lives or what a flush reaches (`object-cache.php`, `advanced-cache.php`, `db.php`), and every other drop-in, refuses the cache flush at review and drift refuses it at run.

Fingerprints bind site configuration, tool/CLI, native binding, core version/config and relevant plugin/theme/drop-in inventory, not every content row. Revalidate under the lock. A removed or changed target refuses before execution. Concurrent application requests and ordinary administration remain outside the lock. Native exit success verifies command completion; cache/rewrite actions do not promise every plugin's hook effects or performance recovery. Inspection and output parsing have explicit byte, item and time caps and reject malformed, mixed or extra output. Permit at most 128 inventory items and one sanitized result record of 16 KiB per action; overflow is unavailable evidence, not a truncated success. Suppress raw command stderr and process stdout through a trusted finite native projection before journald. No raw private values or plugin debug text may be passed through.

A completed inspection publishes its bounded validated result as ordinary native journal output of that unit. Retrieval uses bounded `journalctl` JSON filtered by the exact unit, recorded invocation ID and journald's trusted `_UID=0`, so a line the site user's processes write to the journal's socket is never a record, through the same authorized SSH boundary, and accepts only the one fixed result-record grammar. Qualify the [systemd 255 journalctl](https://raw.githubusercontent.com/systemd/systemd/v255/man/journalctl.xml) and [259 counterpart](https://raw.githubusercontent.com/systemd/systemd/v259/man/journalctl.xml). Journal absence/rotation produces result unavailable; terminal execution outcome still comes solely from systemd unit/cgroup evidence. This adds bounded application-result retrieval, not journal-derived reconciliation or a remote result file. Independent discovery remains authoritative native inspection, never a replay of these operation results. Ordinary or malicious application code can independently log or transmit its own data; the suppression guarantee covers Barectl's command/result path, not hostile application containment.

## Upstream reuse assessment

The existing site, binding, TLS, lifecycle and native adapters own orchestration. Official [pyinfra file operations](https://docs.pyinfra.com/en/3.x/operations/files.html) provide downloads, checksums, templates and publication, and [server operations](https://docs.pyinfra.com/en/3.x/operations/server.html) provide command execution. They do not establish Barectl's immutable approval, detached systemd lifecycle, shared native exclusion or application-secret rules. Reuse their native tool choices inside the established adapter; do not open another SSH deploy path. Native curl/GPG and WP-CLI own acquisition and installation; custom code is limited to reviewed admission, exact operative grammar, bounded parsing, safe publication, permissions and workflow. Record this specific gap and these alternatives in the corresponding implementation issues before adding code.

WP-CLI's [configuration precedence](https://make.wordpress.org/cli/handbook/references/config/) permits YAML and environment changes to commands. Require a controlled working directory, explicit path/URL, empty dedicated package/config locations and an allowlisted environment; refuse project/global YAML and unexpected drop-ins affecting command behavior. Qualify this on the pinned PHAR rather than assuming flags disable every hook. No application code may execute with root privileges even on failure or verification paths.
