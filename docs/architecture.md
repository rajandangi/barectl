# Architecture

## Product boundaries

Barectl is one Django application. It may run locally or on a management host. Managed Linux servers remain agentless and expose SSH only for management. Provisioning will install ordinary web-stack packages; agentless does not mean a server can host applications without those packages.

The [core philosophy](../README.md#core-philosophy) governs discovery and future management workflows. Managed servers must remain independently operable if Barectl and its local database disappear. A persistent controller or external control-plane service must not be required for applications to keep running or for an operator to manage the server through ordinary Linux tools.

The repository has `config`, `dashboard` (interface integration: Vite assets, sign-in form and HTMX request handling), `servers` (registration, removal and server pages), `operations` (the shared remote-operation lifecycle and its worker task), `discovery` (attempts, snapshots and the SSH connection), `bootstrap` (plan preparation, its native evidence, immutable configuration plans, and apply runs with their native execution adapter), `sites` (site plans: request validation, the site convention's templates, privileged read-only site evidence, site admission, and applying and verifying a site), `tls` (TLS plans: Certbot renewal setup's admission, inhibition payload, guarded renewal files and verification, and the challenge route's admission, replacement payload and verification), shared templates, and the Vite frontend sources in `frontend/`. Add domain apps when a workflow needs them. The interface uses USWDS and HTMX 4. `servers/ssh_config.py` resolves controller SSH aliases with paramiko's configuration parser, following pyinfra's handling of a configuration file (`docs/ssh-aliases.md`), and discovery passes only the resolved settings to pyinfra. `discovery/ssh.py` is the only remote execution boundary (`docs/ssh-connections.md`); plan preparation and apply runs use the same `RemoteShell` it opens. In the current release, SSH credentials stay in the controller host's agent or key files. Future saved connection details and optional remote database support must preserve independent access from another authorized controller.

## Request and execution flow

Views validate input and authorize access, then call application services. Services create durable jobs. A separate worker process from the same codebase executes infrastructure adapters. Long SSH operations must not run inside HTTP requests.

Discovery and plan preparation follow this flow. `operations/lifecycle.py` owns every remote operation's lifecycle ([ADR 0004](adr/0004-serialize-remote-operations-in-one-table.md)): queueing with its worker task in one transaction, claiming, conditional transitions that apply only while the operation is still in the expected state, the one active operation per server, and recovery of abandoned operations for kinds that allow it. Each kind registers its step and recovery rule; `discovery/services.py` is the discovery kind. `servers/registration.py` owns registering a server, changing its alias and server removal: `save_server` saves a registration or edit and queues a connection check when the alias is new, and `remove_server` removes a server with its discovery history. It reaches attempts only through `queue_discovery` and `forget_discovery`. Views call those functions, `recorded_discovery` for the removal page and `request_discovery` to check a server again; they turn outcomes into messages and form errors and never change attempts themselves. `servers/discovery_state.py` is the dashboard's one read of discovery: `server_state` for a server's page, with its discovery history, `inventory` for the server list and `activity_rows` for Activity. The page and the list read the controller's alias catalogue too and decide the connection status. Templates never receive attempt rows: each attempt reaches them as an `AttemptView` in the pages' wording, so the server page, its discovery history and Activity describe the same attempt alike, and the polled fragment sends back a token the module issues rather than the stored state. Other modules read attempts only through `discovery/services.py`: `read_discovery` (a server's latest attempt, current snapshot and discovery history in one read), `latest_attempt_statuses`, `history` (every server's attempts for Activity) and `recorded_discovery`. Every public function of that module recovers abandoned attempts first through one decorator, and a test requires it of each. Queueing records a queued attempt and enqueues the `run_remote_operation` task in one transaction, using Django's tasks framework with the `django-tasks-db` database backend. `manage.py db_worker` runs the task. The lifecycle claims the operation and runs its kind's step, recording a failure the same way whatever the step does; the discovery step connects with the attempt's alias through `discovery.ssh.connect_alias`, collects observations with `discovery.observations.collect`, the only public collection function, and publishes the snapshot with the attempt's outcome. The `discovery/observations/` package keeps `collect` and the operating system and capacity observations in `__init__.py`, probe reads and the classification of their failures in `probes.py`, packages and service units in `components.py`, the Nginx and PHP-FPM parsers in `parsers.py`, the Nginx site file and PHP-FPM pool collections in `configuration.py`, and site reconstruction, which compares a site's own evidence with those collections, in `sites.py`. `discovery/releases.py` names the supported releases and their default PHP versions; `bootstrap/releases.py` builds each release's review policy on it. `discovery/snapshot.py` owns the snapshot's shape: the observation types the collectors return, `save_snapshot`, `current_snapshot`, and `attempt_snapshots`, which reads attempts with the snapshots they published for the pages. Only that module reads or writes the snapshot tables, which keep typed columns ([ADR 0003](adr/0003-store-discovery-snapshots-in-typed-columns.md)). `discovery/presentation.py` names each observation once for the operator: `present` turns a snapshot into the server page's sections, with each observation's label, display lines, outcome, warning and sources, and the warnings Activity lists come from the same presentation, so templates lay out observations without interpreting them. Site observations are presented separately by `present_sites`, and the server views pass them to the page only for accounts with their view permission, so neither Activity nor discovery history carries their warnings.

Plan preparation is the second kind (`docs/ssh-connections.md#plan-preparation`). `bootstrap/views.py` validates the requested profile or action and permissions and calls `bootstrap/services.py`, which queues a `PlanPreparation` through the lifecycle and reads plans for the server page, the plan page and Activity. In the worker, the step rechecks the requesting account, `bootstrap/inspection.py` runs fixed read-only commands and validates their output with `bootstrap/evidence.py`, `bootstrap/review.py` decides the plan from the evidence and the profile definitions in `bootstrap/profiles.py` as a pure function, and `bootstrap/plans.py` stores it with the operation's success. Plan rows are typed and immutable; `bootstrap/presentation.py` words them for templates. The server page shows the plan section and Activity lists preparations only to accounts with `bootstrap.view_configurationplan`.

Site plans are plan preparations and configuration plans of the site action (`docs/ssh-connections.md#site-preparation`). `bootstrap/actions.py` is the registry through which another app adds an action to configuration plans without bootstrap importing it: `sites/apps.py` registers the site handler, which names the action's view, prepare and apply permissions, prepares its draft through `sites/inspection.py` and `sites/admission.py`, stores its typed file, directory and account rows through `sites/plans.py` in the transaction that saves the plan, and applies it: the payload through `sites/apply.py` and `sites/native.py`, the copied audit rows, the meaning of its exit statuses, and verification ([ADR 0012](adr/0012-publish-site-files-without-replacing-them.md)). Bootstrap's services, views and presentation ask the registry for an action's permissions and handler, so every family of plans is shown only to its own viewers. `sites/convention.py` renders and recognizes the convention's exact files, and `sites/native.py` holds site preparation's fixed commands, the revalidation digest, the payload and the verification reads. `sites` imports `bootstrap` and `discovery`; neither imports `sites`. `tls/apps.py` registers the challenge route handler the same way; it reuses site inspection and admission, and `tls` imports `sites`, never the reverse.

Apply runs are the third kind (`docs/ssh-connections.md#applying-reviewed-plans`), offered for metadata refresh plans, for plans that clear finished bootstrap runs, and for the Nginx and PHP profiles of each supported Ubuntu release ([ADR 0008](adr/0008-review-each-ubuntu-release-by-its-own-policy.md)). `bootstrap/views.py` calls `bootstrap/apply.py`, which queues an `ApplyRun` for one reviewed revision, with its unique transient unit name and copied audit identity, or returns the revision's existing run. In the worker, the step rechecks the account, the reviewed host key, and sudo authorization for the exact submission, records the dispatch through the lifecycle, and submits and inspects the unit through `bootstrap/native.py`, the one adapter that builds the payload, the `systemd-run` command line and the inspection ([ADR 0006](adr/0006-use-native-bootstrap-execution.md)). Terminal native evidence and a separate verification close the run; anything uncertain leaves it reconciling for Check outcome, which inspects the same unit with a new connection at a new revision. A run without native evidence closes as outcome unknown only after an acknowledgement and a lock probe through the same adapter. A package profile's payload comes from the same adapter's profile-agnostic engine: revalidation digests, exact root versions, and an inline APT pre-install guard admitting only the reviewed transaction ([ADR 0007](adr/0007-admit-exact-package-transactions-with-an-inline-apt-guard.md)); after such a run the step queues discovery.

Read-only discovery connects through pyinfra's SSH connector in `discovery/ssh.py`, whose supported configuration, agent and host-trust behavior is recorded in `docs/ssh-connections.md`. Apply runs use the same pyinfra integration for changes to servers ([v0.2 bootstrap design](v0.2.md)). Transport support remains limited to verified behavior; hardware-backed keys are not promised. pyinfra provides SSH transport and execution only; it does not provide durable remote jobs or coordination across devices.

The pyinfra connection follows these rules:

- Barectl resolves the alias with `servers/ssh_config.py` and passes only the resolved settings. pyinfra does not read the controller's SSH configuration.
- Host keys are checked with `ssh_strict_host_key_checking` set to `yes` against a private copy of the alias's known_hosts entries without revoked keys. pyinfra's default, `accept-new`, adds unknown host keys to known_hosts.
- Collectors keep `RemoteShell` and its numeric exit status, output and truncation flag. The connection recovers them from a fixed shell wrapper; it does not use pyinfra facts or operations for discovery.
- There is one execution backend. It uses pyinfra's documented connector data, including `ssh_paramiko_connect_kwargs`, and paramiko's documented `sock` and `transport_factory` connection arguments.

## State and discovery

Store the registration's SSH alias and timestamped observations separately. In the current release, connection settings stay in the controller's SSH configuration. The remote server is authoritative for observed configuration. A failed discovery must retain the previous successful snapshot while showing it as stale. Discovery never automatically adopts or rewrites an unmanaged site.

A fresh controller with authorized SSH access must be able to reconstruct supported observed state without importing the previous controller's database. Each device maintains a local database by default for its Barectl login, preferences, saved connections, queued requests, operation history, and cached observations. The local Barectl login controls access to that application; SSH access and server permissions determine what it can inspect or change remotely. Future releases will store SSH connection details locally. Configuration must remain inspectable through ordinary server tools, and incomplete observations must remain explicit.

Cached observations speed up the dashboard but cannot establish current server permissions, remote job status, or configuration when native evidence is unavailable. Mark their freshness and verification limits explicitly. Native logs and service state may explain past activity, but discovery cannot recover native history that was never recorded or is no longer retained. Barectl must not create its own server-side tracking files, inventory manifests, audit journals, or management database to fill that gap. Normal service configuration and native execution or coordination facilities remain allowed; discovery itself stays read-only.

Barectl's own operation records stay in its application database. Another independent installation cannot reconstruct those records through discovery, though it can inspect available native server history and current state. A local queued request is not evidence that a server accepted or executed it, and losing local state must not trigger blind replay. Store cached observations in typed columns as defined in [ADR 0003](adr/0003-store-discovery-snapshots-in-typed-columns.md).

### Management from multiple devices

Multiple local Barectl installations must be able to manage the same server independently, without requiring a shared database, synchronization, or a hosted Barectl service. Each device establishes its own authorized SSH access and host trust. Its discovery cycles refresh its local view from the server, including changes made by another device or ordinary administration tools.

Future mutations must revalidate server state and coordinate conflicting operations across devices using native Linux facilities or established, widely used packages verified against upstream guidance. A lock or queued job in one device's database cannot provide that guarantee. [ADR 0004](adr/0004-serialize-remote-operations-in-one-table.md) covers serialization within one application database; additional coordination must satisfy these requirements without a persistent Barectl agent, central service, or custom server-side tracking records. The v0.2 design uses a detached transient systemd service and one native nonblocking mutation lock, with boot/deadline fencing and native reconciliation. Every apply run uses them: metadata refresh, cleanup of finished runs, and the Nginx and PHP profiles. Exclusion is qualified on the disposable acceptance server between two controller processes with independent databases, two aliases and two keys submitting together: at most one mutation runs, the other refuses without waiting and needs a new review. The local database constraint is never presented as that exclusion. [ADR 0006](adr/0006-use-native-bootstrap-execution.md) and the [qualification requirements](v0.2.md#testing-decisions) govern release.

When a conflicting operation is active, show the available native evidence and block the requested change. After it finishes, rediscover and require a new operator review instead of automatically applying a queued stale plan. Another device may detect an active operation without knowing its detailed Barectl history. If reliable coordination cannot be established, refuse the conflicting change; do not claim concurrent execution is safe.

Acceptance must cover two controllers with independent databases: a change from one is discovered by the other, conflicting changes are prevented or explicitly rejected, and an interrupted operation is reconciled against server evidence. Either controller must remain usable when the other controller and its database are unavailable.

### Optional shared database

Operators may choose a remote database to share Barectl application records across local installations. This is planned support, not a requirement for connecting to or managing a server. It does not require hosting the Barectl application, and shared records do not override native server state. An independently configured local installation must still be able to connect through SSH if the shared database is unavailable; automatic offline failover is not promised.

The current release uses local SQLite. Shared database support needs explicit design and testing for account access, connection references, worker ownership, and concurrent records. A shared database alone does not make one device's SSH agent or key files available on another, and it cannot coordinate an independent controller that uses a different database.

### Standard configuration and reconstruction

Future provisioning must use one documented configuration convention for each supported distribution and stack. Choose concrete paths, naming rules, and service configuration from version-matched distribution and upstream guidance before implementing them. These conventions must use ordinary Linux configuration and remain understandable with standard administration tools.

Discovery must reconstruct resources and their relationships from current server evidence. For example, it should follow an Nginx configuration's document root and FastCGI endpoint to the application and PHP-FPM pool, then read the pool's user and relevant service configuration. A naming convention can help locate resources, but names alone must not establish ownership or relationships. Conflicting evidence must produce an explicit unresolved relationship rather than a guess.

Every cycle must reread the supported configuration, recognize external additions, changes, and removals, and avoid retaining an old relationship as current when inspection can no longer verify it. A previous snapshot may support comparison and history; it must not be required for reconstruction. Discovery stays read-only and must not rewrite an existing server to match Barectl's provisioning conventions.

Each future provisioning feature must include a reconstruction acceptance test: configure a disposable server, connect from a separate controller with a fresh application database, and reconstruct the resources and relationships that feature created. Repeat after an external configuration change. Reconstruction must not require importing the first controller's records or reading custom Barectl tracking records from the server.

For server user, native history, and job views, verify reconstruction from retained native evidence and explicit unavailability when it cannot be read or no longer exists. A stale local copy must never be promoted to authoritative state because verification failed. Tests must not rely on custom Barectl records written to the server or promise recovery of another device's private operation history.

## Trust and credentials

Require authentication, Django permissions, CSRF protection, and verified SSH host identity. The current inventory is shared among permitted operators. It is not a tenant-isolated application.

Credentials start with the controller account's SSH agent or the key files its SSH configuration names. Hosted deployments cannot use a browser user's laptop agent automatically. Any future stored credentials need encryption with the encryption secret outside the database, restricted access, rotation, and log redaction. Never accept arbitrary shell commands from the web interface.

## Changes and jobs

Read-only discovery is the first remote workflow. Later mutations need a reviewed plan, revalidation against current state, coordination across controllers, bounded timeouts, audit events in the Barectl application database, and explicit failure recovery. A plan preview is not a transaction or an automatic rollback guarantee. Validate Nginx/PHP configuration before reload and retain previous configuration for recovery.

Future long-running operations accepted by the server and configured server schedules must continue when the initiating device disconnects or Barectl closes. For v0.2 bootstrap, apply runs use the transient systemd service and native lock described in [ADR 0006](adr/0006-use-native-bootstrap-execution.md) and inspect native status on reconnection. General scheduling remains later work. This does not permit a Barectl agent or a custom operation journal on the server. Requests that never reached the server remain local and unexecuted; an uncertain outcome must be verified rather than blindly retried. Acceptance must cover controller disconnection, native completion or failure, and inspection from a second device.

Current discovery jobs use Django's tasks framework with the `django-tasks-db` backend and its `db_worker` command on the controller. They do not continue as background server jobs after that controller stops. Per-server serialization within this application database is one constraint on the table of remote operations, which discovery attempts, plan preparations and apply runs share ([ADR 0004](adr/0004-serialize-remote-operations-in-one-table.md)), with additional coordination needed across independent databases. Remote operations protect their server from deletion, so removal cannot race an attempt (`docs/ssh-connections.md#server-removal`). SQLite transactions begin immediately, so concurrent requests and the worker wait for each other's writes rather than failing with "database is locked"; the write-ahead log keeps a request's reads from waiting behind those writes, and the busy timeout outlasts any single worker transaction, so the wait is a queue, never an error. Attempts and plan preparations interrupted by a forced worker stop, or active for longer than ten minutes, are recovered as interrupted failures, keeping any previous snapshot; finishing filters on still-running attempts so a stale worker cannot overwrite newer results. Queued attempts with a ready task wait for the worker; there is no automatic retry. An apply run is recovered the same way only until it is dispatched; afterwards an interruption or abandonment leaves it reconciling, and it is never submitted again. The recovery sweep records only derived status transitions on rows that already exist, so when another connection holds the table while it runs, the sweep leaves its work to the next entry rather than failing the request.

## Reviewed bootstrap

[v0.2](v0.2.md) defines reviewed bootstrap, released as v0.2.0: explicit package-metadata refresh, immutable Nginx and PHP configuration plans for Ubuntu 24.04 and 26.04, exact package-transition admission, native execution and exclusion, and fresh-controller reconstruction. [ADR 0005](adr/0005-review-exact-bootstrap-transitions.md) records the plan contract. Distribution defaults remain independently manageable; no application sites, database provisioning, general upgrades, or custom stack adoption enter this phase.

Plan preparation is implemented as a separate read-only operation that may run fixed privileged reads, the listener query and, for MariaDB, its read-only administrative check, with root or verified noninteractive sudo; ordinary discovery stays unprivileged. It records immutable plans. All three kinds share local lifecycle ownership ([ADR 0004](adr/0004-serialize-remote-operations-in-one-table.md)); apply runs exist for metadata refresh plans, for clearing finished bootstrap runs and for the Nginx, PHP and MariaDB profiles. Apply execution outcome and postcondition verification are distinct fields. An uncertain submission occupies a reconciling state instead of inheriting discovery's stale-attempt failure rule, and its Check outcome action inspects native state within the same operation.

The only Barectl-specific remote runtime object outside native service state is an empty, root-controlled native lock inode. It contains no inventory, PID, lease, plan, or history and is not persistent management storage. Native package state, transient systemd units, and retained system journals are inspected as native evidence; private approval and audit records remain local. Detached execution, the lock, fencing, cross-controller exclusion, outcome-unknown closure, cleanup and exact package admission for both profiles are qualified on the disposable server, and a real kernel reboot during an installation on Ubuntu's cloud image in a virtual machine; the [qualification record](v0.2-qualification.md) lists the revisions and architectures tested and what was not. Transient execution survives controller and SSH loss, not a server reboot, and journal entries last only as long as the server's retention; outcomes rest on unit state, and evidence lost to a reboot or cleanup leaves the outcome unknown. Fresh-controller reconstruction of both profiles, without the first installation's database, is part of that qualification.

## PHP sites roadmap

[v0.3](v0.3.md) is accepted design. Of it, only the reconstruction of sites from native evidence is implemented ([site observations](ssh-connections.md#site-observations)). It extends the existing reviewed-operation boundary to exact file/account changes, database bootstrap and site bindings, and Certbot issuance with native renewal. [ADR 0009](adr/0009-review-native-file-changes-before-site-mutation.md), [ADR 0010](adr/0010-use-local-site-identities-for-database-access.md) and [ADR 0011](adr/0011-use-native-certbot-renewal-under-shared-exclusion.md) record the recovery, identity and renewal trade-offs. The [native site convention](site-conventions.md) defines the supported layout; the [decision/source record](v0.3-decisions.md) separates upstream behavior from Barectl policy. No v0.3 capability is qualified by the existing bootstrap record.
