# Architecture

## Product boundaries

Barectl is one Django application. It may run locally or on a management host. Managed Linux servers remain agentless and expose SSH only for management. Provisioning will install ordinary web-stack packages; agentless does not mean a server can host applications without those packages.

The [core philosophy](../README.md#core-philosophy) governs discovery and future management workflows. Managed servers must remain independently operable if Barectl and its local database disappear. A persistent controller or external control-plane service must not be required for applications to keep running or for an operator to manage the server through ordinary Linux tools.

The repository has `config`, `dashboard` (interface integration: Vite assets, sign-in form and HTMX request handling), `servers` (registration, removal and server pages), `discovery` (attempts, snapshots, the worker task and the SSH connection), shared templates, and the Vite frontend sources in `frontend/`. Add domain apps when a workflow needs them. The interface uses USWDS and HTMX 4. `servers/ssh_config.py` resolves controller SSH aliases with paramiko's configuration parser, following pyinfra's handling of a configuration file (`docs/ssh-aliases.md`), and discovery passes only the resolved settings to pyinfra. `discovery/ssh.py` is the only remote execution boundary (`docs/ssh-connections.md`). In the current release, SSH credentials stay in the controller host's agent or key files. Future saved connection details and optional remote database support must preserve independent access from another authorized controller.

## Request and execution flow

Views validate input and authorize access, then call application services. Services create durable jobs. A separate worker process from the same codebase executes infrastructure adapters. Long SSH operations must not run inside HTTP requests.

Discovery follows this flow. `discovery/services.py` owns the discovery attempt lifecycle: every change of an attempt's state applies only while the attempt is still in the expected state. `servers/registration.py` owns registering a server, changing its alias and server removal: `save_server` saves a registration or edit and queues a connection check when the alias is new, and `remove_server` removes a server with its discovery history. It reaches attempts only through `queue_discovery` and `forget_discovery`. Views call those functions, `recorded_discovery` for the removal page and `request_discovery` to check a server again; they turn outcomes into messages and form errors and never change attempts themselves. `servers/discovery_state.py` is the dashboard's one read of discovery: `server_state` for a server's page, with its discovery history, `inventory` for the server list and `activity_rows` for Activity. The page and the list read the controller's alias catalogue too and decide the connection status. Templates never receive attempt rows: each attempt reaches them as an `AttemptView` in the pages' wording, so the server page, its discovery history and Activity describe the same attempt alike, and the polled fragment sends back a token the module issues rather than the stored state. Other modules read attempts only through `discovery/services.py`: `read_discovery` (a server's latest attempt, current snapshot and discovery history in one read), `latest_attempt_statuses`, `history` (every server's attempts for Activity) and `recorded_discovery`. Every public function of that module recovers abandoned attempts first through one decorator, and a test requires it of each. Queueing records a queued attempt and enqueues the `run_discovery` task in one transaction, using Django's tasks framework with the `django-tasks-db` database backend. `manage.py db_worker` runs the task. It claims the attempt and runs its step, recording a failure the same way whatever the step does; the discovery step connects with the attempt's alias through `discovery.ssh.connect_alias`, collects observations with `discovery.observations.collect`, the only public collection function, and publishes the snapshot with the attempt's outcome. The `discovery/observations/` package keeps `collect` and the operating system and capacity observations in `__init__.py`, probe reads and the classification of their failures in `probes.py`, packages and service units in `components.py`, the Nginx and PHP-FPM parsers in `parsers.py`, and the Nginx site file and PHP-FPM pool collections in `configuration.py`. `discovery/snapshot.py` owns the snapshot's shape: the observation types the collectors return, `save_snapshot`, `current_snapshot`, and `attempt_snapshots`, which reads attempts with the snapshots they published for the pages. Only that module reads or writes the snapshot tables, which keep typed columns ([ADR 0003](adr/0003-store-discovery-snapshots-in-typed-columns.md)). `discovery/presentation.py` names each observation once for the operator: `present` turns a snapshot into the server page's sections, with each observation's label, display lines, outcome, warning and sources, and the warnings Activity lists come from the same presentation, so templates lay out observations without interpreting them.

Read-only discovery connects through pyinfra's SSH connector in `discovery/ssh.py`, whose supported configuration, agent and host-trust behavior is recorded in `docs/ssh-connections.md`. The [v0.2 bootstrap design](v0.2.md) will use the same pyinfra integration for changes to servers. Transport support remains limited to verified behavior; hardware-backed keys are not promised. pyinfra provides SSH transport and execution only; it does not provide durable remote jobs or coordination across devices.

The pyinfra connection follows these rules:

- Barectl resolves the alias with `servers/ssh_config.py` and passes only the resolved settings. pyinfra does not read the controller's SSH configuration.
- Host keys are checked with `ssh_strict_host_key_checking` set to `yes` against a private copy of the alias's known_hosts entries without revoked keys. pyinfra's default, `accept-new`, adds unknown host keys to known_hosts.
- Collectors keep `RemoteShell` and its numeric exit status, output and truncation flag. The connection recovers them from a fixed shell wrapper; it does not use pyinfra facts or operations for discovery.
- There is one execution backend. It uses pyinfra's documented connector data, including `ssh_paramiko_connect_kwargs`, and paramiko's documented `sock` and `transport_factory` connection arguments.

## State and discovery

Store the registration's SSH alias and timestamped observations separately. In the current release, connection settings stay in the controller's SSH configuration. The remote server is authoritative for observed configuration. A failed discovery must retain the previous successful snapshot while showing it as stale. Discovery never automatically adopts or rewrites an unmanaged site.

A fresh controller with authorized SSH access must be able to reconstruct supported observed state without importing the previous controller's database. Each device maintains a local database by default for its Barectl login, preferences, saved connections, queued requests, operation history, and cached observations. The local Barectl login controls access to that application; SSH access and server permissions determine what it can inspect or change remotely. Future releases will store SSH connection details locally. Configuration must remain inspectable through ordinary server tools, and incomplete observations must remain explicit.

Cached observations speed up the dashboard but cannot establish current server permissions, remote job status, or configuration when native evidence is unavailable. Mark their freshness and verification limits explicitly. Native logs and service state may explain past activity, but discovery cannot recover native history that was never recorded or is no longer retained. Barectl must not create its own server-side tracking files, inventory manifests, audit journals, or management database to fill that gap. Normal service configuration and native execution or coordination facilities remain allowed; discovery itself stays read-only.

Barectl's own operation records stay in its application database. Another independent installation cannot reconstruct those records through discovery, though it can inspect available native server history and current state. A local queued request is not evidence that a server accepted or executed it, and losing local state must not trigger blind replay. Store cached observations in typed columns as defined in [ADR 0003](adr/0003-store-discovery-snapshots-in-typed-columns.md).

### Management from multiple devices

Multiple local Barectl installations must be able to manage the same server independently, without requiring a shared database, synchronization, or a hosted Barectl service. Each device establishes its own authorized SSH access and host trust. Its discovery cycles refresh its local view from the server, including changes made by another device or ordinary administration tools.

Future mutations must revalidate server state and coordinate conflicting operations across devices using native Linux facilities or established, widely used packages verified against upstream guidance. A lock or queued job in one device's database cannot provide that guarantee. [ADR 0004](adr/0004-serialize-remote-operations-in-one-table.md) covers serialization within one application database; additional coordination must satisfy these requirements without a persistent Barectl agent, central service, or custom server-side tracking records. The accepted v0.2 design uses a detached transient systemd service and one native nonblocking mutation lock, with boot/deadline fencing and native reconciliation. This is not implemented; [ADR 0006](adr/0006-use-native-bootstrap-execution.md) and the [qualification requirements](v0.2.md#testing-decisions) govern release.

When a conflicting operation is active, show the available native evidence and block the requested change. After it finishes, rediscover and require a new operator review instead of automatically applying a queued stale plan. Another device may detect an active operation without knowing its detailed Barectl history. If reliable coordination cannot be established, refuse the conflicting change; do not claim concurrent execution is safe.

Acceptance must cover two controllers with independent databases: a change from one is discovered by the other, conflicting changes are prevented or explicitly rejected, and an interrupted operation is reconciled against server evidence. Either controller must remain usable when the other controller and its database are unavailable.

### Optional shared database

Operators may choose a remote database to share Barectl application records across local installations. This is planned support, not a requirement for connecting to or managing a server. It does not require hosting the Barectl application, and shared records do not override native server state. An independently configured local installation must still be able to connect through SSH if the shared database is unavailable; automatic offline failover is not promised.

The current release uses local SQLite. Shared database support needs explicit design and testing for account access, connection references, worker ownership, and concurrent records. A shared database alone does not make one device's SSH agent or key files available on another, and it cannot coordinate an independent controller that uses a different database.

### Standard configuration and reconstruction

Future provisioning must use one documented configuration convention for each supported distribution and stack. Choose concrete paths, naming rules, and service configuration from version-matched distribution and upstream guidance before implementing them. These conventions must use ordinary Linux configuration and remain understandable with standard administration tools.

Discovery must reconstruct resources and their relationships from current server evidence. For example, it should follow an Nginx configuration's document root and FastCGI endpoint to the application and PHP-FPM pool, then read the pool's user and relevant service configuration. A naming convention can help locate resources, but names alone must not establish ownership or relationships. Conflicting evidence must produce an explicit unresolved relationship rather than a guess.

Every cycle must reread the supported configuration, recognize external additions, changes, and removals, and avoid retaining an old relationship as current when inspection can no longer verify it. A previous snapshot may support comparison and history; it must not be required for reconstruction. Discovery stays read-only and must not rewrite an existing server to match Barectl's provisioning conventions.

Each future provisioning feature must include a reconstruction acceptance test: configure a disposable server, connect from a separate controller with a fresh application database, and reconstruct the resources and relationships that feature created. Repeat after an external configuration change. Reconstruction must not require importing the first controller's records or reading custom Barectl tracking records from the server.

For server user, native history, and job views, verify reconstruction from retained native evidence and explicit unavailability when it cannot be read or no longer exists. A stale local copy must never be promoted to authoritative state because verification failed. Tests must not rely on custom Barectl records written to the server or promise recovery of another device's private operation history.

## Trust and credentials

Require authentication, Django permissions, CSRF protection, and verified SSH host identity. The current inventory is shared among permitted operators. It is not a tenant-isolated application.

Credentials start with the controller account's SSH agent or the key files its SSH configuration names. Hosted deployments cannot use a browser user's laptop agent automatically. Any future stored credentials need encryption with the encryption secret outside the database, restricted access, rotation, and log redaction. Never accept arbitrary shell commands from the web interface.

## Changes and jobs

Read-only discovery is the first remote workflow. Later mutations need a reviewed plan, revalidation against current state, coordination across controllers, bounded timeouts, audit events in the Barectl application database, and explicit failure recovery. A plan preview is not a transaction or an automatic rollback guarantee. Validate Nginx/PHP configuration before reload and retain previous configuration for recovery.

Future long-running operations accepted by the server and configured server schedules must continue when the initiating device disconnects or Barectl closes. For v0.2 bootstrap, use the qualified transient systemd service and native lock described in [ADR 0006](adr/0006-use-native-bootstrap-execution.md), and inspect native status on reconnection. General scheduling remains later work. This does not permit a Barectl agent or a custom operation journal on the server. Requests that never reached the server remain local and unexecuted; an uncertain outcome must be verified rather than blindly retried. Acceptance must cover controller disconnection, native completion or failure, and inspection from a second device.

Current discovery jobs use Django's tasks framework with the `django-tasks-db` backend and its `db_worker` command on the controller. They do not continue as background server jobs after that controller stops. Per-server serialization within this application database is a constraint on discovery attempts; planned plan preparation and apply runs will share it as one table of remote operations ([ADR 0004](adr/0004-serialize-remote-operations-in-one-table.md)), with additional coordination needed across independent databases. Discovery attempts protect their server from deletion, so removal cannot race an attempt (`docs/ssh-connections.md#server-removal`). SQLite transactions begin immediately, so concurrent requests and the worker wait for each other's writes rather than failing with "database is locked". Attempts interrupted by a forced worker stop, or active for longer than ten minutes, are recovered as interrupted failures, keeping any previous snapshot; finishing filters on still-running attempts so a stale worker cannot overwrite newer results. Queued attempts with a ready task wait for the worker; there is no automatic retry.

## Reviewed bootstrap

[v0.2](v0.2.md) defines the next phase: explicit package-metadata refresh, immutable Nginx and PHP 8.3 configuration plans, exact package-transition admission, native execution and exclusion, and fresh-controller reconstruction. [ADR 0005](adr/0005-review-exact-bootstrap-transitions.md) records the plan contract. Distribution defaults remain independently manageable; no application sites, database provisioning, general upgrades, or custom stack adoption enter this phase.

Plan preparation is a separate read-only operation and may inspect privileged evidence with explicit authorization. Ordinary discovery stays unprivileged. All three kinds share local lifecycle ownership; [ADR 0004](adr/0004-serialize-remote-operations-in-one-table.md) covers its migration. Apply execution outcome and postcondition verification are distinct. An uncertain submission occupies a reconciling state instead of inheriting discovery's stale-attempt failure rule. Its own Check outcome action can inspect native state without creating a second conflicting operation.

The only Barectl-specific remote runtime object outside native service state is an empty, root-controlled native lock inode. It contains no inventory, PID, lease, plan, or history and is not persistent management storage. Native package state, transient systemd units, and retained system journals are inspected as native evidence; private approval and audit records remain local. These decisions are accepted implementation requirements, not a claim that remote durability, package admission, or cross-device coordination already pass qualification.
