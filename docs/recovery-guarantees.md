# Recovery guarantees

This matrix states what Barectl's recovery evidence guarantees, which test proves each case, what the operator does, and what is explicitly not promised. The [native recovery guide](recovery.md) is the runbook; the [Phase C](phase-c-qualification.md), [Phase D](phase-d-qualification.md) and [Phase E](phase-e-qualification.md) records name the revisions and the scenarios that qualified the behavior. This document links that evidence; it does not re-qualify it. The parent specification is [#528](https://github.com/rajandangi/barectl/issues/528), and the abrupt-termination cases were added by [#538](https://github.com/rajandangi/barectl/issues/538).

A review is not a transaction. Barectl has no automatic rollback and no automatic replay: a change that stopped partway stays as the server left it, and an uncertain run is reconciled or closed as unknown, never retried. No recovery point objective (RPO) or recovery time objective (RTO) is promised beyond the restore scenarios measured in the Phase D record ([capture and restore times](phase-d-qualification.md#capture-and-restore-times)); those scenarios time whole journeys, not a single capture or restore.

## Limits of this evidence

- Every local native run is an arm64 container from the pinned Ubuntu image unless the row names the VM lane; the fast-layer rows are controller tests. Hosted amd64 evidence is named only where the Phase C, D or E record contains it, and a row that states an arm64 container makes no hosted amd64 claim.
- A container stop and start is a **userspace reboot**. It does not change the kernel boot ID, so it is not a kernel reboot, a panic, or a power cut. The VM lane is the only real-kernel evidence, and it does not interrupt a change in flight.
- `RebootedFullBackup` is a breadth-only item, not part of the merge build. It was run on the local arm64 host; no hosted amd64 run of it exists.
- Fast-layer rows prove the controller contract, not native server behavior. The native rows use a disposable server.
- Power loss and abrupt termination were sampled at four stages: before dispatch, after dispatch before acknowledgement, during a native body, and after a full capture paused the site. This is not a proof for every stage of every change.

The abrupt-termination rows in the matrix are the controller death before dispatch, the controller death after dispatch, the server stop mid-body, and the reboot during a paused full capture.

## Matrix

| Failure | What is guaranteed, and the test that proves it | Operator action | Not promised |
| --- | --- | --- | --- |
| Refusal before any write | A native body refuses before persistent mutation: no account, Caddy site file, pool file or changed preimage is left, and a second controller's racing run ends `lock_busy` with no second site (`disposable.test_http_site_validators.HttpSiteValidators.test_changed_preimage_and_unsafe_directory_refuse_before_persistent_mutation`; `disposable.test_target_race.TwoControllerNativeLock.test_two_controllers_racing_admit_one_run_and_refuse_the_other`). | Fix the reported precondition, rediscover if needed, and prepare a new review. The refused run needs no repair. | A refusal is only evidence when its result line is read. A run that dies before its result line belongs to the unknown-outcome rows. Nothing is "rolled back"; nothing was written. A losing controller does not queue or adopt the winner's plan. |
| Change stops partway | An interrupted PHP selection leaves both masters admitted and the previous selection persisted. Native evidence alone makes a fresh controller report `partly_applied`, and a new review finishes to the chosen runtime and proves one effect (`disposable.test_php_recovery.SitePHPControllerRecovery.test_both_ready_interruption_is_finished_without_previous_controller_history`). | Open the site's **Settings**, choose **Finish or reverse the PHP change**, select the runtime to keep and prepare the review. Run discovery first. | No automatic finish, reversal or rollback. Barectl never kills remaining PHP work to complete a switch, and the partial state stays until an operator reviews it. |
| Controller lost while the native body continues | A worker killed while a submitted body keeps running does not stop the native change. The unit reaches `succeeded`, and a second controller with its own empty database reconstructs the site, runtime and Jobs result from server evidence (`disposable.test_http_site_recovery.HttpSiteControllerRecovery.test_native_site_creation_survives_worker_death_and_fresh_controller_discovery`). | Reconnect, refresh observations and continue from the reconstructed state. Do not resubmit the change. | The controller's private review, approval and run history are gone. Reconstruction proves observed state and retained native history, not another controller's records. |
| Controller lost before dispatch (abrupt termination) | A worker killed after review but before dispatch leaves no submission. The run is failed as interrupted with execution `not_submitted`, the page says it stopped before it submitted anything, and it offers **Try again** (`disposable.test_http_site_recovery.WorkerKilledBeforeDispatch.test_worker_killed_after_review_before_dispatch_changes_nothing`). | Review the outcome, then try again. No server repair is needed. | This "nothing changed" guarantee applies only when the run never dispatched. It is not evidence for a run that reached the server. No automatic retry. |
| Controller lost after dispatch (abrupt termination) | A worker killed after dispatch but before acknowledgement cannot prove that nothing ran. The run stays reconciling, **Check what happened** finds no unit or result, and it closes only as **outcome unknown**, never as success or "nothing changed" (`disposable.test_http_site_recovery.WorkerKilledAfterDispatch.test_worker_killed_after_dispatch_is_reconciled_as_unknown_without_submission`). | Choose **Check what happened**. After a restart or the admission deadline, acknowledge **Close as outcome unknown**, then refresh observations and prepare a new review. | The change may have run. There is no replay and no automatic retry. Missing evidence is never proof that nothing ran. |
| Unknown native outcome | Missing evidence keeps the run reconciling. Closing as unknown requires the mutation lock, proof that no Barectl process remains and that the run can no longer start, plus the operator's acknowledgement. The closed run never records success or "no changes" (`operations.test_engine.EngineReconciliationTests.test_missing_evidence_without_a_result_line_stays_reconciling`; `operations.test_engine.EngineReconciliationTests.test_closing_unknown_needs_proof_and_an_acknowledgement`). | Use **Check outcome** first. If the evidence cannot be recovered, close as outcome unknown, run discovery and prepare a fresh review. | This is fast-layer contract evidence, not a native run. It does not make an unreadable or lost result line readable, and it does not promise that the server can be repaired automatically. |
| Server stops mid-body (power loss during a change) | A server stopped while a body is running loses its transient unit. Exactly one submission stays one submission: the run is reconciled as unknown, no second unit is submitted, and no loaded apply unit remains (`disposable.test_http_site_recovery.ServerStoppedDuringBody.test_server_stopped_during_a_body_is_reconciled_as_unknown_without_replay`). | Check the outcome, close as unknown when the evidence supports it, run discovery, then prepare a new review. Inspect the paths the change touched before changing anything. | The container stop is a userspace restart, not a kernel reboot. What the body changed before it stopped is unknown; Barectl does not replay it or restore it automatically. |
| Server reboot mid-run | A reboot during a paused full capture keeps the site gated: it stays on `503`, the backup row is `partial` / `backup_paused`, the page shows one stopped sentence and one **Reopen site**, and no **Finished** claim. **Reopen site** restores the site (`disposable.test_backups.RebootedFullBackup.test_a_reboot_during_a_full_capture_keeps_the_gate`). | Choose **Reopen site** on the site's **Backups** section, then choose what background work should run in **Scheduled tasks** or **Queue workers**. | Breadth-only, local arm64 container evidence. This is a userspace reboot, not a kernel reboot. The site is not reopened automatically, background work stays off, and the incomplete point is never restored. |
| Lost controller database | Two controllers with independent empty databases reconstruct the same target-stack server from native evidence, produce identical observations, and propose no changes. Jobs rows come from the native journal and result line, not the first controller's database (`disposable.test_target_reconstruction.FreshControllerReconstruction.test_two_fresh_controllers_reconstruct_the_same_server_and_propose_nothing`). | Install Barectl, add the server with authorized SSH access and host trust, discover, and review. Do not import another controller's database. | Another controller's private reviews, approvals, audit records and local operation history are not recovered. Cached observations never become authority when native evidence is unavailable. |
| Lost server | A second server connects the same offsite storage with the kit facts, storage keys and passphrase and restores the source point into a matching site under another identifier and domain (`disposable.test_backups.DisasterRecovery.test_a_second_server_restores_from_connected_storage`). Without Barectl, plain restic with the printed kit and the operator's passphrase alone recovers the database (`disposable.test_backups.OfflineRecovery.test_plain_restic_recovers_from_the_kit_and_passphrase_alone`). | Use the recovery kit and passphrase. With Barectl, connect existing backup storage and restore into a matching site of the same kind and database-engine major. Without Barectl, follow the commands in the native recovery guide. | Only recovery points that exist are recoverable. No RPO or RTO is promised beyond the measured restore scenarios; there is no promise to rebuild lost application data, recover the lost host, or recover another controller's private history. A stale listing never authorizes a restore. |
| Real kernel reboot outside an interrupted change | On the VM lane a real kernel reboot changes `/proc/sys/kernel/random/boot_id` and SSH returns (`disposable.test_vm_lane.VmReboot.test_a_real_reboot_changes_the_boot_id_and_ssh_returns`). The reviewed restart body writes its result, reboots, and verifies a new boot and running services (`disposable.test_vm_lane.VmRestart.test_a_reviewed_restart_returns_with_a_new_boot_and_running_services`). | Use the reviewed restart, reconnect, and verify the new boot and services. | The VM lane proves a real reboot and the restart body's own reboot, not a kernel reboot or power loss during another change. The container rows above are userspace reboots. Hosted amd64 evidence for both VM tests is named in the Phase E record. |

## What never changes

Barectl never removes a site, account, runtime or file automatically. It never adopts a resource that differs from the convention, never rebuilds lost application data, and never turns missing evidence into a success or an unchanged claim. When native evidence is gone, the repair is ordinary administration by an operator who can inspect the server.
