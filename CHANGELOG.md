- Create plain PHP sites over HTTP, each with its own account, PHP-FPM master, private HAProxy admission and Caddy site file; switch a site's PHP runtime without dropped requests, and select its Node runtime ([creating a PHP site](docs/sites.md), [site convention](docs/site-conventions.md)).

### PHP sites (Phase B)

- Serve every new site over HTTPS with a certificate Caddy issues and renews, and show its state on the site page: Issued with its expiry, Waiting for DNS and issuance, Failing with Caddy's reason, Renewal due, or Not used for an HTTP-only site. An HTTP-only site is a create-form option; HTTP requests redirect to HTTPS while ACME challenges keep answering, unknown host names get 404 on HTTP and are refused on HTTPS, the public listeners stay SSH, 80/tcp, 443/tcp and 443/udp, and the review warns without refusing when a name does not resolve to the server. Certificate state comes from Caddy's own stored files and journal, so a fresh controller reconstructs it ([HTTPS](docs/tls.md), [ADR 0027](docs/adr/0027-serve-sites-and-https-with-caddy.md)).
- Set or clear the optional certificate contact email from Server **Settings > HTTPS**. The address is Caddy's global `email` option for certificate authority notices; an empty setting publishes no email line, and creating a site never asks for it. One Shared change rewrites only that line in the main configuration, preserves other global options, validates the candidate with Caddy, reloads it and verifies the running configuration, restoring the previous file on failure. Discovery reads the rendered file, so a fresh controller shows the setting without a Barectl marker ([HTTPS](docs/tls.md#certificate-contact-email)).
- Give a plain PHP site a readiness path on its Runtime page, `/` by default. A change is one Site review; after the identity probe, Barectl requests the path with the site's primary Host and requires an answer below 500 at `/` or exactly 200 at another path. A non-default path is native evidence in the site's Caddy file, so a fresh controller reconstructs it without a Barectl marker ([readiness](docs/sites.md#readiness)).
- Edit a site's bounded PHP-FPM pool settings from its Runtime page: the process manager, its children and spare counts, the idle, slow-request and request timeouts, and the memory, upload and post limits. Values outside the supported bounds are refused at the form and at review; applying rewrites only that site's pool file, validates it, and sends a graceful reload to the site's own master, so running requests finish and no other site's master is touched. A fresh controller reconstructs the values from the pool file alone ([PHP settings](docs/sites.md#php-settings)).
- Install MariaDB 11.8 or PostgreSQL 18 as the server's one database engine from Server **Settings > Database**. The review simulates APT against the server's own sources and names every package at its exact version; the run installs exactly those under the inline `DPkg::Pre-Install-Pkgs` guard, starts and enables the service, and hardens MariaDB to its local socket with no anonymous account or test database ([ADR 0007](docs/adr/0007-admit-exact-package-transactions-with-an-inline-apt-guard.md)). It refuses a foreign or other-version engine and installing the second engine, and removal is refused while the engine holds any database. Git can ride the same transaction. Discovery reconstructs the engine and its version from the server alone ([databases](docs/databases.md)).
- Give a site its own database and principal, both named `s<id>`, over the local socket with no password, from Site **Settings > Database**. The review names the convention's statements, runs them one by one and reports progress; the body proves the binding through the site's own PHP master, and a fresh review finishes only what is missing. The principal holds every privilege on that one database and can dump and re-import it, and a fresh controller reconstructs the binding from the server alone ([ADR 0010](docs/adr/0010-use-local-site-identities-for-database-access.md), [ADR 0013](docs/adr/0013-create-a-database-binding-statement-by-statement.md), [databases](docs/databases.md)).
- Create a Laravel site from the dashboard with its domain, Git repository and branch. One reviewed change builds the site and its database, writes a private `.env` from Laravel's production defaults with a server-generated `APP_KEY`, and — for a private SSH repository — generates an ed25519 deploy key as the site user and trusts the repository host key only by an exact fingerprint match (ADR 0034). Only the deploy key's public half is shown, and it never reaches the controller. A fresh controller reconstructs the site, its repository and branch, its environment key names and the deploy key's public half from the server alone ([creating a Laravel site](docs/sites.md#creating-a-laravel-site), [ADR 0019](docs/adr/0019-deploy-laravel-through-reviewed-native-releases.md), [ADR 0034](docs/adr/0034-trust-a-fresh-host-by-confirming-its-fingerprint.md)).
- Deploy a Laravel site from its **Deployments** section. The review resolves the branch to an exact commit and states the free disk, the retained releases it will remove and whether pending migrations will run; the apply fetches that commit, installs from the committed `composer.lock` with the site's own Composer and PHP, builds Laravel's caches, and switches `current` behind a maintenance page, running pending migrations once and lifting the page only when `/up` answers 200. A failure before the switch leaves the old release serving; a failed migration or boot keeps the gate and reports which release is current, and nothing is retried. The run reloads the site's own PHP-FPM master gracefully after switching `current`, so readiness observes the new release and running requests finish. **Roll back** reactivates a retained release with a review that says schema, data, storage and settings are not reversed, and each deploy keeps `current` plus the newest five releases ([ADR 0019](docs/adr/0019-deploy-laravel-through-reviewed-native-releases.md), [ADR 0040](docs/adr/0040-classify-laravel-release-permissions.md), [deploying](docs/sites.md#deploying-a-laravel-site)).
- Reset a WordPress site's administrator password and verify its core files from its **WordPress** section. The new password is typed on the confirm screen and reaches the server only over the confidential channel; WordPress's own sign-in page must accept it before the run succeeds. Core verification compares the installed files with WordPress.org's official checksums and reports a match, a mismatch and an unavailable checksum service as separate outcomes ([WordPress](docs/wordpress.md#actions), [ADR 0032](docs/adr/0032-keep-secrets-in-private-native-files.md)).
- Edit a Laravel site's Environment and a WordPress site's extra constants from the dashboard. The page lists key names and server-computed digests; Laravel's fixed non-secret keys show their values and every other value is write-only. A save sends only the changed keys over the confidential channel, rewrites only their lines as the site user at 0600, leaves untouched lines byte-identical, rebuilds Laravel's cached configuration when one is in use, and keeps Barectl-owned WordPress names fixed ([settings](docs/settings.md), [ADR 0032](docs/adr/0032-keep-secrets-in-private-native-files.md)).
- Remove a site from its **Settings** section. The review lists the Caddy file, services, PHP-FPM and HAProxy configuration, database and principal, stored certificate, directory and accounts, and states that no backup exists before Phase D. Applying is Destructive consent and requires typing the primary domain; the run gates the site, removes those resources, and verifies that nothing remains while the other sites keep serving. A failure reports partly applied and a fresh review finishes the remainder ([removing a site](docs/sites.md#removing-a-site)).
- Create a WordPress site from the dashboard with its domain, title, administrator username and email. The review asks for the administrator password on its confirm screen and sends it only over the confidential channel; it is never stored. One reviewed change builds the site and its MariaDB binding, verifies the pinned core archive's size and SHA-256, installs it as the site user, writes server-generated salts to a private configuration, keeps the site gated until the home, login and REST pages answer over HTTPS, and reports the core version from native files without running PHP. A fresh review finishes an interrupted install without reinstalling into existing tables. PostgreSQL servers disable the tile with the reason ([WordPress](docs/wordpress.md), [ADR 0017](docs/adr/0017-manage-wordpress-as-a-site-application.md), [ADR 0018](docs/adr/0018-generate-wordpress-secrets-on-the-server.md), [ADR 0032](docs/adr/0032-keep-secrets-in-private-native-files.md)).
- Show **Update available** for PHP, Caddy and HAProxy when a newer catalog build ships, naming the affected sites, and apply it through one Shared review: PHP sites move through the switch-and-drain, Caddy and HAProxy restart only when their own build changes, the previous generation stays until verification, and older generations are collected afterwards. A failed build is refused before any profile changes, and **Revert** restores a PHP profile's previous generation. **Remove** a PHP runtime that no site and no server default selects ([runtimes](docs/runtimes.md), [ADR 0038](docs/adr/0038-drain-site-php-through-private-haproxy.md)).
- Install a missing database engine or PHP version from inside Create site as **Step 1**. A WordPress host with no engine offers MariaDB; a Laravel host offers MariaDB or PostgreSQL; the runtime select lists catalog PHP builds it can install. Each step queues the existing reviewed Add runtime or Install database engine change, and its finished run returns to the create form with the operator's answers kept ([Step 1](docs/sites.md#step-1-a-missing-runtime-or-database-engine)).

### Automation and cache (Phase C)

- Run a Laravel site's **database queue workers** from Settings with one reviewed definition: up to eight queue names in priority order, one to four processes and a 30 to 900 second job timeout. Start writes `DB_QUEUE_RETRY_AFTER` above the timeout before any process starts and enables boot activation; Stop disables it so an explicit stop survives a reboot; Restart is graceful and lets each process finish its current job. A crash restarts within a five-start limit and a crash loop reads **stopped after repeated crashes** with a Start action that clears it. Start and Restart refuse without a verified current release, recorded migrations, the `jobs` table, PCNTL or with a duplicate worker; Stop is always available. Discovery reconstructs the definition and state from the units alone ([automation](docs/automation.md#laravel-database-queue-workers), [#266](https://github.com/rajandangi/barectl/issues/266)).
- Run a Laravel site's scheduler from Site **Settings > Scheduled tasks**. **Turn on** publishes one root-owned timer and bounded oneshot service in the site's slice, running `artisan schedule:run` every minute as the site account from its current release and selected PHP; **Turn off** stops and removes them, and **Run now** starts one run and waits for its result. Every run is limited to one hour with the whole process group stopped at that limit, has no catch-up after downtime and never overlaps the next tick. Turning on and Run now need a verified ungated Deploy or Roll back outcome with no pending migrations, a hand-made crontab or Supervisor scheduler blocks turning on, and turning off is always available. Discovery reconstructs the scheduler and distinguishes a skipped tick and a timed-out run from success ([automation](docs/automation.md#turning-the-laravel-scheduler-on-and-off-and-run-now), [#265](https://github.com/rajandangi/barectl/issues/265)).
- Settle the object cache's PHP client as phpredis from the runtime catalog. The lock gains the packaged `redis` extension for PHP 8.4 and 8.5 (`php84_redis`, `php85_redis`) as supply, never as a runtime an operator adds; a site loads it from its locked store path through its own pool and `bin/php`/`composer`/`wp` wrappers, and enabling or disabling it is a Site review that restarts only that site's master ([PHP extensions](docs/runtimes.md#php-extensions), [#390](https://github.com/rajandangi/barectl/issues/390)).
- Point a Laravel site's cache store at its own Valkey instance from **Settings > Object cache**. The change writes `CACHE_STORE=redis`, `REDIS_HOST` and `REDIS_PORT=0` through the Edit settings environment path, rebuilds Laravel's cached configuration and gracefully restarts the site's running workers. The three keys are Barectl-managed and read-only in Environment while they name the site's private cache, and their values stay on the server. Turning off restores the recorded previous store, rebuilds the configuration and restarts workers before the instance stops; a controller without that record refuses to guess, while a gated or partly deployed site can always disconnect. Discovery recognizes the `.env` wiring from digests and reconstructs the state on a fresh controller ([object cache](docs/object-cache.md#laravel-wiring-and-ordering), [#393](https://github.com/rajandangi/barectl/issues/393)).
- Read a site's **Logs** on request: Visits, PHP errors, slow PHP requests, the application log and a WordPress debug log, each as a bounded page of at most 500 lines and 256 KiB with older pages, a search term and a time range; opening the section contacts nothing. Secret values from the site's private environment or WordPress constants are replaced on the server first, access lines show time, method, path, status and duration with the raw line one click away, and a page is kept only 24 hours or until the next read. Reading needs the new view-evidence permission; a Viewer sees the explanation instead. Barectl writes one root-owned rotation file per site for the logs it creates (daily or 20 MiB, five compressed files, 14 days) on every create path, and offers a reviewed **Set up log rotation** repair when it is missing or edited outside the supported shape ([logs](docs/logs.md), [#389](https://github.com/rajandangi/barectl/issues/389)).
- Add **Scheduled tasks**, **Queue workers** and **Object cache** to a site's **Logs**, read from the journal of the units their own conventions name: the WordPress `wpcron` or Laravel `schedule` unit, every installed `queue1`…`queueN` worker in process order, and the site's packaged `valkey-server@<identifier>` instance. Each source keeps the same 500-line and 256 KiB bounds, server-side secret replacement and controller second pass as the file logs, continues older pages by cursor, and offers a live panel that polls `--after-cursor` only while it is visible, appends without moving focus and announces new lines through the Logs status region. A source whose unit is not installed reads as **not configured**, distinct from an empty, missing or unreadable log, and Barectl never classifies an outcome from these lines ([logs](docs/logs.md#live-view), [#397](https://github.com/rajandangi/barectl/issues/397)).
- Install Valkey from Server **Settings > Object cache (Valkey)** as one reviewed APT transaction that names the package, its exact version and APT's download size. The run installs exactly those packages under the inline `DPkg::Pre-Install-Pkgs` guard, stops and masks the distribution's shared `valkey-server.service` so nothing listens on TCP 6379, and restarts the running PHP masters and site proxies so a package transaction's `daemon-reload` leaves them verifiable (#428). It is Shared consent, so a Site operator is refused in the page and on a direct POST; an installed and masked Valkey proposes no changes, and discovery reconstructs the package, version and masked unit from the server alone ([object cache](docs/object-cache.md)).

- Turn on a WordPress site's **Settings > Object cache** for that site alone. One Site review creates the packaged `valkey-server@<identifier>.service` with a root-owned drop-in and configuration, running as the site account over a private `0600` Unix socket with no TCP, password or persistence, `allkeys-lru` and a reviewed memory limit; writes the reserved `WP_REDIS_SCHEME`, `WP_REDIS_PATH` and `WP_REDIS_PREFIX` constants; installs the pinned Redis Object Cache plugin from its checked archive and enables its drop-in; and proves the plugin reports Connected through phpredis. Another site's account can neither open the socket nor read the configuration, and the cache refuses administrative commands while ordinary flushes work. Turning it off disables the drop-in and clears the constants before stopping and removing the instance. The site screen offers **Install Valkey** first and refuses with a reason when Valkey, WordPress or the site's PHP client is missing. Overview shows one cache line, and **Check the cache** reads used memory against the limit, evictions and connected clients on demand through the worker, keeping nothing beyond the request. Discovery reconstructs the instance, its wiring and a supported in-bounds memory edit; a changed `User`, `ExecStart` or socket is reported once and blocks turning it on. Site removal removes the cache with the site ([object cache](docs/object-cache.md#a-sites-own-cache-implemented-392), [#392](https://github.com/rajandangi/barectl/issues/392)).
- Pause a site's background work around every change that alters its code, schema, runtime, settings or files, and start exactly the reviewed work again only after the change verifies. The review records the plan once; the body runtime-masks each timer and service, stops the slice and proves it empty within a budget derived from the units' own stop budgets, and removes boot activation while a maintenance gate is up so a reboot cannot bypass the fence. A unit added, removed or enabled since the review refuses the change with nothing done, and turning work back on is the ordinary Scheduled tasks or Queue workers review, which asks rather than guessing ([automation](docs/automation.md#fencing-site-changes), [ADR 0036](docs/adr/0036-run-site-automation-in-per-site-slices-without-the-global-lock.md), [#395](https://github.com/rajandangi/barectl/issues/395)).
- Qualify Phase C and add the scheduled breadth job: a userspace reboot with no controller, a maintenance gate kept off across that boot, a scheduler tick longer than a calendar minute, and the memory of a cache instance and its workers inside 1, 2 and 4 GiB memory cgroups. The job is never a required check and adds no time to a merge build ([qualification record](docs/phase-c-qualification.md), [test time budget](docs/quality.md#the-scheduled-breadth-job), [#398](https://github.com/rajandangi/barectl/issues/398)).

### Removed

- The Nginx, Certbot, APT PHP, third-party PHP source, database, TLS and WordPress workflows, their discovery and their native suites, deleted at the Phase A exit ([#341](https://github.com/rajandangi/barectl/issues/341)); Phase B builds the HTTPS, database, WordPress and Laravel workflows on the target stack. Servers set up by earlier builds are reported as Not manageable.
- Ubuntu 24.04 support: a server on Ubuntu 24.04 is reported as an unsupported release ([#345](https://github.com/rajandangi/barectl/issues/345)).
- Earlier database migrations: rebuild the local database with `migrate` on an empty database.

## 0.3.0 - 2026-10-04

- Install a site's certificate through one **Create and Install** request with its discovered domain names and contact email. The worker prepares and verifies the challenge route, guarded renewal setup, production order and HTTPS activation automatically. There is no separate agreement checkbox; the request authorizes noninteractive registration. Unknown outcomes pause for Check outcome on the original run, failures stop without replay, and individual plans remain under Advanced TLS diagnostics ([ADR 0014](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/adr/0014-install-site-certificates-with-one-operator-action.md)).

### TLS

- Activate HTTPS for a site with two exact reviewed Nginx candidates ([TLS](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/tls.md#activation)): first the HTTPS server block with HTTP and the challenge route unchanged, then the HTTP redirect to the literal canonical name while preserving the challenge route; no HSTS. The run publishes the shared default TLS rejection server `/etc/nginx/conf.d/tls-default-reject.conf` (IPv4 and IPv6 443 `default_server`, `ssl_reject_handshake on`), keeps the site file's preimage, requires `nginx -t` before every reload, and verifies the certificate actually served for each name, the redirect, the challenge route, that an unknown name receives no certificate and that a Host different from a valid SNI is not served the site. A refused first candidate is restored; a failed redirect leaves the verified HTTPS state, and every stop has its boundary and recovery.
- Order one production certificate for a site ([TLS](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/tls.md#issuance)): the review reads the allowlisted production authority, the operator's contact address and the order request's authorization of noninteractive terms handling, the exact names, the existing lineage and account state (a matching lineage is a plan without changes; other names or another account contact are refused), and repeats the readiness reads fresh. Applying needs `tls.issue_certificate` and runs one `certonly` into Certbot's ordinary lineage under the shared mutation lock, rechecking the site, renewal setup, readiness and lineage digests inside the unit before Certbot runs, and classifying the order's DNS, CAA, rate-limit and account boundaries. Verification records the certificate's names, validity, serial, SHA-256 DER fingerprint, key identity and renewal configuration; a lost answer is checked from the unit alone and the order is never submitted twice.
- Reconstruct activated sites from the server ([site certificate observations](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/ssh-connections.md)): discovery recognizes the four convention site forms, records the Nginx certificate references and the site's stage, reads the public certificate's names, issuer, validity and fingerprint and the certificate served per name over 127.0.0.1 (never private-key bytes), and observes `certbot` and `certbot.timer`. Root-only evidence is named inaccessible, never absent, and a mismatch between the certificate on disk and the one served is visible without being an error.
- The site convention's revision 3 adds the HTTPS and redirect forms and the shared default rejection server ([TLS convention](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/site-conventions.md#https-activation)); site admission recognizes a challenged site as owning its webroot across both activated forms.
- Order a staging certificate to demonstrate the public path ([TLS](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/tls.md#staging)). The staging order repeats the readiness reads fresh, requires the site to be exactly the convention's and the guarded Certbot at its qualified version, and records the operator's contact address and the order request's authorization of noninteractive terms handling. A reviewed staging review proposes one `certonly` order against the allowlisted staging authority through the site's challenge webroot, into isolated configuration, work and log directories (`/etc/letsencrypt-staging/<id>` and siblings); the staged certificate's subject, dates and names are the time-stamped evidence, Nginx never references them, and no production state is read or written. A lost answer is reconciled without ordering twice. The order's exits name DNS/routing, CAA, rate-limit, account and other failures; a lineage for other names is never adopted.
- Review the external prerequisites of a site's TLS with a read-only readiness review ([TLS](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/tls.md#readiness)): for a complete convention site with its challenge route, fresh DNS answers from the server's own resolver, the server's own global addresses, its NTP-synchronized clock and the authority directory's answer over every family the names publish. A proxy or CDN in front of the site, an AAAA record without a working IPv6 path, CAA that names another authority, an unreachable directory or an unsynchronized clock refuses the review.
- Review and apply Certbot renewal setup ([TLS](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/tls.md#certbot-renewal-setup), [ADR 0013](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/adr/0013-inhibit-certbot-renewal-until-the-guard-is-verified.md)). The plan reviews the distribution's Certbot (2.9.0 on 24.04, 4.0.0 on 26.04) exactly as a package profile and adds the runtime inhibition, three renewal files with their complete bytes and the timer's enablement, and shows renewal's current state read-only. Installation or repair is refused while Certbot has accounts, lineages or hooks, or while other certificate automation exists, which Barectl never disables. A fully satisfied guarded setup is inspected without changes after issuance; its native renewal configuration must still meet the supported convention. One native unit masks the timer and service at runtime, installs the reviewed transaction, publishes the wrapper, deploy hook and drop-in, requires systemd to load exactly that override, and only then enables the packaged timer. The wrapper takes the mutation lock with the apply payloads' own steps, skips while a Barectl run has processes, renews with `--no-directory-hooks` and one deploy hook that validates Nginx before reloading, and fails with 80 when a renewed certificate is not the one served. No certificate is ordered.
- Refuse every apply run, cleanup and site run with exit 25, before any change, while Certbot's packaged renewal service `certbot.service` has processes, including one that outlived its main process, and keep an unknown outcome reconciling until it ends ([ADR 0006](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/adr/0006-use-native-bootstrap-execution.md#payload)). The closure probe prints a fifth line for it. Controllers without this check must be upgraded or stopped before renewal is set up.
- Review and apply a site's HTTP-01 challenge route ([TLS](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/tls.md)), with its own `tls.view_tlsplan`, `tls.prepare_tlsplan` and `tls.apply_tlsplan` permissions in a **TLS plans** section. For a complete convention site, one native unit keeps the site file's preimage root-only in `/var/backups/nginx`, creates the webroot `/var/lib/letsencrypt/<id>`, renames the reviewed replacement over the site file only while it still has the reviewed bytes, restores the preimage when `nginx -t` refuses it, reloads Nginx and proves the route with a temporary probe; each later stop is recorded with its boundary. The site convention's revision 2 recognizes the route in site admission and discovery, which reports the webroot as a resource, so a site with its route stays satisfied and never blocks another site. No certificate is ordered.

### PHP sites

- Keep a request's database reads from waiting behind the worker's writes: the SQLite database now uses the write-ahead log, and the busy timeout is 30 seconds, so the worker and concurrent requests queue behind each other instead of failing with "database is locked" ([state and discovery](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/architecture.md#state-and-discovery)).
- Give a complete convention site its own PostgreSQL database in the release default's `main` cluster ([database bindings](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/databases.md#database-bindings)), with the same review, boundaries and proof as MariaDB. The role authenticates by peer through the distribution's `pg_hba.conf` rule and has no password, memberships or powers; its database is created from `template0` with `template1`'s reviewed libc locale, and PUBLIC's `CONNECT` and `TEMPORARY` and its rights on the public schema are revoked (exit 60 when the schema's revoke fails). Each plan's catalog read covers the other engine, so a site keeps one binding and never switches engines.
- Give a complete convention site its own MariaDB database ([database bindings](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/databases.md#database-bindings)). The review requires the established engine and PHP driver, reads the catalog under the site's name and admits only its absence, or no changes for the convention's exact rows; partial, custom and other-engine bindings are refused with what exists. The run revalidates the site, engine, driver and catalog under the lock, proves through the site's pool that PHP runs as the site user with the driver, then creates the unix_socket principal, the utf8mb4 database and its exact grant, each in its own client invocation without conditional statements, compares the catalog with the predicted result, and proves through the pool that the site uses its database and is refused others, administration and password-less TCP ([ADR 0013](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/adr/0013-create-a-database-binding-statement-by-statement.md)). Each boundary has its exit status and recovery; nothing is dropped, resumed or retried. A privileged, read-only catalog inspection reads every binding when discovery cannot, without updating it.
- Review and apply the release's PHP driver for MariaDB or PostgreSQL ([site databases](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/databases.md#php-database-drivers)), with their own `databases` permissions and a **Database plans** section. The exact package transaction installs `php<version>-mysql` or `php<version>-pgsql` at the installed PHP's version, never upgrading PHP, and refuses when no source offers it; the review judges the PHP-FPM tree by the site grammar, lists every pool the reload restarts and invalidates earlier site and database plans. After `php-fpm -t` the run reloads PHP-FPM and waits for every pool's socket (exit 26 when that fails), and verification checks the modules' links, `php-fpm -m` and every socket. The stock PHP profile still refuses a tree with site pools.
- Reconstruct each site's database binding from MariaDB's and PostgreSQL's catalogs ([site database observations](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/ssh-connections.md#site-database-observations)). A root SSH identity reads, without a password or any write, every account, role, database, grant, ACL and `pg_hba.conf` rule under the site's principal name `s<id>`; a satisfied binding matches the [database convention](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/site-conventions.md#database-convention), and partial bindings name their missing statements while custom ones name each difference. Other identities, including ones with sudo, see catalogs as inaccessible, since discovery never escalates; a name in both engines is unsupported, and another account's grant that reaches the name is named and stops the binding from matching. No authentication string, hash or `pg_hba.conf` option is read, and the PostgreSQL profile's readiness check now reads only whether a rule has options or an error. Site admission now also refuses a PHP `conf.d` link that names no present, unmodified distribution module file.
- Reconstruct PHP sites that follow the [native site convention](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/site-conventions.md) from native evidence alone ([site observations](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/ssh-connections.md#site-observations)). Discovery follows each candidate's enabled Nginx file to its root and FastCGI socket, the one pool listening on it, the site user's account, password lock where the shadow database is readable, and each path's and parent directory's owner, group and mode, with the SSH user's own permissions. Every resource has its own observed, absent, inaccessible or unsupported outcome, and broken sockets, missing accounts, shared names, roots, sockets or identities, other pools on the socket, a site that would be the default server, and unknown includes in site files, `nginx.conf` or `php-fpm.conf` leave a site incomplete. A new **Sites** section shows them only to accounts with the `discovery.view_siteobservation` permission. The convention's exact Nginx and pool files are documented, including `include fastcgi.conf;` as its one FastCGI include.
- Apply reviewed site plans ([creating a PHP site](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/sites.md)), with `sites.apply_siteplan` checked at request, at dispatch and for closing an unknown outcome. One native unit under the mutation lock rechecks the reviewed site digest, creates the account with `useradd` and binds its IDs, creates the directories, and publishes each file by staging it beside its destination and linking it into place only while the destination is absent, so nothing is replaced ([ADR 0012](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/adr/0012-publish-site-files-without-replacing-them.md)). It validates the pool and the site before each reload, withdraws only a rejected pool or link it just published, checks Host routing and the PHP identity through a temporary probe, and removes the probe before success. Each stop after the first change is recorded as partly applied with its boundary and ordinary-administration recovery; nothing is removed, resumed or adopted. The worker verifies the site with fresh reads, keeps the reviewed files, directories and account in the run's audit after registration removal, and queues discovery, which finds the site complete.
- Review creating an HTTP PHP site ([reviewing a PHP site](https://github.com/rajandangi/barectl/blob/v0.3.0/docs/sites.md)). A **Site plans** section takes a site identifier and 1 to 10 DNS names of at most 46 characters, and a worker preparation reads the server as root or through noninteractive sudo without writing anything. The plan shows every generated file's complete bytes, the directories, the `useradd` account and its allocation policy, the reloads, routing, the temporary serving probe and the isolation limits, or refuses unsupported layouts, collisions, partial sites and missing or changed evidence; a site that already matches is a plan without changes. Site plans have their own view, prepare and apply permissions, and applying them is not offered. The Nginx and PHP bootstrap profiles still refuse a tree that holds a site.
